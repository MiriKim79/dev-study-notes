{{프로젝트명}} 팀의 협업 규칙 템플릿입니다.  
기획·명세는 `docs/PLANNING.md`, AI 코딩 에이전트 규칙은 `AGENTS.md`를 참고합니다.

> 아래 GitFlow 축소판은 **예시 기본값**입니다. 프로젝트에 GitHub Flow나 다른 방식을 쓰기로 했다면 브랜치 전략·PR base 규칙을 함께 수정하세요.

## 브랜치 전략

[깃 플로우](https://techblog.woowahan.com/2553/)를 프로젝트 규모에 맞게 축소했습니다.

```
main ─── develop ─── feat/…
  └─ hotfix/…       ├─ fix/…
                    └─ refactor/…
```

| 브랜치 | 용도 | 분기 기준 |
| --- | --- | --- |
| `main` | 서비스(배포) 브랜치. 직접 push 금지 | — |
| `develop` | 기본(default) 브랜치. 개발·테스트·릴리즈의 기준 | `main` |
| `feat/*` | 기능 단위 구현 | `develop` |
| `fix/*` | 버그 수정·에러 해결 | `develop` |
| `refactor/*` | 기능 변경 없는 코드 구조 개선 | `develop` |
| `hotfix/*` | 서비스 중 긴급 수정 | `main` |

### 브랜치 이름

`<머릿말>/<내용-kebab-case>-#<이슈번호>`

* 예: `feat/social-login-#5`, `fix/login-error-#8`, `refactor/remove-duplication-#12`

* 이슈 번호는 항상 마지막에 붙입니다.

## 커밋 컨벤션

형식: `머릿말: 설명 (#이슈번호)` — 예: `Feat: 로그인 기능 구현 (#5)`

| 머릿말 | 설명 |
| --- | --- |
| `Feat` | 새로운 기능 추가 |
| `Fix` | 버그 수정 |
| `Refactor` | 코드 리팩토링 (기능 변경 없음) |
| `Style` | 코드 포매팅, 세미콜론 누락 등 동작 변경이 없는 경우 |
| `Comment` | 필요한 주석 추가 및 변경 |
| `Docs` | 문서 수정 |
| `Test` | 테스트 코드 추가·수정 |
| `Chore` | 패키지 매니저 수정, 그 외 기타 수정 (예: .gitignore) |
| `Rename` | 파일·폴더명 수정이나 이동만 있는 경우 |
| `Remove` | 파일 삭제만 있는 경우 |
| `Feat!` / `Fix!` 등 | 기존 사용 방식과 호환되지 않는 breaking change가 있을 때 `!`를 붙이는 팀 규칙으로 사용 가능 |
| `Fix` | `hotfix/*` 브랜치의 긴급 수정도 커밋 내용이 버그 수정이라면 보통 `Fix` 사용 |

규칙:

1. 머릿말은 첫 글자 대문자로 씁니다. (`feat:` ❌ → `Feat:` ⭕)

2. 제목과 본문은 {{한글/영어}}로 쓰고, 빈 줄로 분리합니다.

3. 제목 끝에 마침표를 붙이지 않고, 영문 기준 50자 이내로 씁니다.

4. 본문에는 어떻게보다 **무엇을, 왜** 바꿨는지 씁니다. 항목이 여럿이면 글머리 기호로 나열합니다.

5. 이슈 번호를 제목 끝에 `(#번호)` 형태로 붙입니다.

6. breaking change가 있다면 제목의 type 뒤에 `!`를 붙이거나 본문/푸터에 명확히 기록합니다. 예: `Feat!: 인증 API 응답 구조 변경 (#18)`.

> 이 커밋 형식은 팀이 정한 커스텀 규칙입니다. Conventional Commits를 엄격히 따르고 싶다면 type의 대소문자·footer 규칙을 별도로 맞추세요.

## 이슈

* 모든 작업은 이슈 생성에서 시작합니다. (기능 단위 1이슈)

* 이슈는 `.github/ISSUE_TEMPLATE/`의 템플릿으로 만듭니다: **✨ 기능 구현** (요약·문제 상황·구현 범위·완료 조건) / **🐞 버그** / **🏁 스프린트**

* 브랜치 이름과 커밋 제목에 이슈 번호를 연결합니다.

### 스프린트 구조 (이슈 계층, 선택)

```
[스프린트] 전체 — 프로젝트 목표          ← 최상위 1개
 ├─ [스프린트] {{기간 단위}} 1 — {{목표}}
 │   ├─ [{{파트}}] {{기능}} ({{ID}})
 │   └─ …
 └─ …
```

* 스프린트 이슈의 **하위 이슈 체크리스트**(`#번호`)에 기능 이슈를 넣으면 GitHub이 진행률 바를 표시하고 하위 이슈에 상위 이슈를 자동 연결합니다.

* 기능 이슈를 먼저 만들어 번호를 받은 뒤, 스프린트 이슈에 번호를 채우는 순서가 편합니다.

## PR 규칙

* base는 `develop`입니다. `hotfix/*`만 `main`으로 보냅니다.

* 제목은 커밋과 같은 형식: `Feat: 로그인 기능 구현 (#5)`

* 본문에 변경 요약·이유·확인 방법을 쓰고 `Closes #이슈번호`로 이슈를 연결합니다. (`.github/pull_request_template.md`가 있으면 자동 적용)

* **팀원 1명 이상의 승인** 후에 병합합니다. 셀프 머지는 금지합니다.

* 병합은 **Squash merge**를 사용해 `develop` 히스토리를 커밋 컨벤션 단위로 유지합니다.

| 경로 | 담당 |

| `/{{frontend-dir}}` | {{담당자}} |
| `/{{backend-dir}}` | {{담당자}} |

* **API 명세는 FE/BE 간 계약**입니다. 변경은 전원 합의 후 문서 갱신과 함께 진행합니다.

## 저장소 설정 체크리스트 (관리자)

1. **default 브랜치를** `develop`**으로 변경**

   ```
   gh repo edit {{owner}}/{{repo}} --default-branch develop
   ```

2. **브랜치 보호/Ruleset 확인**
   * GitHub Free의 **public repository**에서는 보호 브랜치를 사용할 수 있습니다.
   * **private repository**에서 보호 브랜치 기능을 사용하려면 GitHub Pro/Team/Enterprise 계열 플랜이 필요할 수 있습니다.
   * 기능을 사용할 수 없다면 팀 규칙으로 `main`/`develop` 직접 push·force push 금지, PR 리뷰 후 머지를 운영합니다.
   * 플랜 정책은 바뀔 수 있으므로 저장소 생성 시 GitHub 공식 문서를 다시 확인합니다.

3. `.github/CODEOWNERS`의 자리표시 ID를 팀원 실제 GitHub ID로 교체

4. 팀원을 저장소 Collaborator로 초대 (Write 권한)

## AI 에이전트 사용 규칙

* Claude Code, Codex 등 AI 코딩 에이전트는 프로젝트의 `AGENTS.md`와 도구 전용 지침을 따릅니다.

* 에이전트가 만든 커밋·PR도 사람과 동일한 컨벤션과 리뷰를 적용하며, **사람 리뷰 없이 병합하지 않습니다.**

* 시크릿(.env, DB 비밀번호, 클라우드 키)은 에이전트에게도 커밋을 요청하지 않습니다.

## PR 작성 전 최종 체크

- [ ] 내 브랜치가 올바른 기준 브랜치에서 시작했는가?
- [ ] 관련 없는 파일까지 함께 수정하지 않았는가?
- [ ] `.env`, 키, 토큰이 포함되지 않았는가?
- [ ] 로컬에서 실행 또는 테스트했는가?
- [ ] API/DB/환경변수 변경을 문서에 반영했는가?
- [ ] PR 설명만 읽어도 리뷰어가 “무엇을 왜 바꿨는지” 알 수 있는가?
- [ ] 큰 PR이라면 기능을 더 작은 PR로 나눌 수 없는가?

PR은 “코드를 합치는 버튼”이 아니라 **팀원이 변경 의도를 검토하는 문서**입니다.
