바이브 코딩으로 개발하기

아이디어부터 배포 전 검증까지 — AI와 함께 개발하는 실제 작업 흐름.

📘 문서 소개
대상: ChatGPT·Claude·Cursor 같은 AI에게 코드를 맡겨서 빠르게 뭔가 만들어보고 싶은 사람
목적: "바이브 코딩"이 정확히 뭔지, 언제 써도 되고 언제 위험한지 감 잡기
주의: 이 문서는 특정 도구 사용법이 아니라 "AI에게 코드를 맡길 때의 태도와 안전장치"를 다룹니다. 유행어라 정의가 아직 유동적이라는 점을 감안하고 읽어주세요.

1. 바이브 코딩이란?#

바이브 코딩(Vibe Coding)은 개발자가 자연어로 "이런 걸 만들어줘"라고 지시하면 AI가 코드를 작성하고, 그 결과를 코드 한 줄 한 줄 다 이해하지 않은 채로 받아들이면서 진행하는 개발 방식을 가리키는 말입니다. 2025년 2월 AI 연구자 안드레 카파시(Andrej Karpathy)가 SNS에 쓴 표현에서 시작해 널리 퍼졌습니다.

기존에도 AI 코드 어시스턴트(자동완성, 코드 생성 제안)는 있었지만, 바이브 코딩의 핵심은 "작동 원리를 완전히 이해하지 않고도 코드를 계속 진행한다"는 태도 자체에 있습니다. "느낌(vibe)대로 큰 그림만 던지고, 세부 로직은 AI에게 맡긴다"는 뜻에서 이름이 붙었습니다.

이 문서를 읽기 전에 알아두면 좋은 것: 이 사이트의 생성형 AI 기능 개발 기초 가이드는 "AI 기능을 서비스에 정확하게 통합하는 법"을 다루고, 이 문서는 그것과는 결이 다른 "AI에게 코드 작성 자체를 맡기고 작업하는 워크플로우"를 다룹니다. 서로 대체 관계가 아니라 보완 관계입니다.

2. 언제 적합한가#

  • 빠른 프로토타입: 아이디어가 실제로 동작하는지 며칠 안에 확인하고 싶을 때
  • 개인 사이드 프로젝트, 장난감 프로젝트: 실패해도 손해가 크지 않은 학습·실험용 코드
  • 이미 익숙한 영역의 반복 작업: 내가 결과 코드를 보면 옳고 그름을 바로 판단할 수 있는 영역(예: CRUD API 뼈대, 간단한 UI 컴포넌트)

3. 언제 위험한가#

  • 프로덕션 서비스, 특히 결제·인증·개인정보를 다루는 코드: 이해하지 못한 채 배포하면 보안 취약점을 그대로 서비스에 실어 보내는 것과 같습니다.
  • 팀 프로젝트에서 리뷰 없이 그대로 머지: 코드 작성자 본인도 설명하지 못하는 코드는 리뷰어도, 미래의 나도 유지보수할 수 없습니다.
  • 내가 전혀 모르는 영역: 결과 코드가 그럴듯해 보여도 틀렸을 때 그걸 알아챌 방법이 없습니다. (생성형 AI 결과물은 비결정적이고 틀릴 수 있다는 원칙은 생성형 AI 기능 개발 기초 가이드 1장에서도 강조합니다.)
💡 핵심 개념

기본 상식#

바이브 코딩은 "AI가 다 알아서 하니 개발자는 몰라도 된다"는 뜻이 아닙니다. 오히려 AI가 낸 결과를 빠르게 검증할 수 있는 능력이 있어야 안전하게 쓸 수 있는 방식입니다. 이 사이트의 Git·GitHub 기초 가이드, 백엔드 기초 가이드 같은 기본기가 없는 상태로 바이브 코딩만 하면, 문제가 생겼을 때 원인을 찾을 방법이 없습니다.

4. 실전 개발 워크플로#

바이브 코딩이 "느낌대로 던지고 받는다"는 태도라면, 실제로 그 태도를 안전하게 실행에 옮기는 절차는 아래 흐름을 따릅니다. 처음 보는 사람도 이 순서대로 따라 하면 됩니다.

text
아이디어/MVP → SPEC·요구사항 → AI에게 프로젝트 context 제공 → 작업을 작은 단위로 분할
→ 구현 요청 → 실행 → 오류 로그/스크린샷 전달 → 수정 → diff 확인 → 테스트 → commit
→ 다음 작업 → 배포 전 검증

1) 아이디어/MVP → SPEC·요구사항#

만들려는 것을 한두 문장이 아니라 완료 조건(Definition of Done)까지 적습니다. "회원가입 기능"이 아니라 "이메일·비밀번호로 가입하고, 중복 이메일이면 에러 메시지를 보여주고, 가입 후 자동 로그인된다"처럼 구체적으로. 완료 조건을 미리 정의해두지 않으면 AI가 어디까지 했는지, 언제 끝났는지 판단할 기준이 없어서 검증이 흐지부지됩니다.

2) AI에게 프로젝트 context 제공#

AI는 대화가 시작될 때 여러분의 프로젝트를 전혀 모릅니다. 다음을 명시적으로 줍니다.

  • 관련 파일 자체를 열어서 보여주거나 붙여넣기 (전체 코드베이스를 다 주지 말고, 지금 작업과 관련된 파일만)
  • 사용 중인 언어/프레임워크 버전 (예: "React 18, Node 20, Python 3.12")
  • 프로젝트의 폴더 구조나 아키텍처 원칙(예: "API 로직은 routes/에만 둔다")

context는 많을수록 좋은 게 아닙니다. 관련 없는 파일까지 잔뜩 넣으면 AI가 엉뚱한 코드를 참고하거나 핵심을 놓칩니다. 딱 이번 작업에 필요한 만큼만 줍니다.

기존 코드부터 읽히는 습관: 새 기능을 만들 때도 "이 프로젝트에 비슷한 패턴이 이미 있는지 먼저 찾아봐"라고 시킵니다. 이미 있는 유틸 함수나 컴포넌트를 무시하고 AI가 새로 만들면, 같은 기능이 중복되고 스타일도 제각각이 됩니다.

작업 범위를 파일 단위로 제한하기: "이 파일만 고쳐라", "다른 파일은 건드리지 마라"처럼 AI가 손댈 수 있는 범위를 명시적으로 좁힙니다. 범위를 정해주지 않으면 AI가 관련 없어 보이는 파일까지 "개선"한다며 같이 수정해버려서, 리뷰해야 할 diff가 불필요하게 커지고 의도치 않은 변경이 섞여 들어갑니다.

3) 작업을 작은 단위로 분할#

"쇼핑몰 만들어줘" 같은 큰 요청은 AI도 사람도 검증할 수 없습니다. "상품 목록 API 하나", "장바구니 추가 버튼 하나"처럼 한 번에 리뷰 가능한 크기로 쪼갭니다. 하나가 끝나고 검증된 뒤에 다음으로 넘어갑니다.

4) 구현 요청 → 실행#

분할한 작업 단위로 구체적으로 요청하고, 나온 코드를 바로 실행해봅니다. 실행해보지 않고 코드만 읽고 "맞겠지"라고 넘어가지 않습니다.

좋은 요청과 나쁜 요청: 요청이 모호할수록 AI는 그럴듯해 보이지만 검증 불가능한 코드를 냅니다.

  • 나쁜 요청: "로그인 기능 만들어줘"
  • 좋은 요청: "auth/ 폴더의 기존 회원가입 로직(signup.ts)과 같은 패턴으로 로그인 API를 만들어줘. 이메일·비밀번호 입력, 비밀번호 불일치 시 401과 {error: "invalid credentials"} 반환, 성공 시 JWT 발급. auth/ 폴더 파일만 수정하고 다른 곳은 건드리지 마."

좋은 요청은 (1) 무엇을 (2) 어떤 파일/패턴을 참고해서 (3) 어떤 결과가 나와야 하는지(완료 조건)까지 포함합니다.

이때 두 가지를 주의합니다.

  • 버전/의존성 확인: AI는 학습 시점 이후 바뀐 API나 이미 deprecated된 문법을 그럴듯하게 제안할 수 있습니다. 공식 문서나 package.json/requirements.txt에 명시된 실제 버전과 맞는지 확인합니다.
  • hallucination 대응: 존재하지 않는 함수, 라이브러리, 옵션을 마치 있는 것처럼 만들어내는 경우가 있습니다. import한 패키지가 실제로 설치되어 있는지, 호출한 함수/메서드가 문서에 존재하는지 실행 전에 한 번 확인하는 습관을 들입니다.
  • secret/API key 노출 금지: .env 파일, API 키, 비밀번호, DB 접속 정보를 절대 AI에게 복붙하거나 파일 그대로 보여주지 않습니다. 예시가 필요하면 sk-xxxx... 같은 더미 값으로 대체합니다.

5) 오류 로그/스크린샷 전달 → 수정#

실행해서 에러가 나면, "안 돼요"라고만 하지 말고 에러 메시지 전문(스택 트레이스)이나 스크린샷을 그대로 전달합니다. AI가 원인을 추측하는 대신 실제 증거를 보고 고치게 하는 것이 핵심입니다.

6) diff 확인#

AI가 수정한 내용을 적용하기 전에 git diff로 무엇이 바뀌었는지 반드시 확인합니다. 요청하지 않은 파일을 건드리지 않았는지, 지워도 되는 코드를 지운 게 맞는지 눈으로 확인하는 단계입니다. "실행이 되니까 맞겠지"가 아니라 diff 리뷰 없이는 결과를 신뢰하지 않습니다.

7) 테스트#

3장에서 언급한 것처럼 최소한의 테스트로 검증합니다. 테스트가 없다면 지금 만든 기능에 대해서만이라도 간단한 테스트를 AI에게 같이 작성시킵니다.

8) commit → 다음 작업#

작업 단위가 끝나고 검증까지 마쳤으면 바로 커밋합니다. 이것이 Git checkpoint입니다 — 작은 단위로 커밋해두면, 다음 AI 요청이 코드를 망가뜨려도 언제든 이 지점으로 되돌아올 수 있습니다. 커밋 없이 계속 진행하다가 문제가 쌓이면 어디까지가 정상이었는지 알 수 없게 됩니다. 커밋 후에는 다음 작은 작업으로 넘어가 2)~8)을 반복합니다.

9) 배포 전 검증#

전체 기능이 완료되면 배포하기 전에 처음 정의한 완료 조건을 다시 확인하고, 민감한 부분(인증, 결제, 개인정보 처리)은 사람이 직접 한 번 더 검토합니다.

5. 실전에서 안전하게 쓰는 법#

  1. 작은 단위로 지시하고, 작은 단위로 커밋한다. 한 번에 "로그인부터 결제까지 다 만들어줘"가 아니라, 기능 하나씩 요청하고 그때그때 결과를 확인합니다.
  2. 결과 코드를 최소한 한 번은 읽는다. 완벽히 이해하지 못해도, "이 함수가 뭘 하려는 건지" 정도는 스스로 설명할 수 있어야 합니다.
  3. 테스트로 검증한다. 코드를 다 이해하지 못하더라도, 테스트가 통과하는지는 확인할 수 있습니다. 테스트 자동화 중급 가이드의 최소한만이라도 적용하는 걸 권장합니다.
  4. 민감한 부분(인증, 결제, 개인정보 처리)은 직접 검토하거나 아예 AI에게 맡기지 않는다.
  5. 버전 관리를 철저히 한다. AI가 만든 결과가 이상하면 언제든 이전 커밋으로 되돌릴 수 있어야 합니다. Git·GitHub 진짜 최소 기초의 커밋·되돌리기만 알아도 훨씬 안전해집니다.
  6. 긴 작업은 context를 정리하며 진행한다. 대화가 길어질수록 AI는 앞에서 한 이야기를 잊거나 뒤섞습니다. 작업이 여러 세션에 걸친다면 진행 상황과 결정 사항을 파일(예: PROGRESS.md)이나 커밋 메시지로 남겨두고 새 세션에서 그걸 다시 던져주며 이어갑니다. 한 세션 안에서도 대화가 너무 길어졌다 싶으면, 지금까지의 요약만 남기고 새로 시작하는 편이 엉뚱한 결과를 받는 것보다 낫습니다.

6. 자주 하는 실수#

  • AI가 만든 코드를 그대로 복붙해서 어디서 에러가 나는지도 모른 채 다시 AI에게 "고쳐줘"만 반복하는 것 — 원인을 스스로 좁혀보는 습관이 없으면 문제가 점점 커집니다.
  • 프로젝트 초반부터 전체 아키텍처를 AI에게 통째로 맡기는 것 — 구조적인 결정(폴더 구조, 데이터 모델)은 사람이 먼저 큰 방향을 잡고, AI에게는 그 안에서의 구현을 맡기는 편이 안전합니다.
  • "AI가 짰으니까 맞겠지"라고 생각하고 보안·성능 검토를 생략하는 것.

7. 여기까지 이해했다면#

  • 바이브 코딩이 기존 AI 코드 자동완성과 뭐가 다른지 설명할 수 있다.
  • 바이브 코딩을 써도 되는 상황과 피해야 하는 상황을 구분할 수 있다.
  • AI가 만든 코드를 안전하게 다루는 최소한의 습관(작은 단위 커밋, 테스트, 리뷰) 한 가지 이상을 말할 수 있다.
  • 아이디어부터 배포 전 검증까지, 실제 개발 워크플로 전체 흐름을 순서대로 설명할 수 있다.
