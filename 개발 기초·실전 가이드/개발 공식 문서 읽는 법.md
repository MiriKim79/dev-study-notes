> **대상:** 공식 문서를 처음 보는 개발 초보자
> **목적:** 공식 문서를 처음부터 끝까지 읽는 대신, 지금 필요한 정보만 빠르게 찾아 코드에 적용하는 법을 익히기

---

# 1. 기본 흐름

```
문제 파악 → 공식 문서 찾기 → 버전 확인 → Quick Start/Guide 확인
→ 검색 → 예제 확인 → API Reference 확인 → 직접 실행 → 결과 검증
```

공식 문서는 소설처럼 처음부터 끝까지 읽는 자료가 아닙니다. **지금 내가 막힌 부분과 관련된 페이지만 찾아서, 필요한 만큼만 읽고 바로 코드에 적용**하는 것이 정상입니다.

---

# 2. 공식 문서에서 먼저 볼 것

문서 사이트를 처음 열면 메뉴가 많아서 어디부터 봐야 할지 막막합니다. 아래 6가지 메뉴가 언제 필요한지만 알아두면 충분합니다.

| 메뉴 | 언제 보는가 |
| --- | --- |
| **Getting Started / Quick Start** | 이 도구를 처음 설치하고 "일단 뭐라도 동작하게" 만들어보고 싶을 때 |
| **Guide / Tutorial** | 특정 기능을 어떤 순서·개념으로 쓰는지 차근차근 배우고 싶을 때 |
| **API Reference** | 함수/옵션 하나의 정확한 이름·매개변수·반환값을 확인하고 싶을 때 (4장 참고) |
| **Examples** | 개념 설명보다 "그냥 동작하는 코드"를 보고 따라 하고 싶을 때 |
| **Migration / Upgrade Guide** | 버전을 올렸더니 기존 코드가 깨졌을 때, 무엇이 바뀌었는지 확인할 때 |
| **Changelog / Release Notes** | 특정 버전에서 무엇이 추가·삭제·수정됐는지 확인할 때 |

막 시작할 땐 **Quick Start**, 뭔가 코드가 있는데 왜 이렇게 동작하는지 모를 땐 **API Reference**, 이렇게 상황별로 다른 메뉴를 엽니다.

# 3. 버전 확인 — 초보자가 가장 많이 놓치는 부분

공식 문서를 제대로 찾아 읽었는데도 안 되는 경우, 절반은 **버전이 다르기 때문**입니다.

확인해야 할 세 가지 버전:

```
1. 내가 실제로 설치한 버전    (예: package.json에 적힌 React 버전)
2. 지금 보고 있는 문서의 버전  (문서 사이트 상단/좌측에 버전 선택 메뉴가 있는 경우가 많음)
3. 검색해서 찾은 예제 코드가 적힌 시점의 버전
```

## 쉬운 사례

블로그에서 찾은 예제가 이렇게 생겼다고 합시다.

```js
// 블로그 예제 (오래된 버전 기준)
ReactDOM.render(<App />, document.getElementById("root"));
```

내 프로젝트는 최신 React를 쓰고 있는데 이 코드를 그대로 붙이면 동작하지 않거나 경고가 뜹니다. React 18부터는 아래 방식으로 바뀌었기 때문입니다.

```js
// 최신 버전 방식
const root = ReactDOM.createRoot(document.getElementById("root"));
root.render(<App />);
```

**"코드가 틀린 게 아니라, 내 버전과 문서/예제의 버전이 다른 것"**임을 의심하는 습관이 중요합니다. 에러 메시지만으로 원인을 못 찾겠다면 가장 먼저 버전을 맞춰서 다시 확인하세요.

# 4. 검색하는 법

문서 사이트 전체를 훑어보지 말고 아래 방법으로 필요한 부분만 찾습니다.

* **문서 사이트 안 검색창**: 대부분의 공식 문서 사이트 상단에 검색창이 있습니다. 함수 이름, 기능 이름으로 검색합니다.
* **`Ctrl+F` (페이지 내 찾기)**: 이미 열어놓은 긴 페이지 안에서 특정 단어(옵션 이름 등)만 빠르게 찾을 때 씁니다.
* **에러 메시지의 핵심 단어로 검색**: 에러 메시지를 그대로 문서 검색창에 넣기보다, 핵심 단어(예: 함수 이름, 옵션 이름)만 뽑아서 검색하면 더 잘 찾아집니다.
* **함수/클래스/옵션 이름으로 직접 검색**: 코드에 이미 쓰여 있는 이름(예: `useEffect`, `timeout`)을 그대로 검색하면 API Reference 페이지로 바로 갈 때가 많습니다.

# 5. API Reference 읽는 법

API Reference는 함수(또는 메서드) 하나를 아래 구조로 설명합니다. 처음 보면 정보가 빽빽해 보이지만, 실제로 필요한 건 이 다섯 가지뿐입니다.

```
함수/메서드 이름   ← 정확한 이름과 대소문자
Parameter         ← 어떤 값을 몇 개, 어떤 순서로 넣는지
Return value      ← 이 함수가 실행되고 나면 무엇을 돌려주는지
Option            ← 선택적으로 넣을 수 있는 추가 설정
Example           ← 실제로 어떻게 호출하는지 보여주는 코드
```

**deprecated**(더 이상 권장하지 않고 곧 없어질 수 있는 기능) 표시가 붙어 있다면, 지금 당장은 동작해도 새 프로젝트에는 쓰지 않는 것이 좋습니다. 문서에 대체 방법이 함께 안내되어 있는 경우가 많습니다.

## 예시로 보기

Python `requests` 라이브러리의 `get` 함수를 문서에서 봤다고 가정합니다.

```python
requests.get(url, params=None, timeout=None)
```

* **이름**: `requests.get`
* **Parameter**: `url`(필수, 요청 주소), `params`(선택, 쿼리 파라미터), `timeout`(선택, 응답을 기다릴 최대 시간)
* **Return value**: 문서에 "Response 객체를 반환한다"고 적혀 있음 — 즉 `response.status_code`, `response.json()` 같은 방식으로 결과를 꺼내 씀
* **Example**: 문서에 `requests.get('https://api.example.com', timeout=5)` 같은 실제 호출 예제가 있음

이 다섯 가지만 짚으면, 처음 보는 함수도 "어떻게 부르고 결과를 어떻게 쓰는지" 바로 파악됩니다.

# 6. 공식 문서 vs 다른 자료

정보가 서로 다를 때는 아래 우선순위로 신뢰합니다.

```
공식 문서 → 공식 예제 → 신뢰할 만한 기술 자료 → Q&A/블로그 → AI 답변
```

블로그나 AI 답변이 "틀렸다"는 뜻이 아닙니다. 다만 **버전이 바뀌었거나, 작성 시점이 오래됐거나, 특정 상황에서만 맞는 설명일 수 있어** 사실 확인의 기준은 항상 공식 문서로 둡니다. 특히 "이게 지금도 되는 방법이 맞나?"가 궁금할 땐 블로그보다 공식 문서의 버전 정보(3장)와 Changelog를 먼저 봅니다.

# 7. AI와 함께 문서 읽기

AI에게 물어볼 때도 공식 문서를 기준으로 확인하게 시키면 정확도가 올라갑니다.

* "이거 지금 최신 버전 기준이 맞아?" 라고 버전을 명시해서 물어봅니다.
* "이 방법 혹시 deprecated된 방식 아니야?" 라고 직접 확인을 요청합니다.
* AI가 알려준 함수·API 이름을 **실제 공식 문서(API Reference)에서 검색해 존재하는지 확인**합니다. AI는 그럴듯하지만 실제로는 없는 함수를 만들어내기도 합니다(hallucination).

AI에게 코드를 맡길 때 필요한 요청·검증 습관은 [바이브 코딩으로 개발하기](바이브%20코딩으로%20개발하기.html) 문서와도 이어집니다. 이 문서의 "버전 확인"·"공식 문서로 검증"이 그 문서가 말하는 "AI 답변을 그대로 적용하지 않고 확인하기"의 구체적인 방법 중 하나입니다.

# 8. 실제 상황 예시

## 예시 1. React Hook 사용법 찾기

* **궁금한 것**: `useEffect`를 언제, 어떻게 쓰는지 모르겠음
* **어디를 찾음**: React 공식 문서의 Reference에서 `useEffect` 검색
* **무엇을 확인**: Parameter(콜백 함수, 의존성 배열), Example 코드, 그리고 지금 문서가 내 React 버전과 맞는지
* **적용**: 예제의 의존성 배열 패턴을 내 코드 상황에 맞게 그대로 옮겨 써봄

## 예시 2. npm 패키지 설치 옵션 확인

* **궁금한 것**: `npm install`에 옵션이 여러 개 있던데 뭐가 다른지 모르겠음
* **어디를 찾음**: npm 공식 문서의 CLI Reference에서 `install` 검색
* **무엇을 확인**: `--save-dev`(개발할 때만 필요한 패키지로 설치) 같은 옵션 각각의 설명
* **적용**: 지금 설치하려는 패키지가 개발용인지 실제 서비스에도 필요한지 판단해 옵션 선택

## 예시 3. Git 명령어 옵션 확인

* **궁금한 것**: `git log`에 옵션을 붙이면 뭐가 달라지는지 모르겠음
* **어디를 찾음**: Git 공식 문서(또는 `git log --help`)에서 옵션 목록 확인
* **무엇을 확인**: `--oneline`(한 줄로 요약), `--graph`(브랜치를 그림으로) 같은 옵션의 역할
* **적용**: 원하는 정보만 보이도록 옵션을 조합해 실행 — Git 관련 기본기는 [Git·GitHub 기초 가이드](Git·GitHub%20기초%20가이드.html) 참고

# 9. 최종 원칙

* 문서는 처음부터 끝까지 읽는 게 아니라 필요한 부분만 찾아 읽는다
* 안 될 때는 버전부터 의심한다 — 내 버전, 문서 버전, 예제 버전이 각각 다를 수 있다
* API Reference는 이름·Parameter·Return value·Option·Example 다섯 가지만 보면 된다
* 정보가 충돌하면 공식 문서를 기준으로 삼는다
* AI 답변에 나온 함수·API는 실제 공식 문서에 있는지 확인하고 쓴다

문서를 읽어도 원인을 못 찾겠다면 [디버깅·오류 해결 기초 가이드](디버깅·오류%20해결%20기초%20가이드.html)와 [브라우저 개발자 도구(DevTools) 기초 가이드](브라우저%20개발자%20도구%28DevTools%29%20기초%20가이드.html)를 함께 참고하세요.
