디버깅·오류 해결 기초 가이드

무작정 AI에게 붙여넣기 전에, 에러 메시지부터 스스로 읽고 범위를 좁히는 법.

📘 문서 소개
대상: 개발 중 오류를 처음 만나는 사람
목적: 에러가 뜨면 무작정 전체를 복사해 AI에게 붙여넣기 전에, 스스로 문제 범위를 줄이고 해결하는 기본 흐름을 익히기
주의: 이 문서는 오류 종류를 전부 나열한 사전이 아닙니다. "어떤 순서로 원인을 좁혀가는가"라는 흐름 자체를 다룹니다.

1. 디버깅 기본 흐름#

오류가 나면 아래 순서를 그대로 따라갑니다. 중간을 건너뛰고 바로 "고쳐야지"로 가면 대부분 엉뚱한 곳을 고치게 됩니다.

text
오류 재현 → 에러 메시지 읽기 → 어디서 실패했는지 찾기
→ 로그/Console 확인 → 원인 범위 줄이기 → 하나씩 수정
→ 다시 실행 → 해결 확인
  • 오류 재현: "가끔 난다"가 아니라 "이렇게 하면 항상 난다"를 먼저 확인합니다. 재현이 안 되면 원인도 못 찾습니다.
  • 에러 메시지 읽기: 2장 참고.
  • 어디서 실패했는지 찾기: stack trace(3장)나 어떤 요청이 실패했는지(Network 탭)를 봅니다.
  • 로그/Console 확인: 4장 참고.
  • 원인 범위 줄이기: 5장 참고.
  • 하나씩 수정: 6장 참고.
  • 다시 실행 → 해결 확인: 고쳤다고 끝이 아니라, 처음 재현했던 그 방법으로 다시 확인합니다.

2. 에러 메시지에서 먼저 볼 것#

에러 메시지는 대부분 아래 세 가지를 담고 있습니다. 전체 문장을 다 이해하려 하지 말고 이 세 가지부터 찾습니다.

text
[에러 종류]                  ← 무슨 문제인지 (TypeError, 404 등)
[대상]                       ← 무엇에 대한 문제인지 (어떤 변수, 어떤 URL)
[위치]                       ← 어느 파일, 몇 번째 줄

예시:

text
TypeError: Cannot read properties of undefined (reading 'name')
    at CourseCard (CourseCard.jsx:12)
  • 에러 종류: TypeError — 값의 타입이 예상과 다름
  • 대상: undefined의 'name' 속성을 읽으려 함 — 즉 course가 undefined인데 course.name을 읽으려 한 것
  • 위치: CourseCard.jsx 12번째 줄

이 세 가지만 뽑아내면 "무엇이, 어디서, 왜" 문제인지 감이 잡힙니다. 에러 메시지를 읽지 않고 바로 코드를 이것저것 고치는 게 가장 흔한 실수입니다.

3. Stack Trace 아주 쉽게 읽는 법#

Stack trace는 에러가 나기까지 함수가 호출된 순서를 기록한 목록입니다. 위에서 아래로 갈수록 "더 먼저 호출된" 함수입니다.

text
TypeError: Cannot read properties of undefined (reading 'name')
    at CourseCard (CourseCard.jsx:12)      ← ① 실제로 에러가 발생한 지점
    at CourseList (CourseList.jsx:25)      ← ② CourseCard를 호출한 곳
    at App (App.jsx:8)                     ← ③ CourseList를 호출한 곳

읽는 순서: 맨 위 줄(①)이 에러가 실제로 터진 지점입니다. 여기부터 확인합니다. 아래 줄들은 "그 함수를 누가 불렀는지"를 거슬러 올라가는 경로일 뿐이라, 처음엔 안 봐도 됩니다.

단, 맨 위 줄이 node_modules나 라이브러리 내부 코드를 가리킬 때가 있습니다. 이럴 땐 stack trace를 아래로 훑어 내려가면서 내가 작성한 파일이 처음 나오는 줄을 찾습니다. 라이브러리 내부보다 그 지점이 실제로 고쳐야 할 곳일 확률이 높습니다.

4. 브라우저 Console vs 터미널 로그#

둘은 서로 다른 곳에서 실행되는 코드의 기록이라 섞어서 보면 안 됩니다.

브라우저 Console (F12)터미널(서버) 로그
무엇이 찍히나프론트엔드(JS) 오류, console.log, 네트워크 요청 실패백엔드(서버) 오류, 서버가 찍은 로그
실행 위치사용자의 브라우저서버가 돌아가는 컴퓨터
언제 봐야 하나화면이 이상하게 동작할 때, 버튼이 안 눌릴 때API 요청은 갔는데 응답이 이상하거나 500 에러가 날 때

화면이 깨졌는데 터미널 로그만 보거나, API가 500을 반환하는데 브라우저 Console만 보는 경우가 흔합니다. 화면 문제면 Console, 서버 응답 문제면 터미널부터 엽니다. 참고로 브라우저 개발자 도구의 Network 탭을 보면 어떤 요청이 어떤 상태 코드로 응답했는지 한눈에 보여서, "프론트 문제인지 백엔드 문제인지"를 가장 먼저 구분하는 데 유용합니다.

5. 자주 보는 오류#

전부 외울 필요는 없고, "이 번호대는 대략 이런 뜻이다"만 기억해둡니다.

코드/오류대략 이런 뜻먼저 볼 곳
404 Not Found요청한 주소 자체가 없음URL 오타, 라우트 경로
401 Unauthorized로그인/인증이 안 된 상태토큰이 안 실렸는지, 만료됐는지
403 Forbidden인증은 됐지만 권한이 없음로그인은 됐는데 권한/역할 문제인지
500 Internal Server Error서버 코드 내부에서 에러 발생서버 터미널 로그(정확한 원인이 거기 있음)
TypeError / undefined 관련값이 예상과 다른 타입이거나 아직 없음그 값이 언제 채워지는지, 초기값은 뭔지
CORS 에러브라우저가 다른 출처로의 요청을 막음프론트엔드 기초 가이드의 CORS 설명 참고

6. 원인 범위를 줄이는 법#

"뭐가 문제인지 전혀 모르겠다"일 때는 코드를 고치기 전에 범위부터 줄입니다.

"어제 됐는데 오늘 안 됨"일 때 확인 순서#

text
1. 정말 코드가 바뀌었는가 → git diff / git log로 최근 변경사항 확인
2. 내가 바꾼 게 아니라면 → 의존성(패키지) 버전이 바뀌었는지 확인
3. 그것도 아니라면 → 환경변수·설정 파일이 바뀌었는지 확인
4. 그것도 아니라면 → 외부 서비스(API, DB)가 바뀌었거나 죽었는지 확인

최근 변경사항 확인이 가장 먼저입니다. git diff나 git log로 최근에 무엇을 바꿨는지 보면, 절반 이상의 "이유 없이 안 됨"은 바로 원인이 보입니다. 방금 건드린 파일부터 의심하세요.

이진 탐색하듯 범위 좁히기#

전체 코드 중 어디가 문제인지 모를 때는, 절반씩 잘라서 확인합니다.

text
전체 함수 실행이 실패한다
→ 함수 중간에 console.log를 하나 찍어본다
→ 거기까지는 찍히면: 문제는 그 아래쪽
→ 거기까지도 안 찍히면: 문제는 그 위쪽
→ 범위를 절반으로 줄여서 반복

이렇게 하면 코드 전체를 다 읽지 않고도 몇 번 만에 문제 지점을 좁힐 수 있습니다.

7. 한 번에 하나씩만 고치기#

원인을 좁혔다면, 의심되는 걸 한 번에 여러 개 동시에 고치지 않습니다. 세 곳을 동시에 고치고 나서 문제가 해결되면, 셋 중 뭐가 실제 원인이었는지 영영 알 수 없습니다. 다음에 비슷한 문제가 또 나도 뭘 봐야 할지 배우지 못합니다.

text
가설 하나 세우기 → 그것만 고치기 → 다시 실행 → 확인
  → 해결 안 됐으면 되돌리고 다음 가설로
  → 해결됐으면 왜 해결됐는지 이해하고 끝

수정 하나당 실행 한 번, 이 리듬을 지키는 것이 가장 빠른 길입니다.

8. 검색할 때 좋은 키워드 만드는 법#

에러 메시지를 검색할 때는 아래처럼 다듬습니다.

  • 바뀌는 값은 지운다: 파일 경로, 변수명, 사용자 데이터처럼 나만의 값은 빼고 검색합니다. * ❌ Cannot read properties of undefined (reading 'name') at CourseCard.jsx:12 * ✅ Cannot read properties of undefined reading + 사용 중인 라이브러리/프레임워크 이름
  • 에러 종류 + 핵심 상황으로 좁힙니다. 예: React useEffect infinite loop, Flask 404 blueprint
  • 검색 결과가 너무 없으면 키워드를 줄이고, 너무 많고 관련 없으면 프레임워크·언어 이름을 추가합니다.

9. AI에게 질문할 때 빠뜨리면 안 되는 것#

에러 메시지 한 줄만 붙여넣으면 AI도 추측만 하게 됩니다. 아래 다섯 가지를 함께 전달하면 답변 정확도가 크게 올라갑니다.

text
1. 하고 싶은 것        — 원래 의도한 동작
2. 실제 결과           — 지금 실제로 무슨 일이 일어나는지
3. 에러 원문           — 메시지를 요약하지 말고 그대로
4. 관련 코드           — 에러가 난 지점과 그 주변 (파일 전체 X)
5. 이미 해본 것        — 시도했지만 안 됐던 방법들

예시:

text
하고 싶은 것: 로그인 후 사용자 이름을 화면에 보여주고 싶습니다.
실제 결과: 로그인은 되는데 이름 대신 화면이 하얗게 깨지고 아래 에러가 납니다.
에러 원문: TypeError: Cannot read properties of undefined (reading 'name')
    at CourseCard (CourseCard.jsx:12)
관련 코드:
  function CourseCard({ user }) {
    return <div>{user.name}</div>;   // 12번째 줄
  }
이미 해본 것: user에 console.log를 찍어봤더니 처음 렌더링될 때 undefined였다가
나중에 값이 채워집니다. optional chaining(user?.name)은 아직 안 써봤습니다.

이 정도 정보면 "user가 아직 로딩되지 않은 시점에 렌더링되는 문제"라는 걸 AI도, 사람도 바로 짚어낼 수 있습니다. 좋은 질문을 만드는 습관은 AI와 함께 개발할 때 특히 중요한데, 이 부분은 바이브 코딩으로 개발하기 문서의 "좋은 요청과 나쁜 요청" 부분과도 이어집니다.

10. AI 답변을 그대로 적용하지 않고 확인하기#

AI가 제안한 수정 코드는 항상 아래를 확인한 뒤에 적용합니다.

  • 왜 그렇게 고치는지 한 문장으로 설명할 수 있는가? 이해 안 되면 물어봐서 이해하고 넘어갑니다.
  • 실제로 실행해서 에러가 사라졌는지 확인했는가? 코드가 그럴듯해 보인다고 바로 커밋하지 않습니다.
  • 다른 곳을 망가뜨리지 않았는가? 수정한 부분과 관련된 다른 기능도 한 번씩 확인합니다.
  • 존재하지 않는 함수나 라이브러리를 그럴듯하게 지어내는 경우(hallucination)도 있으므로, 낯선 함수/패키지가 나오면 실제로 있는지 확인합니다.

11. 해결 후 짧게 기록하기#

문제를 해결했다면 아래 세 줄 정도만 어딘가에 남겨둡니다(커밋 메시지, 이슈 댓글, 개인 메모 등 어디든 괜찮습니다).

text
문제: 로그인 직후 화면이 하얗게 깨짐
원인: user 데이터가 로딩되기 전에 컴포넌트가 먼저 렌더링됨
해결: user가 없을 때는 로딩 화면을 보여주도록 조건 추가

기록해두면 다음에 비슷한 에러가 났을 때 검색 시간이 줄고, 팀원이 같은 문제로 헤매는 것도 막을 수 있습니다.

12. 최종 원칙#

  • 에러 메시지는 끝까지 읽는다 — 특히 첫 줄과 stack trace 맨 위 줄
  • 재현되지 않는 문제는 고칠 수 없다 — 먼저 재현부터
  • 한 번에 하나만 바꾸고 확인한다
  • "어제는 됐는데" 싶으면 git diff부터
  • AI에게 물어보기 전에 최소한의 원인 범위는 스스로 좁혀본다
  • AI 답변도 실행해서 확인한 뒤에만 적용한다

프론트엔드 화면 관련 에러는 프론트엔드 기초 가이드의 "디버깅 순서"를, 서버·API 관련 에러는 백엔드 기초 가이드의 "오류 처리"를, git diff·되돌리기 같은 Git 명령어는 Git·GitHub 기초 가이드를 함께 참고하면 좋습니다. 이 문서가 "어떤 순서로 원인을 좁히는가"라면, 브라우저 Elements/Console/Network에서 실제로 무엇을 눌러 확인하는지는 브라우저 개발자 도구(DevTools) 기초 가이드에서 다룹니다.
