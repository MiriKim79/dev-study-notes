# 0. 시작 전에 — 자주 나오는 용어

개발이 처음이라면 본문을 읽기 전에 아래 표부터 훑어보세요. 본문 중간에 낯선 단어가 나오면 다시 여기로 돌아와 찾아봐도 됩니다.

## 0.1 웹 기본

| 용어 | 쉬운 설명 |
| --- | --- |
| 브라우저(Browser) | 웹페이지를 보여주는 프로그램. Chrome, Safari, Edge 등. |
| 도메인(Domain) | URL에서 사이트를 식별하는 이름 부분(`example.com`). |
| 포트(Port) | 한 컴퓨터에서 여러 프로그램을 구분하는 번호. 개발 서버는 보통 `3000`, `5173` 같은 포트를 씁니다. |
| 로컬(local) / localhost | 지금 쓰고 있는 내 컴퓨터 자신을 가리키는 주소. |
| 서버(Server) | 요청을 받아 응답을 돌려주는 프로그램(백엔드). |
| 클라이언트(Client) | 요청을 보내는 쪽(브라우저). |

## 0.2 HTML/CSS/JS 기본

| 용어 | 쉬운 설명 |
| --- | --- |
| 태그(Tag) | `<button>`처럼 HTML에서 의미 단위를 표시하는 것. |
| 엘리먼트(Element) | 태그로 만들어진 화면 요소 하나. |
| 속성(Attribute) | `<img alt="설명">`처럼 태그에 추가 정보를 주는 것. |
| 선택자(Selector) | CSS에서 “어떤 엘리먼트를 꾸밀지” 지정하는 문법(`.class`, `#id` 등). |
| 클래스(Class) | 여러 엘리먼트에 같은 스타일을 재사용하기 위한 이름표. |
| 박스 모델(Box Model) | 모든 엘리먼트를 margin-border-padding-content 4겹으로 보는 CSS 개념. |
| 변수(Variable) | 값을 담아두는 이름표. JS에서 `const`, `let`으로 선언. |
| 함수(Function) | 특정 동작을 묶어서 이름 붙여둔 코드 덩어리. |

## 0.3 DOM/이벤트

| 용어 | 쉬운 설명 |
| --- | --- |
| DOM | 브라우저가 HTML을 읽어서 JS로 다룰 수 있게 만든 객체 구조. |
| 이벤트(Event) | 클릭, 입력처럼 사용자가 한 행동. |
| 이벤트 리스너(Event Listener) | “이 이벤트가 발생하면 이 함수를 실행해라”라고 등록하는 것. |
| 렌더링(Rendering) | 데이터를 실제 화면(HTML)으로 그려내는 것. |
| 재렌더링(Re-render) | 상태(State)가 바뀌어서 화면을 다시 그리는 것. |

## 0.4 컴포넌트/상태

| 용어 | 쉬운 설명 |
| --- | --- |
| 컴포넌트(Component) | 화면을 이루는 재사용 가능한 작은 단위. 레고 블록 하나에 비유할 수 있습니다. |
| Props | 부모 컴포넌트가 자식 컴포넌트에게 전달하는 값(읽기 전용). |
| State(상태) | 시간이 지나며 바뀌고, 바뀌면 화면도 다시 그려져야 하는 값. |
| 지역 상태 | 컴포넌트 하나 안에서만 쓰는 상태. |
| 전역 상태 | 여러 화면이 공유하는 상태. |
| SPA (Single Page Application) | 페이지 전체를 새로 불러오지 않고 필요한 부분만 JS로 갱신하는 웹앱 방식. React는 SPA를 만드는 데 자주 쓰이지만, Next.js 같은 프레임워크를 사용하면 SSR·SSG 등 여러 렌더링 방식을 함께 사용할 수 있습니다. |

## 0.5 네트워크/비동기

| 용어 | 쉬운 설명 |
| --- | --- |
| API | 서버와 데이터를 주고받기 위해 정해진 약속(창구). |

| Promise | 비동기 작업의 결과(성공/실패)를 나중에 받기로 약속한 객체. |
| async/await | Promise를 마치 동기 코드처럼 읽기 쉽게 쓰는 문법. |
| JSON | `{ "key": "value" }` 형태의 데이터 형식. API 응답에서 가장 흔히 씀. |

## 0.8 개발 환경과 프로젝트 파일

프론트엔드 개발에서는 HTML/CSS/JavaScript만큼 **Node.js·패키지 매니저·프로젝트 설정 파일**을 이해하는 것이 중요합니다.

| 항목 | 쉬운 설명 |
| --- | --- |
| Node.js | 브라우저 밖에서도 JavaScript를 실행할 수 있게 해주는 런타임. 프론트 개발 도구(Vite 등)를 실행할 때 사용 |
| npm | Node.js 패키지 매니저. 라이브러리 설치와 개발 명령 실행에 사용 |
| `package.json` | 프로젝트 이름, 설치된 패키지, 실행 명령(`scripts`)을 기록한 핵심 설정 파일 |
| `node_modules/` | 설치된 패키지가 실제로 들어가는 폴더. 직접 수정하지 않고 Git에도 보통 올리지 않음 |
| lock 파일 | `package-lock.json`, `pnpm-lock.yaml` 등. 팀원이 같은 버전의 의존성을 설치하도록 버전을 고정 |
| Vite | 개발 서버와 빌드 환경을 빠르게 제공하는 대표적인 프론트엔드 빌드 도구 |
| npm script | `npm run dev`, `npm run build`처럼 `package.json`에 이름을 붙여둔 실행 명령 |

### React + Vite 프로젝트를 처음 실행하는 예

```bash
node --version
npm --version

npm create vite@latest my-app -- --template react
cd my-app
npm install
npm run dev
```

기존 프로젝트를 받은 경우에는 새 프로젝트를 만들지 않고 저장소 폴더에서 보통 다음처럼 시작합니다.

```bash
npm install
npm run
npm run dev
```

`npm run`을 입력하면 현재 `package.json`의 `scripts` 목록을 볼 수 있습니다.

### React 프로젝트 폴더 구조 예시

`npm create vite@latest`로 만든 프로젝트는 처음엔 폴더가 거의 비어 있습니다. 기능이 늘어나면서 보통 아래처럼 역할별로 나눠갑니다. 처음부터 이 구조를 다 만들 필요는 없고, 파일이 늘어날 때마다 필요한 폴더를 그때그때 추가하면 됩니다.

```text
my-app/
├── public/                # 그대로 배포되는 정적 파일 (favicon 등)
├── src/
│   ├── main.jsx           # 앱의 시작점 — React를 화면에 처음 그리는 곳
│   ├── App.jsx            # 최상위 컴포넌트, 라우터를 여기서 연결
│   ├── pages/              # 화면(페이지) 단위 컴포넌트 — 라우팅 경로 하나당 보통 파일 하나
│   │   ├── CourseListPage.jsx
│   │   └── CourseDetailPage.jsx
│   ├── components/          # 여러 페이지에서 재사용하는 작은 컴포넌트
│   │   ├── Header.jsx
│   │   └── CourseCard.jsx
│   ├── hooks/               # 재사용 가능한 상태·로직 (예: useAuth, useFetch)
│   ├── api/                 # 서버 요청 함수 모음 — fetch/axios 호출은 전부 여기로
│   │   └── courses.js
│   ├── context/             # 여러 화면이 공유하는 전역 상태 (예: 로그인 사용자 정보)
│   ├── styles/               # 전역 CSS, 변수
│   └── utils/                # 날짜 포맷 등 순수 함수 모음
├── package.json
└── vite.config.js
```

* `pages/`와 `components/`의 차이: **라우팅 경로와 1:1로 대응되면 pages, 여러 곳에서 재사용되면 components**로 나눕니다. 예를 들어 `/courses/10`에 대응하는 화면 전체는 `pages/CourseDetailPage.jsx`이고, 그 안에서 쓰이는 강의 카드 하나는 `components/CourseCard.jsx`입니다.
* `api/` 폴더를 따로 두는 이유: 컴포넌트 안에서 직접 `fetch`를 호출하면 같은 요청 코드가 여러 파일에 흩어집니다. API 함수를 한 곳에 모아두면 서버 주소가 바뀌거나 요청 방식이 바뀔 때 한 파일만 고치면 됩니다.
* 폴더가 늘어나기 시작하는 시점: 컴포넌트 파일이 10개를 넘거나, 같은 폴더 안에서 원하는 파일을 찾는 데 시간이 걸리기 시작하면 그때 세부 폴더(`components/course/`, `components/common/` 등)로 나눕니다.

### `Missing script: "dev"`가 뜨는 이유

```text
npm run dev
→ package.json의 scripts에서 "dev"라는 이름을 찾음
→ 없으면 Missing script 오류
```

따라서 아래 순서로 확인합니다.

1. 현재 터미널 위치가 프론트엔드 프로젝트 폴더인지 확인
2. `package.json`이 현재 폴더에 있는지 확인
3. `npm run`으로 등록된 스크립트 확인
4. README에 실제 실행 명령이 따로 적혀 있는지 확인

### `import` / `export`

파일을 나눠 개발할 때 JavaScript 모듈 문법으로 서로 연결합니다.

```js
// api.js
export async function getCourses() {
  const response = await fetch("/api/courses");
  return response.json();
}

// CoursePage.jsx
import { getCourses } from "./api";
```

초보자가 자주 겪는 오류인 “함수가 정의되지 않았다”, “모듈을 찾을 수 없다”는 문제는 파일 경로·export/import 방식부터 확인합니다.

# 1. 프론트엔드란?

프론트엔드는 사용자가 웹 브라우저에서 직접 보고 조작하는 부분을 개발하는 영역입니다.

프론트엔드는 단순히 화면을 예쁘게 만드는 역할만 하지 않습니다.

* 정보를 이해하기 쉽게 보여주기

* 사용자의 입력을 받기

* 서버에 데이터를 요청하기

* 서버 응답을 화면에 반영하기

* 로딩, 오류, 빈 결과를 처리하기

* 다양한 화면 크기에서 사용할 수 있게 만들기

* 키보드와 보조기술 사용자도 이용할 수 있게 만들기

* 빠르고 안전하게 동작하게 만들기

일반적인 구조:

```
사용자
↓
브라우저
↓
프론트엔드
↓ HTTP 요청
백엔드 API
↓
데이터베이스 또는 외부 서비스
```

프론트엔드는 일반적으로 데이터베이스에 직접 접근하지 않습니다.

# 2. 웹이 동작하는 기본 원리

사용자가 주소를 입력하면 대략 다음 과정이 일어납니다.

```
1. 사용자가 URL 입력
2. 브라우저가 서버에 요청
3. 서버가 HTML, CSS, JavaScript 또는 데이터를 응답
4. 브라우저가 HTML 구조 생성
5. CSS로 화면 표현
6. JavaScript로 동작 추가
7. 필요한 데이터는 API로 다시 요청
8. 응답에 따라 화면 갱신
```

## URL 기본 구조

```
https://example.com:443/products/10?category=book#review
```

| 부분 | 의미 |
| --- | --- |
| `https` | 통신 방식 |
| `example.com` | 도메인 |
| `443` | 포트 |
| `/products/10` | 경로 |
| `?category=book` | Query Parameter |
| `#review` | 페이지 내부 위치 |

# 3. 프론트엔드의 세 가지 기본 기술

## 3.1 HTML

HTML은 웹페이지의 구조와 의미를 작성합니다.

```
<header>
  <h1>온라인 서점</h1>
</header>

<main>
  <article>
    <h2>책 제목</h2>
    <p>책 설명</p>
    <button type="button">장바구니 담기</button>
  </article>
</main>
```

HTML에서 중요한 것은 단순히 화면 모양이 아니라 **의미에 맞는 태그**를 사용하는 것입니다.

* 제목: `h1`~`h6`

* 문단: `p`

* 목록: `ul`, `ol`, `li`

* 링크: `a`

* 버튼: `button`

* 입력: `input`, `select`, `textarea`

* 주요 영역: `header`, `nav`, `main`, `section`, `article`, `footer`

### 기본 상식

* 클릭 동작에는 가능한 한 `div`보다 `button`이나 `a` 사용

* 페이지에 핵심 `h1`은 명확하게 지정

* 이미지는 `alt` 속성 작성

* 입력창은 `label`과 연결

* HTML 구조는 CSS가 없어도 읽을 수 있어야 함

---

## 3.2 CSS

CSS는 화면의 배치, 크기, 색상, 간격, 반응형 표현을 담당합니다.

필수 개념:

* 선택자

* 박스 모델

* `display`

* Flexbox

* Grid

* 위치 지정

* 단위

* 반응형

* 우선순위

* 상속

### 박스 모델

모든 요소는 다음 구조로 생각할 수 있습니다.

```
margin
└── border
    └── padding
        └── content
```

### 자주 사용하는 단위

| 단위 | 용도 |
| --- | --- |
| `px` | 고정된 크기 |
| `%` | 부모 기준 비율 |
| `rem` | 기본 글꼴 기준 |
| `vw`, `vh` | 화면 크기 기준 |
| `fr` | Grid 공간 비율 |

### 레이아웃 기준

* 한 방향 정렬: Flexbox

* 행과 열을 함께 구성: Grid

* 콘텐츠 최대 폭 지정

* 간격은 일정한 규칙 사용

* 절대 위치는 꼭 필요한 경우만 사용

### CSS 기본 상식

* `box-sizing: border-box`를 전역 적용하면 크기 계산이 편해짐

* 클래스 이름은 역할이 드러나게 작성

* 같은 값을 반복하면 CSS 변수 사용

* `!important` 남용 금지

* 모바일 화면을 반드시 확인

* 텍스트가 길어졌을 때 레이아웃이 깨지는지 확인

### CSS가 예상과 다르게 적용될 때

CSS는 “나중에 쓴 코드가 무조건 이긴다”가 아니라 여러 규칙을 함께 봅니다.

- **Cascade(캐스케이드)**: 여러 CSS 규칙이 충돌할 때 최종 스타일을 결정하는 과정
- **Specificity(명시도)**: 선택자가 얼마나 구체적인지에 따른 우선순위
- **Inheritance(상속)**: 일부 속성이 부모 요소에서 자식 요소로 전달되는 성질

```css
p { color: black; }           /* 태그 선택자 */
.card p { color: blue; }      /* 더 구체적 */
#main .card p { color: red; } /* 더 높은 명시도 */
```

스타일이 안 먹으면 `!important`부터 붙이지 말고 **브라우저 개발자 도구 → Elements → Styles/Computed**에서 어떤 규칙이 덮어쓰고 있는지 확인합니다.

## 6.4 Same-Origin Policy와 CORS

브라우저는 보안을 위해 **출처(origin)가 다른 서버로 보내는 일부 요청을 제한**합니다.

Origin은 일반적으로 다음 세 요소의 조합입니다.

```text
프로토콜 + 호스트 + 포트
```

예:

```text
http://localhost:5173   ← 프론트
http://localhost:5000   ← 백엔드
```

포트가 다르므로 서로 다른 origin입니다. 이때 백엔드가 허용 응답 헤더를 보내지 않으면 브라우저에서 CORS 오류가 날 수 있습니다.

중요한 점:

- CORS는 “프론트 코드가 틀렸다”는 뜻이 아닐 수 있습니다.
- 브라우저가 적용하는 보안 정책이므로 Postman에서는 되고 브라우저에서는 막힐 수도 있습니다.
- 허용 origin은 가능하면 필요한 주소만 지정합니다.
- 쿠키 기반 인증을 쓸 때는 프론트의 `credentials` 설정과 서버의 자격 증명 허용 설정을 함께 맞춰야 합니다.

```js
fetch("https://api.example.com/me", {
  credentials: "include",
});
```

CORS 오류가 나면 **브라우저 Console만 보지 말고 Network 탭에서 실제 요청·응답 헤더와 상태를 확인**합니다.

## 요청 경합(Race Condition)과 오래된 응답

검색창처럼 요청이 연속으로 발생하는 화면에서는 **먼저 보낸 요청이 나중에 도착**할 수 있습니다.

```text
"A" 검색 요청 ───────────────→ 늦게 도착
"AB" 검색 요청 ─────→ 먼저 도착

화면이 "AB" 결과를 보여줌
→ 뒤늦게 "A" 응답이 도착
→ 오래된 결과로 화면이 되돌아갈 수 있음
```

해결 방법:

- 요청마다 최신 요청 ID를 비교
- 이전 요청을 `AbortController`로 취소
- React Query/TanStack Query 같은 서버 상태 도구의 기능 활용

모든 화면에 필요한 개념은 아니지만, **검색·자동완성·빠른 페이지 이동**에서 문제가 생기면 이 상황을 의심합니다.

### 실제 코드로 보면 이렇게 생겼습니다 (React 예시)

앞서 나온 Props와 State가 React에서는 실제로 어떤 모습인지 보여드립니다. 강의 카드 컴포넌트 하나를 예로 듭니다.

```
// CourseCard.jsx — 부모가 전달한 값(Props)을 받아서 화면에 그리기만 하는 컴포넌트
function CourseCard({ title, price }) {   // ← title, price가 Props: 부모가 넘겨준 읽기 전용 값
  return (
    <div className="course-card">
      <h2>{title}</h2>
      <p>{price === 0 ? "무료" : `${price}원`}</p>
    </div>
  );
}

// CourseList.jsx — 이 컴포넌트 안에서 바뀌는 값(State)을 직접 관리
import { useState, useEffect } from "react";

function CourseList() {
  const [courses, setCourses] = useState([]);   // ← State: 시간이 지나며 바뀌는 값 (처음엔 빈 배열)
  const [isLoading, setIsLoading] = useState(true);

  useEffect(() => {
    fetch("/api/courses")
      .then((response) => response.json())
      .then((data) => {
        setCourses(data.courses);   // ← State를 바꾸면 React가 화면을 자동으로 다시 그림(재렌더링)
        setIsLoading(false);
      });
  }, []);

  if (isLoading) return <p>불러오는 중입니다...</p>;

  return (
    <div>
      {courses.map((course) => (
        // ← 여기서 CourseCard에게 title, price를 Props로 "내려준다"고 표현
        <CourseCard key={course.id} title={course.title} price={course.price} />
      ))}
    </div>
  );
}
```

* `CourseList`는 서버에서 받아온 데이터를 `courses`라는 **State**로 들고 있습니다. State가 바뀌면(`setCourses` 호출) React가 알아서 화면을 다시 그립니다.

* `CourseCard`는 스스로 상태를 갖지 않고, 부모가 준 `title`·`price` **Props**만 그대로 화면에 표시합니다. 이런 컴포넌트를 “표현만 담당한다”고 말합니다.

* `isLoading` State가 있어서 12장에서 다루는 “로딩 중” 상태를 화면에 따로 보여줄 수 있습니다.

Vue, Svelte도 문법은 다르지만 “부모가 자식에게 값을 내려준다(Props)”와 “컴포넌트 안에서 바뀌는 값을 따로 관리한다(State)”는 개념은 동일합니다.

## TypeScript는 왜 많이 쓰는가?

TypeScript는 JavaScript에 **타입 검사**를 추가한 언어입니다.

```ts
type Course = {
  id: number;
  title: string;
};

function CourseCard({ course }: { course: Course }) {
  return <div>{course.title}</div>;
}
```

장점:

- API 응답 필드명을 잘못 쓰는 실수를 빨리 발견
- 함수에 어떤 값을 넣어야 하는지 명확
- 규모가 커질수록 리팩토링이 안전해짐
- 에디터 자동완성이 좋아짐

처음부터 반드시 TypeScript를 써야 하는 것은 아닙니다. **JavaScript의 변수·함수·객체·배열·비동기를 먼저 이해한 뒤** TypeScript를 배우면 훨씬 쉽습니다.

## CSR / SSR / SSG 기본

| 방식 | 의미 | 특징 |
| --- | --- | --- |
| CSR | 브라우저에서 JavaScript로 화면을 렌더링 | SPA에서 흔함. 초기 HTML은 단순할 수 있음 |
| SSR | 요청 시 서버가 HTML을 만들어 응답 | 초기 화면·SEO에 유리할 수 있음 |
| SSG | 빌드 시 HTML을 미리 만들어 둠 | 자주 바뀌지 않는 페이지에 적합 |

React를 배웠다고 모든 웹사이트가 CSR인 것은 아닙니다. Next.js 같은 프레임워크에서는 페이지 성격에 따라 여러 렌더링 방식을 함께 사용할 수 있습니다.

## XSS(Cross-Site Scripting)란?

위에서 "사용자 입력을 그대로 HTML로 삽입하지 않기"라고 한 이유입니다. 사용자가 입력한 텍스트를 검증 없이 화면에 그대로 그리면, 그 텍스트 안에 `<script>` 태그가 섞여 있을 때 다른 사용자의 브라우저에서 그대로 실행되어 버립니다.

```jsx
// 위험: 사용자 입력을 그대로 HTML로 해석해서 그림
<div dangerouslySetInnerHTML={{ __html: userComment }} />
// userComment에 <script>...</script>가 들어있으면 그대로 실행됨

// 안전: 텍스트로만 그림 (React는 기본적으로 이렇게 동작)
<div>{userComment}</div>
```

React·Vue 같은 프레임워크는 `{userComment}`처럼 평범하게 값을 출력하는 한 자동으로 이스케이프해줘서 비교적 안전합니다. 위험은 `dangerouslySetInnerHTML`, `innerHTML`처럼 "이 문자열을 HTML로 그대로 해석해라"라고 직접 지시하는 지점에서 생깁니다.

## 인증 정보를 어디에 저장할까?

“로그인 토큰은 무조건 localStorage에 넣는다”처럼 외우지 않습니다. 저장 위치는 인증 구조와 위협 모델에 따라 결정합니다.

### 자주 쓰는 선택지

- **HttpOnly Cookie**: JavaScript에서 직접 읽을 수 없게 설정할 수 있어 XSS로 토큰을 탈취하기 어렵게 만들 수 있음
- **메모리 상태**: 새로고침하면 사라지지만 브라우저 저장소에 장기간 남기지 않음
- **localStorage**: 사용이 간단하지만 JavaScript에서 접근 가능하므로 XSS가 발생하면 값이 노출될 수 있음

쿠키 기반 인증에서는 서버가 다음 옵션을 함께 검토합니다.

- `HttpOnly` — JavaScript(`document.cookie`)로 이 쿠키를 읽지 못하게 막는 옵션
- `Secure` — HTTPS 연결에서만 이 쿠키를 전송하게 하는 옵션
- `SameSite` — 다른 사이트에서 걸어온 요청에는 이 쿠키를 자동으로 실어 보내지 않게 하는 옵션

반대로 쿠키를 자동 전송하는 구조에서는 **CSRF**(공격 사이트가 사용자를 대신해 요청을 보내는 공격 — 백엔드 기초 가이드 12장 참고)도 함께 고려해야 합니다.

초보자 기준 핵심은 다음입니다.

> 로그인 정보를 어디에 저장할지는 프론트엔드 혼자 정하지 말고, 백엔드의 인증 방식과 함께 결정한다.

# 22. 놓치기 쉬운 완성도 디테일

기능은 다 동작하는데 뭔가 "만들다 만" 느낌이 나는 사이트가 있습니다. 대부분 아래 항목들을 안 챙겨서입니다. 기능 구현보다 시간이 훨씬 적게 들지만, 있고 없고의 인상 차이는 큽니다.

## 파비콘(Favicon)

브라우저 탭에 뜨는 작은 아이콘입니다. 없으면 브라우저 기본 아이콘(빈 문서 모양)이 뜨고, "이 사이트는 신경 써서 안 만들었구나"라는 인상을 가장 먼저 줍니다.

```html
<link rel="icon" href="/favicon.ico">
<!-- 이미지 파일 없이 이모지 하나로 간단히 만들 수도 있습니다 -->
<link rel="icon" href="data:image/svg+xml,<svg xmlns='http://www.w3.org/2000/svg' viewBox='0 0 100 100'><text y='.9em' font-size='90'>🌱</text></svg>">
```

## 메타 태그 — title과 description

```html
<title>개발 공부 가이드 · 개발 학습·실전 노트</title>
<meta name="description" content="초급부터 고급까지 단계별로 정리된 개발 학습 자료">
```

`<title>`은 브라우저 탭과 검색 결과 제목에, `description`은 검색 결과의 미리보기 문구에 쓰입니다. 모든 페이지가 똑같은 제목("React App")이면 사용자도 검색엔진도 페이지를 구분하지 못합니다.

## OG 태그 — 카톡·인스타에 링크 공유했을 때 뜨는 미리보기

링크를 메신저에 붙여넣었을 때 제목·설명·이미지가 카드 형태로 뜨는 걸 본 적이 있을 겁니다. 이건 `<meta property="og:...">` 태그가 있어야 나타납니다. 없으면 그냥 URL 텍스트만 덩그러니 보입니다.

```html
<meta property="og:title" content="개발 공부 가이드">
<meta property="og:description" content="초급부터 고급까지 단계별로 정리된 개발 학습 자료">
<meta property="og:image" content="https://example.com/preview.png">
<meta property="og:url" content="https://example.com">
```

**기본 상식**: 프로젝트를 다른 사람에게 링크로 공유할 일이 있다면(포트폴리오, 사이드 프로젝트 등) OG 태그는 우선순위가 높습니다. 첫인상이 "텍스트 링크"냐 "미리보기 카드"냐를 가릅니다.

## robots.txt와 sitemap.xml — 검색엔진에게 알려주기

```text
robots.txt   → 검색엔진 크롤러에게 "이 경로는 수집해도 된다/안 된다"를 알려주는 파일
sitemap.xml  → 이 사이트에 어떤 페이지들이 있는지 목록으로 알려주는 파일
```

이 두 파일이 없어도 사이트는 정상 동작하지만, 검색엔진이 페이지를 발견하고 색인하는 속도와 범위에 영향을 줍니다. 로그인 후에만 보이는 페이지처럼 검색에 노출되면 안 되는 경로는 `robots.txt`로 명시적으로 막아둡니다.

## 404 페이지

존재하지 않는 주소로 들어왔을 때 프레임워크의 기본 흰 화면 대신, "이 페이지는 없어요" + 홈으로 돌아가는 링크가 있는 화면을 보여줍니다. 사용자가 오타로 잘못된 링크에 들어왔을 때 그대로 나가버리지 않게 하는 최소한의 배려입니다.

## 정적 자산 캐시 무효화

CSS·JS 파일을 수정해서 다시 배포해도, 이미 방문했던 사용자의 브라우저는 예전 파일을 계속 캐시해서 쓰기도 합니다. 수정 사항이 배포됐는데도 사용자에게는 "안 고쳐진 것처럼" 보이는 원인 중 하나입니다.

```html
<!-- 파일 내용이 바뀔 때마다 값이 바뀌는 버전을 쿼리로 붙여, 바뀐 경우에만 새로 받아가게 함 -->
<link rel="stylesheet" href="style.css?v=a1b2c3">
```

## 폼 자동완성 속성

```html
<input type="email" name="email" autocomplete="email">
<input type="password" name="password" autocomplete="current-password">
```

`autocomplete`와 의미 있는 `name` 값을 붙여두면, 브라우저가 이전에 입력했던 값이나 비밀번호 관리자에 저장된 값을 자동으로 채워줍니다. 사용자가 로그인 폼마다 매번 손으로 다 입력하지 않아도 되게 하는 작은 배려입니다.

## 다크모드 고려

처음부터 다크모드까지 만들 필요는 없지만, 배경·글자색을 코드 곳곳에 하드코딩하지 않고 변수(CSS 커스텀 속성 등)로 관리해두면 나중에 다크모드를 붙이기 훨씬 쉬워집니다.

```css
:root { --bg: #ffffff; --text: #111111; }
body { background: var(--bg); color: var(--text); }
```

# 33. 직접 실습해보기 — 프론트엔드 최소 실습

목표는 예쁜 페이지가 아니라 **“프로젝트 생성 → 상태 → API → 오류 처리 → 빌드”의 전체 흐름을 한 번 경험하는 것**입니다.

## 1단계. React 프로젝트 실행

```bash
npm create vite@latest frontend-practice -- --template react
cd frontend-practice
npm install
npm run dev
```

브라우저에서 터미널에 표시된 `localhost` 주소가 열리면 개발 환경은 정상입니다.

## 2단계. 상태 하나 만들기

버튼을 누르면 숫자가 증가하는 화면을 만듭니다. `src/App.jsx`를 아래처럼 바꿔봅니다.

```jsx
import { useState } from "react";

function App() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>클릭 횟수: {count}</p>
      <button onClick={() => setCount(count + 1)}>클릭</button>
    </div>
  );
}

export default App;
```

확인할 것:

- 저장하자마자 브라우저가 자동으로 새로고침되는지(HMR)
- 버튼을 누를 때마다 화면 숫자가 바뀌는지
- `count`를 `let count = 0`처럼 일반 변수로 바꾸고 값을 바꿔도 화면이 그대로인 이유(리렌더링을 트리거하지 못하기 때문)

왜 이걸 하는지: React에서 화면이 바뀌는 원리는 결국 "상태가 바뀌면 다시 그린다"는 한 가지 규칙입니다. 이걸 가장 작은 예제로 직접 겪어보면 이후 복잡한 컴포넌트를 봐도 같은 원리로 읽을 수 있습니다.

## 3단계. 더미 데이터 목록 만들기

```js
const courses = [
  { id: 1, title: "HTML 기초" },
  { id: 2, title: "React 입문" },
];
```

`map`으로 카드 여러 개를 렌더링하고 각 항목에 안정적인 `key`를 지정합니다.

## 4단계. API 데이터로 교체

```js
async function getCourses() {
  const response = await fetch("http://localhost:5000/courses");
  if (!response.ok) throw new Error("강의 목록 요청 실패");
  return response.json();
}
```

화면에는 최소 네 상태가 있어야 합니다.

```text
로딩 중
성공 + 데이터 있음
성공 + 빈 배열
실패
```

- Request URL
- Method
- Status Code
- Request Headers
- Response Headers
- Response Body

이 경험을 해두면 CORS·401·404·500 오류를 훨씬 빨리 구분할 수 있습니다.
