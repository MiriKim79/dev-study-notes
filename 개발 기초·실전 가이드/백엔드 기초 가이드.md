> **대상:** 웹 백엔드 개발을 처음 시작하는 사람  
> **목적:** Flask·Express·Spring·Django 등 프레임워크가 달라도 공통으로 필요한 서버, API, DB, 인증·인가, 보안, 테스트, 배포의 기본 원리를 이해하는 가이드  
> **사용법:** 용어와 요청 흐름을 먼저 이해한 뒤, 마지막 작은 API 실습으로 서버→DB→응답 흐름을 직접 확인합니다.

# 0. 시작 전에 — 자주 나오는 용어

개발이 처음이라면 본문을 읽기 전에 아래 표부터 훑어보세요. 본문 중간에 낯선 단어가 나오면 다시 여기로 돌아와 찾아봐도 됩니다.

## 0.1 컴퓨터·개발 환경

| 용어 | 쉬운 설명 |
| --- | --- |
| 터미널(Terminal) / 커맨드라인(CLI) | 마우스 클릭 대신 글자로 명령을 입력해 컴퓨터를 조작하는 화면. VS Code에서는 상단 메뉴 `Terminal → New Terminal`로 엽니다. |
| 프로세스(Process) | 실행 중인 프로그램 하나. 서버를 켜면 “서버 프로세스가 떠 있다”고 표현합니다. |
| 포트(Port) | 한 컴퓨터 안에서 여러 프로그램이 동시에 통신할 수 있도록 구분하는 번호(0~65535). 예: `http://localhost:5000`에서 `5000`이 포트 번호입니다. |
| 로컬(local) / localhost | 지금 쓰고 있는 이 컴퓨터 자신을 가리키는 주소(`127.0.0.1`). “로컬에서 돌린다” = 내 컴퓨터에서만 실행한다는 뜻. |
| 패키지 매니저 | 다른 사람이 만든 코드(라이브러리)를 설치·관리해주는 도구. Python은 `pip`, Node.js는 `npm`. |
| 프레임워크 | 특정 종류의 프로그램(웹 서버 등)을 쉽게 만들도록 미리 짜여진 뼈대. 예: Flask, Express, Spring, Django. |

## 0.2 서버·통신

| 용어 | 쉬운 설명 |
| --- | --- |
| 서버(Server) | 요청을 받아서 응답을 돌려주는 프로그램. 백엔드 코드를 짠다 = 서버 프로그램을 만든다는 뜻. |
| 클라이언트(Client) | 서버에 요청을 보내는 쪽. 보통 브라우저(프론트엔드)나 모바일 앱. |
| HTTP | 클라이언트와 서버가 데이터를 주고받을 때 쓰는 공통 약속(규격). |
| 요청(Request) / 응답(Response) | 클라이언트가 서버에 보내는 것 = 요청, 서버가 돌려주는 것 = 응답. |
| 엔드포인트(Endpoint) | 요청을 받는 구체적인 주소 하나. 예: `GET /courses`. |
| 라우팅(Routing) / 라우트(Route) | “이 URL + 이 메서드로 요청이 오면 이 코드를 실행해라”라고 연결해두는 것. |
| API | 프로그램끼리 데이터를 주고받기 위해 미리 정해둔 규칙(창구). “강의 목록 API” = 강의 목록을 요청/응답하는 약속. |
| REST / REST API | URL과 HTTP 메서드로 자원을 표현하는 API 설계 방식(4장에서 자세히 다룸). |
| JSON | `{ "key": "value" }` 형태로 데이터를 표현하는 형식. 요청·응답 바디에 가장 흔히 씀. |
| Query Parameter | URL 뒤에 `?key=value` 형태로 붙는 값. 예: `/courses?category=web`. |
| CORS | 브라우저의 Same-Origin Policy 때문에 다른 출처(origin)의 프론트가 API 응답을 읽으려 할 때, 서버가 어떤 출처·메서드·헤더를 허용할지 응답 헤더로 알려주는 방식. 개발 환경에서 프론트와 백엔드의 포트가 다르면 서로 다른 origin이 될 수 있습니다. |

## 0.3 코드 구조

| 용어 | 쉬운 설명 |
| --- | --- |
| 컨트롤러(Controller) / 핸들러(Handler) | 요청이 들어왔을 때 가장 먼저 받는 코드. “이 요청 값이 올바른지 확인하고 서비스를 불러라” 역할. |
| 서비스(Service) | 실제 비즈니스 규칙(수강 가능 여부 판단 등)을 처리하는 코드. |
| 모델(Model) / 엔티티(Entity) | 데이터베이스 테이블 하나를 코드로 표현한 것. |
| 미들웨어(Middleware) | 모든 요청 앞뒤에 공통으로 끼어들어 실행되는 코드(인증 확인, 로깅 등). |

## 0.4 데이터베이스

| 용어 | 쉬운 설명 |
| --- | --- |
| 데이터베이스(DB) | 데이터를 저장해두는 프로그램/공간. |
| 테이블(Table) | 엑셀 시트 하나와 비슷. 행(row)과 열(column)로 데이터를 저장. |
| 기본키(Primary Key, PK) | 한 행을 유일하게 구분하는 값(보통 `id`). |
| 외래키(Foreign Key, FK) | 다른 테이블의 기본키를 가리켜서 두 테이블을 연결하는 값. |
| SQL | 데이터베이스에 데이터를 넣고·읽고·바꾸고·지울 때 쓰는 언어. |
| ORM | SQL을 직접 안 쓰고 코드(객체)로 데이터베이스를 다루게 해주는 도구. |
| 트랜잭션(Transaction) | 여러 작업을 하나로 묶어서 전부 성공 또는 전부 취소되게 하는 것. |
| 롤백(Rollback) | 트랜잭션 중 하나라도 실패하면 지금까지 한 작업을 없던 일로 되돌리는 것. |
| 마이그레이션(Migration) | 데이터베이스 테이블 구조 변경 내역을 파일로 기록해서 팀과 공유하는 방법. |
| 인덱스(Index) | 책의 “찾아보기”처럼 특정 컬럼 검색을 빠르게 해주는 장치. |

## 0.5 인증·보안

| 용어 | 쉬운 설명 |
| --- | --- |
| 인증(Authentication) | “너 누구야?”를 확인하는 것(로그인). |
| 인가(Authorization) | “너 이거 해도 돼?”를 확인하는 것(권한). |
| 세션(Session) | 로그인 상태를 서버가 기억해두는 방식. |
| 토큰(Token) / JWT | 로그인 상태를 문자열 하나로 표현해서 클라이언트가 들고 다니는 방식. |
| 해싱(Hashing) | 비밀번호 원문을 복원 불가능한 다른 문자열로 바꿔 저장하는 방법. |
| SQL Injection | 사용자 입력을 SQL 문에 그대로 이어붙여서 공격자가 DB를 조작하게 되는 취약점. |
| 환경변수(Environment Variable) | 비밀번호·API 키처럼 코드에 직접 쓰면 안 되는 값을, 코드 밖 별도 파일(`.env`)에 두고 실행할 때 불러오는 방법. |

# 1. 백엔드란?

백엔드는 사용자에게 보이지 않는 곳에서 데이터를 검증·저장·가공하고, 프론트엔드가 요청한 결과를 응답으로 돌려주는 영역입니다.

* 요청을 받고 검증하기

* 인증과 권한을 확인하기

* 데이터베이스에 접근하기

* 비즈니스 로직을 처리하기

* 외부 서비스(AI API, 결제, 이메일 등)와 연동하기

* 일관된 형식으로 응답하기

* 오류를 안전하게 처리하기

* 여러 사용자의 동시 요청을 안정적으로 처리하기

일반적인 구조:

```
프론트엔드
↓ HTTP 요청
백엔드 (라우팅 → 검증 → 인증 → 로직 → DB)
↓
데이터베이스 / 외부 서비스
↓
백엔드가 결과를 가공
↓
프론트엔드에 JSON 응답
```

백엔드는 클라이언트가 보낸 값을 그대로 믿지 않습니다. 화면에서 막았어도 서버에서 다시 검증합니다.

### 비유로 이해하기

식당에 비유하면 이해가 빠릅니다.

```
프론트엔드 = 홀(손님이 보는 메뉴판, 테이블)
백엔드     = 주방(주문을 받아 실제로 요리해서 내보내는 곳)
데이터베이스 = 냉장고·재고 창고(주방이 재료를 꺼내 쓰는 곳)
```

손님(사용자)은 홀(프론트엔드)에서 메뉴를 보고 주문하지만, 실제로 재료를 확인하고 요리하는 일은 주방(백엔드)에서 일어납니다. 손님이 “이 메뉴 재료 다 있어요”라고 말해도 주방은 냉장고를 직접 확인하고 요리합니다 — 이것이 “클라이언트가 보낸 값을 그대로 믿지 않는다”는 원칙과 같은 이야기입니다.

# 2. 요청-응답이 처리되는 기본 흐름

```
1. 클라이언트가 HTTP 요청을 보냄 (메서드 + URL + 헤더 + 바디)
2. 서버가 요청을 받아 해당 라우트를 찾음
3. 미들웨어(인증, 로깅, CORS 등)를 거침
4. 컨트롤러/핸들러가 요청값을 검증함
5. 서비스 로직이 실행됨
6. 필요하면 데이터베이스에 접근함
7. 결과를 응답 형식(JSON 등)으로 가공함
8. 상태 코드와 함께 응답을 반환함
```

이 흐름을 한 번이라도 손으로 그려보면, 어떤 프레임워크를 쓰든 디버깅할 때 “지금 어느 단계에서 문제가 생겼는지”를 빠르게 짚을 수 있습니다.

# 3. 백엔드의 핵심 구성 요소

```
Route (라우팅)
→ 어떤 URL·메서드가 어떤 처리로 연결되는지 정의

Controller / Handler
→ 요청을 받아 검증하고 서비스를 호출

Service / Business Logic
→ 실제 처리 규칙 (예: 수강 신청 가능 여부 판단)

Model / Entity
→ 데이터베이스 테이블과 매핑되는 구조

Repository / DAO (선택)
→ 데이터베이스 접근 코드를 분리

Middleware
→ 인증, 로깅, 오류 처리 등 요청 전후 공통 처리
```

작은 프로젝트는 Controller와 Service를 합쳐도 괜찮지만, 역할이 무엇인지는 항상 구분해서 생각합니다.

### 실제 코드로 보면 이렇게 생겼습니다 (Flask 예시)

위 개념들이 실제 프레임워크에서는 어떤 모습인지, Flask로 강의 하나를 조회하는 예시를 통째로 보여드립니다. 처음 보면 낯설어도 괜찮습니다 — 지금은 “Route → Controller → Service → Model이 각각 어디에 해당하는지”만 눈으로 확인하면 됩니다.

```
# models.py — Model: courses 테이블과 매핑되는 구조
class Course(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    title = db.Column(db.String(200))
    price = db.Column(db.Integer)

# services/course_service.py — Service: 실제 처리 규칙
def get_course_or_raise(course_id):
    course = Course.query.get(course_id)
    if course is None:
        raise CourseNotFound()
    return course

# routes/course_routes.py — Route + Controller가 한 데코레이터 안에 있음
@app.route("/courses/<int:course_id>", methods=["GET"])  # ← 라우팅: 이 URL·메서드로 오면 아래 함수 실행
def get_course(course_id):                                # ← 컨트롤러: 요청을 받아 서비스를 호출
    try:
        course = get_course_or_raise(course_id)            # ← 서비스 호출
        return jsonify({"data": {"id": course.id, "title": course.title}}), 200
    except CourseNotFound:
        return jsonify({"error": {"code": "COURSE_NOT_FOUND", "message": "강의를 찾을 수 없습니다."}}), 404
```

* `@app.route(...)` 한 줄이 **라우팅**입니다: `GET /courses/10` 요청이 오면 `get_course` 함수를 실행하라는 뜻.

* `get_course` 함수 자체가 **컨트롤러**입니다: 요청을 받아 서비스를 부르고, 결과를 HTTP 응답(JSON + 상태 코드)으로 바꿔서 돌려줍니다.

* `get_course_or_raise`가 **서비스**입니다: “존재하지 않으면 오류를 던진다”는 실제 규칙이 여기 있습니다.

* `Course` 클래스가 **모델**입니다: `courses` 테이블의 각 컬럼(`id`, `title`, `price`)을 파이썬 속성으로 표현합니다.

Express(Node.js)나 Spring(Java)도 이름과 문법만 다를 뿐 이 네 가지 역할 구분은 동일합니다.

### 실제 폴더 구조 예시 (Flask)

위 예시의 `models.py`, `services/course_service.py`, `routes/course_routes.py`가 실제 프로젝트에서는 아래처럼 한 폴더 안에 자리잡습니다.

```text
backend/
├── app/
│   ├── __init__.py         # Flask 앱 생성, DB·확장 초기화, 블루프린트 등록
│   ├── models.py            # Model — 테이블과 매핑되는 클래스 모음
│   ├── routes/               # Route + Controller — URL별로 파일을 나눔
│   │   ├── course_routes.py
│   │   └── auth_routes.py
│   ├── services/              # Service — 실제 처리 규칙
│   │   └── course_service.py
│   └── middleware/             # 인증 확인, 로깅 등 공통 처리
├── migrations/                  # DB 테이블 구조 변경 이력 (마이그레이션 도구가 자동 생성)
├── tests/                        # 단위·통합 테스트
├── config.py                     # 환경별 설정값을 모아두는 곳
├── requirements.txt               # 설치된 패키지 목록
├── .env                            # 실제 비밀값 (Git에 올리지 않음)
├── .env.example                    # 필요한 환경변수 "이름"만 공유
└── run.py                           # 서버 실행 시작점
```

Express(Node.js) 프로젝트도 이름만 다를 뿐 같은 역할로 나뉩니다.

```text
backend/
├── src/
│   ├── models/            # Model
│   ├── routes/             # Route
│   ├── controllers/         # Controller
│   ├── services/             # Service
│   └── middleware/            # 공통 처리
├── package.json
└── .env
```

* 파일이 몇 개 안 되는 초기 단계에는 `routes`와 `controllers`를 합쳐도 괜찮습니다. 다만 나중에 나누기 쉽도록 함수 단위는 "요청을 검증하고 서비스를 부르는 부분"과 "실제 처리 규칙"을 섞어 쓰지 않는 습관을 들입니다.
* `migrations/`는 손으로 만드는 폴더가 아니라 Flask-Migrate, Sequelize 같은 도구가 `모델을 바꾸고 명령을 실행하면` 자동으로 만들어주는 폴더입니다. 직접 파일을 수정하지 않습니다.
* `.env`와 `.env.example`을 같이 두는 이유는 14장(환경변수)에서 다룹니다 — 실제 비밀값은 커밋하지 않고, 어떤 값이 필요한지 이름만 공유합니다.

# 4. HTTP와 REST API 설계

## 4.1 HTTP 메서드

| 메서드 | 일반적인 의미 |
| --- | --- |
| `GET` | 데이터 조회 (부작용 없음) |
| `POST` | 데이터 생성 또는 작업 요청 |
| `PUT` | 리소스 전체 수정 |
| `PATCH` | 리소스 일부 수정 |
| `DELETE` | 삭제 |

## 4.2 REST URL 설계 기본

```
GET    /courses          강의 목록 조회
GET    /courses/10       특정 강의 조회
POST   /courses          강의 생성
PATCH  /courses/10       강의 일부 수정
DELETE /courses/10       강의 삭제
```

### 기본 상식

* URL은 명사로 표현 (`/courses`), 동작은 HTTP 메서드로 표현

* 동사를 URL에 넣지 않기 (`/getCourses` ❌ → `GET /courses` ⭕)

* 복수형 명사를 일관되게 사용

* 계층 관계는 경로로 표현 (`/courses/10/reviews`)

* 검색·필터·정렬은 Query Parameter로 (`/courses?category=web&sort=price`)

---


## 4.3 CORS와 API 문서화

### CORS를 정확히 이해하기

CORS는 “서버끼리 통신을 막는 기능”이 아니라 주로 **브라우저가 다른 origin의 응답을 읽는 것을 제어하는 정책과 연결**됩니다.

```text
http://localhost:5173
http://localhost:5000
```

프로토콜·호스트·포트 중 하나라도 다르면 다른 origin입니다.

서버에서 점검할 것:

- 허용할 프론트엔드 origin
- 허용 HTTP 메서드
- 허용 요청 헤더
- 쿠키/자격 증명을 허용할지
- 운영 환경에서 `*`로 과도하게 열지 않았는지

### OpenAPI / Swagger

API가 많아질수록 문서와 실제 코드가 어긋나기 쉽습니다. OpenAPI는 API의 주소·메서드·요청·응답 스키마를 기계가 읽을 수 있게 정의하는 규격이고, Swagger UI 같은 도구로 사람이 테스트 가능한 문서를 만들 수 있습니다.

최소한 다음 정보는 API 문서에 있어야 합니다.

```text
메서드 + URL
인증 필요 여부
Path/Query Parameter
Request Body
성공 Response
오류 Response
상태 코드
```

프론트와 백엔드가 협업할 때는 **“코드가 아니라 API 명세가 계약”**이라는 원칙을 유지합니다.

# 5. 요청과 응답

## 5.1 요청 구성

```
메서드 + URL
헤더 (Content-Type, Authorization 등)
바디 (JSON 등)
```

## 5.2 응답 설계

```
{
  "data": {
    "id": 1,
    "title": "React 입문"
```

오류 응답도 일관된 형식을 유지합니다.

```
  }
```

* 프론트엔드가 필요로 하지 않는 내부 정보(스택 트레이스, 쿼리문 등)를 응답에 노출하지 않기

* 응답 필드명은 프론트엔드와 사전에 확정한 명세를 따름 (임의 변경 금지)

# 6. HTTP 상태 코드

| 코드 | 의미 |
| --- | --- |
| `200` | 요청 성공 |
| `201` | 데이터 생성 성공 |
| `204` | 성공했지만 응답 본문 없음 |
| `400` | 요청값이 잘못됨 |
| `401` | 인증되지 않음 |
| `403` | 인증은 되었지만 권한 없음 |
| `404` | 주소 또는 데이터 없음 |
| `409` | 중복 또는 충돌 |
| `422` | 요청 형식은 맞지만 값 검증 실패 |
| `500` | 서버 내부 오류 |

상태 코드만 정확히 반환하고 끝내지 않습니다. 응답 본문에 원인을 알 수 있는 최소한의 정보를 함께 담습니다.

# 7. 데이터베이스 기초

## 7.1 관계형 데이터베이스

테이블(행·열)로 데이터를 저장하고, 관계(외래키)로 테이블끼리 연결합니다.

```
users            courses           enrollments
──────           ───────           ───────────
id (PK)          id (PK)           id (PK)
email            title             user_id (FK)
password_hash    price             course_id (FK)
                                    enrolled_at
```

## 7.2 기본키와 외래키

```
기본키(Primary Key)
= 한 행을 유일하게 식별하는 값

외래키(Foreign Key)
= 다른 테이블의 기본키를 참조하는 값
```

## 7.3 ERD를 먼저 그리는 이유

* 테이블 간 관계를 미리 파악해 나중에 구조를 뒤엎는 일을 줄임

* 프론트엔드와 데이터 구조를 논의할 때 공통 언어가 됨

* 어떤 데이터가 어디서 필요한지 명확해짐

### 기본 상식

* 하나의 값은 한 곳에만 저장 (중복 저장은 나중에 불일치를 만듦)

* 삭제된 데이터가 필요한 경우 소프트 삭제(상태 컬럼)를 고려

* 컬럼명은 팀 전체가 합의한 규칙(snake\_case/camelCase 등)을 통일해서 사용

---


## 7.4 관계와 제약 조건

관계형 DB에서는 “컬럼이 존재한다”보다 **어떤 값이 허용되는지**까지 설계해야 합니다.

### 기본 제약 조건

| 제약 | 의미 | 예 |
| --- | --- | --- |
| `PRIMARY KEY` | 행을 유일하게 식별 | `users.id` |
| `FOREIGN KEY` | 다른 테이블의 행을 참조 | `enrollments.user_id` |
| `NOT NULL` | 값이 반드시 있어야 함 | `users.email` |
| `UNIQUE` | 중복 금지 | 이메일 |
| `DEFAULT` | 값을 안 넣었을 때 기본값 | `status='ACTIVE'` |
| `CHECK` | 허용 범위 검증 | `price >= 0` |

### 관계 종류

```text
1:1
사용자 1명 ↔ 프로필 1개

1:N
강사 1명 → 강의 여러 개

N:M
사용자 여러 명 ↔ 강의 여러 개
→ 중간 테이블(enrollments)로 표현
```

DB 제약 조건은 서버 검증을 대신하는 것이 아니라 **마지막 안전장치**입니다. 예를 들어 이메일 중복을 서비스 코드에서도 검사하더라도 DB의 `UNIQUE` 제약을 함께 두는 것이 안전합니다.

# 8. SQL 기본

```
SELECT id, title FROM courses WHERE price = 0;

INSERT INTO courses (title, price) VALUES ('React 입문', 0);

UPDATE courses SET price = 10000 WHERE id = 1;

DELETE FROM courses WHERE id = 1;

SELECT c.title, u.email
FROM enrollments e
JOIN courses c ON e.course_id = c.id
JOIN users u ON e.user_id = u.id
WHERE u.id = 3;
```

### 기본 상식

* `WHERE` 없는 `UPDATE`/`DELETE`는 전체 테이블에 적용되므로 실행 전 반드시 확인

* 사용자 입력을 SQL 문자열에 직접 이어붙이지 않기 (SQL Injection 위험 → 파라미터 바인딩 사용)

* 자주 조회하는 컬럼에는 인덱스를 고려

* 실행 전 개발 DB에서 먼저 확인

---

# 9. ORM

ORM(Object-Relational Mapping)은 SQL을 직접 쓰지 않고 객체·함수로 데이터베이스를 다루게 해주는 도구입니다. (예: SQLAlchemy, Sequelize, Prisma, JPA/Hibernate)

```
# 예시 (Python, 개념 설명용 의사코드)
course = Course.query.filter_by(id=1).first()
course.price = 10000
db.session.commit()
```

### 기본 상식

* ORM도 결국 SQL로 변환되므로, 어떤 쿼리가 만들어지는지 가끔 확인하는 습관이 필요

* 관계(1:N, N:M)를 모델에 정확히 정의해야 조회가 예상대로 동작함

* 성능 문제(N+1 쿼리 등)는 ORM을 쓰더라도 발생할 수 있음

---


## 9.1 마이그레이션 — 모델을 바꾸는 것과 DB를 바꾸는 것은 다르다

ORM 모델에 컬럼을 추가했다고 실제 운영 DB의 테이블이 자동으로 안전하게 바뀌는 것은 아닙니다.

```text
코드 모델 변경
→ 마이그레이션 파일 생성
→ 변경 SQL 확인
→ 개발/테스트 DB에 적용
→ 운영 배포 시 같은 마이그레이션 적용
```

마이그레이션 도구 예:

- Flask/SQLAlchemy: Alembic, Flask-Migrate
- Django: Django migrations
- Prisma: Prisma Migrate
- Spring/JPA 프로젝트: Flyway, Liquibase 등을 함께 사용 가능

팀 프로젝트에서는 **DB 스키마를 수동으로만 바꾸지 말고 마이그레이션 파일을 Git으로 공유**합니다.

주의:

- 데이터가 이미 있는 컬럼에 `NOT NULL`을 추가할 때 기본값·데이터 이행 필요
- 컬럼 삭제·타입 변경은 데이터 손실 가능
- 운영 적용 전 백업·롤백 계획 확인

# 10. 트랜잭션

여러 작업을 하나의 단위로 묶어, 전부 성공하거나 전부 취소되게 만드는 것입니다.

```
예: 수강 신청
1. 결제 정보 저장
2. 수강 목록에 추가
3. 강의 인원수 갱신

셋 중 하나라도 실패하면 전부 되돌립니다.
```

### 기본 상식

* 서로 연결된 여러 DB 작업은 트랜잭션으로 묶는다

* 트랜잭션 범위를 너무 넓게 잡으면 성능이 떨어질 수 있다

* 실패 시 반드시 롤백되는지 테스트로 확인한다

# 11. 요청값 검증

클라이언트가 보낸 값은 항상 다시 검증합니다.

검증 예시:

* 필수값 존재 여부

* 자료형 (문자열/숫자/불리언)

* 이메일·전화번호 형식

* 문자열 길이·숫자 범위

* 허용된 값 목록(enum)인지

* 중복 여부 (이메일 중복 가입 등)

### 기본 상식

* 프론트엔드 검증을 믿지 않고 서버에서 다시 확인

* 검증 실패 시 어떤 필드가 왜 잘못됐는지 명확히 응답

* 검증 로직은 여러 라우트에서 재사용할 수 있게 분리

---

# 12. 인증과 인가

```
인증(Authentication)
= 누구인지 확인 (로그인)

인가(Authorization)
= 무엇을 할 수 있는지 확인 (권한)
```

## 12.1 인증 방식

* **세션 기반**: 서버가 로그인 상태를 세션 저장소에 보관, 클라이언트는 세션 ID(쿠키)만 가짐

* **토큰 기반(JWT 등)**: 로그인 시 토큰을 발급, 이후 요청마다 토큰을 헤더에 담아 검증

```
Authorization: Bearer <token>
```

## 12.2 인가 예시

```
일반 사용자
→ 자신의 정보만 조회·수정 가능

강사
→ 자신이 등록한 강의만 수정·삭제 가능

관리자
→ 전체 강의·사용자 관리 가능
```

### 기본 상식

* 인증과 인가는 항상 서버에서 최종 확인 (프론트 화면 숨김만으로 보안 불가)

* 토큰 만료·재발급 정책을 정해둔다

* 다른 사용자의 데이터에 접근하는 요청인지 소유자 확인 로직을 반드시 둔다 (예: 남의 수강 정보 조회 방지)

---


## 12.3 Access Token, Refresh Token, Cookie

토큰 기반 인증에서도 모든 토큰의 역할이 같은 것은 아닙니다.

```text
Access Token
→ API 요청에 사용
→ 비교적 짧은 만료시간

Refresh Token
→ 새 Access Token을 발급받는 데 사용
→ 더 오래 유지되므로 더 조심해서 보관
```

프로젝트에 따라 한 종류의 토큰만 쓸 수도 있고, 세션 기반 인증을 쓸 수도 있습니다. **무조건 JWT 두 개를 써야 하는 것은 아닙니다.**

쿠키로 인증 정보를 전달한다면 다음 옵션을 이해합니다.

| 옵션 | 의미 |
| --- | --- |
| `HttpOnly` | 브라우저 JavaScript에서 쿠키를 읽지 못하게 함 |
| `Secure` | HTTPS 연결에서만 전송 |
| `SameSite` | 다른 사이트에서 시작된 요청에 쿠키를 어느 범위까지 보낼지 제한 |

### CSRF

브라우저가 인증 쿠키를 자동으로 전송하는 구조에서는 공격 사이트가 사용자를 대신해 요청을 보내는 **CSRF(Cross-Site Request Forgery)**를 고려해야 합니다.

대응은 구조에 따라 다음을 조합합니다.

- 적절한 `SameSite` 설정
- CSRF Token
- Origin/Referer 검증
- 중요한 요청의 재인증·사용자 확인

인증 설계는 “토큰을 발급했다”에서 끝나지 않고 **저장 위치·만료·재발급·로그아웃·탈취 시 대응**까지 포함합니다.

# 13. 비밀번호와 보안 기본

* 비밀번호는 평문으로 저장하지 않고 해싱(bcrypt, argon2 등)해서 저장

* 같은 비밀번호라도 매번 다른 해시값이 나오도록 salt 적용 (대부분의 해싱 라이브러리가 자동 처리)

* 클라이언트가 보낸 값을 그대로 SQL·명령어에 사용하지 않기 (SQL Injection, Command Injection 방지)

* 사용자 입력을 화면에 그대로 렌더링하는 경우 XSS 위험 고려 (주로 프론트 책임이지만 API 응답 값도 이스케이프 정책 확인)

* 민감한 값(비밀번호 해시, 내부 토큰 등)은 응답 JSON에 포함하지 않기

* 요청 빈도가 비정상적으로 많은 IP·계정에 대한 제한(rate limiting) 고려

# 14. 환경변수와 설정 관리

환경에 따라 달라지는 값을 코드와 분리합니다.

```
DATABASE_URL=mysql://user:pass@localhost:3306/db
SECRET_KEY=...
AI_API_KEY=...
PORT=5000
```

### 기본 상식

* `.env`는 GitHub에 올리지 않고 `.gitignore`에 포함

* `.env.example`에는 변수 이름만 공유 (실제 값 제외)

* 개발/테스트/운영 환경변수를 분리해서 관리

* 코드에 비밀값을 직접 작성하지 않기

### 실제로 해보기

1. 프로젝트 루트에 `.env` 파일을 만들고 위 예시처럼 `키=값`을 한 줄씩 적습니다. (따옴표 없이, `=` 앞뒤에 공백 없이)

2. Python(Flask)이라면 `python-dotenv` 같은 라이브러리로 파일을 읽어옵니다.

   ```
   from dotenv import load_dotenv
   import os

   load_dotenv()                       # .env 파일을 읽어서 환경변수로 등록
   db_url = os.environ["DATABASE_URL"] # 코드에서는 이렇게 값을 꺼내 씀
   ```

3. 코드 어디에도 실제 비밀번호나 키 문자열이 그대로 적혀 있지 않은지 확인합니다. `os.environ[...]`으로 “꺼내 쓰는” 코드만 있어야 정상입니다.

4. `.gitignore`에 `.env`가 포함되어 있는지 확인합니다. **이미 Git이 추적 중인 `.env`는 `.gitignore`에 추가해도 계속 추적**될 수 있으므로 `git ls-files .env`로 확인하고, 추적 중이면 `git rm --cached .env`로 Git 추적만 해제합니다.

5. 비밀키를 실수로 GitHub에 push했다면 파일만 지우고 끝내지 않습니다. **해당 키·토큰을 즉시 폐기(revoke)하고 새 값으로 교체**합니다. Git 이력에 값이 남았을 가능성도 별도로 처리해야 합니다.

# 15. 오류 처리

## 오류 처리 원칙

* 예상 가능한 오류(검증 실패, 인증 실패 등)는 명확한 상태 코드 + 메시지로 응답

* 예상하지 못한 오류(500)는 사용자에게 상세 내용을 노출하지 않고, 서버 로그에는 상세히 기록

* 오류를 무조건 무시(빈 `except`)하지 않기

* 오류 응답 형식을 프로젝트 전체에서 통일

```
# 개념 예시
try:
    course = get_course(course_id)
except CourseNotFound:
    return error_response(404, "COURSE_NOT_FOUND", "강의를 찾을 수 없습니다.")
except Exception:
    log.exception("unexpected error")
    return error_response(500, "INTERNAL_ERROR", "서버 오류가 발생했습니다.")
```

## 오래 걸리는 작업과 Background Job

이메일 발송, 대용량 파일 처리, 긴 AI 작업처럼 요청 하나에서 오래 걸리는 처리는 별도 작업 큐로 분리할 수 있습니다.

```text
사용자 요청
→ 서버가 작업 등록
→ 즉시 "접수됨" 응답
→ Worker가 백그라운드에서 처리
→ 상태 저장
→ 프론트가 상태 조회 또는 실시간 알림 수신
```

대표적인 개념:

- Queue: 기다리는 작업 목록
- Worker: 큐의 작업을 실제로 처리하는 프로세스
- Job ID: 사용자가 처리 상태를 조회할 수 있는 식별자

모든 프로젝트에 필요하지는 않습니다. 하지만 “API 하나가 30초 이상 붙잡혀 있다”면 비동기 작업 구조를 검토할 신호입니다.

# 20. 테스트

## 종류

* **단위 테스트**: 함수·서비스 로직 하나를 독립적으로 검증

* **통합 테스트**: 여러 컴포넌트(라우트 + DB 등)를 함께 검증

* **API 테스트**: 실제 요청/응답을 도구(Postman, pytest 등)로 확인

## 기본 상식

* 정상 케이스뿐 아니라 잘못된 입력, 권한 없는 요청, 존재하지 않는 데이터도 테스트

* 테스트 DB는 운영 DB와 분리

* 버그가 발생했던 부분은 회귀 테스트를 남기는 것이 좋음

## 운영 서버의 기본 구조

개발할 때 `python app.py`로 실행되는 것과 운영 서비스 구조는 다를 수 있습니다.

```text
사용자
↓ HTTPS
도메인 / DNS
↓
Reverse Proxy (예: Nginx, 클라우드 Load Balancer)
↓
애플리케이션 서버
↓
DB / Cache / 외부 API
```

### 알아둘 용어

- **Reverse Proxy**: 외부 요청을 받아 실제 앱 서버로 전달. HTTPS 종료, 라우팅, 정적 파일 처리 등에 사용
- **TLS/HTTPS**: 통신 내용을 암호화
- **Process Manager**: 서버 프로세스가 죽었을 때 재시작하거나 여러 프로세스를 관리
- **Health Check**: 서버가 살아 있고 요청을 처리할 수 있는지 확인하는 엔드포인트

예:

```http
GET /health
200 OK

{
  "status": "ok"
}
```

헬스체크에서 무거운 작업을 수행하지 않고, 필요에 따라 앱 자체 상태와 DB 같은 핵심 의존성 상태를 구분해 확인합니다.

### 배포 시 DB 마이그레이션

코드 배포와 DB 마이그레이션 순서가 맞지 않으면 새 코드가 없는 컬럼을 조회하거나, 구 코드가 삭제된 컬럼을 참조할 수 있습니다. 운영에서는 **하위 호환 가능한 변경 → 코드 배포 → 정리**처럼 순서를 설계해야 할 때도 있습니다.

# 32. 처음부터 한 번 만들어보기 — 백엔드 최소 실습

목표는 **서버 실행 → GET → POST → DB 저장 → 오류 응답**을 한 번 연결해보는 것입니다. 아래는 Python + Flask + SQLite 예시입니다.

## 1단계. 프로젝트와 가상환경

```bash
mkdir backend-practice
cd backend-practice

python -m venv .venv

# Windows PowerShell
.\.venv\Scripts\Activate.ps1

pip install flask
```

## 2단계. `app.py`

```python
from flask import Flask, request, jsonify
import sqlite3

app = Flask(__name__)

def get_db():
    conn = sqlite3.connect("app.db")
    conn.row_factory = sqlite3.Row
    return conn

@app.get("/courses")
def list_courses():
    conn = get_db()
    rows = conn.execute("SELECT id, title FROM courses ORDER BY id").fetchall()
    conn.close()
    return jsonify([dict(row) for row in rows])

@app.post("/courses")
def create_course():
    body = request.get_json(silent=True) or {}
    title = body.get("title", "").strip()

    if not title:
        return jsonify({
            "error": {
                "code": "INVALID_TITLE",
                "message": "title은 필수입니다."
            }
        }), 400

    conn = get_db()
    cursor = conn.execute("INSERT INTO courses(title) VALUES (?)", (title,))
    conn.commit()
    course_id = cursor.lastrowid
    conn.close()

    return jsonify({"id": course_id, "title": title}), 201

if __name__ == "__main__":
    conn = get_db()
    conn.execute(
        "CREATE TABLE IF NOT EXISTS courses("
        "id INTEGER PRIMARY KEY AUTOINCREMENT, "
        "title TEXT NOT NULL)"
    )
    conn.commit()
    conn.close()

    app.run(debug=True)
```

## 3단계. 실행

```bash
python app.py
```

브라우저 또는 API 도구에서 `GET http://127.0.0.1:5000/courses`를 호출합니다.
