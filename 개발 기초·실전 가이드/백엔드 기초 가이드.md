> **대상:** 백엔드를 처음 보는 사람
> **목적:** 프레임워크(Flask·Express·Spring·Django 등)가 달라도 공통으로 필요한 서버·API·DB·인증·에러 처리·배포의 핵심 흐름을 위에서 아래로 한 번에 이해하기
> **사용법:** 처음부터 끝까지 순서대로 읽고, 맨 뒤의 최소 실습으로 서버→DB→응답 흐름을 직접 손으로 확인합니다. 낯선 용어는 처음 등장하는 자리에서 괄호로 바로 설명합니다.

---

# 1. 백엔드란?

**서버(Server)**는 요청을 받아서 응답을 돌려주는 프로그램입니다. 백엔드 코드를 짠다는 것은 이 서버 프로그램을 만든다는 뜻입니다. 반대로 요청을 보내는 쪽(보통 브라우저나 앱)을 **클라이언트(Client)**라고 합니다. 식당에 비유하면 프론트엔드는 손님이 보는 홀, 백엔드는 주문을 받아 요리하는 주방, 데이터베이스는 주방이 재료를 꺼내 쓰는 냉장고입니다.

손님이 "재료 다 있다"고 말해도 주방은 냉장고를 직접 확인합니다. 마찬가지로 백엔드는 **클라이언트가 보낸 값을 그대로 믿지 않고 서버에서 다시 확인**합니다. 화면에서 입력을 막아뒀어도 요청 자체는 누구나 조작해서 보낼 수 있기 때문입니다.

백엔드가 하는 일: 요청을 받고 검증하기, 인증·권한 확인하기, 데이터베이스 접근하기, 처리 규칙(비즈니스 로직) 수행하기, 일관된 형식으로 응답하고 오류를 안전하게 처리하기.

---

# 2. 요청-응답 흐름

클라이언트와 서버는 **HTTP**(둘이 데이터를 주고받을 때 쓰는 공통 규격)로 대화합니다. 기본 흐름은 다음과 같습니다.

```
1. 클라이언트가 HTTP 요청을 보냄 (메서드 + URL + 헤더 + 바디)
2. 서버가 요청을 받아 해당 라우트를 찾음
3. 미들웨어(인증 확인, 로깅 등 공통 처리)를 거침
4. 요청값을 검증함
5. 실제 처리 로직이 실행됨
6. 필요하면 데이터베이스에 접근함
7. 결과를 JSON 등 응답 형식으로 가공함
8. 상태 코드와 함께 응답을 반환함
```

이 8단계를 한 번이라도 손으로 그려보면, 어떤 프레임워크를 쓰든 디버깅할 때 "지금 어느 단계에서 문제가 생겼는지"를 빠르게 짚을 수 있습니다.

# 3. 라우팅과 백엔드의 기본 구성 요소

**라우팅(Routing)**은 "이 URL + 이 메서드로 요청이 오면 이 코드를 실행해라"라고 미리 연결해두는 것입니다. 요청을 받는 구체적인 주소 하나하나를 **엔드포인트(Endpoint)**라고 부릅니다. 예: `GET /courses`.

작은 프로젝트라도 보통 아래 네 가지 역할로 코드를 나눕니다: **Route**(어떤 URL·메서드가 어떤 처리로 연결되는지 정의) → **Controller/Handler**(요청을 받아 검증하고 아래 로직 호출) → **Service**(실제 처리 규칙) → **Model/Entity**(DB 테이블 하나를 코드로 표현한 것).

## 실제 코드로 보면 이렇게 생겼습니다 (Flask 예시)

강의 하나를 조회하는 예시입니다. Route → Controller → Service → Model이 각각 어디에 해당하는지만 확인하면 됩니다.

```python
# models.py — Model: courses 테이블과 매핑되는 구조
class Course(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    title = db.Column(db.String(200))

# services/course_service.py — Service: 실제 처리 규칙
def get_course_or_raise(course_id):
    course = Course.query.get(course_id)
    if course is None:
        raise CourseNotFound()
    return course

# routes/course_routes.py — Route + Controller
@app.route("/courses/<int:course_id>", methods=["GET"])  # ← 라우팅
def get_course(course_id):                                # ← 컨트롤러
    try:
        course = get_course_or_raise(course_id)            # ← 서비스 호출
        return jsonify({"data": {"id": course.id, "title": course.title}}), 200
    except CourseNotFound:
        return jsonify({"error": {"code": "COURSE_NOT_FOUND", "message": "강의를 찾을 수 없습니다."}}), 404
```

Express(Node.js)나 Spring(Java)도 이름과 문법만 다를 뿐 이 네 가지 역할 구분은 동일합니다. 파일이 몇 개 안 되는 초기 단계에는 route와 controller를 합쳐도 괜찮지만, "검증+호출 부분"과 "실제 처리 규칙"은 섞지 않는 습관을 들이면 나중에 나누기 쉽습니다.

# 4. HTTP 메서드와 REST API 설계

| 메서드 | 의미 |
| --- | --- |
| `GET` | 데이터 조회 (부작용 없음) |
| `POST` | 데이터 생성 또는 작업 요청 |
| `PUT` | 리소스 전체 수정 |
| `PATCH` | 리소스 일부 수정 |
| `DELETE` | 삭제 |

**REST API**는 URL과 HTTP 메서드로 자원을 표현하는 설계 방식입니다.

```
GET    /courses          강의 목록 조회
GET    /courses/10       특정 강의 조회
POST   /courses          강의 생성
PATCH  /courses/10       강의 일부 수정
DELETE /courses/10       강의 삭제
```

기본 상식: URL은 명사로, 동작은 메서드로 표현하고(`/getCourses` ❌ → `GET /courses` ⭕), 복수형 명사를 일관되게 사용합니다. 계층 관계는 경로로(`/courses/10/reviews`), 검색·필터·정렬은 `?key=value` 형태의 **쿼리 파라미터**로 표현합니다(예: `/courses?category=web&sort=price`).

프론트엔드와 백엔드가 서로 다른 포트에서 개발 중이면 브라우저가 서로 다른 출처(origin)로 취급해 응답을 못 읽는 문제가 생길 수 있습니다. 서버가 "이 출처는 허용한다"고 알려주는 설정을 **CORS**라고 합니다. 개발 중 API 호출이 막히면 CORS 설정부터 의심해봅니다.

# 5. 요청과 응답 설계

요청은 크게 메서드+URL, 헤더(Content-Type, Authorization 등), 바디(보통 **JSON** — `{ "key": "value" }` 형태로 데이터를 표현하는 형식)로 구성됩니다.

응답 형식은 프로젝트 전체에서 통일합니다. 정상 응답은 `{ "data": { ... } }`, 오류 응답은 `{ "error": { "code": "COURSE_NOT_FOUND", "message": "..." } }` 형태입니다. 응답에는 스택 트레이스나 내부 쿼리문처럼 프론트가 필요로 하지 않는 정보를 담지 않습니다.

## 상태 코드

| 코드 | 의미 |
| --- | --- |
| `200` | 요청 성공 |
| `201` | 데이터 생성 성공 |
| `204` | 성공했지만 응답 본문 없음 |
| `400` | 요청값이 잘못됨 |
| `401` | 인증되지 않음 |
| `403` | 인증은 되었지만 권한 없음 |
| `404` | 주소 또는 데이터 없음 |
| `409` | 중복 또는 충돌 |
| `422` | 요청 형식은 맞지만 값 검증 실패 |
| `500` | 서버 내부 오류 |

상태 코드만 정확히 반환하고 끝내지 않고, 응답 본문에 원인을 알 수 있는 최소한의 정보를 함께 담습니다.

# 6. 데이터베이스 기초

**데이터베이스(DB)**는 데이터를 저장해두는 프로그램입니다. 관계형 데이터베이스는 데이터를 **테이블**(엑셀 시트처럼 행·열로 이루어진 저장 단위)에 저장하고, 테이블끼리 **관계**로 연결합니다.

```
users            courses           enrollments
──────           ───────           ───────────
id (PK)          id (PK)           id (PK)
email            title             user_id (FK)
password_hash    price             course_id (FK)
                                    enrolled_at
```

* **기본키(Primary Key, PK)**: 한 행을 유일하게 구분하는 값 (보통 `id`)
* **외래키(Foreign Key, FK)**: 다른 테이블의 기본키를 가리켜 두 테이블을 연결하는 값

위 예시에서 `enrollments`(수강 신청)는 `users`와 `courses` 각각의 PK를 FK로 참조해서, 사용자 여러 명과 강의 여러 개가 서로 연결되는 N:M(다대다) 관계를 표현합니다.

테이블을 만들 때는 컬럼뿐 아니라 어떤 값이 허용되는지도 정합니다(`NOT NULL`=값 필수, `UNIQUE`=중복 금지, `DEFAULT`=기본값). 이런 DB 제약은 서버 검증을 대신하는 게 아니라 **마지막 안전장치**입니다. 이메일 중복을 서비스 코드에서 검사하더라도 DB의 `UNIQUE` 제약을 함께 두는 것이 안전합니다.

## SQL 기본

**SQL**은 데이터베이스에 데이터를 넣고·읽고·바꾸고·지울 때 쓰는 언어입니다.

```sql
SELECT id, title FROM courses WHERE price = 0;
INSERT INTO courses (title, price) VALUES ('React 입문', 0);
UPDATE courses SET price = 10000 WHERE id = 1;
DELETE FROM courses WHERE id = 1;
```

기본 상식: `WHERE` 없는 `UPDATE`/`DELETE`는 테이블 전체에 적용되므로 실행 전 반드시 확인하고, 사용자 입력을 SQL 문자열에 직접 이어붙이지 않습니다(뒤에 나올 SQL Injection 위험).

## ORM

매번 SQL 문자열을 직접 쓰는 대신, 객체·함수로 데이터베이스를 다루게 해주는 도구를 **ORM**(Object-Relational Mapping, 예: SQLAlchemy·Sequelize·Prisma·JPA)이라고 합니다.

```python
course = Course.query.filter_by(id=1).first()
course.price = 10000
db.session.commit()
```

ORM도 결국 내부적으로는 SQL로 변환됩니다. 성능 튜닝(N+1 문제 등)은 **중급 가이드에서 다룹니다.**

ORM 모델에 컬럼을 추가한다고 실제 운영 DB가 자동으로 바뀌지는 않습니다. 이 변경 내역을 파일로 기록해 팀과 공유하는 방법을 **마이그레이션**이라고 합니다(도구 예: Alembic/Flask-Migrate, Django migrations). 팀 프로젝트에서는 DB 구조를 수동으로만 바꾸지 말고 마이그레이션 파일을 Git으로 공유합니다.

## 트랜잭션

여러 DB 작업을 하나의 단위로 묶어, 전부 성공하거나 전부 취소되게(롤백) 만드는 것을 **트랜잭션**이라고 합니다. 예를 들어 "결제 저장 → 수강 목록 추가 → 인원수 갱신" 중 하나라도 실패하면 전부 되돌립니다. 서로 연결된 여러 DB 작업은 트랜잭션으로 묶고, 실패 시 반드시 롤백되는지 테스트로 확인합니다.

# 7. 요청값 검증

클라이언트가 보낸 값은 항상 서버에서 다시 검증합니다. 확인할 것: 필수값 존재 여부, 자료형(문자열/숫자/불리언), 이메일·전화번호 형식, 길이·범위, 허용된 값 목록인지, 중복 여부(이메일 중복 가입 등).

검증 실패 시 어떤 필드가 왜 잘못됐는지 명확히 응답하고, 검증 로직은 여러 라우트에서 재사용할 수 있게 분리합니다.

# 8. 인증과 인가

```
인증(Authentication) = 누구인지 확인 (로그인)
인가(Authorization)  = 무엇을 할 수 있는지 확인 (권한)
```

인증 방식은 크게 두 가지입니다.

* **세션(Session) 기반**: 서버가 로그인 상태를 세션 저장소에 보관하고, 클라이언트는 세션 ID(쿠키)만 가집니다.
* **토큰 기반(JWT 등)**: 로그인 시 서버가 **토큰**(로그인 상태를 문자열 하나로 표현한 것)을 발급하고, 이후 요청마다 헤더에 담아 보냅니다.

```
Authorization: Bearer <token>
```

JWT는 `헤더.페이로드.서명` 문자열인데, 페이로드는 **암호화가 아니라 인코딩만 되어 있어 누구나 디코딩해 읽을 수 있습니다.** 그래서 비밀번호 같은 민감정보는 절대 넣지 않습니다. JWT가 세션보다 무조건 우월한 것은 아니며 각각 장단점이 다른 도구입니다. Refresh Token, CSRF 같은 심화 주제는 **중급 가이드에서 다룹니다.**

인가는 "일반 사용자는 자신의 정보만 조회 가능"처럼 역할별로 다르게 적용합니다. 인증과 인가는 항상 서버에서 최종 확인하며(프론트 화면 숨김만으로는 보안이 되지 않습니다), 다른 사용자의 데이터에 접근하는 요청인지 소유자 확인 로직을 반드시 둡니다(예: 남의 수강 정보 조회 방지).

# 9. 비밀번호·보안·환경변수

* 비밀번호는 평문으로 저장하지 않고 **해싱**(원문을 복원 불가능한 문자열로 바꾸는 것)해서 저장합니다. 반드시 비밀번호 저장 전용 알고리즘(Argon2id, bcrypt 등)을 씁니다 — MD5·SHA-256은 계산이 빨라 브루트포스 공격에 취약해 쓰지 않습니다.
* 사용자 입력을 SQL 문에 그대로 이어붙이면 공격자가 SQL을 조작하는 **SQL Injection**이 가능해집니다 — 파라미터 바인딩(예: `?`)을 사용합니다.
* 민감한 값(비밀번호 해시, 내부 토큰 등)은 응답 JSON에 절대 포함하지 않습니다.
* 비밀번호·API 키처럼 코드에 직접 쓰면 안 되는 값은 `.env` 같은 파일로 분리해 코드에서 불러옵니다.

```python
from dotenv import load_dotenv
import os

load_dotenv()                       # .env 파일을 읽어서 환경변수로 등록
db_url = os.environ["DATABASE_URL"] # 코드에서는 이렇게 꺼내 씀
```

`.env`는 `.gitignore`에 포함해 GitHub에 올리지 않고, `.env.example`에는 값 없이 변수 이름만 공유합니다. 비밀키를 실수로 push했다면 파일만 지우지 말고 **해당 키를 즉시 폐기(revoke)하고 새 값으로 교체**합니다.

# 10. 오류 처리와 로그

예상 가능한 오류(검증 실패, 인증 실패 등)는 명확한 상태 코드+메시지로 응답합니다. 예상치 못한 오류(500)는 사용자에게 상세 내용을 노출하지 않되, 서버 로그에는 상세히 기록합니다. 오류를 빈 `except`로 무시하지 않습니다.

```python
try:
    course = get_course(course_id)
except CourseNotFound:
    return error_response(404, "COURSE_NOT_FOUND", "강의를 찾을 수 없습니다.")
except Exception:
    log.exception("unexpected error")
    return error_response(500, "INTERNAL_ERROR", "서버 오류가 발생했습니다.")
```

**로그**는 문제 원인을 되짚기 위한 기록입니다. 요청 URL·오류 스택 트레이스는 남기고, 비밀번호·토큰 원문 같은 민감정보는 절대 남기지 않습니다.

요청 전후에 인증 확인·로깅처럼 공통으로 실행되는 코드를 **미들웨어**라고 합니다(`요청 → [로깅] → [CORS] → [인증 확인] → 라우트 처리 → 응답`). 반복되는 로직은 매 라우트마다 넣지 않고 미들웨어로 분리합니다.

---

# 11. 테스트

* **단위 테스트**: 함수·서비스 로직 하나를 독립적으로 검증
* **통합 테스트**: 라우트+DB처럼 여러 요소를 함께 검증
* **API 테스트**: 실제 요청/응답을 Postman, pytest 등으로 확인

정상 케이스뿐 아니라 잘못된 입력, 권한 없는 요청, 존재하지 않는 데이터도 테스트하고, 테스트 DB는 운영 DB와 분리합니다.

---

# 12. 배포 기초

```
개발 실행 = 내 컴퓨터에서 확인
빌드      = 배포 가능한 형태로 준비
배포      = 다른 사용자가 접속 가능한 서버에 올림
```

운영 서버는 개발 중 `python app.py`로 실행하는 것과 구조가 다를 수 있습니다. 서버가 정상 동작 중인지 확인하는 전용 엔드포인트를 **Health Check**라고 부릅니다(예: `GET /health` → `200 OK`).

배포 전 확인할 것: 운영용 환경변수, 운영 DB 연결, CORS 허용 도메인, 마이그레이션 적용 여부, 비밀값 노출 여부. Reverse Proxy, Process Manager, 컨테이너(Docker) 같은 배포 인프라 구조와 배포 전략은 **중급 가이드에서 다룹니다.**

# 13. 그 외 알아두면 좋은 것 (나중에 배우기)

캐싱, 페이지네이션(데이터를 나눠서 주는 것 — 첫 프로젝트에서도 최소한은 적용 권장), Background Job(오래 걸리는 처리를 분리하는 작업 큐), 외부 API 연동(타임아웃·재시도, API 키는 백엔드 환경변수로만 관리)은 이름과 개념만 기억해두고 필요할 때 찾아봅니다. **중급 가이드에서 다룹니다.**

# 14. 최종 핵심 원칙

```
클라이언트가 보낸 값은 항상 다시 검증한다.

```

# 15. 직접 실습해보기 — 백엔드 최소 실습

목표는 **서버 실행 → GET → POST → DB 저장 → 오류 응답**을 한 번 연결해보는 것입니다. Python + Flask + SQLite 예시입니다.

## 1단계. 프로젝트와 가상환경

가상환경(`.venv`)은 이 프로젝트만을 위한 Python 패키지 설치 공간입니다. 켜지 않으면 "설치했는데 Flask가 없다"는 상황이 생길 수 있습니다.

```bash
mkdir backend-practice
cd backend-practice

python -m venv .venv

# Windows PowerShell
.\.venv\Scripts\Activate.ps1

pip install flask
```

## 2단계. `app.py`

```python
from flask import Flask, request, jsonify
import sqlite3

app = Flask(__name__)

def get_db():
    conn = sqlite3.connect("app.db")
    conn.row_factory = sqlite3.Row
    return conn

@app.get("/courses")
def list_courses():
    conn = get_db()
    rows = conn.execute("SELECT id, title FROM courses ORDER BY id").fetchall()
    conn.close()
    return jsonify([dict(row) for row in rows])

@app.post("/courses")
def create_course():
    body = request.get_json(silent=True) or {}
    title = body.get("title", "").strip()

    if not title:
        return jsonify({
            "error": {
                "code": "INVALID_TITLE",
                "message": "title은 필수입니다."
            }
        }), 400

    conn = get_db()
    cursor = conn.execute("INSERT INTO courses(title) VALUES (?)", (title,))
    conn.commit()
    course_id = cursor.lastrowid
    conn.close()

    return jsonify({"id": course_id, "title": title}), 201

if __name__ == "__main__":
    conn = get_db()
    conn.execute(
        "CREATE TABLE IF NOT EXISTS courses("
        "id INTEGER PRIMARY KEY AUTOINCREMENT, "
        "title TEXT NOT NULL)"
    )
    conn.commit()
    conn.close()

    app.run(debug=True)
```

## 3단계. 실행하고 확인

`python app.py`로 실행한 뒤 브라우저 또는 API 도구에서 `GET http://127.0.0.1:5000/courses`를 호출합니다. 이어서 아래처럼 `POST /courses`를 보내봅니다.

```http
POST /courses
Content-Type: application/json

{
  "title": "백엔드 입문"
}
```

확인할 것: 요청 JSON을 어디서 읽는지, 서버 검증은 어디서 하는지, `?` 파라미터 바인딩을 왜 쓰는지, `201`과 `400`은 언제 반환되는지, DB 파일에 데이터가 실제로 저장되는지.

## 4단계. 다음 단계

이 최소 코드를 이해한 뒤 `한 파일 → Route/Service 분리 → ORM → 마이그레이션 → 인증/인가 → 테스트 → 운영 배포` 순서로 확장합니다. 처음부터 모든 구조를 넣기보다 **동작하는 작은 서버를 먼저 만든 뒤 왜 분리가 필요한지 경험하는 것**이 좋습니다.
