0. 시작 전에 — 자주 나오는 용어#

개발이 처음이라면 본문을 읽기 전에 아래 표부터 훑어보세요. 본문 중간에 낯선 단어가 나오면 다시 여기로 돌아와 찾아봐도 됩니다.

0.1 컴퓨터·개발 환경#

용어쉬운 설명
터미널(Terminal) / 커맨드라인(CLI)마우스 클릭 대신 글자로 명령을 입력해 컴퓨터를 조작하는 화면. VS Code에서는 상단 메뉴 Terminal → New Terminal로 엽니다.
프로세스(Process)실행 중인 프로그램 하나. 서버를 켜면 “서버 프로세스가 떠 있다”고 표현합니다.
포트(Port)한 컴퓨터 안에서 여러 프로그램이 동시에 통신할 수 있도록 구분하는 번호(0~65535). 예: http://localhost:5000에서 5000이 포트 번호입니다.
로컬(local) / localhost지금 쓰고 있는 이 컴퓨터 자신을 가리키는 주소(127.0.0.1). “로컬에서 돌린다” = 내 컴퓨터에서만 실행한다는 뜻.
패키지 매니저다른 사람이 만든 코드(라이브러리)를 설치·관리해주는 도구. Python은 pip, Node.js는 npm.
프레임워크특정 종류의 프로그램(웹 서버 등)을 쉽게 만들도록 미리 짜여진 뼈대. 예: Flask, Express, Spring, Django.

0.2 서버·통신#

용어쉬운 설명
서버(Server)요청을 받아서 응답을 돌려주는 프로그램. 백엔드 코드를 짠다 = 서버 프로그램을 만든다는 뜻.
클라이언트(Client)서버에 요청을 보내는 쪽. 보통 브라우저(프론트엔드)나 모바일 앱.
HTTP클라이언트와 서버가 데이터를 주고받을 때 쓰는 공통 약속(규격).
요청(Request) / 응답(Response)클라이언트가 서버에 보내는 것 = 요청, 서버가 돌려주는 것 = 응답.
엔드포인트(Endpoint)요청을 받는 구체적인 주소 하나. 예: GET /courses.
라우팅(Routing) / 라우트(Route)“이 URL + 이 메서드로 요청이 오면 이 코드를 실행해라”라고 연결해두는 것.
API프로그램끼리 데이터를 주고받기 위해 미리 정해둔 규칙(창구). “강의 목록 API” = 강의 목록을 요청/응답하는 약속.
REST / REST APIURL과 HTTP 메서드로 자원을 표현하는 API 설계 방식(4장에서 자세히 다룸).
JSON{ "key": "value" } 형태로 데이터를 표현하는 형식. 요청·응답 바디에 가장 흔히 씀.
Query ParameterURL 뒤에 ?key=value 형태로 붙는 값. 예: /courses?category=web.
CORS브라우저의 Same-Origin Policy 때문에 다른 출처(origin)의 프론트가 API 응답을 읽으려 할 때, 서버가 어떤 출처·메서드·헤더를 허용할지 응답 헤더로 알려주는 방식. 개발 환경에서 프론트와 백엔드의 포트가 다르면 서로 다른 origin이 될 수 있습니다.

0.3 코드 구조#

용어쉬운 설명
컨트롤러(Controller) / 핸들러(Handler)요청이 들어왔을 때 가장 먼저 받는 코드. “이 요청 값이 올바른지 확인하고 서비스를 불러라” 역할.
서비스(Service)실제 비즈니스 규칙(수강 가능 여부 판단 등)을 처리하는 코드.
모델(Model) / 엔티티(Entity)데이터베이스 테이블 하나를 코드로 표현한 것.
미들웨어(Middleware)모든 요청 앞뒤에 공통으로 끼어들어 실행되는 코드(인증 확인, 로깅 등).

0.4 데이터베이스#

용어쉬운 설명
데이터베이스(DB)데이터를 저장해두는 프로그램/공간.
테이블(Table)엑셀 시트 하나와 비슷. 행(row)과 열(column)로 데이터를 저장.
기본키(Primary Key, PK)한 행을 유일하게 구분하는 값(보통 id).
외래키(Foreign Key, FK)다른 테이블의 기본키를 가리켜서 두 테이블을 연결하는 값.
SQL데이터베이스에 데이터를 넣고·읽고·바꾸고·지울 때 쓰는 언어.
ORMSQL을 직접 안 쓰고 코드(객체)로 데이터베이스를 다루게 해주는 도구.
트랜잭션(Transaction)여러 작업을 하나로 묶어서 전부 성공 또는 전부 취소되게 하는 것.
롤백(Rollback)트랜잭션 중 하나라도 실패하면 지금까지 한 작업을 없던 일로 되돌리는 것.
마이그레이션(Migration)데이터베이스 테이블 구조 변경 내역을 파일로 기록해서 팀과 공유하는 방법.
인덱스(Index)책의 “찾아보기”처럼 특정 컬럼 검색을 빠르게 해주는 장치.

0.5 인증·보안#

용어쉬운 설명
인증(Authentication)“너 누구야?”를 확인하는 것(로그인).
인가(Authorization)“너 이거 해도 돼?”를 확인하는 것(권한).
세션(Session)로그인 상태를 서버가 기억해두는 방식.
토큰(Token) / JWT로그인 상태를 문자열 하나로 표현해서 클라이언트가 들고 다니는 방식.
해싱(Hashing)비밀번호 원문을 복원 불가능한 다른 문자열로 바꿔 저장하는 방법.
SQL Injection사용자 입력을 SQL 문에 그대로 이어붙여서 공격자가 DB를 조작하게 되는 취약점.
환경변수(Environment Variable)비밀번호·API 키처럼 코드에 직접 쓰면 안 되는 값을, 코드 밖 별도 파일(.env)에 두고 실행할 때 불러오는 방법.

0.6 개발·배포#

용어쉬운 설명
로그(Log)서버가 무슨 일을 했는지 남기는 기록. 문제가 생겼을 때 원인을 찾는 단서.
캐싱(Caching)자주 쓰는 결과를 미리 저장해뒀다가 재사용해서 속도를 높이는 것.
페이지네이션(Pagination)데이터를 한 번에 다 주지 않고 “1페이지, 2페이지”로 나눠서 주는 것.
빌드(Build)소스 코드를 실제 서버에서 실행 가능한 형태로 준비하는 과정.
배포(Deploy)빌드 결과를 다른 사람이 접속할 수 있는 서버에 올리는 것.

0.7 개발 환경·의존성 관리#

백엔드는 “코드만 받으면 바로 실행되는 것”이 아닙니다. 언어 버전 + 의존성 + 환경변수 + DB가 맞아야 실행됩니다.

Python 프로젝트 예시#

항목역할
.venv/프로젝트별 Python 패키지를 격리하는 가상환경
requirements.txt설치할 Python 패키지 목록을 기록하는 전통적인 방식
pyproject.toml최근 Python 도구에서 프로젝트·의존성 설정에 많이 사용하는 표준 파일
pipPython 패키지 설치 도구
bash
python --version
python -m venv .venv

# Windows PowerShell
.\.venv\Scripts\Activate.ps1

# macOS/Linux
source .venv/bin/activate

pip install -r requirements.txt

가상환경을 켜지 않으면 “설치했는데 Flask가 없다고 나오는” 상황이 생길 수 있습니다. 터미널 앞에 (.venv) 같은 표시가 있는지, python과 pip가 같은 환경을 가리키는지 확인합니다.

Node.js 백엔드 예시#

  • package.json: 의존성·실행 스크립트
  • node_modules/: 설치된 패키지
  • npm install: 의존성 설치
  • npm run dev / npm start: 프로젝트가 정한 실행 스크립트

Java/Spring 예시#

  • build.gradle / build.gradle.kts: Gradle 설정
  • pom.xml: Maven 설정
  • gradlew / gradlew.bat: 팀 전체가 같은 Gradle 버전을 쓰게 해주는 Wrapper

새 프로젝트를 받으면 README와 의존성 파일을 먼저 읽고, 임의로 전역 설치부터 하지 않습니다.

1. 백엔드란?#

백엔드는 사용자에게 보이지 않는 곳에서 데이터를 검증·저장·가공하고, 프론트엔드가 요청한 결과를 응답으로 돌려주는 영역입니다.

  • 요청을 받고 검증하기
  • 인증과 권한을 확인하기
  • 데이터베이스에 접근하기
  • 비즈니스 로직을 처리하기
  • 외부 서비스(AI API, 결제, 이메일 등)와 연동하기
  • 일관된 형식으로 응답하기
  • 오류를 안전하게 처리하기
  • 여러 사용자의 동시 요청을 안정적으로 처리하기

일반적인 구조:

text
프론트엔드
↓ HTTP 요청
백엔드 (라우팅 → 검증 → 인증 → 로직 → DB)
↓
데이터베이스 / 외부 서비스
↓
백엔드가 결과를 가공
↓
프론트엔드에 JSON 응답

백엔드는 클라이언트가 보낸 값을 그대로 믿지 않습니다. 화면에서 막았어도 서버에서 다시 검증합니다.

비유로 이해하기#

식당에 비유하면 이해가 빠릅니다.

text
프론트엔드 = 홀(손님이 보는 메뉴판, 테이블)
백엔드     = 주방(주문을 받아 실제로 요리해서 내보내는 곳)
데이터베이스 = 냉장고·재고 창고(주방이 재료를 꺼내 쓰는 곳)

손님(사용자)은 홀(프론트엔드)에서 메뉴를 보고 주문하지만, 실제로 재료를 확인하고 요리하는 일은 주방(백엔드)에서 일어납니다. 손님이 “이 메뉴 재료 다 있어요”라고 말해도 주방은 냉장고를 직접 확인하고 요리합니다 — 이것이 “클라이언트가 보낸 값을 그대로 믿지 않는다”는 원칙과 같은 이야기입니다.

2. 요청-응답이 처리되는 기본 흐름#

text
1. 클라이언트가 HTTP 요청을 보냄 (메서드 + URL + 헤더 + 바디)
2. 서버가 요청을 받아 해당 라우트를 찾음
3. 미들웨어(인증, 로깅, CORS 등)를 거침
4. 컨트롤러/핸들러가 요청값을 검증함
5. 서비스 로직이 실행됨
6. 필요하면 데이터베이스에 접근함
7. 결과를 응답 형식(JSON 등)으로 가공함
8. 상태 코드와 함께 응답을 반환함

이 흐름을 한 번이라도 손으로 그려보면, 어떤 프레임워크를 쓰든 디버깅할 때 “지금 어느 단계에서 문제가 생겼는지”를 빠르게 짚을 수 있습니다.

3. 백엔드의 핵심 구성 요소#

text
Route (라우팅)
→ 어떤 URL·메서드가 어떤 처리로 연결되는지 정의

Controller / Handler
→ 요청을 받아 검증하고 서비스를 호출

Service / Business Logic
→ 실제 처리 규칙 (예: 수강 신청 가능 여부 판단)

Model / Entity
→ 데이터베이스 테이블과 매핑되는 구조

Repository / DAO (선택)
→ 데이터베이스 접근 코드를 분리

Middleware
→ 인증, 로깅, 오류 처리 등 요청 전후 공통 처리

작은 프로젝트는 Controller와 Service를 합쳐도 괜찮지만, 역할이 무엇인지는 항상 구분해서 생각합니다.

실제 코드로 보면 이렇게 생겼습니다 (Flask 예시)#

위 개념들이 실제 프레임워크에서는 어떤 모습인지, Flask로 강의 하나를 조회하는 예시를 통째로 보여드립니다. 처음 보면 낯설어도 괜찮습니다 — 지금은 “Route → Controller → Service → Model이 각각 어디에 해당하는지”만 눈으로 확인하면 됩니다.

text
# models.py — Model: courses 테이블과 매핑되는 구조
class Course(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    title = db.Column(db.String(200))
    price = db.Column(db.Integer)

# services/course_service.py — Service: 실제 처리 규칙
def get_course_or_raise(course_id):
    course = Course.query.get(course_id)
    if course is None:
        raise CourseNotFound()
    return course

# routes/course_routes.py — Route + Controller가 한 데코레이터 안에 있음
@app.route("/courses/<int:course_id>", methods=["GET"])  # ← 라우팅: 이 URL·메서드로 오면 아래 함수 실행
def get_course(course_id):                                # ← 컨트롤러: 요청을 받아 서비스를 호출
    try:
        course = get_course_or_raise(course_id)            # ← 서비스 호출
        return jsonify({"data": {"id": course.id, "title": course.title}}), 200
    except CourseNotFound:
        return jsonify({"error": {"code": "COURSE_NOT_FOUND", "message": "강의를 찾을 수 없습니다."}}), 404
  • @app.route(...) 한 줄이 라우팅입니다: GET /courses/10 요청이 오면 get_course 함수를 실행하라는 뜻.
  • get_course 함수 자체가 컨트롤러입니다: 요청을 받아 서비스를 부르고, 결과를 HTTP 응답(JSON + 상태 코드)으로 바꿔서 돌려줍니다.
  • get_course_or_raise가 서비스입니다: “존재하지 않으면 오류를 던진다”는 실제 규칙이 여기 있습니다.
  • Course 클래스가 모델입니다: courses 테이블의 각 컬럼(id, title, price)을 파이썬 속성으로 표현합니다.

Express(Node.js)나 Spring(Java)도 이름과 문법만 다를 뿐 이 네 가지 역할 구분은 동일합니다.

4.3 CORS와 API 문서화#

CORS를 정확히 이해하기#

CORS는 “서버끼리 통신을 막는 기능”이 아니라 주로 브라우저가 다른 origin의 응답을 읽는 것을 제어하는 정책과 연결됩니다.

text
http://localhost:5173
http://localhost:5000

프로토콜·호스트·포트 중 하나라도 다르면 다른 origin입니다.

서버에서 점검할 것:

  • 허용할 프론트엔드 origin
  • 허용 HTTP 메서드
  • 허용 요청 헤더
  • 쿠키/자격 증명을 허용할지
  • 운영 환경에서 *로 과도하게 열지 않았는지

OpenAPI / Swagger#

API가 많아질수록 문서와 실제 코드가 어긋나기 쉽습니다. OpenAPI는 API의 주소·메서드·요청·응답 스키마를 기계가 읽을 수 있게 정의하는 규격이고, Swagger UI 같은 도구로 사람이 테스트 가능한 문서를 만들 수 있습니다.

최소한 다음 정보는 API 문서에 있어야 합니다.

text
메서드 + URL
인증 필요 여부
Path/Query Parameter
Request Body
성공 Response
오류 Response
상태 코드

프론트와 백엔드가 협업할 때는 “코드가 아니라 API 명세가 계약”이라는 원칙을 유지합니다.

7. 데이터베이스 기초#

7.1 관계형 데이터베이스#

테이블(행·열)로 데이터를 저장하고, 관계(외래키)로 테이블끼리 연결합니다.

text
users            courses           enrollments
──────           ───────           ───────────
id (PK)          id (PK)           id (PK)
email            title             user_id (FK)
password_hash    price             course_id (FK)
                                    enrolled_at

7.2 기본키와 외래키#

text
기본키(Primary Key)
= 한 행을 유일하게 식별하는 값

외래키(Foreign Key)
= 다른 테이블의 기본키를 참조하는 값

7.3 ERD를 먼저 그리는 이유#

  • 테이블 간 관계를 미리 파악해 나중에 구조를 뒤엎는 일을 줄임
  • 프론트엔드와 데이터 구조를 논의할 때 공통 언어가 됨
  • 어떤 데이터가 어디서 필요한지 명확해짐
💡 핵심 개념

기본 상식#

  • 하나의 값은 한 곳에만 저장 (중복 저장은 나중에 불일치를 만듦)
  • 삭제된 데이터가 필요한 경우 소프트 삭제(상태 컬럼)를 고려
  • 컬럼명은 팀 전체가 합의한 규칙(snake\_case/camelCase 등)을 통일해서 사용

7.4 관계와 제약 조건#

관계형 DB에서는 “컬럼이 존재한다”보다 어떤 값이 허용되는지까지 설계해야 합니다.

기본 제약 조건#

제약의미예
PRIMARY KEY행을 유일하게 식별users.id
FOREIGN KEY다른 테이블의 행을 참조enrollments.user_id
NOT NULL값이 반드시 있어야 함users.email
UNIQUE중복 금지이메일
DEFAULT값을 안 넣었을 때 기본값status='ACTIVE'
CHECK허용 범위 검증price >= 0

관계 종류#

text
1:1
사용자 1명 ↔ 프로필 1개

1:N
강사 1명 → 강의 여러 개

N:M
사용자 여러 명 ↔ 강의 여러 개
→ 중간 테이블(enrollments)로 표현

DB 제약 조건은 서버 검증을 대신하는 것이 아니라 마지막 안전장치입니다. 예를 들어 이메일 중복을 서비스 코드에서도 검사하더라도 DB의 UNIQUE 제약을 함께 두는 것이 안전합니다.

8. SQL 기본#

text
SELECT id, title FROM courses WHERE price = 0;

INSERT INTO courses (title, price) VALUES ('React 입문', 0);

UPDATE courses SET price = 10000 WHERE id = 1;

DELETE FROM courses WHERE id = 1;

SELECT c.title, u.email
FROM enrollments e
JOIN courses c ON e.course_id = c.id
JOIN users u ON e.user_id = u.id
WHERE u.id = 3;
💡 핵심 개념

기본 상식#

  • WHERE 없는 UPDATE/DELETE는 전체 테이블에 적용되므로 실행 전 반드시 확인
  • 사용자 입력을 SQL 문자열에 직접 이어붙이지 않기 (SQL Injection 위험 → 파라미터 바인딩 사용)
  • 자주 조회하는 컬럼에는 인덱스를 고려
  • 실행 전 개발 DB에서 먼저 확인

9. ORM#

ORM(Object-Relational Mapping)은 SQL을 직접 쓰지 않고 객체·함수로 데이터베이스를 다루게 해주는 도구입니다. (예: SQLAlchemy, Sequelize, Prisma, JPA/Hibernate)

text
# 예시 (Python, 개념 설명용 의사코드)
course = Course.query.filter_by(id=1).first()
course.price = 10000
db.session.commit()
💡 핵심 개념

기본 상식#

  • ORM도 결국 SQL로 변환되므로, 어떤 쿼리가 만들어지는지 가끔 확인하는 습관이 필요
  • 관계(1:N, N:M)를 모델에 정확히 정의해야 조회가 예상대로 동작함
  • 성능 문제(N+1 쿼리 등)는 ORM을 쓰더라도 발생할 수 있음

9.1 마이그레이션 — 모델을 바꾸는 것과 DB를 바꾸는 것은 다르다#

ORM 모델에 컬럼을 추가했다고 실제 운영 DB의 테이블이 자동으로 안전하게 바뀌는 것은 아닙니다.

text
코드 모델 변경
→ 마이그레이션 파일 생성
→ 변경 SQL 확인
→ 개발/테스트 DB에 적용
→ 운영 배포 시 같은 마이그레이션 적용

마이그레이션 도구 예:

  • Flask/SQLAlchemy: Alembic, Flask-Migrate
  • Django: Django migrations
  • Prisma: Prisma Migrate
  • Spring/JPA 프로젝트: Flyway, Liquibase 등을 함께 사용 가능

팀 프로젝트에서는 DB 스키마를 수동으로만 바꾸지 말고 마이그레이션 파일을 Git으로 공유합니다.

주의:

  • 데이터가 이미 있는 컬럼에 NOT NULL을 추가할 때 기본값·데이터 이행 필요
  • 컬럼 삭제·타입 변경은 데이터 손실 가능
  • 운영 적용 전 백업·롤백 계획 확인

10. 트랜잭션#

여러 작업을 하나의 단위로 묶어, 전부 성공하거나 전부 취소되게 만드는 것입니다.

text
예: 수강 신청
1. 결제 정보 저장
2. 수강 목록에 추가
3. 강의 인원수 갱신

셋 중 하나라도 실패하면 전부 되돌립니다.
💡 핵심 개념

기본 상식#

  • 서로 연결된 여러 DB 작업은 트랜잭션으로 묶는다
  • 트랜잭션 범위를 너무 넓게 잡으면 성능이 떨어질 수 있다
  • 실패 시 반드시 롤백되는지 테스트로 확인한다

11. 요청값 검증#

클라이언트가 보낸 값은 항상 다시 검증합니다.

검증 예시:

  • 필수값 존재 여부
  • 자료형 (문자열/숫자/불리언)
  • 이메일·전화번호 형식
  • 문자열 길이·숫자 범위
  • 허용된 값 목록(enum)인지
  • 중복 여부 (이메일 중복 가입 등)
💡 핵심 개념

기본 상식#

  • 프론트엔드 검증을 믿지 않고 서버에서 다시 확인
  • 검증 실패 시 어떤 필드가 왜 잘못됐는지 명확히 응답
  • 검증 로직은 여러 라우트에서 재사용할 수 있게 분리

12. 인증과 인가#

text
인증(Authentication)
= 누구인지 확인 (로그인)

인가(Authorization)
= 무엇을 할 수 있는지 확인 (권한)

12.1 인증 방식#

  • 세션 기반: 서버가 로그인 상태를 세션 저장소에 보관, 클라이언트는 세션 ID(쿠키)만 가짐
  • 토큰 기반(JWT 등): 로그인 시 토큰을 발급, 이후 요청마다 토큰을 헤더에 담아 검증
text
Authorization: Bearer <token>

12.2 인가 예시#

text
일반 사용자
→ 자신의 정보만 조회·수정 가능

강사
→ 자신이 등록한 강의만 수정·삭제 가능

관리자
→ 전체 강의·사용자 관리 가능
💡 핵심 개념

기본 상식#

  • 인증과 인가는 항상 서버에서 최종 확인 (프론트 화면 숨김만으로 보안 불가)
  • 토큰 만료·재발급 정책을 정해둔다
  • 다른 사용자의 데이터에 접근하는 요청인지 소유자 확인 로직을 반드시 둔다 (예: 남의 수강 정보 조회 방지)

12.3 Access Token, Refresh Token, Cookie#

토큰 기반 인증에서도 모든 토큰의 역할이 같은 것은 아닙니다.

text
Access Token
→ API 요청에 사용
→ 비교적 짧은 만료시간

Refresh Token
→ 새 Access Token을 발급받는 데 사용
→ 더 오래 유지되므로 더 조심해서 보관

프로젝트에 따라 한 종류의 토큰만 쓸 수도 있고, 세션 기반 인증을 쓸 수도 있습니다. 무조건 JWT 두 개를 써야 하는 것은 아닙니다.

쿠키로 인증 정보를 전달한다면 다음 옵션을 이해합니다.

옵션의미
HttpOnly브라우저 JavaScript에서 쿠키를 읽지 못하게 함
SecureHTTPS 연결에서만 전송
SameSite다른 사이트에서 시작된 요청에 쿠키를 어느 범위까지 보낼지 제한

CSRF#

브라우저가 인증 쿠키를 자동으로 전송하는 구조에서는 공격 사이트가 사용자를 대신해 요청을 보내는 CSRF(Cross-Site Request Forgery)를 고려해야 합니다.

대응은 구조에 따라 다음을 조합합니다.

  • 적절한 SameSite 설정
  • CSRF Token
  • Origin/Referer 검증
  • 중요한 요청의 재인증·사용자 확인

인증 설계는 “토큰을 발급했다”에서 끝나지 않고 저장 위치·만료·재발급·로그아웃·탈취 시 대응까지 포함합니다.

13. 비밀번호와 보안 기본#

  • 비밀번호는 평문으로 저장하지 않고 해싱(bcrypt, argon2 등)해서 저장
  • 같은 비밀번호라도 매번 다른 해시값이 나오도록 salt 적용 (대부분의 해싱 라이브러리가 자동 처리)
  • 클라이언트가 보낸 값을 그대로 SQL·명령어에 사용하지 않기 (SQL Injection, Command Injection 방지)
  • 사용자 입력을 화면에 그대로 렌더링하는 경우 XSS 위험 고려 (주로 프론트 책임이지만 API 응답 값도 이스케이프 정책 확인)
  • 민감한 값(비밀번호 해시, 내부 토큰 등)은 응답 JSON에 포함하지 않기
  • 요청 빈도가 비정상적으로 많은 IP·계정에 대한 제한(rate limiting) 고려

14. 환경변수와 설정 관리#

환경에 따라 달라지는 값을 코드와 분리합니다.

text
DATABASE_URL=mysql://user:pass@localhost:3306/db
SECRET_KEY=...
AI_API_KEY=...
PORT=5000
💡 핵심 개념

기본 상식#

  • .env는 GitHub에 올리지 않고 .gitignore에 포함
  • .env.example에는 변수 이름만 공유 (실제 값 제외)
  • 개발/테스트/운영 환경변수를 분리해서 관리
  • 코드에 비밀값을 직접 작성하지 않기

실제로 해보기#

  1. 프로젝트 루트에 .env 파일을 만들고 위 예시처럼 키=값을 한 줄씩 적습니다. (따옴표 없이, = 앞뒤에 공백 없이)

  2. Python(Flask)이라면 python-dotenv 같은 라이브러리로 파일을 읽어옵니다.

    text
    from dotenv import load_dotenv
import os

load_dotenv()                       # .env 파일을 읽어서 환경변수로 등록
db_url = os.environ["DATABASE_URL"] # 코드에서는 이렇게 값을 꺼내 씀
  3. 코드 어디에도 실제 비밀번호나 키 문자열이 그대로 적혀 있지 않은지 확인합니다. os.environ[...]으로 “꺼내 쓰는” 코드만 있어야 정상입니다.
  4. .gitignore에 .env가 포함되어 있는지 확인합니다. 이미 Git이 추적 중인 .env는 .gitignore에 추가해도 계속 추적될 수 있으므로 git ls-files .env로 확인하고, 추적 중이면 git rm --cached .env로 Git 추적만 해제합니다.
  5. 비밀키를 실수로 GitHub에 push했다면 파일만 지우고 끝내지 않습니다. 해당 키·토큰을 즉시 폐기(revoke)하고 새 값으로 교체합니다. Git 이력에 값이 남았을 가능성도 별도로 처리해야 합니다.

15. 오류 처리#

오류 처리 원칙#

  • 예상 가능한 오류(검증 실패, 인증 실패 등)는 명확한 상태 코드 + 메시지로 응답
  • 예상하지 못한 오류(500)는 사용자에게 상세 내용을 노출하지 않고, 서버 로그에는 상세히 기록
  • 오류를 무조건 무시(빈 except)하지 않기
  • 오류 응답 형식을 프로젝트 전체에서 통일
text
# 개념 예시
try:
    course = get_course(course_id)
except CourseNotFound:
    return error_response(404, "COURSE_NOT_FOUND", "강의를 찾을 수 없습니다.")
except Exception:
    log.exception("unexpected error")
    return error_response(500, "INTERNAL_ERROR", "서버 오류가 발생했습니다.")

16. 로그#

로그는 문제가 생겼을 때 원인을 되짚어보기 위한 기록입니다.

기록하면 좋은 것:

  • 요청 URL·메서드·처리 시간
  • 오류 발생 시 스택 트레이스
  • 인증 실패, 권한 거부 이벤트
  • 외부 API 호출 실패

기록하면 안 되는 것:

  • 비밀번호, 토큰 원문
  • 카드번호 등 민감한 개인정보
💡 핵심 개념

기본 상식#

  • 로그 레벨(info/warning/error)을 구분해서 사용
  • 운영 환경에서는 너무 상세한 디버그 로그를 남기지 않기 (성능·용량 문제)

17. 미들웨어#

요청 전후에 공통으로 실행되는 처리입니다.

text
요청 → [로깅] → [CORS] → [인증 확인] → 실제 라우트 처리 → [오류 처리] → 응답
💡 핵심 개념

기본 상식#

  • 반복되는 로직(인증 확인, 로깅 등)은 미들웨어로 분리
  • 미들웨어 순서에 따라 동작이 달라질 수 있음을 이해

18. 캐싱과 성능 기본#

  • 자주 조회되지만 자주 바뀌지 않는 데이터는 캐싱 고려 (예: 인기 강의 목록)
  • 반복되는 무거운 쿼리는 인덱스·쿼리 구조 개선을 먼저 검토
  • N+1 쿼리 문제(목록 하나마다 개별 쿼리를 추가로 날리는 문제)를 확인
  • 페이지네이션 없이 전체 데이터를 한 번에 응답하지 않기
💡 핵심 개념

기본 상식#

  • 최적화 전에 실제 병목을 측정 (느낌으로 최적화하지 않기)
  • 캐시는 최신 데이터와 다를 수 있다는 점을 감안해 무효화 전략을 함께 설계

19. 외부 연동 (파일 업로드, 외부 API, AI API 등)#

  • 파일 업로드는 크기·확장자·용량 제한을 서버에서 검증
  • 외부 API 호출은 실패·지연을 가정하고 타임아웃·재시도 정책을 둠
  • 외부 API 키는 백엔드 환경변수로만 관리 (프론트엔드에 노출 금지)
  • AI API 등 응답 시간이 긴 요청은 사용자에게 로딩 상태를 전달할 방법을 함께 설계

오래 걸리는 작업과 Background Job#

이메일 발송, 대용량 파일 처리, 긴 AI 작업처럼 요청 하나에서 오래 걸리는 처리는 별도 작업 큐로 분리할 수 있습니다.

text
사용자 요청
→ 서버가 작업 등록
→ 즉시 "접수됨" 응답
→ Worker가 백그라운드에서 처리
→ 상태 저장
→ 프론트가 상태 조회 또는 실시간 알림 수신

대표적인 개념:

  • Queue: 기다리는 작업 목록
  • Worker: 큐의 작업을 실제로 처리하는 프로세스
  • Job ID: 사용자가 처리 상태를 조회할 수 있는 식별자

모든 프로젝트에 필요하지는 않습니다. 하지만 “API 하나가 30초 이상 붙잡혀 있다”면 비동기 작업 구조를 검토할 신호입니다.

20. 테스트#

종류#

  • 단위 테스트: 함수·서비스 로직 하나를 독립적으로 검증
  • 통합 테스트: 여러 컴포넌트(라우트 + DB 등)를 함께 검증
  • API 테스트: 실제 요청/응답을 도구(Postman, pytest 등)로 확인

기본 상식#

  • 정상 케이스뿐 아니라 잘못된 입력, 권한 없는 요청, 존재하지 않는 데이터도 테스트
  • 테스트 DB는 운영 DB와 분리
  • 버그가 발생했던 부분은 회귀 테스트를 남기는 것이 좋음

21. 배포 기초#

실행과 배포의 차이#

text
개발 실행 = 내 컴퓨터에서 확인
빌드      = 배포 가능한 형태로 준비
배포      = 다른 사용자가 접속 가능한 서버에 올림

배포 체크리스트#

  • 운영용 환경변수
  • 운영 데이터베이스 연결 확인
  • CORS 허용 도메인 설정
  • 포트·방화벽·보안그룹
  • 프로세스 상시 실행 (재시작 정책)
  • 마이그레이션 적용 여부
  • 로그 확인 방법
  • 실제 사용자 흐름 테스트
  • 비밀값 노출 여부

운영 서버의 기본 구조#

개발할 때 python app.py로 실행되는 것과 운영 서비스 구조는 다를 수 있습니다.

text
사용자
↓ HTTPS
도메인 / DNS
↓
Reverse Proxy (예: Nginx, 클라우드 Load Balancer)
↓
애플리케이션 서버
↓
DB / Cache / 외부 API

알아둘 용어#

  • Reverse Proxy: 외부 요청을 받아 실제 앱 서버로 전달. HTTPS 종료, 라우팅, 정적 파일 처리 등에 사용
  • TLS/HTTPS: 통신 내용을 암호화
  • Process Manager: 서버 프로세스가 죽었을 때 재시작하거나 여러 프로세스를 관리
  • Health Check: 서버가 살아 있고 요청을 처리할 수 있는지 확인하는 엔드포인트

예:

http
GET /health
200 OK

{
  "status": "ok"
}

헬스체크에서 무거운 작업을 수행하지 않고, 필요에 따라 앱 자체 상태와 DB 같은 핵심 의존성 상태를 구분해 확인합니다.

배포 시 DB 마이그레이션#

코드 배포와 DB 마이그레이션 순서가 맞지 않으면 새 코드가 없는 컬럼을 조회하거나, 구 코드가 삭제된 컬럼을 참조할 수 있습니다. 운영에서는 하위 호환 가능한 변경 → 코드 배포 → 정리처럼 순서를 설계해야 할 때도 있습니다.

22. Git 협업 기본 (백엔드 관점)#

일반적인 흐름은 프론트엔드와 동일합니다: 기준 브랜치 최신화 → 기능 브랜치 → 구현 → 테스트 → 커밋 → PR → 리뷰 → 머지. 백엔드에서 특히 주의할 부분:

공유가 필요한 변경#

  • API URL, 요청/응답 필드 변경
  • DB 스키마(컬럼, 테이블) 변경 — 마이그레이션 파일로 관리
  • 인증 방식 변경
  • 환경변수 추가
  • 외부 패키지 추가

충돌 가능성이 높은 공통 파일#

  • 라우터 등록 파일
  • 모델 정의 파일
  • 설정 파일 (DB 연결, 미들웨어 등록)
  • 마이그레이션 파일

이런 파일을 수정할 때는 팀에 미리 알립니다.

27. 프레임워크를 배운 뒤에도 설명할 수 있어야 하는 것#

  • 요청이 들어와서 응답이 나가기까지의 전체 흐름
  • 라우팅, 컨트롤러, 서비스, 모델의 역할 차이
  • REST API를 설계하는 기본 규칙
  • 관계형 데이터베이스의 기본키·외래키 개념
  • ORM이 내부적으로 SQL로 변환된다는 사실
  • 인증과 인가의 차이
  • 비밀번호를 해싱해서 저장하는 이유
  • 트랜잭션이 필요한 상황
  • 상태 코드별 의미
  • 환경변수를 쓰는 이유
  • 배포와 빌드의 차이
  • Git 브랜치를 사용하는 이유

28. 자주 하는 실수#

  • 요청값 검증 없이 바로 DB에 저장
  • 클라이언트가 보낸 사용자 ID·권한 값을 그대로 신뢰
  • 비밀번호를 평문으로 저장
  • 비밀값(API Key, DB 비밀번호)을 코드에 직접 작성
  • 오류를 그대로 삼켜서 원인을 알 수 없게 만듦
  • WHERE 없는 UPDATE/DELETE 실행
  • API 필드명을 프론트엔드와 상의 없이 임의로 변경
  • 트랜잭션 없이 여러 DB 작업을 나눠서 실행
  • 테스트 없이 공용 브랜치에 Merge
  • 응답에 불필요한 내부 정보(스택 트레이스 등) 노출
  • 모든 로직을 컨트롤러 하나에 몰아서 작성

2단계. app.py#

python
from flask import Flask, request, jsonify
import sqlite3

app = Flask(__name__)

def get_db():
    conn = sqlite3.connect("app.db")
    conn.row_factory = sqlite3.Row
    return conn

@app.get("/courses")
def list_courses():
    conn = get_db()
    rows = conn.execute("SELECT id, title FROM courses ORDER BY id").fetchall()
    conn.close()
    return jsonify([dict(row) for row in rows])

@app.post("/courses")
def create_course():
    body = request.get_json(silent=True) or {}
    title = body.get("title", "").strip()

    if not title:
        return jsonify({
            "error": {
                "code": "INVALID_TITLE",
                "message": "title은 필수입니다."
            }
        }), 400

    conn = get_db()
    cursor = conn.execute("INSERT INTO courses(title) VALUES (?)", (title,))
    conn.commit()
    course_id = cursor.lastrowid
    conn.close()

    return jsonify({"id": course_id, "title": title}), 201

if __name__ == "__main__":
    conn = get_db()
    conn.execute(
        "CREATE TABLE IF NOT EXISTS courses("
        "id INTEGER PRIMARY KEY AUTOINCREMENT, "
        "title TEXT NOT NULL)"
    )
    conn.commit()
    conn.close()

    app.run(debug=True)
