브라우저 개발자 도구(DevTools) 기초 가이드

Elements·Console·Network로 화면·JS·API 문제를 직접 확인하는 법.

📘 문서 소개
대상: 웹 개발을 처음 하는 사람
목적: 브라우저에서 문제가 생겼을 때 DevTools를 열고 어느 탭을 봐야 하는지 바로 판단하기
주의: 여기서는 Chrome DevTools 기준으로 설명합니다. Firefox·Edge·Safari에도 이름만 다를 뿐 거의 같은 기능이 있습니다. 이 문서는 도구 사용법이고, "어떤 순서로 원인을 찾는가"라는 흐름은 디버깅·오류 해결 기초 가이드에서 다룹니다 — 함께 읽으면 좋습니다.

1. DevTools 여는 법#

  • 페이지 아무 곳이나 우클릭 → 검사(Inspect)
  • 또는 단축키: Windows/Linux F12 또는 Ctrl+Shift+I, Mac Cmd+Option+I

열리면 위쪽에 Elements / Console / Network / Application 같은 탭이 보입니다. 이 문서는 그중 초보자가 실제로 자주 쓰는 4개 탭만 다룹니다.

2. Elements — 화면(HTML/CSS) 확인#

2.1 HTML 구조 확인#

Elements 탭은 지금 화면에 실제로 그려진 HTML을 보여줍니다(내가 작성한 소스 코드가 아니라, JS가 실행되고 난 최종 결과입니다). 왼쪽 위 화살표 아이콘(요소 선택 도구)을 누르고 화면의 요소를 클릭하면, Elements 탭이 그 요소의 HTML 위치로 자동으로 이동합니다. "이 버튼이 코드에서 어디에 해당하는지 모르겠다"일 때 가장 먼저 쓰는 기능입니다.

2.2 CSS가 왜 적용되지 않는지 확인#

요소를 클릭하면 오른쪽에 Styles 패널이 뜹니다. 여기서 확인할 것:

  • 내가 준 스타일이 목록에 있는지 — 없으면 클래스 이름 오타나, 엉뚱한 요소에 스타일을 준 것입니다.
  • 있는데 취소선이 그어져 있는지 — 다른 규칙이 그 스타일을 덮어쓰고 있다는 뜻입니다. 취소선 위에 있는 규칙(더 구체적이거나 나중에 선언된 규칙)이 이긴 것입니다.
  • Computed 탭에서는 여러 규칙이 합쳐진 "최종 값"만 볼 수 있어, 실제로 지금 적용된 크기·색상·여백을 바로 확인할 때 편합니다.

2.3 임시 스타일 수정#

Styles 패널에서 값(예: color: red)을 직접 클릭해 바꿔볼 수 있습니다. 이 수정은 새로고침하면 사라지고, 실제 코드 파일은 바뀌지 않습니다. "이 값을 이렇게 바꾸면 원하는 모양이 되는지" 빠르게 실험해보고, 맞으면 그 값을 실제 CSS 파일에 옮겨 적는 용도로 씁니다.

3. Console — JavaScript 오류·로그 확인#

3.1 JavaScript 오류 확인#

화면이 이상하게 동작하면 가장 먼저 Console을 엽니다. 빨간 글씨로 에러가 찍혀 있다면, 그 메시지와 파일:줄번호를 확인합니다(에러 메시지 읽는 법과 stack trace는 디버깅·오류 해결 기초 가이드 2~3장 참고). 에러가 하나도 없는데 화면이 이상하다면 JS 자체 문제가 아니라 CSS나 데이터 문제일 가능성이 높습니다.

3.2 console.log 활용#

코드 중간에 console.log(값)을 넣어두면 그 시점에 값이 무엇인지 여기서 확인할 수 있습니다.

js
function handleSubmit(user) {
  console.log("submit 시점의 user:", user);   // 여기서 user가 뭔지 확인
  if (!user.email) return;
  // ...
}

"이 함수가 실행은 되는지", "이 시점에 이 값이 뭔지"가 궁금할 때 가장 빠른 확인 방법입니다. 확인이 끝난 console.log는 커밋 전에 지웁니다.

4. Network — API 요청 확인#

Network 탭을 열어둔 채로 화면을 새로고침하거나 버튼을 눌러야 요청이 기록됩니다(탭을 늦게 열면 그 전 요청은 안 보입니다). 목록에서 요청 하나를 클릭하면 아래 정보를 확인할 수 있습니다.

항목확인 내용
URL정확한 주소로 요청이 갔는가 (오타, 잘못된 경로 없는지)
MethodGET/POST/PATCH/DELETE 등 의도한 메서드가 맞는가
Status응답 상태 코드 (바로 아래 표 참고)
Request내가 보낸 데이터(헤더, 바디)가 의도한 값이 맞는가
Response서버가 실제로 뭘 돌려줬는가 — 화면에 안 보여도 응답 자체는 정상일 수 있습니다

Status 코드가 보이면 무엇부터 확인할지#

  • 404 — URL 자체가 틀림. 오타, 앞뒤 슬래시, 포트 번호부터 확인
  • 401 — 로그인/인증 정보가 요청에 안 실렸거나 만료됨. Request 헤더에 토큰이 있는지 확인
  • 403 — 인증은 됐지만 권한이 없음. 로그인한 계정의 권한을 확인
  • 500 — 서버 내부 오류. Response 내용만으로는 부족할 때가 많아 서버 터미널 로그를 봐야 함

요청 자체가 목록에 아예 안 보인다면, 프론트엔드 코드에서 요청을 보내는 함수가 실행되지 않았다는 뜻이니 Console부터 다시 확인합니다.

5. Application — 저장된 데이터 확인#

Application 탭 왼쪽의 Storage 항목에서 확인합니다.

  • Local Storage — 브라우저를 꺼도 남아있는 저장 값(로그인 토큰 등)
  • Session Storage — 탭을 닫으면 사라지는 저장 값
  • Cookies — 서버 요청에 자동으로 실려가는 값

초보자가 이 탭을 여는 상황은 보통 정해져 있습니다: "로그인이 안 풀렸는데 왜 로그인 화면이 뜨지", "로그아웃했는데 값이 남아있다" 처럼 로그인 상태나 저장된 값 자체를 의심할 때입니다. 값을 직접 지우거나 수정해서 "저장된 값이 문제인지, 코드가 문제인지"를 구분할 수 있습니다.

6. Responsive/Device Mode — 모바일 화면 확인#

DevTools 왼쪽 위의 기기 아이콘(또는 Ctrl+Shift+M)을 누르면 화면을 모바일 크기로 바꿔 미리 볼 수 있습니다. 실제 폰이 없어도 "작은 화면에서 레이아웃이 깨지지 않는지"를 바로 확인할 수 있습니다. 상단에서 화면 폭(예: 375px, 390px)을 직접 입력해 여러 크기를 테스트해봅니다.

7. 캐시 문제일 때#

"분명히 코드를 고쳤는데 화면이 안 바뀐다"면 브라우저가 예전 파일을 캐시(다시 안 받아오려고 저장해둔 예전 버전)해서 쓰고 있을 수 있습니다.

  • 먼저 강력 새로고침: Windows Ctrl+Shift+R, Mac Cmd+Shift+R
  • 그래도 안 바뀌면 Network 탭에서 Disable cache 체크박스를 켜고(DevTools가 열려 있는 동안만 적용) 다시 새로고침

"내 컴퓨터에서만 옛날 화면이 보이고 남들은 새 화면이 보인다"는 대부분 이 문제입니다.

8. 실제 상황 예시#

예시 1. 버튼을 눌러도 아무 반응이 없음#

  • 증상: 버튼을 클릭했는데 아무 일도 안 일어남
  • 어느 탭: Console
  • 무엇을 확인: 빨간 에러가 있는지 본다. 있다면 그 시점에 코드 실행이 멈춘 것 (예: onClick 함수 안에서 에러가 나서 이후 로직이 실행 안 됨)
  • 다음 행동: 에러 메시지의 파일:줄번호로 이동해 그 지점부터 확인. 에러가 없다면 버튼에 이벤트가 실제로 연결됐는지 Elements에서 요소를 확인

예시 2. API 데이터가 화면에 안 나옴#

  • 증상: 로딩은 끝났는데 목록이 비어있음
  • 어느 탭: Network
  • 무엇을 확인: 해당 요청의 Status가 200인지, Response에 실제로 데이터가 들어있는지 확인
  • 다음 행동: Status가 200이고 Response에 데이터도 있다면 프론트엔드가 응답을 화면에 그리는 코드 쪽 문제 → Console로 이동해 관련 에러가 있는지 확인. Status가 200이 아니라면 4장의 코드별 확인 순서로

예시 3. CSS가 적용되지 않음#

  • 증상: 색이나 여백을 줬는데 화면에 그대로 반영 안 됨
  • 어느 탭: Elements
  • 무엇을 확인: 해당 요소를 클릭해 Styles 패널에서 내가 준 스타일이 목록에 있는지, 취소선이 그어져 있는지 확인
  • 다음 행동: 스타일 자체가 안 보이면 클래스 이름 오타 확인, 취소선이 있으면 어떤 규칙이 덮어쓰는지 확인 후 선택자를 더 구체적으로 바꾸거나 그 규칙을 수정

9. 최종 원칙#

  • 화면 문제 → Elements, JS 동작 문제 → Console, 서버 통신 문제 → Network, 로그인/저장값 문제 → Application
  • Network 탭은 요청이 일어나기 전에 열어둔다
  • 코드를 고쳤는데 안 바뀌면 캐시부터 의심한다(강력 새로고침)
  • Elements에서 고친 스타일은 저장되지 않는다 — 확인용으로만 쓰고 실제 파일에 옮겨 적는다

DevTools로 "어디가 문제인지" 확인했다면, 그다음 "어떤 순서로 원인을 좁히고 고치는지"는 디버깅·오류 해결 기초 가이드를 참고하세요.
