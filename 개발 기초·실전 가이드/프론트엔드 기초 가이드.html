0. 시작 전에 — 자주 나오는 용어#

개발이 처음이라면 본문을 읽기 전에 아래 표부터 훑어보세요. 본문 중간에 낯선 단어가 나오면 다시 여기로 돌아와 찾아봐도 됩니다.

0.1 웹 기본#

용어쉬운 설명
브라우저(Browser)웹페이지를 보여주는 프로그램. Chrome, Safari, Edge 등.
도메인(Domain)URL에서 사이트를 식별하는 이름 부분(example.com).
포트(Port)한 컴퓨터에서 여러 프로그램을 구분하는 번호. 개발 서버는 보통 3000, 5173 같은 포트를 씁니다.
로컬(local) / localhost지금 쓰고 있는 내 컴퓨터 자신을 가리키는 주소.
서버(Server)요청을 받아 응답을 돌려주는 프로그램(백엔드).
클라이언트(Client)요청을 보내는 쪽(브라우저).

0.2 HTML/CSS/JS 기본#

용어쉬운 설명
태그(Tag)<button>처럼 HTML에서 의미 단위를 표시하는 것.
엘리먼트(Element)태그로 만들어진 화면 요소 하나.
속성(Attribute)<img alt="설명">처럼 태그에 추가 정보를 주는 것.
선택자(Selector)CSS에서 “어떤 엘리먼트를 꾸밀지” 지정하는 문법(.class, #id 등).
클래스(Class)여러 엘리먼트에 같은 스타일을 재사용하기 위한 이름표.
박스 모델(Box Model)모든 엘리먼트를 margin-border-padding-content 4겹으로 보는 CSS 개념.
변수(Variable)값을 담아두는 이름표. JS에서 const, let으로 선언.
함수(Function)특정 동작을 묶어서 이름 붙여둔 코드 덩어리.

0.3 DOM/이벤트#

용어쉬운 설명
DOM브라우저가 HTML을 읽어서 JS로 다룰 수 있게 만든 객체 구조.
이벤트(Event)클릭, 입력처럼 사용자가 한 행동.
이벤트 리스너(Event Listener)“이 이벤트가 발생하면 이 함수를 실행해라”라고 등록하는 것.
렌더링(Rendering)데이터를 실제 화면(HTML)으로 그려내는 것.
재렌더링(Re-render)상태(State)가 바뀌어서 화면을 다시 그리는 것.

0.4 컴포넌트/상태#

용어쉬운 설명
컴포넌트(Component)화면을 이루는 재사용 가능한 작은 단위. 레고 블록 하나에 비유할 수 있습니다.
Props부모 컴포넌트가 자식 컴포넌트에게 전달하는 값(읽기 전용).
State(상태)시간이 지나며 바뀌고, 바뀌면 화면도 다시 그려져야 하는 값.
지역 상태컴포넌트 하나 안에서만 쓰는 상태.
전역 상태여러 화면이 공유하는 상태.
SPA (Single Page Application)페이지 전체를 새로 불러오지 않고 필요한 부분만 JS로 갱신하는 웹앱 방식. React는 SPA를 만드는 데 자주 쓰이지만, Next.js 같은 프레임워크를 사용하면 SSR·SSG 등 여러 렌더링 방식을 함께 사용할 수 있습니다.

0.5 네트워크/비동기#

용어쉬운 설명
API서버와 데이터를 주고받기 위해 정해진 약속(창구).
fetch / axios브라우저에서 서버에 HTTP 요청을 보낼 때 쓰는 JS 도구.
비동기(Async)결과가 바로 오지 않는 작업(서버 요청 등)을 기다리는 동안 다른 일도 할 수 있게 처리하는 방식.
Promise비동기 작업의 결과(성공/실패)를 나중에 받기로 약속한 객체.
async/awaitPromise를 마치 동기 코드처럼 읽기 쉽게 쓰는 문법.
JSON{ "key": "value" } 형태의 데이터 형식. API 응답에서 가장 흔히 씀.

0.6 브라우저 저장소#

용어쉬운 설명
localStorage브라우저를 꺼도 유지되는 저장 공간.
sessionStorage탭을 닫으면 사라지는 저장 공간.
쿠키(Cookie)서버 요청에 자동으로 따라붙는 작은 저장 데이터.

0.7 도구/배포#

용어쉬운 설명
개발 서버(Dev Server)코드를 수정하면 바로 화면에 반영해주는, 개발할 때만 쓰는 서버.
번들(Bundle)여러 JS/CSS 파일을 배포용으로 하나(또는 몇 개)로 합친 결과물.
빌드(Build)소스 코드를 배포 가능한 형태로 만드는 과정.
배포(Deploy)빌드 결과를 사용자가 접속 가능한 서버에 올리는 것.
접근성(Accessibility, a11y)장애나 사용 환경에 관계없이 누구나 웹을 쓸 수 있게 만드는 것.

0.8 개발 환경과 프로젝트 파일#

프론트엔드 개발에서는 HTML/CSS/JavaScript만큼 Node.js·패키지 매니저·프로젝트 설정 파일을 이해하는 것이 중요합니다.

항목쉬운 설명
Node.js브라우저 밖에서도 JavaScript를 실행할 수 있게 해주는 런타임. 프론트 개발 도구(Vite 등)를 실행할 때 사용
npmNode.js 패키지 매니저. 라이브러리 설치와 개발 명령 실행에 사용
package.json프로젝트 이름, 설치된 패키지, 실행 명령(scripts)을 기록한 핵심 설정 파일
node_modules/설치된 패키지가 실제로 들어가는 폴더. 직접 수정하지 않고 Git에도 보통 올리지 않음
lock 파일package-lock.json, pnpm-lock.yaml 등. 팀원이 같은 버전의 의존성을 설치하도록 버전을 고정
Vite개발 서버와 빌드 환경을 빠르게 제공하는 대표적인 프론트엔드 빌드 도구
npm scriptnpm run dev, npm run build처럼 package.json에 이름을 붙여둔 실행 명령

React + Vite 프로젝트를 처음 실행하는 예#

bash
node --version
npm --version

npm create vite@latest my-app -- --template react
cd my-app
npm install
npm run dev

기존 프로젝트를 받은 경우에는 새 프로젝트를 만들지 않고 저장소 폴더에서 보통 다음처럼 시작합니다.

bash
npm install
npm run
npm run dev

npm run을 입력하면 현재 package.json의 scripts 목록을 볼 수 있습니다.

React 프로젝트 폴더 구조 예시#

npm create vite@latest로 만든 프로젝트는 처음엔 폴더가 거의 비어 있습니다. 기능이 늘어나면서 보통 아래처럼 역할별로 나눠갑니다. 처음부터 이 구조를 다 만들 필요는 없고, 파일이 늘어날 때마다 필요한 폴더를 그때그때 추가하면 됩니다.

text
my-app/
├── public/                # 그대로 배포되는 정적 파일 (favicon 등)
├── src/
│   ├── main.jsx           # 앱의 시작점 — React를 화면에 처음 그리는 곳
│   ├── App.jsx            # 최상위 컴포넌트, 라우터를 여기서 연결
│   ├── pages/              # 화면(페이지) 단위 컴포넌트 — 라우팅 경로 하나당 보통 파일 하나
│   │   ├── CourseListPage.jsx
│   │   └── CourseDetailPage.jsx
│   ├── components/          # 여러 페이지에서 재사용하는 작은 컴포넌트
│   │   ├── Header.jsx
│   │   └── CourseCard.jsx
│   ├── hooks/               # 재사용 가능한 상태·로직 (예: useAuth, useFetch)
│   ├── api/                 # 서버 요청 함수 모음 — fetch/axios 호출은 전부 여기로
│   │   └── courses.js
│   ├── context/             # 여러 화면이 공유하는 전역 상태 (예: 로그인 사용자 정보)
│   ├── styles/               # 전역 CSS, 변수
│   └── utils/                # 날짜 포맷 등 순수 함수 모음
├── package.json
└── vite.config.js
  • pages/와 components/의 차이: 라우팅 경로와 1:1로 대응되면 pages, 여러 곳에서 재사용되면 components로 나눕니다. 예를 들어 /courses/10에 대응하는 화면 전체는 pages/CourseDetailPage.jsx이고, 그 안에서 쓰이는 강의 카드 하나는 components/CourseCard.jsx입니다.
  • api/ 폴더를 따로 두는 이유: 컴포넌트 안에서 직접 fetch를 호출하면 같은 요청 코드가 여러 파일에 흩어집니다. API 함수를 한 곳에 모아두면 서버 주소가 바뀌거나 요청 방식이 바뀔 때 한 파일만 고치면 됩니다.
  • 폴더가 늘어나기 시작하는 시점: 컴포넌트 파일이 10개를 넘거나, 같은 폴더 안에서 원하는 파일을 찾는 데 시간이 걸리기 시작하면 그때 세부 폴더(components/course/, components/common/ 등)로 나눕니다.

Missing script: "dev"가 뜨는 이유#

text
npm run dev
→ package.json의 scripts에서 "dev"라는 이름을 찾음
→ 없으면 Missing script 오류

따라서 아래 순서로 확인합니다.

  1. 현재 터미널 위치가 프론트엔드 프로젝트 폴더인지 확인
  2. package.json이 현재 폴더에 있는지 확인
  3. npm run으로 등록된 스크립트 확인
  4. README에 실제 실행 명령이 따로 적혀 있는지 확인

import / export#

파일을 나눠 개발할 때 JavaScript 모듈 문법으로 서로 연결합니다.

js
// api.js
export async function getCourses() {
  const response = await fetch("/api/courses");
  return response.json();
}

초보자가 자주 겪는 오류인 “함수가 정의되지 않았다”, “모듈을 찾을 수 없다”는 문제는 파일 경로·export/import 방식부터 확인합니다.

1. 프론트엔드란?#

프론트엔드는 사용자가 웹 브라우저에서 직접 보고 조작하는 부분을 개발하는 영역입니다.

프론트엔드는 단순히 화면을 예쁘게 만드는 역할만 하지 않습니다.

  • 정보를 이해하기 쉽게 보여주기
  • 사용자의 입력을 받기
  • 서버에 데이터를 요청하기
  • 서버 응답을 화면에 반영하기
  • 로딩, 오류, 빈 결과를 처리하기
  • 다양한 화면 크기에서 사용할 수 있게 만들기
  • 키보드와 보조기술 사용자도 이용할 수 있게 만들기
  • 빠르고 안전하게 동작하게 만들기

일반적인 구조:

text
사용자
↓
브라우저
↓
프론트엔드
↓ HTTP 요청
백엔드 API
↓
데이터베이스 또는 외부 서비스

프론트엔드는 일반적으로 데이터베이스에 직접 접근하지 않습니다.

사용자가 주소를 입력하면 대략 다음 과정이 일어납니다.

text
1. 사용자가 URL 입력
2. 브라우저가 서버에 요청
3. 서버가 HTML, CSS, JavaScript 또는 데이터를 응답
4. 브라우저가 HTML 구조 생성
5. CSS로 화면 표현
6. JavaScript로 동작 추가
7. 필요한 데이터는 API로 다시 요청
8. 응답에 따라 화면 갱신

  • 텍스트가 길어졌을 때 레이아웃이 깨지는지 확인

CSS가 예상과 다르게 적용될 때#

CSS는 “나중에 쓴 코드가 무조건 이긴다”가 아니라 여러 규칙을 함께 봅니다.

  • Cascade(캐스케이드): 여러 CSS 규칙이 충돌할 때 최종 스타일을 결정하는 과정
  • Specificity(명시도): 선택자가 얼마나 구체적인지에 따른 우선순위
  • Inheritance(상속): 일부 속성이 부모 요소에서 자식 요소로 전달되는 성질
css
p { color: black; }           /* 태그 선택자 */
.card p { color: blue; }      /* 더 구체적 */
#main .card p { color: red; } /* 더 높은 명시도 */

스타일이 안 먹으면 !important부터 붙이지 말고 브라우저 개발자 도구 → Elements → Styles/Computed에서 어떤 규칙이 덮어쓰고 있는지 확인합니다.

6.4 Same-Origin Policy와 CORS#

브라우저는 보안을 위해 출처(origin)가 다른 서버로 보내는 일부 요청을 제한합니다.

Origin은 일반적으로 다음 세 요소의 조합입니다.

text
프로토콜 + 호스트 + 포트

예:

text
http://localhost:5173   ← 프론트
http://localhost:5000   ← 백엔드

포트가 다르므로 서로 다른 origin입니다. 이때 백엔드가 허용 응답 헤더를 보내지 않으면 브라우저에서 CORS 오류가 날 수 있습니다.

중요한 점:

  • CORS는 “프론트 코드가 틀렸다”는 뜻이 아닐 수 있습니다.
  • 브라우저가 적용하는 보안 정책이므로 Postman에서는 되고 브라우저에서는 막힐 수도 있습니다.
  • 허용 origin은 가능하면 필요한 주소만 지정합니다.
  • 쿠키 기반 인증을 쓸 때는 프론트의 credentials 설정과 서버의 자격 증명 허용 설정을 함께 맞춰야 합니다.
js
fetch("https://api.example.com/me", {
  credentials: "include",
});

CORS 오류가 나면 브라우저 Console만 보지 말고 Network 탭에서 실제 요청·응답 헤더와 상태를 확인합니다.

요청 경합(Race Condition)과 오래된 응답#

검색창처럼 요청이 연속으로 발생하는 화면에서는 먼저 보낸 요청이 나중에 도착할 수 있습니다.

text
"A" 검색 요청 ───────────────→ 늦게 도착
"AB" 검색 요청 ─────→ 먼저 도착

화면이 "AB" 결과를 보여줌
→ 뒤늦게 "A" 응답이 도착
→ 오래된 결과로 화면이 되돌아갈 수 있음

해결 방법:

  • 요청마다 최신 요청 ID를 비교
  • 이전 요청을 AbortController로 취소
  • React Query/TanStack Query 같은 서버 상태 도구의 기능 활용

모든 화면에 필요한 개념은 아니지만, 검색·자동완성·빠른 페이지 이동에서 문제가 생기면 이 상황을 의심합니다.

실제 코드로 보면 이렇게 생겼습니다 (React 예시)#

앞서 나온 Props와 State가 React에서는 실제로 어떤 모습인지 보여드립니다. 강의 카드 컴포넌트 하나를 예로 듭니다.

text
// CourseCard.jsx — 부모가 전달한 값(Props)을 받아서 화면에 그리기만 하는 컴포넌트
function CourseCard({ title, price }) {   // ← title, price가 Props: 부모가 넘겨준 읽기 전용 값
  return (
    <div className="course-card">
      <h2>{title}</h2>
      <p>{price === 0 ? "무료" : `${price}원`}</p>
    </div>
  );
}

// CourseList.jsx — 이 컴포넌트 안에서 바뀌는 값(State)을 직접 관리
import { useState, useEffect } from "react";

function CourseList() {
  const [courses, setCourses] = useState([]);   // ← State: 시간이 지나며 바뀌는 값 (처음엔 빈 배열)
  const [isLoading, setIsLoading] = useState(true);

  useEffect(() => {
    fetch("/api/courses")
      .then((response) => response.json())
      .then((data) => {
        setCourses(data.courses);   // ← State를 바꾸면 React가 화면을 자동으로 다시 그림(재렌더링)
        setIsLoading(false);
      });
  }, []);

  if (isLoading) return<p>불러오는 중입니다...</p>;

  return (
    <div>
      {courses.map((course) => (
        // ← 여기서 CourseCard에게 title, price를 Props로 "내려준다"고 표현
        <CourseCard key={course.id} title={course.title} price={course.price} />
      ))}
    </div>
  );
}
  • CourseList는 서버에서 받아온 데이터를 courses라는 State로 들고 있습니다. State가 바뀌면(setCourses 호출) React가 알아서 화면을 다시 그립니다.
  • CourseCard는 스스로 상태를 갖지 않고, 부모가 준 title·price Props만 그대로 화면에 표시합니다. 이런 컴포넌트를 “표현만 담당한다”고 말합니다.
  • isLoading State가 있어서 12장에서 다루는 “로딩 중” 상태를 화면에 따로 보여줄 수 있습니다.

Vue, Svelte도 문법은 다르지만 “부모가 자식에게 값을 내려준다(Props)”와 “컴포넌트 안에서 바뀌는 값을 따로 관리한다(State)”는 개념은 동일합니다.

  • 대규모 코드 구조화
  • 개발 생태계 활용

대표 선택지:

  • React
  • Vue
  • Angular
  • Svelte
  • Next.js
  • Nuxt

선택 기준#

  • 프로젝트 요구사항
  • 팀의 경험
  • 생태계
  • 배포 환경
  • SEO 필요 여부

💡 핵심 개념

기본 상식#

  • 모든 프로젝트에 프레임워크가 필요한 것은 아님
  • React는 웹 그 자체가 아니라 UI 라이브러리
  • 프레임워크를 배워도 HTML, CSS, JavaScript 기초가 필요
  • 도구 이름보다 웹의 원리를 이해하는 것이 중요

TypeScript는 왜 많이 쓰는가?#

TypeScript는 JavaScript에 타입 검사를 추가한 언어입니다.

ts
type Course = {
  id: number;
  title: string;
};

function CourseCard({ course }: { course: Course }) {
  return <div>{course.title}</div>;
}

장점:

  • API 응답 필드명을 잘못 쓰는 실수를 빨리 발견
  • 함수에 어떤 값을 넣어야 하는지 명확
  • 규모가 커질수록 리팩토링이 안전해짐
  • 에디터 자동완성이 좋아짐

처음부터 반드시 TypeScript를 써야 하는 것은 아닙니다. JavaScript의 변수·함수·객체·배열·비동기를 먼저 이해한 뒤 TypeScript를 배우면 훨씬 쉽습니다.

CSR / SSR / SSG 기본#

방식의미특징
CSR브라우저에서 JavaScript로 화면을 렌더링SPA에서 흔함. 초기 HTML은 단순할 수 있음
SSR요청 시 서버가 HTML을 만들어 응답초기 화면·SEO에 유리할 수 있음
SSG빌드 시 HTML을 미리 만들어 둠자주 바뀌지 않는 페이지에 적합

React를 배웠다고 모든 웹사이트가 CSR인 것은 아닙니다. Next.js 같은 프레임워크에서는 페이지 성격에 따라 여러 렌더링 방식을 함께 사용할 수 있습니다.

10. 라우팅#

라우팅은 URL과 화면을 연결하는 것입니다.

text
/                 홈
/products         상품 목록
/products/10      상품 상세
/login            로그인
/mypage           마이페이지

URL Parameter#

특정 항목을 식별합니다.

text
/products/10

여기서 10은 상품 ID입니다.

Query Parameter#

검색, 필터, 정렬 조건을 표현합니다.

text
/products?category=book&sort=price

라우팅 기본 상식#

  • 새로고침 후에도 필요한 상태가 유지되는지 확인
  • 검색과 필터는 URL에 표현하면 공유와 뒤로가기가 쉬움
  • 존재하지 않는 경로는 404 화면 처리
  • 권한이 필요한 경로는 접근 제어
  • URL에는 민감한 정보를 넣지 않기

13. 반응형 웹#

반응형 웹은 화면 크기에 따라 자연스럽게 레이아웃이 변하는 웹입니다.

확인할 화면:

  • 태블릿
  • 노트북

  • 고정 폭 남용 금지
  • 콘텐츠 최대 폭 사용
  • 이미지가 부모보다 커지지 않게 처리
  • 작은 화면에서 메뉴와 표가 깨지지 않는지 확인
  • 터치 영역을 너무 작게 만들지 않기
  • 가로 스크롤이 의도치 않게 생기지 않는지 확인

14. 웹 접근성#

웹 접근성은 장애 여부나 사용 환경과 관계없이 웹을 사용할 수 있게 만드는 것입니다.

기본 확인:

  • 키보드만으로 조작 가능
  • 포커스 위치가 보임
  • 이미지 대체 텍스트
  • 충분한 색상 대비
  • 입력창에 Label 제공
  • 버튼과 링크의 의미가 명확함
  • 색상만으로 상태를 구분하지 않음
  • 제목 구조가 논리적임

접근성은 특정 프로젝트의 선택 기능이 아니라 기본 품질에 가깝습니다.

16. 보안 기본 상식#

프론트엔드 코드와 브라우저 저장소는 사용자가 볼 수 있습니다.

따라서:

  • API Key와 비밀번호를 프론트 코드에 넣지 않기
  • 민감한 보안 판단을 프론트에서만 하지 않기
  • 사용자 입력을 그대로 HTML로 삽입하지 않기
  • 토큰 저장 방식의 위험을 이해하기
  • HTTPS 사용
  • 외부 링크와 파일 업로드 주의
  • 개인정보를 Console에 출력하지 않기

프론트엔드 환경변수도 빌드 결과에 포함될 수 있으므로 비밀값 저장소가 아닙니다.

인증 정보를 어디에 저장할까?#

“로그인 토큰은 무조건 localStorage에 넣는다”처럼 외우지 않습니다. 저장 위치는 인증 구조와 위협 모델에 따라 결정합니다.

자주 쓰는 선택지#

  • HttpOnly Cookie: JavaScript에서 직접 읽을 수 없게 설정할 수 있어 XSS로 토큰을 탈취하기 어렵게 만들 수 있음
  • 메모리 상태: 새로고침하면 사라지지만 브라우저 저장소에 장기간 남기지 않음
  • localStorage: 사용이 간단하지만 JavaScript에서 접근 가능하므로 XSS가 발생하면 값이 노출될 수 있음

쿠키 기반 인증에서는 서버가 다음 옵션을 함께 검토합니다.

  • HttpOnly
  • Secure
  • SameSite

반대로 쿠키를 자동 전송하는 구조에서는 CSRF도 함께 고려해야 합니다.

초보자 기준 핵심은 다음입니다.

로그인 정보를 어디에 저장할지는 프론트엔드 혼자 정하지 말고, 백엔드의 인증 방식과 함께 결정한다.

17. 브라우저 저장소#

localStorage#

  • 브라우저를 닫아도 유지
  • 문자열 형태로 저장
  • JavaScript에서 접근 가능

sessionStorage#

  • 탭이 닫히면 삭제
  • JavaScript에서 접근 가능

Cookie#

  • 서버 요청에 자동 포함 가능
  • 만료, 도메인, 보안 옵션 설정 가능

IndexedDB#

  • 브라우저에서 구조화된 대용량 데이터 저장
💡 핵심 개념

기본 상식#

  • 저장소에는 꼭 필요한 데이터만 저장
  • 비밀번호 저장 금지
  • 민감한 토큰 저장 방식은 보안 요구사항에 따라 결정
  • 저장된 데이터가 오래되어 잘못될 수 있음을 고려
  • JSON 저장 시 직렬화와 역직렬화 필요

  • 새로고침과 뒤로가기 확인

  • 중복 코드 점검
  • 커밋과 문서 업데이트

27. 프레임워크를 배운 뒤에도 설명할 수 있어야 하는 것#

  • HTML, CSS, JavaScript의 역할
  • 브라우저가 페이지를 표시하는 과정
  • DOM과 이벤트
  • 클라이언트와 서버의 차이
  • HTTP 요청과 응답
  • Props와 State 또는 해당 프레임워크의 유사 개념
  • 지역 상태와 공유 상태의 차이
  • 서버 데이터를 불러오는 흐름
  • URL Parameter와 Query Parameter
  • 인증과 인가의 차이
  • 로딩·빈 결과·오류 상태를 나눈 이유
  • 반응형과 접근성을 확인하는 이유
  • 브라우저 개발자 도구 사용법
  • 빌드와 배포의 차이
  • Git 브랜치를 사용하는 이유

28. 자주 하는 실수#

  • HTML과 CSS 기초 없이 프레임워크만 공부
  • 모든 코드를 하나의 파일에 작성
  • 모든 상태를 전역으로 관리
  • 성공 응답만 가정
  • 서버 데이터를 임의의 필드명으로 추측
  • 로딩과 빈 결과를 같은 상태로 처리
  • CSS를 수정하며 다른 화면 영향 확인 안 함
  • 모바일과 키보드 사용을 확인하지 않음
  • Console 오류를 남긴 채 완료 처리
  • API Key를 프론트 코드에 작성
  • AI가 생성한 코드를 이해하지 않고 사용
  • 테스트하지 않고 공용 브랜치에 Merge
  • 디자인 완성에 시간을 모두 쓰고 핵심 기능을 못 끝냄

29. AI를 이용한 프론트엔드 학습 방법#

좋은 요청:

text
HTML, CSS, JavaScript의 역할을 먼저 설명하고,
그 다음 React에서 같은 기능이 어떻게 구현되는지 비교해주세요.
초보자가 이해할 수 있도록 브라우저에서 실행되는 순서도 설명해주세요.

코드를 받을 때 확인할 내용:

  1. 이 코드가 브라우저에서 언제 실행되는가?
  2. 어떤 입력을 받는가?
  3. 어떤 상태를 변경하는가?
  4. 어떤 DOM 또는 화면이 바뀌는가?
  5. API 요청이 있다면 요청과 응답은 무엇인가?
  6. 오류가 발생하면 어떻게 처리하는가?
  7. 특정 프레임워크에만 해당하는 부분은 무엇인가?
  8. 순수 JavaScript로는 어떤 원리인가?

AI의 답을 그대로 외우기보다, 작은 예제로 직접 실행하고 수정해봅니다.

32. 처음부터 한 번 만들어보기 — 프론트엔드 최소 실습#

목표는 예쁜 페이지가 아니라 “프로젝트 생성 → 상태 → API → 오류 처리 → 빌드”의 전체 흐름을 한 번 경험하는 것입니다.

1단계. React 프로젝트 실행#

bash
npm create vite@latest frontend-practice -- --template react
cd frontend-practice
npm install
npm run dev

브라우저에서 터미널에 표시된 localhost 주소가 열리면 개발 환경은 정상입니다.

2단계. 상태 하나 만들기#

버튼을 누르면 숫자가 증가하는 화면을 만듭니다.

확인할 것:

  • 컴포넌트가 무엇인지
  • State가 바뀔 때 왜 다시 렌더링되는지
  • 이벤트 핸들러가 언제 실행되는지

3단계. 더미 데이터 목록 만들기#

js
const courses = [
  { id: 1, title: "HTML 기초" },
  { id: 2, title: "React 입문" },
];

map으로 카드 여러 개를 렌더링하고 각 항목에 안정적인 key를 지정합니다.

4단계. API 데이터로 교체#

js
async function getCourses() {
  const response = await fetch("http://localhost:5000/courses");
  if (!response.ok) throw new Error("강의 목록 요청 실패");
  return response.json();
}

화면에는 최소 네 상태가 있어야 합니다.

text
로딩 중
성공 + 데이터 있음
성공 + 빈 배열
실패

5단계. Network 탭 확인#

API 요청 하나를 클릭해서 다음을 직접 봅니다.

  • Request URL
  • Method
  • Status Code
  • Request Headers
  • Response Headers
  • Response Body

이 경험을 해두면 CORS·401·404·500 오류를 훨씬 빨리 구분할 수 있습니다.

6단계. 빌드#

bash
npm run build

dist/ 같은 빌드 결과물이 생성되는지 확인합니다.

이 실습을 끝내고 설명할 수 있어야 하는 것#

text
package.json은 무엇인가?
npm install과 npm run dev는 무엇이 다른가?
State와 일반 변수의 차이는 무엇인가?
API 요청은 어디서 확인하는가?
CORS 오류는 왜 생길 수 있는가?
개발 서버와 빌드 결과물은 무엇이 다른가?

여기까지 직접 해보면 프론트엔드 가이드의 나머지 장은 추상적인 용어가 아니라 실제 경험과 연결해서 읽을 수 있습니다.
