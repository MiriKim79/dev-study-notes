> **대상:** GitHub에 프로젝트를 올렸지만 README를 어떻게 써야 할지 모르는 사람
> **목적:** README를 예쁘게 꾸미는 법이 아니라, **다른 사람이 이 프로젝트를 빠르게 이해하고 직접 실행할 수 있게 만드는 법**을 익히기

---

# 1. 기본 흐름

```
프로젝트 소개 → 핵심 기능 → 실행 방법 → 환경설정 → 기술 스택
→ 구조/아키텍처 → 사용 방법 → 팀/역할 → 문제 해결 → 링크
```

이 순서를 그대로 다 채워야 하는 것은 아닙니다. 작은 개인 프로젝트라면 앞의 4~5개만으로도 충분하고, 팀 프로젝트나 포트폴리오용이라면 뒤쪽까지 채우는 것이 좋습니다.

---

# 2. 가장 먼저 보여줄 것

README 맨 위에는 아래를 담습니다. 여기까지만 읽어도 "이게 뭔지, 왜 만들었는지"가 이해돼야 합니다.

* **프로젝트 이름**
* **한 줄 소개** — "이게 뭐 하는 서비스인지" 한 문장
* **왜 만들었는지** — 학습 목적인지, 실제 불편을 해결하려 한 것인지
* **핵심 기능 3~5개** — 전체 기능이 아니라 가장 중요한 것만
* **실제 화면/데모 링크** — 있다면 반드시 넣습니다. 글보다 스크린샷 한 장이 훨씬 빠르게 이해시킵니다.

```markdown
# 오늘 뭐 배웠지
스터디원끼리 학습 진도를 기록하고 공유하는 웹 앱입니다.

혼자 공부하면 진도가 흐지부지되기 쉬워서, 매일 배운 걸 짧게 기록하고
서로 확인할 수 있게 만들었습니다.

## 주요 기능
- 오늘 배운 내용 짧게 기록하기
- 스터디원 진도를 한 화면에서 보기
- 연속 기록일 표시

데모: https://example.com
```

# 3. 실행 방법

처음 보는 사람이 저장소를 clone한 뒤 그대로 따라 하면 실행되도록, 순서를 명확히 씁니다. **명령어만 나열하지 말고, 왜 필요한지 한마디씩 붙입니다.**

```bash
# 1. 저장소 내려받기
git clone https://github.com/아이디/저장소.git
cd 저장소

# 2. 의존성 설치 (package.json에 적힌 라이브러리들을 설치)
npm install

# 3. 환경변수 설정 (4장 참고)
cp .env.example .env

# 4. 실행
npm run dev
```

명령어 하나하나가 "무엇을 위한 단계인지" 알면, 중간에 에러가 나도 어느 단계에서 막혔는지 스스로 판단할 수 있습니다.

---

# 4. 환경변수 — `.env` 노출 주의

**실제 `.env` 값이나 API 키를 README에 그대로 적지 않습니다.** README는 저장소와 함께 공개되므로, 실제 비밀값을 적으면 그대로 유출됩니다.

대신 아래처럼 **`.env.example`** 파일을 만들어, 어떤 변수 이름이 필요한지만 값 없이 공유합니다.

```bash
# .env.example (실제 값은 비워두고 변수 이름만 안내)
DATABASE_URL=
API_KEY=
PORT=3000
```

README에는 이렇게 안내합니다.

```markdown
## 환경변수
`.env.example`을 복사해 `.env`를 만들고, 각자 발급받은 값을 채워 넣으세요.
```

`.env`는 `.gitignore`에 포함해 저장소에 올라가지 않게 하고, `.env.example`만 공유합니다.

# 5. 기술 스택 — 나열이 아니라 이유

로고 이미지를 잔뜩 붙이는 것보다, **실제로 사용한 기술**과 **왜 그 기술을 골랐는지**(필요한 경우에만) 짧게 적는 것이 더 신뢰를 줍니다. 써보지 않은 기술을 장식으로 넣지 않습니다.

```markdown
## 기술 스택
- React — 컴포넌트 단위로 화면을 나누기 위해
- Express + PostgreSQL — REST API와 사용자 데이터 저장
- Socket.io — 실시간 알림 기능에 필요해서 사용
```

"왜 썼는지"는 모든 항목에 다 붙일 필요는 없습니다. 특별한 이유 없이 흔히 쓰는 조합이라면 이름만 나열해도 충분합니다.

---

# 6. 프로젝트 구조 — 중요한 폴더만

폴더 전체를 나열하지 말고, **읽는 사람이 코드를 찾아갈 때 도움이 되는 상위 폴더만** 간단히 보여줍니다.

```text
src/
├─ components/   # 재사용하는 화면 조각
├─ pages/        # 라우트 단위 화면
├─ api/          # 서버 요청 함수 모음
└─ hooks/        # 커스텀 훅
```

각 폴더가 하는 역할을 한 줄씩만 적으면 충분합니다. 세부 파일까지 다 적을 필요는 없습니다.

---

# 7. 아키텍처 — 필요한 프로젝트에서만

프론트/백엔드/DB가 어떻게 연결되는지 구조 설명이 필요한 프로젝트라면 간단한 그림이나 텍스트 다이어그램을 추가합니다.

```text
[React 프론트엔드] → [Express API 서버] → [PostgreSQL]
```

혼자 만든 작은 프로젝트, 프론트엔드만 있는 프로젝트라면 이 항목은 생략해도 됩니다. **모든 프로젝트에 거창한 아키텍처 다이어그램을 억지로 넣을 필요는 없습니다.**

---

# 8. 팀 프로젝트 — 역할은 구체적으로

팀 프로젝트라면 팀원과 각자 맡은 기능을 적습니다. `Frontend`/`Backend`처럼 직군만 적기보다, **실제로 무엇을 구현했는지**를 씁니다.

```markdown
## 팀
| 이름 | 담당 |
| --- | --- |
| 김OO | 로그인/회원가입, JWT 인증 구현 |
| 이OO | 게시글 목록·상세 API, 페이지네이션 |
| 박OO | 전체 배포 환경 구성, CI 파이프라인 |
```

"Frontend 담당"보다 "로그인/회원가입, JWT 인증 구현"이 훨씬 구체적이라, 읽는 사람이 실제로 무엇을 했는지 바로 알 수 있습니다.

# 9. 문제 해결(트러블슈팅) 정리하기

프로젝트를 진행하며 의미 있었던 문제 1~3개를 아래 형식으로 정리합니다.

```markdown
## 트러블슈팅

### 문제: 목록이 새로고침할 때마다 순서가 바뀜
- 원인: 정렬 기준 없이 DB가 반환하는 순서 그대로 사용
- 해결: 정렬 기준을 API 쿼리에 명시적으로 추가
- 배운 점: DB가 "기본 순서"를 보장하지 않는다는 것을 알게 됨
```

이 섹션은 포트폴리오용 README에서 특히 유용합니다. 단순히 "다 만들었다"보다 **"어떤 문제를 어떻게 풀었는지"**가 실력을 더 잘 보여줍니다.

# 10. 하지 말아야 할 것

* 배지만 과도하게 붙이기 (배지 자체는 나쁘지 않지만, 내용보다 튀면 안 됩니다)
* 기술 스택만 잔뜩 나열하고 왜 썼는지는 하나도 없음
* 실행 방법이 아예 없음

* README와 실제 프로젝트 상태가 다름 (README엔 있는데 실제로는 없는 기능 등)

# 12. 최종 원칙

* README는 예쁜 문서가 아니라 **실행 가능한 안내서**다
* 모든 섹션을 다 채우려 하지 말고, 프로젝트 규모에 맞게 고른다
* 실행 방법은 clone부터 실행까지 빠짐없이, 이유도 함께 적는다
* 비밀값은 절대 README나 저장소에 올리지 않는다
* 기술 스택은 나열보다 "왜"가 있을 때 더 설득력 있다

GitHub 프로필 자체를 어떻게 구성할지(Pinned Repository 고르는 기준 등)는 [GitHub 프로필 꾸미기 가이드](GitHub%20프로필%20꾸미기%20가이드.html)를, 저장소를 clone하고 커밋·push하는 Git 명령어 자체는 [Git·GitHub 기초 가이드](Git·GitHub%20기초%20가이드.html)를, 팀 프로젝트에서 README를 언제 준비하면 좋은지는 [팀 개발 시작 가이드](팀%20개발%20시작%20가이드.html)를, README에 정리한 트러블슈팅과 기능을 발표 자료로 옮기는 법은 [개발자 발표·데모 잘하는 법](개발자%20발표·데모%20잘하는%20법.html)을 참고하세요.
