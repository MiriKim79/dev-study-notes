GitHub 프로필 꾸미기 가이드

꾸미기보다 먼저, 무엇을 보여줄지부터 — 대표 프로젝트·README·역할 정리법.

📘 문서 소개
대상: GitHub 계정은 있고, 프로필과 저장소를 신입/학생 채용 담당자·동료가 봤을 때 제대로 보이게 만들고 싶은 사람
목적: 배지·통계 카드 같은 "꾸미기"보다 먼저, 무엇을 보여줘야 실제로 평가에 도움이 되는지를 잡는다.
핵심: 채용 담당자는 배지 개수를 보지 않습니다. Pinned Repository에 뭐가 있는지, README만 보고 이 프로젝트가 뭔지 이해되는지를 봅니다.

0. 무엇을 보여주는 게 중요한가#

0-1. 대표 프로젝트 선정 기준#

신입/학생 지원자의 GitHub를 볼 때 채용 담당자·동료가 실제로 확인하는 것은 대체로 이 순서입니다.

  1. Pinned Repository 6개 — 프로필 최상단에 고정되는 저장소. 가장 먼저, 가장 오래 보는 영역입니다.
  2. 각 저장소의 README — 커밋 로그나 코드 전체를 다 읽지는 않습니다. README만 보고 "뭘 만들었는지"가 이해되는지를 봅니다.
  3. 커밋 히스토리의 일관성 — 마지막에 몰아서 커밋했는지, 꾸준히 작업했는지 정도는 훑어봅니다.

따라서 대표 프로젝트를 고를 때는 다음 기준을 씁니다.

  • 완성도가 있는가 — 진행 중이어도 좋지만, 실행하면 최소한 동작하는 상태여야 합니다. 절반만 구현된 프로젝트만 여러 개 있는 것보다, 끝까지 완성한 것 1~2개가 낫습니다.
  • 본인이 무엇을 했는지 설명할 수 있는가 — 튜토리얼을 그대로 따라 한 프로젝트만 있으면 면접에서 할 말이 없습니다. 직접 설계하거나 문제를 해결한 경험이 드러나야 합니다.
  • 기술스택 조합이 다양한가 — 6개 전부 같은 스택(예: React 토이 프로젝트 6개)보다, 프론트/백엔드/알고리즘/팀 프로젝트 등 서로 다른 역량을 보여주는 조합이 낫습니다.

0-2. Pinned Repository 구성 방법#

  1. 본인 프로필 페이지 → Customize your pins 클릭
  2. 프로필에 노출할 저장소를 최대 6개까지 체크 → 저장
  3. 포크(fork)한 저장소보다는 본인이 만든 저장소를 우선 고정합니다. 포크는 "내가 만든 것"으로 보이지 않습니다.

고르는 우선순위 예시:

  • 완성도 있는 개인/팀 프로젝트 1~2개 (지원 직무와 관련된 스택 우선)
  • 알고리즘/CS 학습 저장소 (있다면, 꾸준함을 보여줌)
  • 서로 다른 기술스택을 보여주는 프로젝트 (프론트 1개 + 백엔드 1개처럼)
  • 오래되었거나 완성도 낮은 저장소, 중복되는 스택의 저장소는 제외

0-3. 프로젝트 README 작성 요령#

프로젝트 저장소의 README는 다음 항목을 이 순서로 담는 것이 좋습니다.

  • 무엇을 만들었는지 — 한두 문장으로 요약 (예: "실시간 채팅이 가능한 할 일 관리 웹 앱")
  • 왜 만들었는지 — 학습 목적이었는지, 실제 불편을 해결하려 한 것인지
  • 어떤 기술을 왜 썼는지 — 단순 나열이 아니라 선택 이유 (예: "실시간 갱신이 필요해서 WebSocket을 사용했다")
  • 본인의 역할·기여도 — 팀 프로젝트라면 본인이 맡은 부분을 명시 (예: "인증/로그인 기능과 배포 담당")
  • 실행 방법 — git clone부터 실행까지 그대로 따라 할 수 있는 명령어
  • 스크린샷 또는 데모 링크 — 글로만 설명하는 것보다 화면 캡처나 배포 URL이 훨씬 설득력이 있습니다.
markdown
## 프로젝트 소개
학습 진도를 기록하고 공유하는 웹 앱입니다.

## 왜 만들었나
스터디원끼리 진도를 따로 관리하기 불편해서, 직접 만들어보기로 했습니다.

## 기술 스택
- React: 컴포넌트 단위로 UI를 나누기 위해
- Express + MySQL: REST API와 사용자 데이터 저장

## 담당 역할
- 프론트엔드 UI 구현, 백엔드 API 연동

## 실행 방법
\`\`\`bash
git clone https://github.com/아이디/저장소.git
cd 저장소
npm install
npm run dev
\`\`\`

## 데모
https://example.com (또는 스크린샷 이미지 삽입)

0-4. 프로필에서 역할·기술스택 드러내기#

프로필 README 자기소개에는 "무엇을 공부하고 있다"보다 "무엇을 할 수 있다"가 더 명확히 드러나야 합니다.

  • 막연한 나열 대신, 실제 사용 경험이 있는 기술만 적습니다. (이력서와 마찬가지로, 면접에서 질문받을 수 있다고 가정하세요.)
  • 실제 프로젝트에서 써본 기술과 튜토리얼만 따라 해본 기술을 섞어서 나열하지 마세요. 구분이 어렵다면 "능숙"/"사용 경험 있음"처럼 구간을 나누거나, 프로젝트에서 실제로 쓴 것 위주로만 적는 편이 안전합니다.
  • 관심 분야(예: 프론트엔드/백엔드/풀스택)를 한 줄로 명시하면 채용 담당자가 어떤 포지션에 맞는지 빠르게 판단할 수 있습니다.

0-5. 연락처·포트폴리오·블로그 링크 정리#

  • 이력서/포트폴리오 사이트, 기술 블로그, 이메일(공개해도 되는 경우) 등을 프로필 README 상단이나 GitHub 프로필의 bio/Social accounts 항목에 정리합니다.
  • 링크는 실제로 접속 가능한지, 최신 내용인지 확인 후 등록합니다. 방치된 블로그 링크는 안 넣느니만 못합니다.

1. 프로필 README란 무엇인가#

GitHub는 자신의 아이디와 똑같은 이름의 저장소를 만들면, 그 저장소의 README.md 내용을 프로필 페이지 맨 위에 자동으로 보여주는 기능을 제공합니다.

text
github.com/mirikim79 라는 프로필을 꾸미고 싶다면
→ mirikim79/mirikim79 라는 이름의 저장소를 새로 만들고
→ 그 안의 README.md에 원하는 내용을 적으면 끝
  • 저장소 이름이 정확히 내 GitHub 아이디와 같아야 이 기능이 작동합니다.
  • 이 저장소는 Public(공개)이어야 프로필에 노출됩니다.
  • 새 저장소를 만들 때 "Add a README file"을 체크하면 바로 시작할 수 있습니다.

여기부터는 선택사항입니다. 아래 배지·통계 카드·기여 잔디는 프로필을 "보기 좋게" 만들어줄 뿐, 실제 평가에서 중요한 것은 위 0장(대표 프로젝트, Pinned Repository, README 작성법)입니다. 시간이 부족하다면 0장에 집중하고 이 이후는 건너뛰어도 됩니다.

2. 기본 구성 요소#

프로필 README에 흔히 들어가는 요소들입니다. 전부 필수는 아니고, 마음에 드는 것만 골라 써도 충분합니다.

  • 자기소개: 관심 분야, 지금 배우고 있는 것, 연락 방법(선택) 한두 문단.
  • 기술 스택 배지: shields.io에서 만드는 작은 이미지 배지. 마크다운 이미지 문법으로 붙입니다.
  • GitHub 통계 카드: 커밋 수, 자주 쓰는 언어 등을 이미지로 보여주는 서드파티 서비스(대표적으로 github-readme-stats).
  • 기여 잔디(Contribution graph): 프로필 자체에 이미 표시되는 잔디 외에, README 안에 별도로 넣고 싶다면 서드파티 서비스를 이용합니다.
  • 방문자 카운터: 프로필에 몇 번 방문했는지 보여주는 뱃지형 카운터.

4. 통계 카드·잔디 넣기 (서드파티 서비스)#

github-readme-stats, github-readme-streak-stats 같은 오픈소스 프로젝트는 내 GitHub 아이디를 넣은 이미지 URL을 만들어주고, 그 URL을 프로필 README에 붙이면 자동으로 통계 이미지가 렌더링됩니다.

markdown
![내 GitHub 통계](https://github-readme-stats.vercel.app/api?username=내아이디&show_icons=true)

알아두면 좋은 점

  • 이런 서비스는 대부분 개인이 운영하는 무료 공개 서버입니다. 공식 GitHub 기능이 아니므로 트래픽이 몰리면 일시적으로 이미지가 안 뜨거나 느릴 수 있습니다. 안 보인다고 내 설정이 잘못된 게 아닐 수 있으니, 시간을 두고 새로고침해보세요.
  • 자기 서버에 직접 배포해서 쓰는 방법도 있지만(레포를 fork해서 Vercel 등에 배포), 처음에는 공개 인스턴스를 그대로 쓰는 것으로 충분합니다.
  • 이런 서비스는 프로젝트마다 유지 상태가 다르므로, 사용 전에 저장소가 최근까지 관리되고 있는지 정도는 확인하는 게 좋습니다.
  • 기여 잔디(Contribution graph)가 빽빽하다고 실력이 좋다는 뜻은 아닙니다. 매일 커밋한다고 실력이 느는 것도 아니고, 채용 담당자도 잔디 개수를 실력 지표로 크게 보지 않습니다. 잔디를 채우는 데 시간을 쓰기보다 실제 프로젝트 완성도에 집중하세요.

5. 자주 하는 실수#

  • 배지·카드를 너무 많이 붙여서 정작 자기소개 글이 안 보임. 3~5개 정도의 핵심 배지면 충분합니다.
  • 이메일·전화번호 같은 개인정보를 그대로 노출. 공개하고 싶은 정보만 신중하게 넣습니다.
  • 저장소 이름 오타. 내아이디/내아이디가 정확히 일치해야 프로필에 표시됩니다. 대소문자는 GitHub 아이디 자체가 대소문자를 구분하지 않으므로 문제되지 않지만, 저장소 이름을 아이디와 다르게 지으면 그냥 평범한 저장소가 됩니다.
  • 화려하게 만드는 데 시간을 너무 많이 씀. 이건 재미로 하는 꾸미기입니다 — 실제 학습·프로젝트에 쓸 시간을 이걸로 크게 줄이지는 마세요.

6. 여기까지 이해했다면#

  • 채용 담당자가 GitHub 프로필에서 실제로 보는 것(Pinned Repository, README)이 무엇인지 설명할 수 있다.
  • 대표 프로젝트를 고르는 기준(완성도, 본인 기여, 다양한 기술스택)을 안다.
  • 프로젝트 README에 무엇을, 왜, 어떻게 썼는지, 본인 역할, 실행 방법, 데모 링크를 담을 수 있다.
  • 프로필 README가 어떤 저장소의 README.md로 만들어지는지 설명할 수 있다.
  • 배지·통계 카드는 선택사항이며, 과하게 넣으면 오히려 안 좋다는 것을 안다.

더 배우고 싶다면: Git·GitHub 기초 가이드에서 저장소·커밋·PR 흐름부터 제대로 잡아보세요. 프로필 꾸미기는 어디까지나 곁가지입니다.
