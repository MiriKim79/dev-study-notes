0. 시작 전에 — 자주 나오는 용어#

이 문서는 프론트엔드·백엔드·AI 전체를 아우르므로, 분야별 상세 용어는 짝 문서에서 더 자세히 다룹니다.

  • HTML/CSS/JS/브라우저 용어 → 프론트엔드 기초 가이드 0장
  • 서버/DB/API 용어 → 백엔드 기초 가이드 0장
  • 프롬프트·토큰·모델 선택 등 AI 개발 상세 용어 → 생성형 AI 기능 개발 기초 가이드 0장
  • Git 명령어·인증·충돌 해결 상세 → Git·GitHub 기초 가이드

여기서는 이 문서에서만 나오는 기획·협업·AI 용어를 정리합니다.

0.1 기획·개발 진행#

용어쉬운 설명
요구사항(Requirement)사용자가 무엇을 할 수 있어야 하는지 적은 문장. 예: “사용자는 이메일로 로그인할 수 있다.”
MVP (Minimum Viable Product)“이것만 있으면 서비스가 성립한다”고 할 수 있는 최소 기능 묶음.
사용자 흐름(User Flow)사용자가 서비스 안에서 움직이는 순서(예: 회원가입 → 로그인 → 강의 검색 → 수강 신청).
API 계약(API Contract)프론트와 백엔드가 미리 합의한 “요청·응답이 정확히 어떤 모양인지”의 약속. 한쪽이 마음대로 바꾸면 다른 쪽 화면이 즉시 깨집니다.
폴더 구조코드 파일을 어디에 둘지에 대한 규칙.

0.2 Git·협업#

용어쉬운 설명
저장소(Repository, repo)프로젝트 코드 전체와 변경 이력이 저장된 공간.
브랜치(Branch)저장소 안에서 독립적으로 작업하는 작업선. 내 작업은 내 브랜치에서.
커밋(Commit)변경 내용을 저장하는 단위. 게임의 세이브 포인트에 비유할 수 있습니다.
Push / Pull내 커밋을 원격 저장소에 올리는 것 / 남의 커밋을 받아오는 것.
Pull Request(PR)“내 브랜치를 기준 브랜치에 합쳐 달라”는 요청이자 코드 리뷰가 이루어지는 곳.
머지(Merge)PR이 승인되어 실제로 두 브랜치가 합쳐지는 것.
충돌(Conflict)같은 부분을 두 사람이 고쳐서 Git이 자동으로 합치지 못하는 상태.

0.3 환경·배포#

용어쉬운 설명
환경변수(Environment Variable)비밀번호·API 키 등 환경마다 달라지는 값을 코드 밖에 분리해 관리하는 방법.
개발/테스트/운영 환경각각 “내 컴퓨터에서 확인”, “배포 전 검증”, “실제 사용자가 쓰는 곳”을 뜻합니다.
빌드(Build) / 배포(Deploy)배포 가능한 형태로 만드는 것 / 실제 서버에 올리는 것.

0.4 AI 개발#

용어쉬운 설명
모델(Model)학습이 끝난 AI 프로그램 자체(예: GPT, Claude 같은 이름이 곧 모델 이름).
API (AI 맥락)내 코드가 AI 모델을 호출할 수 있게 열어둔 창구. 대부분 인터넷 너머에 있는 모델을 호출합니다.
프롬프트(Prompt)AI 모델에게 보내는 입력 텍스트(지시문).
토큰(Token, AI 맥락)AI가 텍스트를 처리하는 단위. 단어나 음절 정도의 조각이며, 요금은 보통 토큰 수로 계산됩니다.
구조화된 출력AI 응답을 자유 텍스트가 아니라 JSON처럼 정해진 형식으로 강제해서 받는 것.
환각(Hallucination)AI가 사실이 아닌 내용을 그럴듯하게 지어내는 현상.
지연 시간(Latency)요청부터 응답까지 걸리는 시간. AI 응답은 일반 API보다 느린 경우가 많습니다.
평가 데이터AI 결과가 잘 나오는지 확인하기 위해 미리 준비해둔 입력·정답 쌍.

1. 개발을 시작할 때 가장 먼저 기억할 원칙#

1.1 바로 코딩하지 않는다#

개발은 코드를 입력하는 일보다 무엇을 만들지 정확히 정하는 일이 먼저입니다.

개발 시작 전 최소한 다음 질문에 답할 수 있어야 합니다.

text
1. 누가 사용하는 기능인가?
2. 사용자가 무엇을 할 수 있어야 하는가?
3. 성공한 상태는 무엇인가?
4. 어떤 데이터가 필요한가?
5. 다른 기능이나 팀원의 작업과 어디에서 연결되는가?
6. 이번 기간 안에 반드시 구현할 범위는 어디까지인가?

기능이 명확하지 않은 상태에서 코딩을 시작하면 다음 문제가 생깁니다.

  • 필요한 기능과 불필요한 기능이 섞임
  • 프론트엔드와 백엔드의 데이터 형식이 달라짐
  • 같은 기능을 두 명이 중복 구현함
  • 파일 구조가 계속 바뀜
  • 마지막에 통합할 때 많은 코드를 다시 작성함

1.2 큰 기능을 작은 작업으로 나눈다#

좋지 않은 작업 단위:

text
로그인 완성하기
강의 기능 만들기
AI 추천 시스템 구현하기

좋은 작업 단위:

text
로그인 페이지 입력창 만들기
이메일 형식 검사 추가하기
로그인 API 함수 만들기
로그인 성공 시 토큰 저장하기
로그인 실패 메시지 표시하기

작업 하나는 가능하면 몇 시간 안에 구현하고 직접 확인할 수 있는 크기로 나눕니다.

1.3 동작하는 최소 기능을 먼저 만든다#

처음부터 완벽한 디자인, 모든 예외 처리, 고급 기능을 넣지 않습니다.

text
기본 동작
→ 데이터 연결
→ 오류 처리
→ 디자인 개선
→ 부가 기능

예시:

text
강의 카드 한 개 표시
→ 더미 데이터 여러 개 표시
→ 백엔드 강의 목록 연결
→ 로딩·오류 처리
→ 반응형 디자인 적용

1.4 모르는 상태에서 추측으로 연결하지 않는다#

특히 다음 내용은 상대 팀 또는 명세와 반드시 확인합니다.

  • API 주소
  • 요청 메서드
  • 요청 필드명
  • 응답 필드명
  • 인증 방식
  • 오류 응답 형식
  • 데이터베이스 컬럼
  • 이미지 URL 형식
  • 배포 주소와 포트

추측으로 작성한 코드는 나중에 대부분 다시 수정하게 됩니다.

3. 1단계: 요구사항 확인#

3.1 요구사항이란?#

사용자가 무엇을 할 수 있어야 하는지 설명한 내용입니다.

예시:

text
사용자는 이메일과 비밀번호로 로그인할 수 있다.
사용자는 강의 제목으로 강의를 검색할 수 있다.
로그인한 사용자는 무료 강의를 수강 신청할 수 있다.

3.2 요구사항 확인 체크리스트#

  • 사용자 대상이 누구인지 확인
  • 필수 기능과 선택 기능 구분
  • 완료 조건 확인
  • 제한 시간 확인
  • 사용할 기술 확인
  • 배포 필요 여부 확인
  • 팀원별 역할 확인
  • 실제 데이터가 필요한지 확인
  • 외부 API나 AI 모델 사용 여부 확인

4. 2단계: MVP 범위 결정#

MVP는 사용자가 핵심 가치를 경험할 수 있는 최소 기능입니다.

예를 들어 온라인 강의 플랫폼의 MVP는 다음과 같습니다.

text
회원가입
로그인
강의 목록
강의 상세
수강 신청
내 강의 확인

다음 기능은 시간이 남을 때 추가할 수 있습니다.

text
찜하기
리뷰
장바구니
결제
강사 관리
추천 시스템

범위를 결정할 때 사용하는 기준#

  1. 없으면 서비스 흐름이 끊기는가?
  2. 발표에서 핵심 기능으로 보여줘야 하는가?
  3. 현재 기간 안에 구현할 수 있는가?
  4. 다른 기능보다 먼저 완성되어야 하는가?
  5. 실패했을 때 다른 기능까지 막히는가?

5. 3단계: 사용자 흐름 정리#

사용자가 서비스에서 움직이는 순서를 먼저 적습니다.

text
메인 접속
→ 회원가입
→ 로그인
→ 강의 검색
→ 강의 상세
→ 수강 신청
→ 마이페이지
→ 로그아웃

각 단계에는 필요한 화면과 API를 연결합니다.

사용자 행동프론트엔드 화면백엔드 기능
로그인로그인 페이지사용자 확인, JWT 발급
강의 조회강의 목록강의 목록 조회
강의 선택강의 상세특정 강의 조회
수강 신청수강 버튼수강 정보 저장
내 강의 확인마이페이지사용자별 수강 목록 조회

이 표가 있으면 프론트엔드와 백엔드가 서로 무엇을 기다리는지 알 수 있습니다.

6. 4단계: 기술과 구조 결정#

6.1 기술을 선택할 때 기준#

  • 팀원이 사용할 수 있는가?
  • 프로젝트 기간 안에 익힐 수 있는가?
  • 핵심 기능 구현에 실제로 필요한가?
  • 공식 문서와 사례가 충분한가?
  • 배포가 가능한가?
  • 다른 기술과 잘 연결되는가?

새 기술이 멋있어 보인다는 이유만으로 추가하지 않습니다.

6.2 폴더 구조를 정하는 이유#

파일 위치와 역할이 명확하면 다음 장점이 있습니다.

  • 팀원이 코드를 쉽게 찾음
  • 같은 기능을 중복 작성하지 않음
  • 파일 충돌이 줄어듦
  • 코드가 커져도 관리하기 쉬움

폴더 구조는 처음부터 지나치게 복잡하게 만들지 않습니다.

예시로 비교하기#

같은 로그인 기능이라도 폴더를 어떻게 나누느냐에 따라 나중에 찾기 쉬운 정도가 달라집니다.

text
나쁜 예 (역할 구분 없이 한 폴더에 몰아넣기)
src/
├── LoginPage.jsx
├── SignupPage.jsx
├── CourseListPage.jsx
├── api.js              ← 로그인, 강의, 마이페이지 요청이 전부 이 한 파일에 섞임
└── utils.js

좋은 예 (기능·역할별로 분리)
src/
├── pages/
│   ├── auth/LoginPage.jsx
│   └── course/CourseListPage.jsx
├── api/
│   ├── auth.js          ← 로그인 관련 요청만
│   └── courses.js        ← 강의 관련 요청만
└── utils/

파일이 5~6개뿐인 초기 단계라면 나쁜 예처럼 시작해도 괜찮습니다. 문제는 그 상태로 계속 파일이 늘어나는 것입니다 — "이 파일에 뭐가 더 들어있는지 스크롤해봐야 안다"는 느낌이 들기 시작하면 그때 폴더를 나눕니다.

프로젝트 전체(프론트엔드+백엔드)를 한 저장소에 담는 모노레포 구조는 보통 이렇게 최상위를 나눕니다.

text
project/
├── frontend/       # 프론트엔드 프로젝트 전체 (프론트 담당자 폴더)
├── backend/         # 백엔드 프로젝트 전체 (백엔드 담당자 폴더)
├── docs/             # 기획서, API 명세, 회의록 등 코드가 아닌 문서
└── README.md          # 프로젝트 소개와 실행 방법

이렇게 나누면 "이 파일은 어느 담당자 것인지"가 폴더 이름만 보고도 바로 구분되어, 여러 명이 같은 저장소에서 작업해도 충돌이 줄어듭니다. 프론트엔드·백엔드 내부를 더 세부적으로 어떻게 나누는지는 각 분야 가이드(프론트엔드 기초 가이드 0.8절, 백엔드 기초 가이드 3장)를 참고하세요.

7. 5단계: 데이터와 API 계약#

7.1 API 계약이란?#

프론트엔드와 백엔드가 데이터를 주고받는 규칙입니다.

예시:

text
POST /api/auth/login

요청:

text
{
  "email": "user@example.com",
  "password": "password"
}

응답:

text
{
  "accessToken": "token",
  "user": {
    "id": 1,
    "nickname": "사용자"
  }
}

프론트엔드와 백엔드는 다음을 정확히 맞춰야 합니다.

  • HTTP 메서드
  • URL
  • 요청 데이터
  • 응답 데이터
  • 상태 코드
  • 인증 필요 여부
  • 오류 메시지

7.2 API가 확정되지 않았을 때#

프론트엔드는 더미 데이터를 사용해 화면을 먼저 만듭니다.

text
const mockCourse = {
  id: 1,
  title: "React 입문",
  price: 0,
};

백엔드는 임시 API 응답을 만들어 테스트할 수 있습니다.

그러나 실제 API가 확정되기 전까지 필드명을 프로젝트 전체에 흩어놓지 않습니다.

8. 6단계: 저장소와 브랜치 준비#

8.1 저장소와 브랜치의 차이#

text
저장소
= 프로젝트 전체 코드와 변경 기록이 저장되는 공간

브랜치
= 같은 저장소 안에서 특정 기능을 독립적으로 작업하는 작업선

8.2 브랜치 구조는 팀이 선택한다#

브랜치 구조는 모든 프로젝트가 똑같이 써야 하는 규칙이 아닙니다. 아래는 GitFlow 축소판을 선택한 팀의 예시입니다.

text
main
└── develop
    ├── feat/frontend-auth
    ├── feat/backend-auth
    ├── feat/course-api
    └── feat/ai-recommendation
  • main: 배포 가능한 안정된 코드
  • develop: 기능을 합치는 개발 기준 브랜치
  • feat/...: 기능 개발
  • fix/...: 오류 수정
  • refactor/...: 기능 변화 없는 구조 개선
  • hotfix/...: 운영 서비스의 긴급 수정

작은 팀은 main + 기능 브랜치만 쓰는 GitHub Flow가 더 단순할 수 있습니다. 중요한 것은 브랜치 개수가 아니라 “어디서 분기하고 어디로 PR을 보낼지”를 팀 전체가 같은 규칙으로 쓰는 것입니다. 선택 기준은 개발 협업 방식 선택 가이드를 참고합니다.

8.3 작업 시작 순서#

text
git switch develop
git pull origin develop
git switch -c feat/기능명

8.4 작업 종료 순서#

text
git status
git add 변경파일
git commit -m "Feat: 기능 설명"
git push -u origin feat/기능명

그다음 Pull Request를 생성합니다.

text
feat/기능명
→ develop

9. 7단계: 개발 환경 설정#

공통 확인 항목#

  • 필요한 언어 설치
  • 언어 버전 확인
  • 패키지 매니저 확인
  • 프로젝트 의존성 설치
  • 환경변수 파일 준비
  • 개발 서버 실행
  • 데이터베이스 연결 확인
  • Git 브랜치 확인
  • .gitignore 확인

실제로 확인하는 명령어#

터미널에 아래 명령을 입력해 버전이 출력되면 설치가 된 것입니다. “command not found” 같은 오류가 뜨면 설치가 안 된 것이니 공식 사이트에서 설치합니다.

text
git --version        # Git이 설치됐는지 확인
node --version        # Node.js 버전 확인 (프론트엔드)
npm --version          # npm(패키지 매니저) 버전 확인
python --version       # Python 버전 확인 (백엔드가 Python 계열일 때)

프로젝트마다 실행 명령이 다릅니다. 먼저 저장소의 README, package.json, requirements.txt, pyproject.toml, build.gradle 같은 설정 파일을 확인합니다.

Node.js/프론트엔드 예시#

bash
npm install
npm run
npm run dev

npm run은 package.json의 scripts에 등록된 실행 명령을 보여줍니다. npm run dev에서 Missing script: "dev"가 나오면 서버 문제가 아니라 현재 폴더의 package.json에 dev 스크립트가 없거나, 잘못된 폴더에서 명령을 실행한 것일 가능성이 큽니다.

Python 백엔드 예시#

bash
python -m venv .venv

# Windows PowerShell
.\.venv\Scripts\Activate.ps1

# macOS/Linux
source .venv/bin/activate

pip install -r requirements.txt
python app.py

프로젝트에 따라 flask run, uvicorn ..., python manage.py runserver처럼 실행 명령이 달라집니다.

Java/Spring 예시#

bash
# Windows
gradlew.bat bootRun

# macOS/Linux
./gradlew bootRun

문서에 적힌 실행 명령을 그대로 확인한 뒤 실행하는 습관이 중요합니다.

자주 사용하는 명령의 의미#

text
install
→ 필요한 패키지를 설치

run / start
→ 프로그램 실행

build
→ 배포 가능한 결과물 생성

test
→ 테스트 실행

lint
→ 코드 문법과 규칙 검사

환경변수#

환경에 따라 달라지는 값을 코드와 분리해 저장합니다.

예시:

text
API_BASE_URL=http://localhost:5000
DATABASE_URL=mysql://...
SECRET_KEY=...

주의:

  • .env는 GitHub에 올리지 않기
  • .env.example에는 변수 이름만 공유
  • 비밀번호, API Key, 토큰을 코드에 직접 작성하지 않기

  • 개인정보 보호
  • 모델 버전 변경 가능성

AI 개발 상식#

  • AI 응답은 항상 맞지 않음
  • 같은 입력에도 결과가 달라질 수 있음
  • 결과를 그대로 데이터베이스에 확정 저장하지 않음
  • 중요한 판단에는 검증 단계가 필요함
  • 비밀번호와 개인정보를 프롬프트에 넣지 않음
  • 모델 이름보다 평가 결과가 중요함
  • 좋은 프롬프트만으로 모든 문제가 해결되지 않음
  • 실패 시 사용자에게 재시도 또는 대체 방법을 제공해야 함

16. HTTP 상태 코드 기본 상식#

코드의미
200요청 성공
201데이터 생성 성공
204성공했지만 응답 본문 없음
400요청값이 잘못됨
401인증되지 않음
403인증은 되었지만 권한 없음
404주소 또는 데이터 없음
409중복 또는 충돌
422요청 형식은 맞지만 값 검증 실패
500서버 내부 오류

상태 코드만 보고 판단하지 않고 응답 본문과 서버 로그도 함께 확인합니다.

“코드가 안 돌아간다”면 먼저 구분하기#

text
설치가 안 됨
→ 언어/런타임/패키지 매니저 문제

명령 자체가 없음
→ 잘못된 폴더 또는 scripts/실행 설정 문제

서버는 켜졌지만 페이지 접속 안 됨
→ 포트/주소/방화벽/프로세스 문제

페이지는 뜨지만 데이터가 안 나옴
→ API/CORS/인증/백엔드/DB 문제

API는 성공하지만 화면이 이상함
→ 프론트 상태/렌더링/데이터 매핑 문제

오류 메시지를 보기 전에 코드를 많이 바꾸지 않습니다. 현재 어느 단계까지 정상인지부터 한 단계씩 확인합니다.

30. 최종 체크 — 이 문서를 이해했다면#

다음 질문을 자기 말로 설명할 수 있으면 충분합니다.

  • 요구사항과 구현 방법은 왜 다른가?
  • MVP를 먼저 정하는 이유는 무엇인가?
  • 사용자 흐름과 API 계약은 왜 코딩보다 먼저 필요한가?
  • 브랜치 전략은 왜 프로젝트마다 다를 수 있는가?
  • 환경변수는 왜 Git에 올리면 안 되는가?
  • 프론트·백엔드·AI가 각각 어디까지 책임지는가?
  • 오류가 났을 때 어느 계층부터 확인해야 하는가?
  • “내 컴퓨터에서 실행됨”과 “배포됨”은 무엇이 다른가?

모두 외우는 것이 목표가 아니라, 필요할 때 이 문서의 어느 장으로 돌아가야 하는지 아는 것이 목표입니다.
