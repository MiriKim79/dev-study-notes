1. 팀 개발은 혼자 개발과 무엇이 다른가#

혼자 개발할 때는 코드가 전부 내 머릿속에 있어 굳이 적어두지 않아도 됩니다. 여러 명이 같이 개발하면 상황이 달라집니다.

  • 내가 짠 코드를 다른 사람이 이해할 수 있어야 합니다.
  • 내 작업과 남의 작업이 같은 코드에서 충돌하지 않아야 합니다.
  • 프론트엔드가 기대하는 데이터 모양과 백엔드가 실제로 보내는 데이터 모양이 같아야 합니다.
  • 누가 무엇을 하고 있는지 서로 알아야 중복 작업이 없습니다.

이 문서는 실제 프로젝트가 진행되는 순서를 따라갑니다.

text
1. 요구사항·MVP 범위 정하기
2. 역할·작업 분배
3. Git·개발 환경 준비
4. 구현 (이슈/PR/코드리뷰로 소통하며)
5. 통합·테스트
6. 배포·회고

2. 요구사항 정리와 MVP 범위 정하기#

코드를 짜기 전에 팀 전체가 아래 질문에 답할 수 있어야 합니다.

text
1. 누가 사용하는 기능인가?
2. 사용자가 무엇을 할 수 있어야 하는가?
3. 성공한 상태는 무엇인가?
4. 어떤 데이터가 필요한가?
5. 다른 팀원의 작업과 어디에서 연결되는가?
6. 이번 기간 안에 반드시 구현할 범위는 어디까지인가?

이걸 건너뛰고 코딩부터 시작하면 프론트엔드와 백엔드의 데이터 형식이 서로 다르게 만들어지고, 같은 기능을 두 명이 각자 구현하고, 마지막에 합칠 때(통합) 많은 코드를 다시 써야 하는 문제가 자주 생깁니다.

MVP(Minimum Viable Product, 최소 기능 제품)란?#

"이것만 있으면 서비스가 성립한다"고 할 수 있는 최소 기능 묶음입니다. 예를 들어 온라인 강의 플랫폼이라면 회원가입·로그인·강의 목록·강의 상세·수강 신청·내 강의 확인 정도가 MVP이고, 찜하기·리뷰·결제·추천 시스템은 시간이 남을 때 추가합니다. 범위를 정할 때는 "없으면 서비스 흐름이 끊기는가", "현재 기간 안에 만들 수 있는가"를 기준으로 삼습니다.

사용자 흐름과 API를 먼저 표로 정리#

사용자가 서비스 안에서 움직이는 순서를 적고, 각 단계마다 필요한 화면과 API를 연결해 봅니다.

text
메인 접속 → 회원가입 → 로그인 → 강의 검색 → 강의 상세 → 수강 신청 → 마이페이지
사용자 행동프론트엔드 화면백엔드 기능
로그인로그인 페이지사용자 확인, 토큰 발급
강의 조회강의 목록강의 목록 조회
수강 신청수강 버튼수강 정보 저장

이 표만 있어도 프론트엔드와 백엔드가 서로 무엇을 기다리는지 알 수 있습니다.

작업 단위는 "로그인 완성하기"처럼 크게 잡지 않고, "로그인 입력창 만들기", "이메일 형식 검사 추가하기"처럼 몇 시간 안에 끝내고 확인할 수 있는 크기로 쪼갭니다. 그래야 팀원끼리 진행 상황을 짧게 공유할 수 있고, 한 사람이 며칠씩 브랜치를 붙들고 있다가 거대한 충돌을 만드는 일이 줄어듭니다.

추측으로 코드를 잇지 마세요. 특히 API 계약(요청/응답 필드명, 인증 방식, 오류 형식 등 프론트-백엔드 간 약속)은 "이 정도겠지"로 짜지 말고 팀원과 직접 확인합니다. API가 아직 확정되지 않았다면 프론트엔드는 아래처럼 더미 데이터로 화면을 먼저 만들고, 확정되는 대로 한 번에 정리합니다.

js
const mockCourse = { id: 1, title: "React 입문", price: 0 };

3. 역할 분담과 작업 공간 나누기#

3.1 역할 나누기#

보통 프론트엔드·백엔드·(있다면) AI 담당으로 나누고, 각자의 책임 범위는 이렇게 구분됩니다.

text
사용자 → 프론트엔드 화면 → 백엔드 API → DB / AI 모델 → 결과 정리 → 화면 표시
  • 프론트엔드: 입력 받기, 요청 보내기, 결과 표시, 로딩·오류 처리
  • 백엔드: 입력값 검증, 인증·권한 확인, DB 조회/저장, 결과 가공, 오류 응답
  • AI: 분류·추천·요약·생성 등 (프론트엔드가 AI API 키를 직접 쓰지 않고, 백엔드가 감싸서 호출)

각 분야의 기술 스택·개발 순서·체크리스트는 프론트엔드 기초 가이드 / 백엔드 기초 가이드 / 생성형 AI 기능 개발 기초 가이드를 참고하세요.

3.2 폴더 구조로 담당 구분#

파일 위치가 명확하면 팀원이 코드를 쉽게 찾고, 같은 기능을 중복 작성하지 않고, 파일 충돌도 줄어듭니다. 프론트엔드와 백엔드를 하나의 저장소에 담는 방식을 모노레포(Monorepo)라고 합니다.

text
project/
├── frontend/    # 프론트 담당자 폴더
├── backend/     # 백엔드 담당자 폴더
├── docs/        # 기획서, API 명세, 회의록
└── README.md

폴더 이름만 보고도 "이 파일은 누구 것인지" 구분되어 충돌이 줄어듭니다. 내부를 더 세부적으로 나누는 방법은 프론트엔드/백엔드 기초 가이드를 참고하세요.

4. Git·개발 환경 준비#

4.1 브랜치로 작업 공간 나누기#

저장소(Repository)는 프로젝트 코드 전체와 변경 이력이 저장되는 공간이고, 브랜치(Branch)는 그 안에서 각자 독립적으로 작업하는 작업선입니다. 여러 명이 main에 동시에 코드를 밀어 넣으면 서로의 작업이 뒤섞이므로, 각자 자기 브랜치에서 작업하고 끝나면 합칩니다.

text
main
└── develop
    ├── feat/frontend-auth
    ├── feat/backend-auth
    └── feat/course-api

하나의 정답 구조는 아니고, 브랜치 이름과 구성은 팀마다 다를 수 있는 예시입니다.

  • main: 배포 가능한 안정된 코드
  • develop: 각자의 기능을 모으는 기준 브랜치
  • feat/...: 기능 개발, fix/...: 오류 수정

작은 팀은 main + 기능 브랜치만 쓰는 더 단순한 구조도 충분합니다. 중요한 것은 브랜치 개수가 아니라 "어디서 갈라져서 어디로 합칠지"를 팀 전체가 같은 규칙으로 쓰는 것입니다. 브랜치 전략을 고르는 기준, merge/rebase 등 실제 Git 명령어는 Git·GitHub 기초 가이드를 참고하세요.

4.2 개발 환경 확인#

필요한 언어·버전, 패키지 매니저, 프로젝트 의존성, 환경변수 파일, 개발 서버 실행, DB 연결, .gitignore — 프로젝트를 열면 가장 먼저 확인합니다. 실제 실행 명령은 프로젝트마다 다르므로 저장소의 README, package.json, requirements.txt 같은 설정 파일을 먼저 확인하세요.

비밀번호·API 키처럼 환경마다 달라지는 값은 코드와 분리해 .env 파일에 두고, .env는 GitHub에 올리지 않습니다. 변수 이름만 담은 .env.example을 대신 공유합니다.

text
API_BASE_URL=http://localhost:5000
SECRET_KEY=...

5. 구현 — 소통하며 진행하기#

5.1 이슈 → 브랜치 → 커밋 → PR → 코드리뷰#

혼자 개발할 때는 필요 없던 소통 절차가 팀 개발에는 꼭 필요합니다.

  • 이슈(Issue): "무엇을 왜 해야 하는지"를 코드를 짜기 전에 짧은 글로 남기는 것. 이슈 번호(예: #12)로 이후 브랜치·커밋과 연결합니다.
  • Pull Request(PR): "내 브랜치를 기준 브랜치(develop 등)에 합쳐 달라"는 요청이자, 합치기 전에 다른 사람이 코드를 확인하는 자리. 무엇을 완료했고 무엇이 안 됐는지, 어떤 API/데이터 형식이 바뀌었는지 적어두면 리뷰가 빨라집니다.
  • 코드리뷰: 리뷰 없이 바로 머지하면 팀원이 서로 무슨 코드가 들어왔는지 모른 채 작업하게 되고 오류가 뒤늦게 발견됩니다. 작은 팀이라도 최소 한 명은 merge 전에 diff를 훑어보는 규칙을 두는 것이 좋습니다.
bash
# 작업 시작
git switch develop
git pull origin develop
git switch -c feat/기능명

# 작업 종료
git add 변경파일
git commit -m "Feat: 기능 설명"
git push -u origin feat/기능명
# → GitHub에서 develop으로 Pull Request 생성

5.2 매일 공유해야 하는 것#

  • 지금 어떤 기능을 작업 중인지, 어떤 파일을 수정했는지
  • API나 데이터 구조가 바뀌었는지
  • 머지 가능한 상태인지, 아직 해결 못 한 문제가 있는지

특히 공통 파일 수정, API 필드 변경, DB 컬럼 변경, 패키지 추가, 환경변수 추가는 반드시 팀원에게 알립니다.

text
작업 브랜치: feat/frontend-auth
완료: 로그인 화면과 입력값 검증
미완료: 실제 로그인 API 연결
변경 파일: LoginPage.jsx
필요한 정보: 로그인 요청·응답 필드

5.3 충돌 방지#

같은 부분을 두 사람이 고쳐서 Git이 자동으로 합치지 못하는 상태를 충돌(Conflict)이라고 합니다. 여러 명이 코드를 같이 쓰면 자연히 생기는 상황이지만, 아래 습관으로 빈도와 크기를 줄일 수 있습니다.

  • 브랜치를 오래 붙들지 않고 작은 단위로 자주 머지한다.
  • 작업 시작 전 develop을 최신 상태로 pull 한다.
  • 여러 사람이 같이 건드리는 공통 파일은 미리 "누가 언제 수정할지" 정해두거나 수정 전 팀원에게 알린다.
  • 다른 팀원이 작업 중인 파일을 알림 없이 함부로 고치지 않는다.

충돌이 나면 당황하지 말고 어느 부분이 겹쳤는지 확인한 뒤 팀원과 함께 어떤 코드를 남길지 정합니다. 실제 충돌 해결 명령어는 Git·GitHub 기초 가이드를 참고하세요.

5.4 구현 중 행동 요령#

작업 시작 전: 현재 브랜치 확인 → 최신 develop pull → 오늘 할 작업 한두 개 결정 → 관련 API 확인 → 공통 파일을 건드리는 작업인지 확인

작업 중: 작은 단위로 구현하고 바로 실행해서 확인 → 오류 메시지 끝까지 읽기 → 이해 못 한 코드는 바로 질문 → 다른 팀원 파일을 함부로 수정하지 않기 → 기능 단위로 커밋

작업 종료 전: 정상 동작과 잘못된 입력 모두 확인 → Console/서버 로그 확인 → 다른 화면·API가 깨지지 않았는지 확인 → 커밋·push → 변경 내용 팀에 공유

5.5 AI 코딩 도구를 팀 프로젝트에서 쓸 때#

AI에게 코드를 요청할 때는 프로젝트 목적, 기술 스택, 관련 파일 코드, 기대하는 동작을 함께 알려줘야 팀 프로젝트의 기존 구조에 맞는 코드가 나옵니다. AI가 준 코드도 팀원 코드와 똑같이 다루세요 — 실제로 실행해보고, 무슨 코드인지 설명할 수 있어야 하고, 리뷰 없이 바로 develop이나 main에 머지하지 않습니다. 비밀번호·API Key를 AI에게 입력하지 않고, 존재하지 않는 API를 사실처럼 쓰지 않고, 전체 구조를 이해하지 못한 채 대규모 수정을 허용하지 않습니다.

5.6 하지 말아야 할 행동#

  • 요구사항 확인 없이 코딩 시작
  • main/develop에서 직접 기능 개발
  • 여러 기능을 한 커밋에 모두 넣기
  • 팀원 코드를 무단으로 삭제하거나 API 필드를 혼자 임의로 확정
  • 비밀번호·API Key를 GitHub에 업로드
  • 작동하지 않는 코드를 머지, 이해하지 못한 AI 코드를 그대로 사용

6. 통합·테스트#

각자 만든 기능을 합쳐서 전체가 함께 동작하는지 확인하는 단계입니다. 오류가 나면 코드를 무작정 바꾸지 않고 순서대로 확인합니다.

text
1. 오류를 다시 재현한다
2. 오류 메시지를 정확히 읽는다
3. 어느 영역의 문제인지 구분한다 (화면 / Console / Network / 서버 로그 / DB)
4. 가장 작은 원인부터 확인하고, 한 번에 하나만 고친다
5. 다시 재현해서 고쳐졌는지 확인한다

팀원에게 질문할 때는 아래 형식이면 훨씬 빨리 도움을 받습니다.

text
하려던 작업:
실행한 명령:
예상 결과 / 실제 결과:
오류 메시지 전체:
현재 브랜치:
이미 시도한 방법:

자주 보는 상태 코드: 400(요청값 오류), 401(인증 안 됨), 403(권한 없음), 404(없음), 500(서버 오류). 상태 코드만 보고 판단하지 말고 응답 본문과 서버 로그도 함께 확인합니다. 더 자세한 디버깅 절차와 도구는 각 분야 가이드를 참고하세요.

7. 배포와 회고#

빌드는 배포 가능한 결과물을 만드는 것이고, 배포는 실제로 다른 사용자가 접속할 수 있는 서버에 올리는 것입니다. 배포 전에는 운영용 환경변수, DB 연결, 프론트 API 주소, CORS, 포트, 로그, 비밀값 노출 여부를 팀 전체가 체크리스트로 확인합니다. 세부 배포 절차는 프로젝트 환경에 따라 다르므로 각 분야 가이드를 참고하세요.

프로젝트가 끝나면 잘된 점, 어려웠던 점, 다시 한다면 바꿀 순서, 팀 협업에서 개선할 점, AI가 실제로 도움이 된 부분/문제가 됐던 부분을 짧게 기록합니다. 회고는 실패를 기록하는 문서가 아니라 다음 프로젝트의 시행착오를 줄이는 문서입니다.

8. 직접 실습해보기 — 이슈부터 PR까지 미니 시나리오#

GitHub에 연습용 Public 저장소 하나를 만들어서, 이 문서에서 배운 흐름(이슈 → 브랜치 → 커밋 → PR → merge)을 처음부터 끝까지 한 번 따라가 봅니다.

1단계. 이슈 만들기#

GitHub 저장소 → Issues 탭 → New issue에서 작성합니다.

text
제목: README에 프로젝트 소개 한 줄 추가
본문:
- 목적: 저장소를 처음 보는 사람이 무슨 프로젝트인지 알 수 있게 한다
- 완료 조건: README.md 맨 위에 한 줄 소개 문구가 있다

2단계. 브랜치 만들고 작업하기#

bash
git switch -c docs/readme-intro-#1

README.md 맨 위에 한두 줄 소개 문구를 추가합니다.

3단계. 커밋하고 push#

bash
git add README.md
git commit -m "Docs: README에 프로젝트 소개 추가 (#1)"
git push -u origin docs/readme-intro-#1

커밋 메시지에 이슈 번호(#1)를 넣으면 GitHub이 이슈와 커밋을 자동으로 연결해줍니다.

4단계. PR 만들기#

text
제목: Docs: README에 프로젝트 소개 추가
본문: Closes #1

Closes #1을 본문에 적으면 이 PR이 merge될 때 이슈가 자동으로 닫힙니다.

5단계. merge하고 정리#

bash
git switch main
git pull
git branch -d docs/readme-intro-#1
정답 확인

아래 항목을 스스로 체크해보세요. 전부 "예"라면 이 실습을 제대로 끝낸 것입니다.

  • ☐ 코드를 작성하기 전에 이슈를 먼저 만들어 "무엇을, 왜" 할지 글로 남겼다
  • ☐ 이슈 번호가 포함된 브랜치 이름(docs/readme-intro-#1)으로 작업했다
  • ☐ 커밋 메시지에 이슈 번호를 넣어 GitHub에서 커밋과 이슈가 연결된 것을 확인했다
  • ☐ PR 본문에 Closes #1을 적었고, merge 후 이슈가 자동으로 닫히는 것을 확인했다
  • ☐ merge 후 사용한 브랜치를 삭제해 브랜치 목록을 깔끔하게 정리했다
  • ☐ 이슈 → 브랜치 → 커밋 → PR → merge, 이 다섯 단계가 왜 이 순서로 이어지는지 설명할 수 있다
