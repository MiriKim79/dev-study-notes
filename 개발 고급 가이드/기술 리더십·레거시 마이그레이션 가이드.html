🧭 개발 고급 가이드

기술 리더십·레거시 마이그레이션 가이드

코드는 잘 짜는데 팀을 어떻게 이끌지 모르겠다? 기술 결정과 낡은 코드 전환의 기준을 다룹니다.

📘 문서 소개
대상: 코드는 문제없이 짜지만, 기술 결정을 직접 내리거나 낡은 코드를 어떻게 바꿔야 할지 판단해야 하는 위치가 된 사람
목적: 기술 의사결정을 기록하고 공유하는 방법, 레거시 코드를 안전하게 단계적으로 전환하는 전략을 정리합니다

0. 시작 전에 — 자주 나오는 용어#

중급 가이드에서 다룬 코드 리뷰·회고 개념은 이미 안다고 가정합니다. 여기서는 이 문서에서 새로 나오는 용어만 정리합니다.

용어쉬운 설명
ADR (Architecture Decision Record)중요한 기술 결정을 "왜 그렇게 정했는지"까지 남기는 짧은 기록 문서
기술 부채(Technical Debt)지금 당장은 동작하지만 나중에 시간을 들여 손봐야 할 임시방편 코드나 설계
레거시 코드(Legacy Code)오래돼서 지금 기준으로는 손대기 어렵거나 이해하기 힘든, 그러나 여전히 운영 중인 코드
스트랭글러 패턴(Strangler Fig Pattern)낡은 시스템을 한 번에 다 바꾸지 않고, 새 시스템이 기능 단위로 조금씩 감싸며 대체해가는 전환 방법
RFC (Request for Comments)실행 전에 팀 전체 의견을 모으기 위해 작성·공유하는 기술 제안 문서
영향력 행사(Influence without Authority)직급상 지시 권한이 없어도, 근거와 신뢰로 다른 사람의 결정에 영향을 주는 것
포스트모템(Postmortem)장애가 끝난 뒤 원인과 재발 방지책을 남기는 회고 문서
기능 플래그(Feature Flag)코드를 배포한 뒤에도 특정 기능을 켜고 끌 수 있게 만드는 스위치

1. "내가 제일 잘 짠다"에서 "팀이 잘 짜게 만든다"로#

주니어일 때 좋은 개발자의 기준은 "내가 얼마나 잘 짜는가"입니다. 기술적 결정을 내리는 위치가 되면 기준이 바뀝니다 — "내가 없어도 팀이 같은 기준으로 판단할 수 있는가"가 됩니다.

text
주니어 관점: 이 코드를 어떻게 짤까
리드 관점: 이 결정을 왜 이렇게 내렸는지 다른 사람이 6개월 뒤에도 이해할 수 있을까

기본 상식: 좋은 기술 결정은 "정답을 아는 것"이 아니라 "트레이드오프를 명확히 하고, 그 근거를 남기는 것"입니다. 완벽한 결정은 없고, 대신 나중에 왜 그렇게 결정했는지 추적 가능해야 합니다.

2. ADR(Architecture Decision Record)로 결정 기록하기#

중요한 기술 결정을 할 때마다 짧은 문서로 남깁니다.

markdown
# ADR 007: 세션 저장소를 Redis로 변경

## 상태: 승인됨 (2026-08-01)

## 배경
서버를 2대 이상으로 확장해야 하는데, 세션이 서버 메모리에 있어 수평 확장이 막힘

## 검토한 대안
1. 서버 메모리 유지 + Sticky Session (로드밸런서가 같은 서버로만 보냄)
2. Redis로 세션 이전
3. JWT로 전환해 세션 자체를 없앰

## 결정
2번(Redis) 선택

## 이유
- 1번은 특정 서버 장애 시 그 서버의 세션이 전부 로그아웃됨
- 3번은 세션 무효화(로그아웃)가 어려워짐 — 현재 로그아웃 요구사항과 충돌
- Redis는 도입 비용이 적고 세션 무효화도 그대로 유지 가능

## 결과로 감수하는 것
Redis 장애 시 전체 로그인이 영향받음 → Redis를 이중화(replica)로 운영하기로 결정

기본 상식: ADR의 핵심은 "결정"이 아니라 "검토했지만 선택하지 않은 대안과 그 이유"입니다. 나중에 "왜 Redis를 안 쓰고 다른 걸 썼냐"는 질문에 새로 오는 팀원도 이 문서 하나로 답을 찾을 수 있어야 합니다.

ADR 상태(Status)를 관리하기#

ADR은 한 번 쓰고 끝이 아니라 상태가 바뀝니다.

상태의미
제안됨(Proposed)논의 중, 아직 확정 아님
승인됨(Accepted)현재 적용된 결정
폐기됨(Deprecated)더 이상 유효하지 않지만 기록은 남김
대체됨(Superseded by ADR-0xx)다른 ADR로 교체됨 — 어느 문서로 이어지는지 링크

실무 팁: ADR을 지웠다가 나중에 "그때 왜 이걸 안 썼지?"를 다시 논의하는 팀을 많이 봅니다. 오래된 결정도 지우지 말고 "폐기됨/대체됨"으로 표시만 바꿔 이력을 남깁니다.

3. 기술 부채를 다루는 방법#

기술 부채는 "나쁜 코드"가 아니라 "지금 당장의 속도를 위해 나중으로 미룬 비용"입니다. 문제는 부채 자체가 아니라, 그걸 아무도 기록하지 않고 잊는 것입니다.

text
기록하지 않은 부채: "언젠가 저 부분 고쳐야 하는데" → 아무도 언제 왜인지 기억 못 함 → 영원히 방치
기록한 부채: 이슈로 등록 + "이 조건이 되면 반드시 처리" 명시 → 우선순위 회의에서 계속 재검토됨

기본 상식: 모든 기술 부채를 당장 갚을 필요는 없습니다. 다만 "이 부채가 얼마나 위험한지"(자주 건드리는 코드인가, 버그가 잦은가)와 "갚는 비용"을 함께 기록해두면, 팀이 우선순위를 판단할 수 있는 근거가 됩니다.

기술 부채 사분면으로 우선순위 정하기#

모든 부채를 같은 무게로 다루면 아무것도 못 갚습니다. "영향도"와 "빈도"로 나눠 우선순위를 정합니다.

자주 건드리는 코드가끔 건드리는 코드
위험도 높음(버그·장애 잦음)최우선 — 다음 스프린트에 처리다음 분기 계획에 포함
위험도 낮음(안정적)리팩터링 규칙 정해두고 손댈 때마다 조금씩굳이 지금 안 갚아도 됨

실무 팁: "언젠가 시간 나면 고치자"는 사실상 "안 고친다"와 같습니다. 부채를 이슈로 등록할 때는 반드시 "이걸 방치하면 생기는 구체적 비용"(배포 시간 증가, 신규 기능 추가 시 예상 공수)을 함께 적어, 우선순위 논의에서 근거로 쓸 수 있게 합니다.

4. 레거시 코드를 단계적으로 바꾸는 전략#

스트랭글러 패턴(Strangler Fig Pattern)#

한 번에 다 바꾸는 "대개편"은 실패 확률이 매우 높습니다. 대신 새 시스템이 낡은 시스템을 조금씩 감싸며 대체합니다. 이름처럼 담쟁이 넝쿨(strangler fig)이 나무를 천천히 감싸며 대체하듯, 낡은 시스템을 기능 단위로 조금씩 새 시스템으로 옮깁니다.

text
1단계: 프록시(라우터)를 앞에 두고, 모든 요청은 여전히 레거시로 전달
2단계: 새로 만든 기능(예: 결제 모듈)만 새 시스템으로 라우팅
3단계: 레거시의 해당 기능은 죽은 코드가 됨 — 트래픽이 없음을 확인 후 제거
4단계: 다음 기능으로 반복 → 모든 기능이 이전되면 낡은 시스템 제거

기본 상식: 이 패턴의 핵심은 "언제든 중단해도 서비스가 절반은 정상 동작한다"는 것입니다. 대개편(Big Bang Rewrite)은 프로젝트가 중간에 중단되면 이도 저도 아닌 상태가 되지만, 스트랭글러 패턴은 각 단계가 끝날 때마다 실제로 가치를 전달합니다.

"왜 이 코드가 이렇게 짜여 있는지" 먼저 이해하기#

text
성급한 접근: "이 코드 이상하네, 갈아엎자" → 숨겨진 이유(과거의 특정 버그 회피, 특이 케이스 처리)를 놓치고 재발
신중한 접근: 테스트를 먼저 추가해 현재 동작을 고정 → 그 다음 리팩터링 → 테스트가 계속 통과하는지 확인

기본 상식: 레거시 코드를 "누가 이따위로 짰지"라고 생각하기 전에, 그 코드가 해결했던 실제 문제(버그, 요구사항)가 있었을 가능성을 먼저 의심합니다. 테스트로 현재 동작을 고정한 뒤에 손대면, 실수로 그 숨은 이유를 깨뜨릴 위험이 줄어듭니다.

병렬 실행(Parallel Run)으로 안전하게 검증하기#

새 시스템으로 완전히 전환하기 전, 옛 시스템과 새 시스템을 동시에 돌려 결과를 비교하는 방법입니다.

text
1. 요청을 옛 시스템으로 처리하고 응답은 그대로 사용자에게 반환
2. 동시에 같은 요청을 새 시스템에도 보내 결과만 기록(사용자에게는 영향 없음)
3. 두 결과를 비교해 불일치 건을 로그로 수집
4. 불일치가 일정 기간 0에 가까워지면 실제 트래픽을 새 시스템으로 전환

실무 팁: 이 방식을 "섀도 트래픽(Shadow Traffic)"이라고도 부릅니다. 결제·정산처럼 실수 비용이 큰 도메인일수록 전환 전에 반드시 이 검증 단계를 거칩니다.

5. 결정을 팀에 공유하는 방법#

  • 결론만 통보하지 않고, 검토한 대안과 트레이드오프를 함께 공유
  • "왜 이 방식이 아닌지"를 먼저 설명하면 반복되는 질문이 줄어듦
  • 결정에 영향받는 사람에게는 결정 *전에* 의견을 구함 — 결정 후 통보는 신뢰를 깎음
  • 중요한 결정일수록 글로 남겨서, 그 자리에 없었던 사람도 나중에 맥락을 알 수 있게 함

RFC(Request for Comments)로 큰 결정을 사전 검토받기#

영향 범위가 큰 결정(DB 교체, 아키텍처 변경)은 결정하고 나서 공유하는 대신, 결정하기 *전에* 초안을 공유해 의견을 모읍니다.

text
1. 문제 정의 + 제안하는 방향을 짧은 문서로 작성해 공유
2. 정해진 기간(예: 3일) 동안 댓글로 의견 수렴
3. 반대 의견은 무시하지 않고 문서에 "검토했으나 채택하지 않음 + 이유"로 기록
4. 기간이 끝나면 최종 결정 확정 → ADR로 전환해 보관

기본 상식: RFC의 목적은 "만장일치"가 아니라 "모두가 반대 의견을 낼 기회를 가졌는가"입니다. 나중에 문제가 생겨도 "그때 의견 낼 기회는 있었다"는 것 자체가 팀의 신뢰를 지킵니다.

권한 없이 영향력 행사하기 (Influence without Authority)#

시니어라고 항상 결정권이 있는 건 아닙니다. 다른 팀·다른 직군을 설득해야 할 때 쓰는 방법입니다.

  • 내 입장이 아니라 상대의 목표를 먼저 파악하고, 그 목표에 내 제안이 어떻게 도움이 되는지 연결
  • 추상적 주장 대신 숫자와 사례로 설득 (예: "느려요" 대신 "이 API가 P95 기준 1.2초로, 목표 300ms를 4배 초과")
  • 한 번에 설득하려 하지 않고, 작은 실험(파일럿)으로 증거를 먼저 만든 뒤 확대 제안
  • 반대 의견을 "틀렸다"고 하지 않고, 그 의견이 옳은 조건을 먼저 인정한 뒤 다른 조건을 제시

6. 마이그레이션 리스크 관리#

레거시 전환은 기능 구현보다 "실패했을 때 되돌릴 수 있는가"가 더 중요합니다.

롤백 가능한 배포 설계#

전략설명되돌리는 방법
기능 플래그코드는 배포하되 플래그로 켜고 끔플래그만 끄면 즉시 원복
블루-그린 배포신/구 버전을 동시에 띄워두고 트래픽만 전환로드밸런서를 구버전으로 재전환
카나리 배포신버전에 트래픽 일부(예: 5%)만 먼저 보냄이상 감지 시 카나리 비율을 0으로
데이터 마이그레이션신/구 스키마를 동시에 유지하며 점진 이관구 스키마가 남아있는 동안은 복구 가능
text
위험한 마이그레이션: 스키마 변경 + 코드 배포 + 데이터 이관을 한 번에 실행 → 실패 시 되돌리기 매우 어려움
안전한 마이그레이션: 각 단계를 분리해 하나씩 배포 → 문제 생긴 단계만 롤백

실무 팁: 마이그레이션 계획을 세울 때 "성공했을 때 무엇을 할지"만큼 "3단계에서 실패하면 어떻게 되돌릴지"를 먼저 적어둡니다. 롤백 절차가 없는 마이그레이션 계획은 계획이 아니라 도박입니다.

데이터 마이그레이션의 이중 쓰기(Dual Write)#

text
1단계: 새 코드가 기존 테이블과 새 테이블에 동시에 씀(이중 쓰기)
2단계: 배치 작업으로 과거 데이터를 새 테이블로 백필(backfill)
3단계: 두 테이블의 데이터 일치 여부를 검증
4단계: 읽기를 새 테이블로 전환
5단계: 일정 기간 안정성 확인 후 기존 테이블/이중 쓰기 코드 제거

주의: 이중 쓰기 중 한쪽 쓰기만 실패하면 두 테이블이 어긋납니다. 반드시 실패 시 재시도·알림 로직을 넣고, 최종적으로 데이터 정합성 검증 스크립트를 돌려 확인합니다.

7. 포스트모템(Postmortem)으로 배우는 조직 만들기#

장애는 없앨 수 없지만, 같은 장애가 반복되는 것은 막을 수 있습니다.

markdown
## 장애 요약
2026-07-20 14:32~14:51 (19분) 결제 API 응답 지연으로 주문 실패율 12% 발생

## 타임라인
14:32 배포 완료 직후 응답 지연 알람 발생
14:35 담당자 확인, 원인 파악 중
14:41 신규 배포 롤백 결정
14:51 정상화 확인

## 근본 원인
새로 추가한 로그 기록 코드가 매 요청마다 동기적으로 외부 로그 서버를 호출 → 로그 서버 지연이 결제 API 지연으로 전파

## 재발 방지 액션
1. 로그 전송을 비동기 큐로 변경 (담당: 홍길동, 기한: 8/25)
2. 외부 호출에 타임아웃 미설정된 곳 전수 점검 (담당: 김철수, 기한: 8/30)
3. 배포 후 15분간 핵심 지표 자동 모니터링 알람 추가 (담당: 이영희, 기한: 9/5)

기본 상식: 좋은 포스트모템은 "누가 실수했나"를 찾지 않습니다(비난 없는 포스트모템, Blameless Postmortem). 사람은 실수할 수 있다는 전제 위에서, "왜 이 실수가 시스템에 그대로 전파됐는가"를 고칩니다. 담당자를 처벌하는 문화에서는 다음부터 아무도 장애를 솔직하게 보고하지 않습니다.

8. 자주 하는 실수#

  • 중요한 기술 결정을 회의에서 구두로만 논의하고 기록을 남기지 않음
  • 기술 부채를 "알고 있다"로만 두고 이슈로 등록하지 않아 계속 방치됨
  • 레거시 시스템을 한 번에 다 바꾸려다 프로젝트가 중단됨(대개편의 함정)
  • 테스트 없이 레거시 코드를 리팩터링해서 숨은 동작을 깨뜨림
  • 팀원에게 결정 이유를 설명하지 않고 결과만 통보
  • 마이그레이션 계획에 롤백 절차 없이 진행 단계만 적음
  • 포스트모템에서 담당자를 비난해, 다음부터 문제를 숨기는 문화가 됨
  • RFC 기간 없이 이미 정해진 결정을 "의견 수렴"이라는 이름으로 형식만 갖춤

9. 팀 성장을 위한 코드 리뷰 리더십#

시니어 개발자의 리뷰는 코드 정확성뿐 아니라 팀 전체의 실력을 끌어올리는 도구이기도 합니다.

text
- "왜 이렇게 하면 안 되는지"를 링크(문서, 이전 장애 사례)와 함께 설명
- 같은 실수가 반복되면 개인 코멘트 대신 팀 전체 가이드 문서를 만들어 공유
- 주니어의 좋은 시도는 구체적으로 칭찬 — 무엇이 왜 좋았는지 짚어줌
- 모든 걸 직접 고쳐주지 않고, 스스로 답을 찾을 수 있는 질문을 던짐
  ("이 함수가 null을 받으면 어떻게 될까요?")

실무 팁: 코드 리뷰에서 반복적으로 지적하는 패턴이 3번 이상 나온다면, 그건 개인의 실수가 아니라 팀의 가이드나 린트 규칙이 부족하다는 신호입니다. 사람이 매번 기억해야 하는 규칙은 가능한 한 자동 검사(ESLint 규칙, CI 체크)로 옮깁니다.

10. 실전 체크리스트#

  • 중요한 기술 결정마다 검토한 대안과 이유를 기록으로 남기는가(ADR)
  • ADR의 상태(제안/승인/폐기/대체)를 갱신하며 관리하는가
  • 기술 부채가 이슈로 등록되고, 영향도·빈도 기준으로 우선순위가 논의되는가
  • 레거시 전환을 한 번의 대개편이 아니라 기능 단위 단계적 전환으로 계획했는가
  • 레거시 코드를 고치기 전에 현재 동작을 고정하는 테스트를 먼저 추가했는가
  • 위험도 높은 전환은 병렬 실행(섀도 트래픽)으로 먼저 검증했는가
  • 마이그레이션 계획에 각 단계별 롤백 절차가 명시돼 있는가
  • 큰 결정 전에 RFC로 의견을 미리 수렴했는가
  • 결정에 영향받는 사람에게 결정 전에 의견을 구했는가
  • 장애 후 비난 없는 포스트모템으로 재발 방지 액션을 기록하고 담당자·기한을 정했는가
