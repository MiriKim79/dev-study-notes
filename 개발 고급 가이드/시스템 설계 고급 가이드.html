시스템 설계 고급 가이드

서버 한 대로는 더 이상 안 된다? MSA와 이벤트 기반 설계로 넘어갈 때 필요한 판단 기준입니다.

0. 시작 전에 — 자주 나오는 용어#

중급 가이드까지 다룬 API 서버·캐싱·N+1 등의 개념은 이미 안다고 가정합니다. 고급 가이드는 처음 보는 용어가 특히 많이 나오므로, 각 문서 맨 앞에 그 문서에서 쓰는 용어를 정리해둡니다.

용어쉬운 설명
모놀리식(Monolithic)하나의 코드베이스·하나의 서버로 모든 기능을 처리하는 구조
MSA (Microservice Architecture)기능을 여러 개의 독립된 작은 서비스로 나눠서 운영하는 구조
도메인(Domain)"결제", "수강 신청"처럼 실제 업무 단위를 기준으로 나눈 영역. 기술 계층이 아니라 업무 기준으로 나누는 것을 의미
동기 통신(Synchronous)요청을 보낸 쪽이 응답이 올 때까지 기다리는 통신 방식
비동기 통신(Asynchronous)요청만 보내고 결과를 기다리지 않는 통신 방식. 나중에 별도로 처리됨
메시지 브로커(Message Broker)여러 서비스 사이에서 이벤트·메시지를 전달해주는 중간 시스템(Kafka, RabbitMQ 등)
장애 전파(Cascading Failure)한 서비스의 장애가 그 서비스를 호출하는 다른 서비스까지 연쇄적으로 무너뜨리는 현상
서킷 브레이커(Circuit Breaker)실패가 잦은 서비스에는 잠시 요청을 보내지 않고 회복할 시간을 주는 장치
재시도 폭풍(Retry Storm)느려진 서비스에 여러 클라이언트가 동시에 재시도를 몰아넣어 부하가 오히려 더 커지는 현상
분산 트랜잭션여러 서비스(여러 데이터베이스)에 걸친 작업을 하나의 트랜잭션처럼 안전하게 처리하는 것
Saga 패턴분산 트랜잭션을 여러 단계로 나눠 실행하고, 실패하면 이전 단계를 거꾸로 취소(보상)하는 방식
보상 트랜잭션(Compensating Transaction)이미 실행된 작업을 되돌리기 위해 실행하는 "취소" 작업
최종 일관성(Eventual Consistency)지금 당장은 데이터가 서로 다를 수 있지만, 시간이 지나면 결국 같은 값으로 맞춰진다는 개념

1. 모놀리식을 먼저 의심하지 않기#

MSA(Microservice Architecture)는 "요즘 트렌드"가 아니라 모놀리식으로 감당이 안 될 때 쓰는 해결책입니다. 순서가 반대로 되면 안 됩니다.

text
잘못된 순서: 처음부터 MSA로 설계 → 서비스 3개인데 통신·배포·모니터링 복잡도만 3배
맞는 순서: 모놀리식으로 시작 → 실제로 아래 신호가 나타나면 그때 분리 검토

분리를 검토할 신호

  • 팀이 커져서 한 저장소에 여러 팀이 동시에 배포하려다 서로 막힘
  • 특정 기능(예: 결제)만 트래픽이 튀는데 전체 서버를 다 같이 확장해야 함
  • 한 기능의 장애(메모리 누수 등)가 관련 없는 다른 기능까지 전부 죽임

기본 상식: "언젠가 커질 수도 있으니 미리 MSA로" 는 대부분 손해로 끝납니다. 모놀리식 안에서도 모듈 경계(폴더·패키지 분리)를 잘 지키면, 나중에 분리할 때 그 경계를 그대로 서비스 경계로 옮기면 됩니다. 지금 당장 잘 나뉜 모놀리식이 나중에 잘 나뉜 MSA가 됩니다.

2. 서비스 경계를 나누는 기준#

기술 기준(이 코드는 프론트, 이 코드는 백엔드)이 아니라 업무 기준(도메인)으로 나눕니다.

text
나쁜 예: user-db-service, user-api-service, user-cache-service
→ 기술 계층으로 나뉘어서 기능 하나 고칠 때마다 3개 서비스를 같이 배포해야 함

좋은 예: user-service, course-service, payment-service, notification-service
→ "수강 신청"이라는 하나의 기능 변경이 대부분 course-service 안에서 끝남

각 서비스는 자기 데이터베이스를 따로 가집니다. 다른 서비스의 테이블에 직접 SQL을 날리지 않고, 반드시 API(또는 이벤트)를 통해서만 접근합니다. 이게 지켜지지 않으면 서비스는 나눴는데 실제로는 여전히 하나의 거대한 시스템(분산 모놀리식)이 됩니다.

3. 서비스 간 통신 — 동기 vs 비동기#

동기 통신 (REST, gRPC)#

text
주문 서비스 → (즉시 응답 필요) → 재고 서비스: "재고 있어?"

응답이 바로 필요할 때 씁니다. 대신 재고 서비스가 느려지거나 죽으면 주문 서비스도 같이 느려지거나 실패합니다(장애 전파).

비동기 통신 (메시지 큐, 이벤트)#

text
주문 서비스 → "주문 완료" 이벤트 발행 → 메시지 브로커(Kafka, RabbitMQ 등)
                                          ├→ 알림 서비스가 구독해서 이메일 발송
                                          └→ 정산 서비스가 구독해서 매출 집계

주문 서비스는 이벤트만 발행하고 끝입니다. 알림 서비스가 지금 죽어있어도 주문은 성공하고, 알림 서비스가 살아나면 밀린 이벤트를 처리합니다. 응답이 즉시 필요 없는 후속 작업에 적합합니다.

기본 상식: 모든 통신을 이벤트 기반으로 바꾸는 게 목표가 아닙니다. "지금 바로 결과를 알아야 하는가?"로 나눕니다 — 결제 승인처럼 결과를 바로 알아야 하면 동기, 알림 발송·통계 집계처럼 나중에 처리해도 되면 비동기입니다.

4. 장애 격리 — 한 서비스의 장애가 전체로 번지지 않게#

타임아웃#

호출한 서비스가 응답이 없을 때 무한정 기다리지 않고 일정 시간 뒤 포기합니다. 타임아웃이 없으면, 느려진 서비스 하나 때문에 호출한 쪽 스레드가 전부 그 응답을 기다리다 함께 멈춥니다.

서킷 브레이커(Circuit Breaker)#

text
정상 상태(Closed) → 요청 정상 통과
   ↓ 실패율이 임계치를 넘으면
차단 상태(Open) → 일정 시간 동안 요청을 보내지 않고 즉시 실패 처리
   ↓ 일정 시간 후
반열림 상태(Half-Open) → 요청 몇 개만 시험 삼아 보내봄 → 성공하면 다시 Closed

죽어가는 서비스에 계속 요청을 보내면 그 서비스가 살아날 기회조차 없이 더 죽습니다. 서킷 브레이커는 "이미 실패하고 있는 서비스"에는 잠시 요청을 끊어서 회복할 시간을 줍니다.

재시도(Retry) — 그러나 신중하게#

일시적인 네트워크 오류는 재시도로 해결되지만, 재시도 자체가 장애를 더 키우기도 합니다.

기본 상식: 이미 트래픽이 몰려서 느려진 서비스에 모든 클라이언트가 동시에 재시도하면 요청량이 오히려 폭증합니다(재시도 폭풍). 재시도 간격에 무작위성을 섞고(Exponential Backoff + Jitter), 재시도 횟수 상한을 반드시 둡니다.

5. 데이터 일관성 — 분산 트랜잭션 문제#

한 서비스 안에서는 DB 트랜잭션으로 "전부 성공 또는 전부 실패"를 보장할 수 있지만, 여러 서비스에 걸친 작업은 그게 안 됩니다.

text
예: 주문 생성(주문 서비스) → 재고 차감(재고 서비스) → 결제 승인(결제 서비스)
중간에 결제가 실패하면? 이미 만들어진 주문과 차감된 재고는 어떻게 되돌리나?

Saga 패턴: 각 단계를 별도 트랜잭션으로 실행하고, 실패하면 지금까지 실행된 단계를 역순으로 "취소하는 보상 작업(Compensating Transaction)"을 실행합니다.

text
주문 생성 → 재고 차감 → 결제 승인 (실패!)
          ← 재고 복구  ← (보상 시작)
← 주문 취소

기본 상식: 완벽한 원자성(전부 성공 또는 전부 실패가 한순간에 보장되는 것)은 분산 시스템에서 비용이 매우 큽니다. 대신 "결국은 맞게 정리된다"는 최종 일관성(Eventual Consistency)을 받아들이고, 그 사이 잠깐의 불일치를 사용자에게 어떻게 보여줄지(예: "결제 확인 중") 설계하는 쪽이 현실적입니다.

6. 언제 쓰고 언제 쓰지 않는가#

상황권장
팀 5명 이하, 트래픽 예측 가능모놀리식 유지, 코드 안에서 모듈 경계만 명확히
특정 기능만 트래픽이 튀고 나머지는 안정적그 기능만 먼저 분리 (전체 MSA 전환 X)
여러 팀이 동시에 서로 다른 배포 주기로 일해야 함MSA 분리 검토
강한 정합성이 반드시 필요한 결제·잔액 처리가능하면 하나의 서비스·트랜잭션 안에서 처리

7. 자주 하는 실수#

  • 팀 규모·트래픽 근거 없이 "MSA가 정답"이라 믿고 처음부터 잘게 쪼갬
  • 서비스는 나눴지만 다른 서비스의 DB를 직접 조회 — 사실상 분산 모놀리식
  • 타임아웃·서킷 브레이커 없이 동기 호출만 연쇄적으로 연결 (장애 전파)
  • 분산 트랜잭션 실패 시 보상 로직 없이 "일단 성공한 부분은 그대로 둠"
  • 재시도 로직에 상한·백오프 없이 무한 재시도

8. 실전 체크리스트#

  • 지금 이 서비스를 분리해야 하는 구체적인 신호(배포 충돌, 부분 확장 필요, 장애 전파)가 있는가
  • 서비스 경계가 기술 계층이 아니라 업무 도메인 기준인가
  • 서비스 간 호출에 타임아웃이 설정되어 있는가
  • 연쇄 장애를 막을 서킷 브레이커 또는 격리 전략이 있는가
  • 여러 서비스에 걸친 작업의 실패 시나리오(보상 로직)를 설계했는가
