> **대상:** API 서버 하나(모놀리식)를 만들고 운영까지 해봤고, 이제 서비스가 커지면서 "이걸 나눠야 하나" 고민이 시작된 사람
> **목적:** MSA로 나눌지 말지 판단하는 기준, 나눴을 때 생기는 통신·장애·데이터 문제와 대응 방법을 정리합니다

# 0. 시작 전에 — 자주 나오는 용어

중급 가이드까지 다룬 API 서버·캐싱·N+1 등의 개념은 이미 안다고 가정합니다. 고급 가이드는 처음 보는 용어가 특히 많이 나오므로, 각 문서 맨 앞에 그 문서에서 쓰는 용어를 정리해둡니다.

| 용어 | 쉬운 설명 |
| --- | --- |
| 모놀리식(Monolithic) | 하나의 배포 단위 안에 여러 기능이 함께 구성되는 구조. 서버(인스턴스)를 여러 대로 늘려 수평 확장하는 것은 가능하지만, 배포·릴리스 단위는 하나로 묶여 있음 |
| MSA (Microservice Architecture) | 기능을 여러 개의 독립된 작은 서비스로 나눠서 운영하는 구조 |
| 도메인(Domain) | "결제", "수강 신청"처럼 실제 업무 단위를 기준으로 나눈 영역. 기술 계층이 아니라 업무 기준으로 나누는 것을 의미 |
| 동기 통신(Synchronous) | 요청을 보낸 쪽이 응답이 올 때까지 기다리는 통신 방식 |
| 비동기 통신(Asynchronous) | 호출한 쪽이 결과를 받을 때까지 그 자리에서 block하며 기다리지 않는 통신 방식. 결과는 나중에 callback·이벤트·polling·future 등의 형태로 전달됨 |
| 메시지 브로커(Message Broker) | 여러 서비스 사이에서 이벤트·메시지를 전달해주는 중간 시스템(Kafka, RabbitMQ 등) |
| 장애 전파(Cascading Failure) | 한 서비스의 장애가 그 서비스를 호출하는 다른 서비스까지 연쇄적으로 무너뜨리는 현상 |
| 서킷 브레이커(Circuit Breaker) | 실패가 잦은 서비스에는 잠시 요청을 보내지 않고 회복할 시간을 주는 장치 |
| 재시도 폭풍(Retry Storm) | 느려진 서비스에 여러 클라이언트가 동시에 재시도를 몰아넣어 부하가 오히려 더 커지는 현상 |
| 분산 트랜잭션 | 여러 서비스(여러 데이터베이스)에 걸친 작업을 하나의 트랜잭션처럼 안전하게 처리하는 것 |
| Saga 패턴 | 분산 트랜잭션을 여러 단계로 나눠 실행하고, 실패하면 이전 단계를 거꾸로 취소(보상)하는 방식 |
| 보상 트랜잭션(Compensating Transaction) | 이미 실행된 작업을 되돌리기 위해 실행하는 "취소" 작업 |
| 최종 일관성(Eventual Consistency) | 지금 당장은 데이터가 서로 다를 수 있지만, 시간이 지나면 결국 같은 값으로 맞춰진다는 개념 |

---

# 1. 모놀리식을 먼저 의심하지 않기

MSA(Microservice Architecture)는 "요즘 트렌드"가 아니라 **모놀리식으로 감당이 안 될 때 쓰는 해결책**입니다. 순서가 반대로 되면 안 됩니다.

```text
잘못된 순서: 처음부터 MSA로 설계 → 서비스 3개인데 통신·배포·모니터링 복잡도만 3배
맞는 순서: 모놀리식으로 시작 → 실제로 아래 신호가 나타나면 그때 분리 검토
```

**분리를 검토할 신호**

- 팀이 커져서 한 저장소에 여러 팀이 동시에 배포하려다 서로 막힘
- 특정 기능(예: 결제)만 트래픽이 튀는데 전체 서버를 다 같이 확장해야 함
- 한 기능의 장애(메모리 누수 등)가 관련 없는 다른 기능까지 전부 죽임

**기본 상식**: "언젠가 커질 수도 있으니 미리 MSA로" 는 대부분 손해로 끝납니다. 모놀리식 안에서도 모듈 경계(폴더·패키지 분리)를 잘 지키면, 나중에 분리할 때 그 경계를 그대로 서비스 경계로 옮기면 됩니다. 지금 당장 잘 나뉜 모놀리식이 나중에 잘 나뉜 MSA가 됩니다.

---

# 2. 서비스 경계를 나누는 기준

기술 기준(이 코드는 프론트, 이 코드는 백엔드)이 아니라 **업무 기준(도메인)**으로 나눕니다.

```text
나쁜 예: user-db-service, user-api-service, user-cache-service
→ 기술 계층으로 나뉘어서 기능 하나 고칠 때마다 3개 서비스를 같이 배포해야 함

좋은 예: user-service, course-service, payment-service, notification-service
→ "수강 신청"이라는 하나의 기능 변경이 대부분 course-service 안에서 끝남
```

핵심은 **각 서비스가 자신의 데이터를 소유하고, 다른 서비스가 그 내부 데이터에 직접 의존하지 않는 것**입니다. 다른 서비스의 테이블에 직접 SQL을 날리지 않고, 반드시 API(또는 이벤트)를 통해서만 접근합니다. 이를 물리적으로 강제하는 가장 확실한 방법은 서비스마다 별도의 DB 인스턴스를 두는 것이지만, 반드시 인스턴스 자체를 분리해야만 하는 것은 아닙니다 — 같은 DB 서버 안에서 스키마·테이블 접근 권한을 분리해 "이 테이블 그룹은 이 서비스만 쓴다"는 경계를 지키는 것도 실무에서 흔한 절충안입니다. 어떤 방식이든 이 소유권 경계가 지켜지지 않으면 서비스는 나눴는데 실제로는 여전히 하나의 거대한 시스템(분산 모놀리식)이 됩니다.

# 3. 서비스 간 통신 — 동기 vs 비동기

## 동기 통신 (REST, gRPC)

```text
주문 서비스 → (즉시 응답 필요) → 재고 서비스: "재고 있어?"
```

응답이 바로 필요할 때 씁니다. 대신 재고 서비스가 느려지거나 죽으면 주문 서비스도 같이 느려지거나 실패합니다(장애 전파).

## 비동기 통신 (메시지 큐, 이벤트)

```text
주문 서비스 → "주문 완료" 이벤트 발행 → 메시지 브로커(Kafka, RabbitMQ 등)
                                          ├→ 알림 서비스가 구독해서 이메일 발송
                                          └→ 정산 서비스가 구독해서 매출 집계
```

주문 서비스는 이벤트만 발행하고 끝입니다. 알림 서비스가 지금 죽어있어도 주문은 성공하고, 알림 서비스가 살아나면 밀린 이벤트를 처리합니다. **응답이 즉시 필요 없는 후속 작업**에 적합합니다.

비동기 처리의 핵심은 "호출한 쪽이 결과가 나올 때까지 그 자리에서 멈춰 기다리지(block) 않는다"는 것입니다. 결과 자체가 사라지는 게 아니라, 나중에 다른 방식으로 전달됩니다.

```text
callback: 작업이 끝나면 미리 등록해둔 함수를 실행해줌
event/pub-sub: 작업이 끝났다는 사실을 이벤트로 발행하고, 관심 있는 쪽이 구독해서 받음
polling: 호출한 쪽이 주기적으로 "다 됐어?"라고 다시 물어봄
future/promise: 즉시 "결과를 나중에 채워줄 상자"를 받고, 필요할 때 그 상자를 열어봄
```

# 4. 장애 격리 — 한 서비스의 장애가 전체로 번지지 않게

## 타임아웃

호출한 서비스가 응답이 없을 때 무한정 기다리지 않고 일정 시간 뒤 포기합니다. 타임아웃이 없으면, 느려진 서비스 하나 때문에 호출한 쪽 스레드가 전부 그 응답을 기다리다 함께 멈춥니다.

## 서킷 브레이커(Circuit Breaker)

```text
정상 상태(Closed) → 요청 정상 통과
   ↓ 실패율이 임계치를 넘으면
차단 상태(Open) → 일정 시간 동안 요청을 보내지 않고 즉시 실패 처리
   ↓ 일정 시간 후
반열림 상태(Half-Open) → 요청 몇 개만 시험 삼아 보내봄 → 성공하면 다시 Closed
```

죽어가는 서비스에 계속 요청을 보내면 그 서비스가 살아날 기회조차 없이 더 죽습니다. 서킷 브레이커는 "이미 실패하고 있는 서비스"에는 잠시 요청을 끊어서 회복할 시간을 줍니다.

## 재시도(Retry) — 그러나 신중하게

일시적인 네트워크 오류는 재시도로 해결되지만, 재시도 자체가 장애를 더 키우기도 합니다.

**기본 상식**: 이미 트래픽이 몰려서 느려진 서비스에 모든 클라이언트가 동시에 재시도하면 요청량이 오히려 폭증합니다(재시도 폭풍). 재시도 간격에 무작위성을 섞고(Exponential Backoff + Jitter), 재시도 횟수 상한을 반드시 둡니다.

# 5. 데이터 일관성 — 분산 트랜잭션 문제

한 서비스 안에서는 DB 트랜잭션으로 "전부 성공 또는 전부 실패"를 보장할 수 있지만, 여러 서비스에 걸친 작업은 그게 안 됩니다.

```text
예: 주문 생성(주문 서비스) → 재고 차감(재고 서비스) → 결제 승인(결제 서비스)
중간에 결제가 실패하면? 이미 만들어진 주문과 차감된 재고는 어떻게 되돌리나?
```

**Saga 패턴**: 각 단계를 별도 트랜잭션으로 실행하고, 실패하면 지금까지 실행된 단계를 역순으로 "취소하는 보상 작업(Compensating Transaction)"을 실행합니다.

```text
주문 생성 → 재고 차감 → 결제 승인 (실패!)
          ← 재고 복구  ← (보상 시작)
← 주문 취소
```

# 9. API 게이트웨이 패턴

여러 개의 마이크로서비스를 클라이언트가 직접 각각 호출하지 않고, 하나의 진입점(게이트웨이)을 거치게 하는 패턴입니다.

```text
게이트웨이 없이: 클라이언트가 강의 서비스, 결제 서비스, 리뷰 서비스를 각각 따로 호출
게이트웨이 사용: 클라이언트 → API 게이트웨이 → 내부적으로 필요한 서비스들을 호출·조합
```

게이트웨이가 맡는 공통 역할: 인증·인가 검증, Rate Limiting, 요청 로깅, 여러 서비스 응답을 하나로 조합(BFF, Backend for Frontend).

**기본 상식**: 게이트웨이는 편리하지만 모든 트래픽이 거치는 단일 지점이므로, 그 자체가 병목이나 장애 지점이 되지 않도록 무상태로 설계하고 수평 확장 가능하게 만들어야 합니다.

# 10. 분산 시스템에서의 시간과 순서

여러 서버에 걸친 이벤트의 순서를 정확히 아는 것은 생각보다 어렵습니다. 각 서버의 시계는 완벽히 동기화되지 않기 때문입니다.

```text
문제: 서버A에서 "재고 감소" 이벤트, 서버B에서 "주문 취소" 이벤트가
     거의 동시에 발생했을 때, 실제로 어느 것이 먼저 일어났는가?

해결 방법
- 논리적 시계(Lamport Timestamp): 실제 시간 대신 "이벤트 발생 순서"만 보장하는 카운터
- 벡터 시계(Vector Clock): 여러 노드 간 이벤트의 인과관계(무엇이 무엇보다 먼저인지)를 추적
- 실무에서는 대부분 메시지 큐의 파티션 순서 보장이나, 단일 리더가 순서를 결정하는
  방식으로 단순화해서 사용
```

**기본 상식**: "정확한 절대 시각 순서"가 반드시 필요한지부터 따져봅니다. 대부분의 서비스는 완벽한 전역 순서 대신, 인과관계가 있는 이벤트끼리만 순서가 보장되면 충분합니다.

# 11. CAP 정리와 트레이드오프

분산 시스템은 **일관성(Consistency)·가용성(Availability)·네트워크 분단 허용(Partition Tolerance)** 세 가지를 동시에 완벽히 만족할 수 없습니다. 네트워크 분단은 현실에서 언제든 발생할 수 있으므로, 실질적으로는 **분단 상황에서 일관성과 가용성 중 무엇을 우선할지**를 고르는 문제입니다.

| 선택 | 의미 | 이런 데이터에 적합할 수 있음 |
| --- | --- | --- |
| CP (일관성 우선) | 네트워크 분단이 발생하면 응답을 거부하거나 지연시키더라도 데이터는 항상 최신값만 보여줌 | 결제 잔액, 재고 차감처럼 틀린 값을 보여주는 게 더 위험한 데이터 |
| AP (가용성 우선) | 네트워크 분단 중에도 응답은 계속하되, 오래된 값을 보여줄 수 있음 | 좋아요 수, 조회수처럼 잠깐 옛날 값이어도 서비스 지속이 더 중요한 데이터 |

주의할 점은, "이 서비스는 CP다/AP다"처럼 서비스 전체를 하나로 단정할 수 없다는 것입니다. 같은 서비스 안에서도 어떤 데이터는 CP 전략, 다른 데이터는 AP 전략을 쓸 수 있습니다.

```text
질문: 이 데이터가 잠깐 옛날 값을 보여줘도 되는가?
- "안 된다"(결제 잔액) → CP 성향 시스템/전략 선택
- "된다"(추천 목록, 인기순 정렬) → AP 성향으로 가용성·성능을 우선
```

**기본 상식**: CAP는 "어떤 DB가 더 좋은가"의 문제가 아니라 "우리 서비스의 이 데이터는 어느 쪽을 희생해도 되는가"를 도메인별로 나눠서 판단하는 도구입니다. 하나의 서비스 안에서도 잔액은 CP, 추천 피드는 AP처럼 데이터별로 다른 선택을 할 수 있습니다.

# 12. 멱등성(Idempotency)으로 재시도를 안전하게

같은 요청이 네트워크 문제로 중복 전달돼도 결과가 한 번만 반영되게 만드는 성질입니다. 분산 시스템은 "정확히 한 번(Exactly-once)" 전달을 보장하기 매우 어렵기 때문에, 대신 "여러 번 와도 결과는 한 번"이 되도록 만듭니다.

여기서 착각하기 쉬운 부분은, **클라이언트가 idempotency key를 보낸다고 해서 그 자체로 멱등성이 보장되는 게 아니라는 점**입니다. 클라이언트는 어디까지나 "이 요청들은 같은 작업이다"라는 표시(키)를 제공할 뿐이고, 실제로 중복 요청을 식별해서 같은 작업이 두 번 반영되지 않도록 처리하는 책임은 서버에 있습니다. 서버가 이 키를 저장·검사하는 로직을 구현하지 않으면, 클라이언트가 아무리 키를 보내도 이중 결제를 막을 수 없습니다.

```text
문제 상황: 결제 요청 → 응답이 타임아웃으로 유실 → 클라이언트가 재시도
         → 서버는 이미 첫 요청을 처리했는데 두 번째 요청도 처리하면 이중 결제
```

```http
POST /payments
Idempotency-Key: 8f14e45f-ceea-467e-9b39-1a2c3d4e5f6a
```

```text
서버 처리:
1. Idempotency-Key로 이미 처리한 요청인지 확인
2. 이미 처리됐다면 새로 처리하지 않고 기존 결과를 그대로 반환
3. 처음 보는 키라면 정상 처리 후 키와 결과를 함께 저장
```

**기본 상식**: 재시도 로직을 아무리 잘 만들어도, 서버가 멱등하지 않으면 재시도할 때마다 부작용(중복 결제, 중복 발송)이 쌓입니다. 결제·주문·알림 발송처럼 부작용이 있는 API는 멱등키 설계를 재시도 전략과 항상 함께 고려합니다.

# 13. 용량 산정(Capacity Estimation)

시스템 설계 인터뷰나 실제 설계에서 "얼마나 큰 트래픽을 견뎌야 하는가"를 대략적으로 어림잡아 설계 방향을 정하는 방법입니다.

```text
예: 사용자 100만 명, 하루 평균 1인당 10회 API 호출 가정

일 평균 요청 수 = 100만 × 10 = 1,000만 건/일
초당 평균(QPS)  = 1,000만 / 86,400초 ≈ 116 QPS
피크 트래픽(평균의 3배 가정) ≈ 350 QPS

저장 용량 예시: 요청 1건당 로그 1KB → 하루 1,000만 × 1KB ≈ 10GB/일
              1년 보관 시 ≈ 3.6TB
```

**기본 상식**: 정확한 숫자를 맞히는 게 목적이 아니라, "이 정도 규모면 단일 서버로 되는지, 캐시가 필요한지, 샤딩이 필요한지"를 판단할 감을 잡는 것이 목적입니다. 어림수 계산 과정에서 세운 가정(피크 배수, 사용자당 호출 수)을 명시해두면, 나중에 실측치와 비교해 가정을 수정할 수 있습니다.

# 14. CQRS와 이벤트 소싱 맛보기

## CQRS (Command Query Responsibility Segregation)

데이터를 "바꾸는 연산(Command)"과 "조회하는 연산(Query)"을 아예 다른 모델로 분리하는 패턴입니다.

```text
일반적 구조: 하나의 모델로 쓰기와 읽기를 모두 처리
CQRS: 쓰기용 모델(정규화된 테이블) + 읽기용 모델(조회에 최적화된 뷰/캐시)을 분리
      쓰기가 발생하면 이벤트로 읽기 모델을 갱신
```

**기본 상식**: 조회 패턴이 복잡하고 쓰기와 읽기의 트래픽 비율이 크게 다를 때(예: 쓰기는 적고 읽기는 매우 많음) 효과가 있습니다. 대부분의 서비스에는 과한 복잡도이므로, "조회 성능이 정말 병목인가"를 먼저 캐싱·인덱스로 해결해보고, 그래도 부족할 때 검토합니다.

## 이벤트 소싱(Event Sourcing) 개념만

현재 상태만 저장하는 대신, **상태를 변화시킨 모든 이벤트를 순서대로 저장**하고 필요할 때 이벤트를 재생해 현재 상태를 계산합니다.

```text
일반적 저장: 계좌 잔액 = 50,000원 (현재 값만 저장)
이벤트 소싱: [입금 100,000원] → [출금 30,000원] → [출금 20,000원] (이벤트 이력 저장)
            → 필요할 때 이벤트를 순서대로 합산해 현재 잔액(50,000원)을 계산
```

**기본 상식**: 이벤트 소싱은 "언제 무슨 일이 있었는지"에 대한 완전한 이력이 중요한 도메인(회계, 감사 로그)에 강력하지만, 구현·운영 복잡도가 매우 높습니다. 대부분의 서비스에는 필요 이상의 복잡도이므로, 감사 이력이 법적·비즈니스적으로 필수인 경우가 아니라면 신중히 검토합니다.

# 15. 서비스 디스커버리와 백프레셔

## 서비스 디스커버리(Service Discovery)

서비스가 여러 대로 늘었다 줄었다 할 때, 서로의 주소를 어떻게 아는지에 대한 문제입니다.

```text
정적 방식: 서비스 주소를 설정 파일에 하드코딩 → 서버가 늘어날 때마다 수동 갱신 필요
동적 방식: 서비스가 뜰 때 레지스트리(Consul, Kubernetes Service 등)에 자기 주소를 등록
         → 호출하는 쪽은 레지스트리에 물어봐서 현재 살아있는 인스턴스 목록을 받음
```

## 백프레셔(Backpressure)

받는 쪽이 처리할 수 있는 속도보다 요청이 더 빨리 들어올 때, 무작정 다 받지 않고 밀어내는 제어 방법입니다.

```text
백프레셔 없음: 큐에 요청이 무한정 쌓임 → 메모리 부족으로 서비스 전체가 다운
백프레셔 있음: 큐가 임계치를 넘으면 새 요청을 429(Too Many Requests)로 거절하거나
              업스트림에 "천천히 보내라" 신호를 보냄
```

**기본 상식**: 시스템은 "얼마나 빨리 처리하는가"만큼 "감당 못 할 때 어떻게 안전하게 거절하는가"가 안정성을 좌우합니다. 큐가 무한정 커지도록 방치하는 설계는 장애를 늦게, 그러나 더 크게 터뜨립니다.
