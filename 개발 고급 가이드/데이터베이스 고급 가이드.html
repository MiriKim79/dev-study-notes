데이터베이스 고급 가이드

복제·샤딩 기초는 안다? 분산 트랜잭션과 샤딩을 실전에 적용할 때의 함정을 다룹니다.

0. 시작 전에 — 자주 나오는 용어#

중급 가이드에서 다룬 인덱스·복제·샤딩 기초 개념은 이미 안다고 가정합니다. 여기서는 이 문서에서 새로 나오는 용어만 정리합니다.

용어쉬운 설명
분산 트랜잭션(Distributed Transaction)여러 데이터베이스에 걸친 작업을 "전부 성공 또는 전부 실패"로 묶어 처리하려는 것
2단계 커밋(2PC, Two-Phase Commit)모든 참여 DB에게 먼저 "가능한지" 묻고, 전부 동의해야만 실제로 커밋하는 방식
Saga 패턴분산 트랜잭션을 여러 단계로 나눠 실행하고, 실패하면 이전 단계를 거꾸로 취소하는 방식
강한 일관성(Strong Consistency)데이터를 쓴 직후 어디서 읽어도 항상 최신값이 보장되는 것
최종 일관성(Eventual Consistency)지금 당장은 값이 다를 수 있지만, 시간이 지나면 결국 같은 값으로 맞춰지는 것
샤드 키(Shard Key)데이터를 어느 샤드(분산 서버)로 보낼지 정하는 기준 컬럼
핫스팟(Hotspot)샤드 키를 잘못 골라 특정 샤드에만 트래픽이 몰리는 현상
리샤딩(Resharding)이미 나눠둔 샤드를 새로운 기준으로 다시 나누는 작업. 비용이 매우 큼
Expand-Contract 패턴스키마 변경을 "추가 → 이전 → 코드 전환 → 제거" 여러 단계로 나눠, 서비스를 멈추지 않고 안전하게 진행하는 방법

1. 분산 트랜잭션이 어려운 이유#

한 DB 안에서는 트랜잭션(BEGIN ~ COMMIT)으로 "전부 성공 또는 전부 실패"가 보장됩니다. 하지만 데이터가 여러 DB(또는 여러 서비스)에 나뉘어 있으면 이 보장이 깨집니다.

text
계좌 A에서 출금(DB 1) → 계좌 B로 입금(DB 2)
DB 1은 성공, DB 2는 네트워크 오류로 실패 → 돈이 사라짐

2단계 커밋(2PC)— 이론적 해법과 현실의 한계#

text
1단계(준비): 모든 참여 DB에게 "커밋할 수 있어?"를 묻고 전부 "예"를 받음
2단계(커밋): 전부 "예"였으면 실제로 커밋, 하나라도 "아니오"면 전부 롤백

이론적으로는 완벽하지만, 1단계와 2단계 사이에 어느 DB가 응답 없이 멈추면 다른 모든 참여자도 그 시간 동안 잠긴 채 기다려야 합니다. 참여 DB가 많아질수록 이 대기 문제가 커져서, 실무에서는 거의 쓰이지 않습니다.

기본 상식: 대부분의 실무 시스템은 강한 일관성(2PC) 대신, 앞서 시스템 설계 가이드에서 다룬 Saga 패턴(보상 트랜잭션)으로 최종 일관성을 선택합니다. "완벽하게 동시에 맞아떨어짐"보다 "잠깐 어긋나도 결국은 맞게 정리됨"을 목표로 합니다.

2. 샤딩을 실전에 적용할 때의 함정#

샤딩 기초(사용자 ID로 서버를 나누는 것) 자체는 개념이 단순하지만, 실제로 적용하면 여러 문제가 따라옵니다.

샤드 키를 잘못 고르면#

text
나쁜 예: 가입일 기준으로 샤딩 → 최근 가입자가 몰린 샤드에 트래픽 집중(핫스팟)
나은 예: 사용자 ID를 해시(hash)해서 고르게 분산 → 샤드마다 트래픽이 균등

JOIN이 안 됨#

같은 샤드 안의 데이터끼리는 JOIN이 되지만, 다른 샤드에 있는 데이터끼리는 DB 레벨에서 JOIN할 수 없습니다. 애플리케이션 코드에서 여러 샤드를 각각 조회한 뒤 직접 합쳐야 합니다.

리샤딩(샤드를 다시 나누는 일)이 매우 비쌉니다#

text
샤드 2개로 시작 → 트래픽이 늘어 샤드 4개로 재분배 필요
→ 기존 데이터를 새 규칙에 맞게 전부 이동시켜야 하고, 그동안 서비스는 계속 돌아가야 함

기본 상식: 처음부터 완벽한 샤드 키를 고르기는 어렵습니다. 그래서 많은 팀이 "당장 샤딩하지 않아도 나중에 샤딩하기 쉬운 구조"(예: 샤드 키가 될 만한 컬럼을 처음부터 모든 테이블에 포함)로 설계해두고, 실제 필요해졌을 때 샤딩을 도입합니다.

3. 정합성 모델 이해하기#

모델의미예시
강한 일관성(Strong Consistency)쓰기 직후 어디서 읽어도 항상 최신값계좌 잔액, 재고 수량
최종 일관성(Eventual Consistency)잠깐의 지연 후 결국 모두 같은 값으로 수렴좋아요 수, 조회수, 알림

모든 데이터에 강한 일관성을 요구하면 시스템이 느려지고 확장이 어려워집니다. 데이터마다 정말 강한 일관성이 필요한지 구분하는 것이 설계의 핵심입니다.

기본 상식: "결제 금액"과 "동시 접속자 수"에 같은 수준의 정합성이 필요하지 않습니다. 강한 일관성이 필요한 데이터를 먼저 좁게 정의하고, 나머지는 최종 일관성으로 처리해 시스템 전체의 확장성을 확보합니다.

4. 대규모 마이그레이션 전략#

서비스를 운영하며 스키마를 바꾸거나 DB 엔진을 옮겨야 할 때, 서비스를 멈추지 않고 진행하는 방법입니다.

Expand-Contract 패턴#

text
1단계(Expand): 새 컬럼/테이블을 추가만 함 — 기존 코드는 그대로 동작
2단계(Migrate): 기존 데이터를 새 구조로 백그라운드에서 서서히 옮김
3단계(코드 전환): 애플리케이션 코드가 새 구조를 읽고 쓰도록 배포
4단계(Contract): 아무도 옛 구조를 쓰지 않는 게 확인되면 옛 컬럼/테이블 제거

한 번에 스키마를 바꾸는 대신 여러 단계로 나눠서, 각 단계마다 롤백이 가능한 상태를 유지합니다.

기본 상식: "이번 배포에 스키마 변경과 코드 변경을 동시에 넣는 것"이 대규모 장애의 흔한 원인입니다. 스키마 변경(추가)과 코드 변경(그 컬럼을 사용)을 서로 다른 배포로 분리하면, 문제가 생겨도 원인을 좁혀서 되돌릴 수 있습니다.

5. 자주 하는 실수#

  • 강한 일관성이 필요 없는 데이터에도 무조건 트랜잭션·잠금을 걺
  • 샤드 키를 트래픽 분산이 아니라 구현 편의로 골라 핫스팟 발생
  • 스키마 변경과 코드 배포를 한 번에 묶어서 롤백이 불가능한 상태를 만듦
  • 리샤딩·대규모 마이그레이션을 트래픽이 몰리는 시간대에 진행
  • "최종 일관성"을 이유로 데이터가 언제 수렴하는지 사용자에게 전혀 알려주지 않음

6. 실전 체크리스트#

  • 이 데이터가 정말 강한 일관성이 필요한지, 최종 일관성으로 충분한지 구분했는가
  • 여러 DB/서비스에 걸친 작업의 실패 시 보상(되돌리기) 절차가 있는가
  • 샤드 키가 실제 트래픽 패턴 기준으로 고르게 분산되는가
  • 스키마 변경을 Expand-Contract처럼 단계적으로 배포할 수 있는가
  • 마이그레이션을 실제로 되돌려본 적(리허설)이 있는가
