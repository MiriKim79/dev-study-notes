데이터베이스 고급 가이드

복제·샤딩 기초는 안다? 분산 트랜잭션과 샤딩을 실전에 적용할 때의 함정을 다룹니다.

0. 시작 전에 — 자주 나오는 용어#

중급 가이드에서 다룬 인덱스·복제·샤딩 기초 개념은 이미 안다고 가정합니다. 여기서는 이 문서에서 새로 나오는 용어만 정리합니다.

용어쉬운 설명
분산 트랜잭션(Distributed Transaction)여러 데이터베이스에 걸친 작업을 "전부 성공 또는 전부 실패"로 묶어 처리하려는 것
2단계 커밋(2PC, Two-Phase Commit)모든 참여 DB에게 먼저 "가능한지" 묻고, 전부 동의해야만 실제로 커밋하는 방식
Saga 패턴분산 트랜잭션을 여러 단계로 나눠 실행하고, 실패하면 이전 단계를 거꾸로 취소하는 방식
강한 일관성(Strong Consistency)데이터를 쓴 직후 어디서 읽어도 항상 최신값이 보장되는 것
최종 일관성(Eventual Consistency)지금 당장은 값이 다를 수 있지만, 시간이 지나면 결국 같은 값으로 맞춰지는 것
샤드 키(Shard Key)데이터를 어느 샤드(분산 서버)로 보낼지 정하는 기준 컬럼
핫스팟(Hotspot)샤드 키를 잘못 골라 특정 샤드에만 트래픽이 몰리는 현상
리샤딩(Resharding)이미 나눠둔 샤드를 새로운 기준으로 다시 나누는 작업. 비용이 매우 큼
Expand-Contract 패턴스키마 변경을 "추가 → 이전 → 코드 전환 → 제거" 여러 단계로 나눠, 서비스를 멈추지 않고 안전하게 진행하는 방법

1. 분산 트랜잭션이 어려운 이유#

한 DB 안에서는 트랜잭션(BEGIN ~ COMMIT)으로 "전부 성공 또는 전부 실패"가 보장됩니다. 하지만 데이터가 여러 DB(또는 여러 서비스)에 나뉘어 있으면 이 보장이 깨집니다.

text
계좌 A에서 출금(DB 1) → 계좌 B로 입금(DB 2)
DB 1은 성공, DB 2는 네트워크 오류로 실패 → 돈이 사라짐

2단계 커밋(2PC)— 이론적 해법과 현실의 한계#

text
1단계(준비): 모든 참여 DB에게 "커밋할 수 있어?"를 묻고 전부 "예"를 받음
2단계(커밋): 전부 "예"였으면 실제로 커밋, 하나라도 "아니오"면 전부 롤백

이론적으로는 완벽하지만, 1단계와 2단계 사이에 어느 DB가 응답 없이 멈추면 다른 모든 참여자도 그 시간 동안 잠긴 채 기다려야 합니다. 참여 DB가 많아질수록 이 대기 문제가 커져서, 실무에서는 거의 쓰이지 않습니다.

기본 상식: 대부분의 실무 시스템은 강한 일관성(2PC) 대신, 앞서 시스템 설계 가이드에서 다룬 Saga 패턴(보상 트랜잭션)으로 최종 일관성을 선택합니다. "완벽하게 동시에 맞아떨어짐"보다 "잠깐 어긋나도 결국은 맞게 정리됨"을 목표로 합니다.

2. 샤딩을 실전에 적용할 때의 함정#

샤딩 기초(사용자 ID로 서버를 나누는 것) 자체는 개념이 단순하지만, 실제로 적용하면 여러 문제가 따라옵니다.

샤드 키를 잘못 고르면#

text
나쁜 예: 가입일 기준으로 샤딩 → 최근 가입자가 몰린 샤드에 트래픽 집중(핫스팟)
나은 예: 사용자 ID를 해시(hash)해서 고르게 분산 → 샤드마다 트래픽이 균등

JOIN이 안 됨#

같은 샤드 안의 데이터끼리는 JOIN이 되지만, 다른 샤드에 있는 데이터끼리는 DB 레벨에서 JOIN할 수 없습니다. 애플리케이션 코드에서 여러 샤드를 각각 조회한 뒤 직접 합쳐야 합니다.

리샤딩(샤드를 다시 나누는 일)이 매우 비쌉니다#

text
샤드 2개로 시작 → 트래픽이 늘어 샤드 4개로 재분배 필요
→ 기존 데이터를 새 규칙에 맞게 전부 이동시켜야 하고, 그동안 서비스는 계속 돌아가야 함

기본 상식: 처음부터 완벽한 샤드 키를 고르기는 어렵습니다. 그래서 많은 팀이 "당장 샤딩하지 않아도 나중에 샤딩하기 쉬운 구조"(예: 샤드 키가 될 만한 컬럼을 처음부터 모든 테이블에 포함)로 설계해두고, 실제 필요해졌을 때 샤딩을 도입합니다.

3. 정합성 모델 이해하기#

모델의미예시
강한 일관성(Strong Consistency)쓰기 직후 어디서 읽어도 항상 최신값계좌 잔액, 재고 수량
최종 일관성(Eventual Consistency)잠깐의 지연 후 결국 모두 같은 값으로 수렴좋아요 수, 조회수, 알림

모든 데이터에 강한 일관성을 요구하면 시스템이 느려지고 확장이 어려워집니다. 데이터마다 정말 강한 일관성이 필요한지 구분하는 것이 설계의 핵심입니다.

기본 상식: "결제 금액"과 "동시 접속자 수"에 같은 수준의 정합성이 필요하지 않습니다. 강한 일관성이 필요한 데이터를 먼저 좁게 정의하고, 나머지는 최종 일관성으로 처리해 시스템 전체의 확장성을 확보합니다.

4. 대규모 마이그레이션 전략#

서비스를 운영하며 스키마를 바꾸거나 DB 엔진을 옮겨야 할 때, 서비스를 멈추지 않고 진행하는 방법입니다.

Expand-Contract 패턴#

text
1단계(Expand): 새 컬럼/테이블을 추가만 함 — 기존 코드는 그대로 동작
2단계(Migrate): 기존 데이터를 새 구조로 백그라운드에서 서서히 옮김
3단계(코드 전환): 애플리케이션 코드가 새 구조를 읽고 쓰도록 배포
4단계(Contract): 아무도 옛 구조를 쓰지 않는 게 확인되면 옛 컬럼/테이블 제거

한 번에 스키마를 바꾸는 대신 여러 단계로 나눠서, 각 단계마다 롤백이 가능한 상태를 유지합니다.

기본 상식: "이번 배포에 스키마 변경과 코드 변경을 동시에 넣는 것"이 대규모 장애의 흔한 원인입니다. 스키마 변경(추가)과 코드 변경(그 컬럼을 사용)을 서로 다른 배포로 분리하면, 문제가 생겨도 원인을 좁혀서 되돌릴 수 있습니다.

5. 자주 하는 실수#

  • 강한 일관성이 필요 없는 데이터에도 무조건 트랜잭션·잠금을 걺
  • 샤드 키를 트래픽 분산이 아니라 구현 편의로 골라 핫스팟 발생
  • 스키마 변경과 코드 배포를 한 번에 묶어서 롤백이 불가능한 상태를 만듦
  • 리샤딩·대규모 마이그레이션을 트래픽이 몰리는 시간대에 진행
  • "최종 일관성"을 이유로 데이터가 언제 수렴하는지 사용자에게 전혀 알려주지 않음

6. 실전 체크리스트#

  • 이 데이터가 정말 강한 일관성이 필요한지, 최종 일관성으로 충분한지 구분했는가
  • 여러 DB/서비스에 걸친 작업의 실패 시 보상(되돌리기) 절차가 있는가
  • 샤드 키가 실제 트래픽 패턴 기준으로 고르게 분산되는가
  • 스키마 변경을 Expand-Contract처럼 단계적으로 배포할 수 있는가
  • 마이그레이션을 실제로 되돌려본 적(리허설)이 있는가

7. CAP 정리와 실전 선택#

분산 시스템은 일관성(Consistency), 가용성(Availability), 파티션 허용성(Partition tolerance) 세 가지를 동시에 완벽히 만족할 수 없습니다. 네트워크 분리(파티션)는 항상 일어날 수 있으므로, 실제로는 "파티션이 발생했을 때 일관성과 가용성 중 무엇을 우선할지"의 선택입니다.

선택의미예시
CP (일관성 우선)파티션 발생 시 응답을 거부하더라도 데이터 정합성을 지킴결제, 재고 차감
AP (가용성 우선)파티션 발생 시 오래된 값이라도 일단 응답상품 조회, 좋아요 수

기본 상식: 하나의 서비스 안에서도 데이터 종류에 따라 CP/AP를 다르게 선택할 수 있습니다. "우리 서비스는 CP다/AP다"로 전체를 한 번에 정하기보다, 데이터별로 요구되는 일관성 수준을 판단합니다.

8. 이벤트 소싱과 CQRS 기초#

이벤트 소싱(Event Sourcing)#

현재 상태만 저장하는 대신, "무슨 일이 일어났는지"를 이벤트로 순서대로 저장하고 현재 상태는 이벤트들을 재생해서 계산합니다.

text
일반적인 방식: orders 테이블의 status 컬럼을 직접 UPDATE
이벤트 소싱: OrderCreated → OrderPaid → OrderShipped 이벤트를 순서대로 저장
            현재 상태 = 이 이벤트들을 순서대로 적용한 결과

장점: 과거 상태를 그대로 재현할 수 있고, "왜 이 상태가 됐는지" 이력이 자연스럽게 남습니다. 단점: 조회가 복잡해지고(이벤트를 재생해야 함), 팀 전체가 익숙해지기까지 학습 비용이 큽니다.

CQRS (Command Query Responsibility Segregation)#

쓰기(Command)와 읽기(Query)의 모델을 분리하는 패턴입니다. 이벤트 소싱과 자주 함께 쓰입니다.

text
쓰기: 이벤트를 이벤트 저장소에 기록
읽기: 이벤트를 조회하기 편한 형태(읽기 전용 테이블)로 미리 가공해둠

기본 상식: 이벤트 소싱과 CQRS는 강력하지만 복잡도가 크게 늘어납니다. 감사(audit) 이력이 법적으로 중요하거나, 복잡한 도메인 이벤트 흐름을 정확히 추적해야 하는 경우(금융, 재고)에 국한해서 검토하고, 단순 CRUD로 충분한 도메인에는 과한 선택입니다.

9. 읽기/쓰기 분리와 복제 지연#

트래픽이 늘면 읽기(SELECT)와 쓰기(INSERT/UPDATE/DELETE)를 서로 다른 서버로 분리합니다.

text
쓰기 요청 → Primary(마스터) DB
읽기 요청 → Replica(복제본) DB 여러 대로 분산

Primary의 변경 내용은 비동기로 Replica에 복제됨

복제 지연(Replication Lag) 문제#

text
1. 사용자가 글을 작성 → Primary에 저장됨
2. 곧바로 목록 페이지로 이동 → Replica에서 조회
3. 복제가 아직 도착하지 않아 방금 쓴 글이 안 보임 (복제 지연)
대응 방법방식
쓰기 직후 읽기는 Primary에서방금 쓴 사용자 본인에게 보여줄 데이터는 Replica가 아닌 Primary에서 바로 읽음
복제 지연 허용 범위 설계"최신 글 목록"처럼 몇 초 지연이 괜찮은 화면만 Replica로 보냄
복제 지연 모니터링지연 시간이 임계치를 넘으면 알림을 받아, 해당 Replica를 일시적으로 트래픽에서 제외

기본 상식: 모든 읽기를 무조건 Replica로 보내면 "내가 방금 쓴 데이터가 안 보인다"는 사용자 불만이 생깁니다. 사용자 자신의 최신 데이터를 다시 보여줘야 하는 화면(마이페이지, 방금 작성한 글)은 Primary에서 읽도록 예외를 둡니다.

10. 멀티 리전 데이터베이스 전략#

사용자가 전 세계에 분산되어 있을 때, 지리적으로 가까운 리전에서 DB를 응답하게 해 지연시간을 줄이는 전략입니다.

text
단일 리전: 모든 사용자가 서울 리전의 DB를 사용 → 해외 사용자는 왕복 지연이 큼

멀티 리전 옵션:
1. Active-Passive: 한 리전만 쓰기를 받고, 다른 리전은 읽기 전용 복제본으로 대기
   (재해 발생 시 대기 리전으로 전환 — DR, Disaster Recovery 목적)
2. Active-Active: 여러 리전이 동시에 쓰기를 받음
   (지연시간은 가장 좋지만, 서로 다른 리전에 동시에 들어온 쓰기 간 충돌 해결이 필요)

기본 상식: Active-Active 멀티 리전은 강력하지만 "같은 데이터를 두 리전에서 동시에 수정하면 어느 것이 최종본인가"라는 충돌 해결 문제가 항상 따라옵니다. 실무에서는 꼭 필요한 경우(글로벌 대규모 서비스)가 아니라면, 하나의 쓰기 리전 + 여러 읽기 전용 리전(Active-Passive에 가까운 구조)으로 복잡도를 낮추는 경우가 많습니다.

11. 대용량 배치 작업이 운영 DB에 미치는 영향#

야간 정산, 대량 데이터 이관처럼 한 번에 많은 행을 처리하는 배치 작업은 운영 중인 서비스에 영향을 줄 수 있습니다.

문제가 되는 이유#

text
UPDATE orders SET status = 'archived' WHERE created_at < '2023-01-01';
-- 대상이 수백만 건이면:
-- 1) 트랜잭션이 오래 걸려 잠금이 길게 유지됨 → 같은 테이블을 쓰는 서비스 요청이 대기
-- 2) 한 번에 큰 트랜잭션 로그가 쌓여 복제 지연이 커짐

대응 방법 — 배치 쪼개기#

python
# 한 번에 다 처리하지 않고, 작은 단위로 나눠 커밋
BATCH_SIZE = 1000
while True:
    rows = db.execute(
        "SELECT id FROM orders WHERE status=&#x27;pending' LIMIT %s", (BATCH_SIZE,)
    )
    if not rows:
        break
    db.execute("UPDATE orders SET status=&#x27;archived' WHERE id IN %s", (tuple(rows),))
    db.commit()
    time.sleep(0.1)  # 다른 요청이 끼어들 틈을 잠깐 줌

기본 상식: "한 번에 빨리 끝내는 것"보다 "서비스에 영향을 주지 않고 끝내는 것"이 배치 작업의 우선순위입니다. 트래픽이 적은 새벽 시간대에 실행하고, 배치를 작은 단위로 나눠 각 단위 사이에 다른 요청이 끼어들 틈을 주는 것이 기본 원칙입니다.

12. 백업·복구 전략 심화 — PITR#

백업의 기본 종류#

종류방식특징
전체 백업(Full Backup)특정 시점의 DB 전체를 통째로 복사복구가 간단하지만 백업 자체가 크고 시간이 걸림
증분 백업(Incremental)마지막 백업 이후 변경분만 저장백업은 빠르지만 복구 시 여러 백업을 순서대로 적용해야 함

PITR(Point-In-Time Recovery)#

전체 백업 + 그 이후의 변경 로그(WAL, binlog 등)를 함께 보관해두면, "특정 시각 직전"으로 복구할 수 있습니다.

text
예시 사고: 오후 3시에 실수로 대량 DELETE 실행
전체 백업(매일 새벽 3시) + 이후 변경 로그를 보관하고 있었다면
→ "오후 2시 59분 시점"으로 정확히 복구 가능 (DELETE 직전까지의 데이터는 보존)

기본 상식: "백업이 있다"와 "복구가 된다"는 다릅니다. 백업을 실제로 복구해보는 훈련(복구 리허설)을 정기적으로 하지 않으면, 정작 사고가 났을 때 백업 파일이 손상되어 있거나 복구 절차 자체가 틀렸다는 사실을 그제서야 알게 됩니다.

13. 데이터베이스 마이그레이션 도구와 무중단 마이그레이션 실전#

마이그레이션 도구 비교#

도구특징
Flask-Migrate / AlembicPython/Flask 생태계에서 널리 사용, 마이그레이션 파일을 자동 생성
Django MigrationsDjango 내장, 모델 변경을 감지해 마이그레이션 자동 생성
Flyway / Liquibase언어에 독립적, SQL 파일 기반으로 다양한 스택에서 공용으로 사용 가능

무중단으로 큰 테이블에 컬럼을 추가/변경할 때#

text
문제: 수천만 행짜리 테이블에 NOT NULL 컬럼을 기본값과 함께 추가하면,
     DB가 기존 모든 행에 값을 채워 넣는 동안 테이블 전체에 장시간 잠금이 걸릴 수 있음

안전한 순서:
1. 컬럼을 NULL 허용으로 먼저 추가 (즉시 완료, 잠금 거의 없음)
2. 배치로 기존 행에 기본값을 서서히 채움 (앞 장의 "배치 쪼개기" 기법 적용)
3. 모든 행이 채워진 뒤, NOT NULL 제약을 추가 (이 시점엔 이미 값이 다 채워져 있어 빠름)

기본 상식: 마이그레이션 도구가 생성해주는 마이그레이션 파일을 그대로 실행하기 전에, 대상 테이블의 행 수를 확인합니다. 작은 테이블(수천 행)은 도구의 기본 방식으로도 충분하지만, 대형 테이블은 위처럼 단계를 나누지 않으면 배포 시점에 서비스 전체가 잠깐 멈추는 사고로 이어질 수 있습니다.

14. 커넥션 풀 튜닝#

애플리케이션과 DB 사이의 연결(Connection)을 매 요청마다 새로 맺으면 비용이 크므로, 미리 만들어둔 연결을 재사용하는 커넥션 풀을 씁니다.

text
풀 크기가 너무 작으면 → 요청이 몰릴 때 연결을 기다리다 응답 지연·타임아웃
풀 크기가 너무 크면   → DB 서버가 감당해야 할 동시 연결 수가 늘어 오히려 DB 성능 저하
python
# 예시: SQLAlchemy 커넥션 풀 설정
engine = create_engine(
    DATABASE_URL,
    pool_size=10,        # 기본으로 유지할 연결 수
    max_overflow=5,      # 순간적으로 더 필요할 때 추가로 허용할 연결 수
    pool_timeout=30,      # 풀에 여유 연결이 없을 때 최대 대기 시간(초)
    pool_recycle=1800,    # 오래된 연결을 주기적으로 재생성 (DB의 idle timeout 대비)
)

기본 상식: 적정 풀 크기는 "애플리케이션 서버 대수 × 풀 크기"가 DB가 감당 가능한 총 연결 수를 넘지 않도록 계산합니다. 서버를 여러 대로 늘렸는데 각 서버의 풀 크기를 그대로 두면, 전체 연결 수가 DB의 한계를 넘어 장애로 이어질 수 있습니다.

15. 멀티 테넌시 데이터 설계#

하나의 서비스를 여러 고객(테넌트)이 함께 쓰는 구조에서 데이터를 어떻게 분리할지 결정해야 합니다.

방식구조특징
공유 DB, 공유 테이블모든 테넌트가 같은 테이블을 쓰고 tenant_id 컬럼으로 구분관리가 간단하지만, 쿼리마다 tenant_id 필터를 빠뜨리면 다른 테넌트 데이터가 노출되는 심각한 사고로 이어짐
공유 DB, 스키마 분리테넌트마다 별도 스키마 사용데이터 격리가 조금 더 명확하지만 스키마 수가 늘면 마이그레이션 관리가 복잡해짐
테넌트별 DB 분리테넌트마다 완전히 다른 DB 인스턴스격리·독립적 스케일링이 가장 강력하지만 운영 비용이 큼

기본 상식: 가장 흔한 구현인 "공유 테이블 + tenant_id" 방식에서는 애플리케이션 코드가 아니라 DB 자체에서 강제하는 것이 안전합니다(Row-Level Security 등). 애플리케이션 로직에만 의존하면 개발자가 실수로 필터를 빠뜨리는 순간 심각한 정보 유출 사고가 됩니다.
