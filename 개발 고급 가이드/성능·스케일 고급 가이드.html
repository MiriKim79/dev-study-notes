성능·스케일 고급 가이드

트래픽이 갑자기 몰리면 어떻게 될까 불안하다? 병목을 찾고 확장하는 실전 방법을 다룹니다.

📘 문서 소개
대상: 캐싱·인덱싱 등 개별 최적화는 해봤고, 이제 트래픽이 실제로 늘어나는 서비스를 운영하기 시작한 사람
목적: 병목을 찾는 방법, 캐싱 전략, 부하 테스트, 수평·수직 확장의 판단 기준을 정리합니다

1. 추측하지 말고 먼저 측정하기#

"느린 것 같다"는 느낌으로 아무 데나 최적화하면 시간만 쓰고 정작 진짜 병목은 그대로 남습니다.

text
잘못된 순서: "DB가 느릴 것 같으니" 캐싱부터 추가 → 실제로는 외부 API 호출이 병목이었음
맞는 순서: 실제 요청의 각 구간(네트워크, 서버, DB, 외부 API) 시간을 측정 → 가장 큰 구간부터 개선

기본 상식: APM(Application Performance Monitoring) 도구나 분산 트레이싱으로 요청 하나가 어느 구간에서 얼마나 시간을 쓰는지 먼저 확인합니다. "느껴지는 것"이 아니라 "측정된 숫자"로 우선순위를 정합니다.

2. 병목을 찾는 순서#

text
1. 응답 시간이 느린 API를 특정 (평균이 아니라 상위 5%, 상위 1% 응답 시간 — p95, p99)
2. 그 API 안에서 시간이 가장 오래 걸리는 구간 특정 (DB 쿼리? 외부 API? 반복 연산?)
3. 그 구간을 개선
4. 다시 측정해서 실제로 나아졌는지 확인

기본 상식: 평균 응답 시간만 보면 소수의 매우 느린 요청이 가려집니다. 사용자가 실제로 "느리다"고 느끼는 건 평균이 아니라 느린 쪽 꼬리(p95, p99)입니다. 평균이 200ms여도 p99가 5초면 100명 중 1명은 5초를 기다리고 있다는 뜻입니다.

3. 캐싱 전략#

캐시 계층#

text
브라우저 캐시 (정적 파일)
→ CDN 캐시 (이미지, JS/CSS, 자주 안 바뀌는 API 응답)
→ 애플리케이션 캐시 (Redis 등 — 자주 조회되는 DB 결과)
→ DB 자체 캐시

요청이 앞 단계에서 처리될수록 서버·DB 부하가 줄어듭니다.

캐시 무효화 — 캐싱에서 가장 어려운 부분#

text
문제: 강의 가격을 수정했는데 캐시된 예전 가격이 계속 보임
전략방식
TTL(Time To Live)일정 시간 후 자동 만료 — 간단하지만 그 시간 동안은 옛 데이터를 보여줄 수 있음
명시적 무효화데이터가 바뀌는 시점에 캐시를 직접 삭제/갱신 — 정확하지만 놓치는 지점이 생기기 쉬움
Write-Through데이터를 쓸 때 캐시도 함께 갱신 — 일관성이 좋지만 쓰기가 느려짐

기본 상식: "캐시 무효화와 이름 짓기가 컴퓨터 과학에서 가장 어려운 두 가지"라는 말이 있을 만큼, 캐시는 언제 지울지가 언제 저장할지보다 어렵습니다. 절대 틀리면 안 되는 데이터(가격, 재고)는 TTL을 짧게 잡거나 캐싱 대상에서 제외하는 편이 안전합니다.

4. 부하 테스트#

실제 트래픽이 오기 전에, 서비스가 얼마나 버티는지 미리 확인합니다.

bash
# 예시: k6로 초당 100명이 5분간 요청을 보내는 시나리오
k6 run --vus 100 --duration 5m load-test.js
text
확인할 것:
- 요청량이 늘 때 응답 시간이 어느 지점부터 급격히 나빠지는가 (한계점)
- 에러율이 늘기 시작하는 트래픽 수준은 어디인가
- 그 한계에서 CPU/메모리/DB 커넥션 중 무엇이 먼저 바닥나는가

기본 상식: 부하 테스트는 실제 운영 트래픽과 비슷한 시나리오(로그인 → 목록 조회 → 상세 조회 비율 등)로 해야 의미가 있습니다. 단순히 같은 엔드포인트 하나만 반복 호출하면 실제 병목과 다른 결과가 나옵니다.

5. 수평 확장 vs 수직 확장#

방식의미장단점
수직 확장(Scale Up)서버 한 대의 사양(CPU/메모리)을 늘림적용이 간단하지만 한계가 있고, 그 서버가 죽으면 전체가 멈춤
수평 확장(Scale Out)서버 대수를 늘림한 대가 죽어도 나머지가 버팀(가용성↑), 대신 서버 간 상태 공유 문제가 생김

수평 확장을 하려면 서버가 무상태(Stateless)여야 합니다 — 로그인 세션 등을 서버 메모리에 두면 안 되고, Redis 같은 공유 저장소에 둬야 어느 서버로 요청이 가도 동작합니다.

text
안 되는 예: 서버 A에 로그인한 세션이 서버 A 메모리에만 있음 → 다음 요청이 서버 B로 가면 로그인 풀림
되는 예: 세션을 Redis에 저장 → 어느 서버로 요청이 가도 같은 세션을 조회 가능

기본 상식: 서버를 무상태로 만들어두면, 트래픽이 늘 때 서버 대수만 늘리면 되고(오토스케일링과도 궁합이 좋음) 서버 하나가 죽어도 서비스가 끊기지 않습니다.

6. 자주 하는 실수#

  • 측정 없이 "느낌"으로 최적화 대상을 정함
  • 평균 응답 시간만 보고 p95/p99의 심각한 지연을 놓침
  • 절대 틀리면 안 되는 데이터(가격, 재고)까지 긴 TTL로 캐싱해서 정합성 문제 발생
  • 부하 테스트를 실제 사용 패턴과 다른 단순 반복 요청으로만 진행
  • 세션·업로드 파일 등을 서버 로컬에 저장해서 수평 확장이 막힘

7. 실전 체크리스트#

  • 병목을 실제 측정(APM, 트레이싱)으로 찾았는가
  • 평균이 아니라 p95/p99 응답 시간을 확인하는가
  • 캐싱 대상마다 무효화 전략(TTL/명시적 삭제)을 정했는가
  • 운영 트래픽과 비슷한 시나리오로 부하 테스트를 해봤는가
  • 서버가 무상태로 설계되어 수평 확장이 가능한가
