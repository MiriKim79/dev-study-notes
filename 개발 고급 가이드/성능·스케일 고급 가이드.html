0. 시작 전에 — 자주 나오는 용어#

중급 가이드에서 다룬 캐싱·수평 확장 기초 개념은 이미 안다고 가정합니다. 여기서는 이 문서에서 새로 나오는 용어만 정리합니다.

용어쉬운 설명
APM (Application Performance Monitoring)요청마다 걸린 시간과 느린 지점을 자동으로 추적해주는 모니터링 도구
분산 트레이싱(Distributed Tracing)요청 하나가 여러 서비스를 거칠 때, 각 구간에서 얼마나 시간이 걸렸는지 추적하는 것
p95 / p99전체 요청 중 가장 느린 5%(p95), 1%(p99)가 얼마나 걸렸는지 나타내는 지표. 평균보다 실제 체감에 가까움
CDN (Content Delivery Network)이미지·JS/CSS 같은 정적 파일을 사용자와 가까운 서버에 미리 복사해뒀다 빠르게 전달하는 서비스
TTL (Time To Live)캐시가 자동으로 사라지기까지의 유효 시간
부하 테스트(Load Test)실제 트래픽이 오기 전에, 얼마나 많은 요청까지 버틸 수 있는지 미리 확인하는 테스트
수직 확장(Scale Up)서버 한 대의 사양(CPU·메모리)을 늘리는 방식
수평 확장(Scale Out)서버 사양은 그대로 두고 대수를 늘리는 방식
무상태(Stateless)서버가 사용자 상태를 자기 메모리에 담아두지 않는 설계. 여러 서버로 나눠도 문제없이 동작함
오토스케일링(Autoscaling)트래픽에 따라 서버 대수를 자동으로 늘리고 줄이는 기능

1. 추측하지 말고 먼저 측정하기#

"느린 것 같다"는 느낌으로 아무 데나 최적화하면 시간만 쓰고 정작 진짜 병목은 그대로 남습니다.

text
잘못된 순서: "DB가 느릴 것 같으니" 캐싱부터 추가 → 실제로는 외부 API 호출이 병목이었음
맞는 순서: 실제 요청의 각 구간(네트워크, 서버, DB, 외부 API) 시간을 측정 → 가장 큰 구간부터 개선

기본 상식: APM(Application Performance Monitoring) 도구나 분산 트레이싱으로 요청 하나가 어느 구간에서 얼마나 시간을 쓰는지 먼저 확인합니다. "느껴지는 것"이 아니라 "측정된 숫자"로 우선순위를 정합니다.

2. 병목을 찾는 순서#

text
1. 응답 시간이 느린 API를 특정 (평균이 아니라 상위 5%, 상위 1% 응답 시간 — p95, p99)
2. 그 API 안에서 시간이 가장 오래 걸리는 구간 특정 (DB 쿼리? 외부 API? 반복 연산?)
3. 그 구간을 개선
4. 다시 측정해서 실제로 나아졌는지 확인

기본 상식: 평균 응답 시간만 보면 소수의 매우 느린 요청이 가려집니다. 사용자가 실제로 "느리다"고 느끼는 건 평균이 아니라 느린 쪽 꼬리(p95, p99)입니다. 평균이 200ms여도 p99가 5초면 100명 중 1명은 5초를 기다리고 있다는 뜻입니다.

3. 캐싱 전략#

캐시 계층#

text
브라우저 캐시 (정적 파일)
→ CDN 캐시 (이미지, JS/CSS, 자주 안 바뀌는 API 응답)
→ 애플리케이션 캐시 (Redis 등 — 자주 조회되는 DB 결과)
→ DB 자체 캐시

요청이 앞 단계에서 처리될수록 서버·DB 부하가 줄어듭니다.

캐시 무효화 — 캐싱에서 가장 어려운 부분#

text
문제: 강의 가격을 수정했는데 캐시된 예전 가격이 계속 보임
전략방식
TTL(Time To Live)일정 시간 후 자동 만료 — 간단하지만 그 시간 동안은 옛 데이터를 보여줄 수 있음
명시적 무효화데이터가 바뀌는 시점에 캐시를 직접 삭제/갱신 — 정확하지만 놓치는 지점이 생기기 쉬움
Write-Through데이터를 쓸 때 캐시도 함께 갱신 — 일관성이 좋지만 쓰기가 느려짐

기본 상식: "캐시 무효화와 이름 짓기가 컴퓨터 과학에서 가장 어려운 두 가지"라는 말이 있을 만큼, 캐시는 언제 지울지가 언제 저장할지보다 어렵습니다. 절대 틀리면 안 되는 데이터(가격, 재고)는 TTL을 짧게 잡거나 캐싱 대상에서 제외하는 편이 안전합니다.

4. 부하 테스트#

실제 트래픽이 오기 전에, 서비스가 얼마나 버티는지 미리 확인합니다.

bash
# 예시: k6로 초당 100명이 5분간 요청을 보내는 시나리오
k6 run --vus 100 --duration 5m load-test.js
text
확인할 것:
- 요청량이 늘 때 응답 시간이 어느 지점부터 급격히 나빠지는가 (한계점)
- 에러율이 늘기 시작하는 트래픽 수준은 어디인가
- 그 한계에서 CPU/메모리/DB 커넥션 중 무엇이 먼저 바닥나는가

기본 상식: 부하 테스트는 실제 운영 트래픽과 비슷한 시나리오(로그인 → 목록 조회 → 상세 조회 비율 등)로 해야 의미가 있습니다. 단순히 같은 엔드포인트 하나만 반복 호출하면 실제 병목과 다른 결과가 나옵니다.

5. 수평 확장 vs 수직 확장#

방식의미장단점
수직 확장(Scale Up)서버 한 대의 사양(CPU/메모리)을 늘림적용이 간단하지만 한계가 있고, 그 서버가 죽으면 전체가 멈춤
수평 확장(Scale Out)서버 대수를 늘림한 대가 죽어도 나머지가 버팀(가용성↑), 대신 서버 간 상태 공유 문제가 생김

수평 확장을 하려면 서버가 무상태(Stateless)여야 합니다 — 로그인 세션 등을 서버 메모리에 두면 안 되고, Redis 같은 공유 저장소에 둬야 어느 서버로 요청이 가도 동작합니다.

text
안 되는 예: 서버 A에 로그인한 세션이 서버 A 메모리에만 있음 → 다음 요청이 서버 B로 가면 로그인 풀림
되는 예: 세션을 Redis에 저장 → 어느 서버로 요청이 가도 같은 세션을 조회 가능

기본 상식: 서버를 무상태로 만들어두면, 트래픽이 늘 때 서버 대수만 늘리면 되고(오토스케일링과도 궁합이 좋음) 서버 하나가 죽어도 서비스가 끊기지 않습니다.

6. 자주 하는 실수#

  • 측정 없이 "느낌"으로 최적화 대상을 정함
  • 평균 응답 시간만 보고 p95/p99의 심각한 지연을 놓침
  • 절대 틀리면 안 되는 데이터(가격, 재고)까지 긴 TTL로 캐싱해서 정합성 문제 발생
  • 부하 테스트를 실제 사용 패턴과 다른 단순 반복 요청으로만 진행
  • 세션·업로드 파일 등을 서버 로컬에 저장해서 수평 확장이 막힘

7. 실전 체크리스트#

  • 병목을 실제 측정(APM, 트레이싱)으로 찾았는가
  • 평균이 아니라 p95/p99 응답 시간을 확인하는가
  • 캐싱 대상마다 무효화 전략(TTL/명시적 삭제)을 정했는가
  • 운영 트래픽과 비슷한 시나리오로 부하 테스트를 해봤는가
  • 서버가 무상태로 설계되어 수평 확장이 가능한가

8. CDN과 엣지 캐싱#

정적 자원(이미지, JS, CSS)과 일부 API 응답을 사용자와 지리적으로 가까운 서버(엣지)에 캐싱해 지연시간을 줄입니다.

text
캐시 안 함: 사용자(서울) → 원본 서버(미국 버지니아) 매번 왕복 → 느림
CDN 사용: 사용자(서울) → 가까운 엣지 서버(서울 리전) → 캐시된 응답 즉시 반환
text
Cache-Control: public, max-age=86400, s-maxage=604800
→ 브라우저는 1일, CDN은 7일 동안 캐싱

기본 상식: 자주 바뀌지 않는 정적 자원은 파일명에 해시를 붙여(main.a1b2c3.js) 영구 캐싱하고, 내용이 바뀌면 파일명 자체가 바뀌게 하는 것이 일반적입니다. 이러면 캐시 무효화를 신경 쓸 필요 없이 "새 파일명 = 새 버전"이 자동으로 보장됩니다.

9. 대규모 트래픽 급증 대응(Spike 대응)#

이벤트·할인 등으로 순간 트래픽이 평소의 수십 배로 튀는 상황에 대비하는 전략입니다.

text
- 오토스케일링: 트래픽에 따라 서버 대수를 자동으로 늘림(단, 즉시 늘어나지 않으므로
  미리 예측되는 이벤트는 사전 스케일 업 권장)
- 대기열(Queue) 도입: 순간적으로 몰리는 요청(선착순 이벤트 등)을 큐에 넣고
  처리 가능한 속도로만 뒤에서 소화 — 서버가 죽는 대신 사용자는 대기 화면을 봄
- 서킷 브레이커: 특정 하위 시스템이 느려지면 그 기능만 일시적으로 차단해
  전체 서비스가 함께 무너지는 것을 막음
- Rate Limiting: 악의적/비정상 트래픽을 정상 사용자와 구분해 우선 차단

실무 팁: 선착순 이벤트처럼 예측 가능한 대량 트래픽은 "얼마나 견딜 수 있는가"를 사전 부하 테스트로 확인하고, 견딜 수 있는 한도를 넘는 요청은 서버가 죽는 대신 대기열/안내 화면으로 우아하게 처리하도록 설계합니다.

10. 데이터베이스 커넥션 풀링 심화#

DB 연결을 매 요청마다 새로 맺으면 연결 수립 자체에 시간이 걸립니다. 미리 맺어둔 연결을 재사용하는 것이 커넥션 풀입니다.

text
연결 풀이 없을 때: 요청마다 "TCP 연결 → 인증 → 쿼리 → 연결 종료"를 반복 → 매번 오버헤드
연결 풀이 있을 때: 미리 맺어둔 연결 여러 개를 재사용 → 쿼리만 바로 실행

풀 크기를 잘못 잡으면 생기는 문제#

text
풀이 너무 작으면: 동시 요청이 많을 때 빈 연결을 기다리는 대기열이 생겨 응답이 느려짐
풀이 너무 크면: DB 서버가 감당할 수 있는 최대 연결 수를 초과해 DB 자체가 거부하거나 느려짐
              (서버 인스턴스가 여러 대면, "인스턴스 수 × 풀 크기"가 DB 최대 연결 수를 넘지 않아야 함)
python
# SQLAlchemy 예시
engine = create_engine(
    DATABASE_URL,
    pool_size=10,       # 기본으로 유지할 연결 수
    max_overflow=5,     # 순간적으로 더 필요할 때 추가로 허용할 연결 수
    pool_timeout=30,    # 빈 연결을 기다리는 최대 시간(초)
    pool_recycle=1800,  # 오래된 연결을 주기적으로 재생성(DB 쪽 타임아웃보다 짧게)
)

기본 상식: 서버 인스턴스를 오토스케일링으로 늘릴 때 커넥션 풀 크기도 함께 고려해야 합니다. 인스턴스 10대가 각각 풀 크기 20을 쓰면 최대 200개 연결이 DB에 몰릴 수 있으므로, DB의 최대 연결 수 설정과 반드시 맞춰봅니다.

11. 비동기 처리와 메시지 큐로 부하 분산#

사용자를 기다리게 하지 않아도 되는 작업(이메일 발송, 썸네일 생성, 통계 집계)을 요청-응답 흐름에서 분리합니다.

text
동기 처리: 사용자가 회원가입 → 이메일 발송까지 끝나야 응답 → 이메일 서버가 느리면 회원가입도 느려짐

비동기 처리: 사용자가 회원가입 → "회원가입 완료" 즉시 응답
            → 이메일 발송 작업을 메시지 큐(Redis Queue, Celery, SQS 등)에 넣음
            → 별도의 워커(worker)가 큐에서 꺼내 백그라운드에서 처리

# Celery 예시
@app.route("/signup", methods=["POST"])

    user = create_user(request.json)
    send_welcome_email.delay(user.id)   # 큐에 작업만 넣고 즉시 반환
    return {"status": "ok"}, 201

@celery.task
def send_welcome_email(user_id):
    ...  # 워커 프로세스에서 별도로 실행됨

기본 상식: 큐에 작업을 넣는 것과 실제로 처리되는 것은 별개입니다. 워커가 다운되거나 큐가 밀리면 작업이 늦게 처리될 수 있으므로, "정확히 언제까지 완료돼야 하는가"에 따라 동기/비동기를 구분합니다 — 결제 승인처럼 즉시 결과를 알아야 하는 작업은 비동기로 미루면 안 됩니다.

12. 프로파일링 도구 활용#

APM으로 "어떤 API가 느린지"를 알았다면, 프로파일러로 "그 API 안의 어느 코드 라인이 느린지"까지 파고듭니다.

python
import cProfile

cProfile.run("process_large_report()")
# 함수별 호출 횟수, 누적 시간을 출력해 어떤 함수가 전체 시간의 대부분을 차지하는지 확인
text
프로파일링 결과 읽는 법:
- 호출 횟수는 적은데 시간이 오래 걸리는 함수 → 그 함수 자체의 로직 최적화 대상
- 호출 횟수가 비정상적으로 많은 함수 → 불필요하게 반복 호출되고 있을 가능성
  (예: 반복문 안에서 매번 DB 쿼리를 날리는 N+1 문제)

기본 상식: 프로파일링은 상시로 켜두지 않습니다. 프로파일러 자체가 실행 속도를 늦추므로, 문제가 재현되는 특정 상황에서만 짧게 켜서 측정하고 바로 끕니다. 운영 환경에서는 샘플링 방식(전체 요청 중 일부만 프로파일링)을 쓰는 것이 일반적입니다.

13. 용량 계획 (Capacity Planning)#

트래픽이 늘어날 것을 미리 예측해, 언제 얼마나 서버를 늘려야 하는지 계획하는 작업입니다.

text
1. 현재 서버 한 대(또는 한 단위)가 초당 처리 가능한 요청 수를 부하 테스트로 확인
   예: 서버 1대 = 초당 200 요청까지 안정적으로 처리(p99 300ms 이내)

2. 예상 트래픽을 추정
   예: 다음 분기 마케팅으로 동시 접속자가 현재의 3배로 예상

3. 필요한 서버 대수를 역산
   예: 현재 5대로 초당 1,000 요청을 처리 중 → 3배 트래픽이면 최소 15대 필요
      (안전 마진을 더해 여유 있게 산정)

4. 오토스케일링 정책의 상한선(최대 인스턴스 수)을 이 값 이상으로 미리 설정해둠

기본 상식: 오토스케일링이 설정되어 있어도 "최대 인스턴스 수" 상한을 낮게 잡아두면 트래픽 급증 시 그 이상 늘어나지 못하고 막힙니다. 예측 가능한 큰 이벤트(할인 행사, 대규모 마케팅) 전에는 상한을 미리 올려두고, 이벤트가 예측 범위를 넘어설 경우를 대비해 앞 장의 대기열·서킷 브레이커 같은 안전장치도 함께 준비합니다.
