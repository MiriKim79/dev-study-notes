🧪 자격증 대비

CSTS 대비 가이드

테스트 코드는 짜봤다? 이제 테스트 설계 기법과 결함 관리 이론으로 검증해볼 차례입니다.

📘 문서 소개
대상: 테스트 자동화 중급 가이드로 실무 테스트 코드는 짜봤고, 소프트웨어 테스트 전문가(CSTS) 자격증으로 이론까지 검증받고 싶은 사람
목적: 소프트웨어 테스트의 표준 이론(테스트 레벨, 설계 기법, 결함 관리)을 정리합니다
사용법: 이 문서는 공식 교재 『소프트웨어 테스트 전문가(CSTS) 가이드』의 4개 구성(테스트 개요·테스트 설계기법·테스트 프로세스·자격시험 예제)에 맞춰 내용을 정리했습니다. 시행 기관은 한국정보통신기술협회(TTA)이며, 정확한 문항 수·접수 일정은 이 문서가 다루지 않으니 응시 전에는 반드시 TTA 자격시험 소개에서 최신 공식 공고를 직접 확인하세요.
📝 이 문서는 핵심 요약노트입니다. 정식 교재를 대체하지 않습니다 — 감을 잡고 복습하는 용도로 쓰고, 실전 대비는 공식 교재와 기출문제로 함께 준비하세요.

🎯 이 문서로 얼마나 커버되나#

이 문서 내용을 완전히 이해하면 CSTS 시험에서 다루는 표준 테스트 이론(테스트 원칙, V-모델, 설계 기법, 결함 관리 프로세스)의 핵심은 대부분 다루게 됩니다. 다만 실제 시험은 공식 교재의 세부 용어 정의·사례 응용 문제가 나올 수 있어, 정식 교재와 기출 유형 문제를 함께 준비하는 것을 권장합니다. 정확한 합격 기준(과락 여부, 커트라인 점수)은 시행기관(TTA) 공지를 확인하세요.

0. 시작 전에 — 자주 나오는 용어#

테스트 자동화 중급 가이드에서 다룬 단위/통합/E2E 테스트, TDD, Mock/Stub 개념은 이미 안다고 가정합니다. 여기서는 이 문서에서 새로 나오는 이론 용어만 정리합니다.

용어쉬운 설명
오류(Error)사람이 실수하는 것(코드를 잘못 짬)
결함(Defect/Bug)그 실수가 코드에 남아있는 상태
실패(Failure)그 결함이 실제 실행 중에 겉으로 드러나는 것(화면에 오류가 뜸)
테스트 오라클(Test Oracle)"이 결과가 맞는지 틀린지" 판단하는 기준(예상 결과)
V-모델개발 단계(요구사항→설계→구현)와 테스트 단계(인수→시스템→통합→단위)를 짝지어 보여주는 모델
블랙박스 테스트내부 코드는 보지 않고, 입력과 출력만으로 테스트 케이스를 설계하는 방식
화이트박스 테스트내부 코드 구조(분기, 경로)를 보고 테스트 케이스를 설계하는 방식
동등 분할(Equivalence Partitioning)비슷하게 동작할 것으로 예상되는 입력값들을 그룹으로 묶어, 그룹당 대표값 하나만 테스트하는 기법
경계값 분석(Boundary Value Analysis)오류가 몰리기 쉬운 값의 경계(최솟값, 최댓값, 경계 바로 앞뒤)를 집중적으로 테스트하는 기법
결정 테이블(Decision Table)여러 조건의 조합에 따라 결과가 달라질 때, 그 조합을 표로 정리해 빠짐없이 테스트하는 기법
검증(Verification)산출물이 명세(설계 문서 등)와 일치하는지 확인하는 것 — "올바르게 만들고 있는가"
확인(Validation)실제 사용자의 요구를 충족하는지 확인하는 것 — "올바른 것을 만들고 있는가"
상태 전이 테스트(State Transition Testing)상태가 바뀌는 기능에서, 허용되는/허용되지 않는 상태 변화를 모두 테스트하는 기법
탐색적 테스트(Exploratory Testing)미리 케이스를 다 정하지 않고, 테스트하며 배운 내용으로 다음 테스트를 즉석에서 설계하는 방식
테스트 독립성(Test Independence)테스트를 코드 작성자 본인이 아니라 다른 사람·조직이 수행하는 정도
회귀 테스트(Regression Testing)코드가 바뀐 뒤, 이미 잘 되던 기존 기능이 그대로 잘 되는지 다시 확인하는 테스트
재테스트(Confirmation Testing)수정을 요청했던 그 결함이 실제로 고쳐졌는지만 확인하는 테스트 (회귀 테스트와는 확인 대상이 다름)
스모크 테스트(Smoke Test)본격적인 테스트를 시작하기 전, 핵심 기능이 최소한 동작은 하는지 짧게 훑어보는 테스트
리스크 기반 테스트(Risk-Based Testing)결함 발생 가능성과 발생 시 영향도가 큰 부분부터 우선적으로 테스트하는 전략
정적 테스트 / 동적 테스트정적 테스트는 코드를 실행하지 않고 검토(리뷰, 정적 분석)하는 것, 동적 테스트는 실제로 실행해서 확인하는 것
조건/결정 커버리지, 조건 조합 커버리지분기 커버리지보다 더 엄격한 화이트박스 기준 — 조건/결정 커버리지는 개별 조건의 참/거짓과 전체 분기 결과까지, 조건 조합 커버리지(MCC)는 여러 조건의 모든 참/거짓 조합까지 실행했는지 확인

1. 소프트웨어 테스트의 기본 원칙#

검증(Verification)과 확인(Validation)#

테스트 이론에서 가장 먼저 구분해야 하는 두 단어입니다.

text
검증(Verification): "제품을 올바르게 만들고 있는가?" — 산출물이 명세(설계 문서 등)와 일치하는지 확인
확인(Validation):   "올바른 제품을 만들고 있는가?" — 실제 사용자의 요구를 충족하는지 확인

기본 상식: 검증을 통과해도 확인에서 떨어질 수 있습니다 — 설계 문서대로 완벽하게 구현했어도(검증 통과), 그 설계 자체가 사용자가 원하는 게 아니었다면(확인 실패) 쓸모없는 소프트웨어가 됩니다. 이것이 아래 "오류-부재의 궤변" 원칙과 이어집니다.

테스트의 7가지 기본 원칙#

테스트 이론에서 공통적으로 다루는 원칙들입니다. 특정 도구나 언어와 무관하게 "테스트를 대하는 태도"에 가깝습니다.

원칙의미
결함이 있음을 보여줄 뿐 없음을 증명하지 못함테스트를 통과해도 "버그가 없다"가 아니라 "발견한 버그가 없다"는 뜻
완벽한 테스트는 불가능가능한 모든 입력·경로를 다 테스트할 수는 없으므로, 위험도 기준으로 우선순위를 정함
조기 테스트(Early Testing)결함은 발견이 늦어질수록 고치는 비용이 커짐 — 요구사항 단계부터 테스트를 고려
결함 집중(Defect Clustering)결함은 몇몇 모듈에 몰려있는 경향이 있음(파레토 법칙과 유사)
살충제 패러독스(Pesticide Paradox)같은 테스트 케이스를 계속 반복하면 새로운 결함을 못 찾게 됨 — 테스트도 주기적으로 갱신 필요
테스트는 정황 의존적게임 앱과 의료기기 소프트웨어는 테스트 방식·강도가 달라야 함
오류-부재의 궤변(Absence-of-Errors Fallacy)버그를 다 고쳐도,애초에 잘못된 요구사항을 구현했다면 쓸모없는 소프트웨어가 됨

2. 테스트 레벨 — V-모델#

text
요구사항 분석 ─────────────── 인수 테스트(Acceptance Test)
    설계 ──────────────────── 시스템 테스트(System Test)
        상세 설계 ──────────── 통합 테스트(Integration Test)
            구현(코딩) ─────── 단위 테스트(Unit Test)

각 개발 단계에서 나온 산출물(요구사항 문서, 설계 문서)이 바로 그 레벨의 테스트 기준이 됩니다. 예를 들어 인수 테스트는 요구사항 문서를 기준으로, 단위 테스트는 코드 자체를 기준으로 통과 여부를 판단합니다.

레벨무엇을 확인하는가이 사이트와 연결
단위 테스트함수·컴포넌트 하나가 의도대로 동작하는가테스트 자동화 중급 가이드 1장
통합 테스트여러 모듈이 맞물려 동작하는가테스트 자동화 중급 가이드 1장
시스템 테스트전체 시스템이 요구된 기능·성능을 만족하는가성능·스케일 고급 가이드(성능 측면)
인수 테스트실제 사용자·발주자 관점에서 받아들일 만한가팀 개발 시작 가이드(요구사항 확인)

3. 테스트 설계 기법#

블랙박스 기법 — 명세(입출력) 기준#

text
예: 나이 입력값에 따라 "미성년자/성인" 분류하는 기능 (경계: 19세)

동등 분할: [0~18세] 그룹에서 하나, [19세 이상] 그룹에서 하나 — 총 2개만 테스트해도 충분
경계값 분석: 18세, 19세(경계 바로 앞뒤)를 정확히 테스트 — 경계 오류(< 를 <= 로 잘못 쓰는 실수)를 가장 잘 잡아냄

기본 상식: 실무 경험상 버그는 "평범한 값"보다 "경계에 딱 걸치는 값"에서 훨씬 자주 발생합니다. 동등 분할로 테스트 개수를 줄이고, 경계값 분석으로 그 안에서 가장 위험한 지점을 정확히 겨냥하는 것이 효율적인 조합입니다.

결정 테이블 — 조건 조합이 많을 때#

text
예: "회원 등급"과 "쿠폰 보유 여부"에 따라 할인율이 달라지는 기능

| 회원 등급=VIP | 쿠폰 보유 | 결과      |
|---------------|-----------|-----------|
| Y             | Y         | 30% 할인  |
| Y             | N         | 20% 할인  |
| N             | Y         | 10% 할인  |
| N             | N         | 할인 없음 |

조건이 여러 개 얽혀 있을 때, 감으로 케이스를 뽑으면 조합을 빠뜨리기 쉽습니다. 표로 모든 조합을 나열하면 누락 없이 테스트 케이스를 뽑을 수 있습니다.

상태 전이 테스트 — 상태에 따라 동작이 달라질 때#

text
예: 주문 상태가 [결제대기 → 결제완료 → 배송중 → 배송완료]로 바뀌는 기능

각 상태에서 "허용되는 전환"과 "허용되지 않는 전환"을 모두 테스트
- 정상: 결제대기 → 결제완료 (허용)
- 비정상: 배송완료 → 결제대기로 되돌리기 시도 (허용되면 안 됨 — 이걸 확인하는 게 핵심)

로그인 상태, 주문 상태, 신호등처럼 "지금 상태에 따라 다음에 할 수 있는 행동이 달라지는" 기능에 씁니다. 정상적인 상태 전환뿐 아니라, 일어나면 안 되는 전환을 시도했을 때 실제로 막히는지까지 확인하는 것이 핵심입니다.

경험 기반 테스트#

text
탐색적 테스트(Exploratory Testing): 미리 케이스를 다 정해두지 않고, 테스트하면서 학습한 내용을 바탕으로
                                    다음 테스트를 즉석에서 설계해나가는 방식
오류 추정법(Error Guessing): 과거 경험·직관으로 "여기서 버그가 날 것 같다"는 부분을 우선 집중 테스트

기본 상식: 경험 기반 기법은 "체계적이지 않다"는 뜻이 아니라, 문서화된 명세만으로는 못 찾는 결함(문서에 없는 예외 상황 등)을 찾는 데 강점이 있습니다. 동등분할·경계값분석 같은 명세 기반 기법과 상호 보완적으로 씁니다.

화이트박스 기법 — 코드 구조 기준#

text
구문 커버리지(Statement Coverage): 모든 코드 줄이 최소 한 번은 실행됐는가
분기 커버리지(Branch Coverage): 모든 if/else 분기가 각각 한 번씩은 실행됐는가
경로 커버리지(Path Coverage): 코드가 지날 수 있는 모든 경로(분기의 모든 조합)가 실행됐는가 — 가장 엄격하지만 조건이 많으면 경로 수가 기하급수적으로 늘어남

테스트 자동화 중급 가이드에서 다룬 "커버리지의 함정"과 같은 맥락입니다 — 구문 커버리지 100%여도 특정 조건 조합은 안 돌아봤을 수 있어, 분기·경로 커버리지가 더 엄격한 기준입니다.

커버리지 계산 문제 — 실제로 숫자를 구해보기#

시험에는 간단한 코드나 흐름도를 주고 "이 테스트 케이스들로 구문/분기 커버리지가 몇 %인가"를 직접 계산하게 하는 문제가 나옵니다.

text
function classify(score) {
  if (score >= 90) {         // 분기 1
    grade = 'A';              // 구문 A
  } else {
    grade = 'B';              // 구문 B
  }
  if (score < 0) {            // 분기 2
    grade = 'ERROR';          // 구문 C
  }
  return grade;                // 구문 D
}

이 함수는 구문 4개(A, B, C, D 중 진입 경로에 따라 D는 항상 실행)와 분기 2개(if 2개, 각각 참/거짓 총 4가지 분기 결과)로 이루어져 있습니다.

테스트 케이스score실행되는 구문실행되는 분기
TC195A, D분기1-참, 분기2-거짓
TC250B, D분기1-거짓, 분기2-거짓

두 if문은 else-if로 묶이지 않은 독립된 조건문이므로, 모든 입력에서 두 조건이 각각 평가됩니다. TC1, TC2 두 개만 실행하면 구문 A, B, D는 실행됐지만 C(분기2-참, score < 0)는 한 번도 실행되지 않았습니다.

  • 구문 커버리지 = (실행된 구문 수) ÷ (전체 구문 수) = 3 ÷ 4 = 75%
  • 분기 커버리지 = (실행된 분기 결과 수) ÷ (전체 분기 결과 수) = 3 ÷ 4 = 75% (분기1-참, 분기1-거짓, 분기2-거짓은 실행, 분기2-참만 미실행)

구문 커버리지 100%, 분기 커버리지 100%를 모두 만들려면 score = -5(분기2-참, 구문 C 실행) 케이스를 TC3으로 추가해야 합니다.

기본 상식: "구문 커버리지가 100%면 분기 커버리지도 항상 100%다"는 틀린 문장입니다. 반대(분기 커버리지 100% → 구문 커버리지 100%)는 일반적으로 성립하지만, 구문 커버리지만으로는 if 문의 거짓 분기(else가 생략된 경우 등)를 놓칠 수 있습니다. 이 비대칭 관계를 묻는 문제가 자주 나옵니다.

결정 테이블 — 조합 개수 계산#

조건이 n개이고 각 조건이 참/거짓 2가지 값을 가지면, 이론상 최대 조합 수는 2ⁿ개입니다.

text
조건이 3개(회원등급 Y/N, 쿠폰보유 Y/N, 첫구매 Y/N)면 → 2³ = 8가지 조합

실제 시험에서는 "조건이 4개일 때 완전 결정 테이블의 최대 규칙(조합) 수는?"처럼 2ⁿ 계산을 직접 묻는 문제가 나옵니다(조건 4개 → 2⁴ = 16가지). 다만 실무·시험 모두 이 중 "말이 되지 않는 조합"이나 "결과가 같은 조합"은 합쳐서 축약 결정 테이블로 정리하는 경우가 많습니다.

4. 테스트 프로세스#

테스트도 "그냥 실행하고 끝"이 아니라 정해진 단계를 따라 진행합니다.

text
1. 테스트 계획 및 통제(Planning & Control) — 무엇을, 얼마나, 어떤 순서로 테스트할지 정함
2. 테스트 분석 및 설계(Analysis & Design) — 요구사항을 바탕으로 테스트 케이스를 뽑음(2장의 동등분할·경계값분석 등)
3. 테스트 구현 및 실행(Implementation & Execution) — 테스트 케이스를 실제 스크립트·수동 절차로 만들고 실행
4. 완료 평가 및 보고(Evaluating Exit Criteria & Reporting) — "충분히 테스트했는가"를 판단하고 결과를 보고
5. 테스트 종료 활동(Closure) — 다음 프로젝트를 위해 결과·노하우를 정리하고 마무리

기본 상식: 이 단계들은 한 번에 끝나는 게 아니라 반복될 수 있습니다. 예를 들어 실행 중 요구사항이 바뀌면 다시 분석·설계 단계로 돌아가 테스트 케이스를 보완합니다.

결함 관리(Defect Management)#

테스트 실행 중 발견한 결함은 정해진 흐름으로 처리합니다.

text
발견(Detected) → 보고(Reported) → 확인(Confirmed, 담당자 배정)
→ 수정(Fixed) → 재테스트(Retest) → 종료(Closed)

기본 상식: 결함을 보고할 때는 "안 된다"가 아니라 재현 절차(어떤 입력을 어떤 순서로 넣었을 때, 무엇을 기대했는데 실제로 무엇이 나왔는지)를 함께 남겨야 담당자가 바로 재현·수정할 수 있습니다. 이 사이트의 팀 개발 시작 가이드에 있는 "버그 기록 템플릿"과 같은 목적입니다.

심각도(Severity) vs 우선순위(Priority) — 가장 헷갈리는 결함 속성#

text
심각도(Severity): 결함이 시스템에 끼치는 기술적 영향의 크기(얼마나 심각하게 망가지는가)
우선순위(Priority): 결함을 얼마나 빨리 고쳐야 하는가(비즈니스 관점의 시급성)
사례심각도우선순위설명
메인 로고 이미지가 깨져 보임낮음(기능은 정상)높음(첫 화면이라 브랜드 이미지에 즉각 영향)기술적으로는 사소하지만 즉시 고쳐야 함
한 달에 한 번 실행되는 배치 작업이 특정 조건에서 죽음높음(데이터 정합성 깨짐)낮음(다음 실행까지 여유 있음)기술적으로 심각하지만 당장 급하지 않을 수 있음
결제 완료 후 결제 금액이 이중 차감됨매우 높음매우 높음심각도·우선순위 둘 다 최상위

기본 상식: "심각도가 높으면 우선순위도 항상 높다"는 틀린 명제입니다. 둘은 서로 다른 축이며, 심각도는 QA/개발이 기술적으로 판단하고 우선순위는 비즈니스 임팩트를 고려해 결정하는 경우가 많습니다. 이 둘의 조합(높음/낮음 사분면)으로 결함 처리 순서를 정하는 문제가 시험에 자주 나옵니다.

테스트 산출물 메트릭 — 계산 문제 유형#

text
전체 테스트 케이스 300개 중 280개 실행, 20개 미실행
실행된 280개 중 260개 통과, 20개 실패

테스트 실행률 = 실행 케이스 수 ÷ 전체 케이스 수 = 280 ÷ 300 = 약 93.3%
테스트 통과율 = 통과 케이스 수 ÷ 실행 케이스 수 = 260 ÷ 280 = 약 92.9%
결함 발견율(실행 대비) = 실패 케이스 수 ÷ 실행 케이스 수 = 20 ÷ 280 = 약 7.1%

기본 상식: "통과율"의 분모를 "전체 케이스 수"로 할지 "실행된 케이스 수"로 할지 헷갈리기 쉽습니다. 미실행 케이스는 통과도 실패도 아니므로, 통과율은 일반적으로 실행된 케이스 중 통과 비율로 계산합니다. 시험에서 분모를 다르게 낚는 함정 보기가 자주 나오므로, 문제에서 "전체 대비"인지 "실행 대비"인지를 정확히 읽어야 합니다.

테스트 독립성#

text
독립성이 가장 낮음: 개발자 본인이 자기 코드를 테스트
독립성이 가장 높음: 개발 조직과 분리된 별도 테스트 전담 조직/외부 기관이 테스트

기본 상식: 자기가 짠 코드는 "당연히 되겠지"라는 가정이 무의식중에 섞여서, 정작 자신이 놓친 케이스를 스스로 찾기 어렵습니다. 독립성이 높을수록 이런 사각지대를 더 잘 찾아내지만, 그만큼 비용과 시간이 더 듭니다. 상황에 맞는 수준의 독립성을 선택하는 것이 원칙입니다.

5. 연습문제#

⚠️ 아래 문제는 개념 이해를 돕기 위해 직접 만든 연습문제이며, 실제 CSTS 기출문제가 아닙니다.

문제 1. 같은 테스트 케이스를 계속 반복 실행하면 새로운 결함을 더는 찾지 못하게 되는 현상을 가리키는 원칙은? A) 결함 집중(Defect Clustering) B) 살충제 패러독스(Pesticide Paradox) C) 오류-부재의 궤변 D) 조기 테스트

문제 2. "18세, 19세"처럼 경계에 딱 걸치는 값을 집중적으로 테스트하는 기법은? A) 동등 분할 B) 결정 테이블 C) 경계값 분석 D) 상태 전이 테스트

문제 3. "설계 문서대로 완벽하게 구현했지만, 사용자가 원하던 기능이 아니었다"는 상황이 가리키는 것은? A) 검증(Verification)은 통과, 확인(Validation)은 실패 B) 검증도 확인도 모두 통과 C) 검증도 확인도 모두 실패 D) 검증은 실패, 확인은 통과

문제 4. 미리 테스트 케이스를 다 정해두지 않고, 테스트하며 학습한 내용으로 다음 테스트를 즉석에서 설계하는 기법은? A) 경계값 분석 B) 결정 테이블 C) 탐색적 테스트 D) 구문 커버리지

정답: 1번 B / 2번 C / 3번 A / 4번 C

6. 실전 연습문제 (정답 클릭 확인)#

⚠️ 이 섹션의 문제는 실제 기출 유형·난이도를 참고해 새로 만든 오리지널 연습문제이며, 실제 기출문제 원문이 아닙니다. 정답을 클릭하면 해설이 펼쳐집니다.

Q1. 동일한 테스트를 반복하면 더 이상 새로운 결함을 찾지 못하게 되는 현상을 가리키는 테스트 7원칙은? A) 결함 집중(Defect Clustering) B) 살충제 패러독스(Pesticide Paradox) C) 오류-부재의 궤변(Absence-of-errors Fallacy) D) 테스팅은 정황 의존적(Testing is Context Dependent)

정답 보기

정답: B

같은 테스트 케이스를 반복하면 새로운 결함을 찾는 효과가 줄어드는 현상을 살충제 패러독스라 하며, 테스트 케이스를 주기적으로 수정·추가해야 합니다.

Q2. V-모델에서 '요구사항 분석' 단계와 대응되는 테스트 레벨은? A) 단위 테스트 B) 통합 테스트 C) 시스템 테스트 D) 인수 테스트

정답 보기

정답: D

V-모델은 왼쪽 개발 단계와 오른쪽 테스트 레벨이 대응됩니다. 요구사항 분석은 인수 테스트, 아키텍처 설계는 시스템 테스트, 상세 설계는 통합 테스트, 코딩은 단위 테스트와 짝을 이룹니다.

Q3. 프로그램의 내부 구조(코드)를 보지 않고 입력과 출력만으로 테스트 케이스를 설계하는 기법 범주는? A) 화이트박스 테스트 B) 블랙박스 테스트 C) 회색박스 테스트 D) 구조 기반 테스트

정답 보기

정답: B

블랙박스 테스트는 내부 구현을 몰라도 명세(요구사항)를 기준으로 입력·출력을 검증하는 기법으로, 동등 분할·경계값 분석 등이 대표적입니다.

Q4. '20세 미만은 청소년 요금, 20세 이상은 성인 요금'이라는 조건에서 19세, 20세를 집중적으로 테스트하는 기법은? A) 동등 분할(Equivalence Partitioning) B) 결정 테이블(Decision Table) C) 경계값 분석(Boundary Value Analysis) D) 상태 전이 테스트(State Transition Testing)

정답 보기

정답: C

경계값 분석은 조건이 갈리는 경계 지점(19세/20세) 근처 값을 집중적으로 테스트해 경계에서 발생하는 결함을 찾는 기법입니다.

Q5. (OX) 검증(Verification)은 '제품을 올바르게 만들었는가'를, 확인(Validation)은 '올바른 제품을 만들었는가'를 다룬다.

정답 보기

정답: O

검증은 명세·설계 문서대로 제대로 구현했는지를 보는 것이고, 확인은 실제 사용자 요구를 충족하는지를 보는 것입니다.

Q6. (OX) 테스트를 아무리 철저히 해도 소프트웨어에 결함이 없다는 것을 증명할 수는 없다.

정답 보기

정답: O

'오류-부재의 궤변' 원칙에 따르면, 결함을 찾지 못했다고 해서 소프트웨어에 결함이 없다는 뜻은 아니며, 사용자 요구를 만족하지 못하면 여전히 실패입니다.

Q7. 결함(Defect) 생명주기에서 개발자가 수정 완료 후 테스터가 재검증하기 전 단계로 가장 알맞은 상태는? A) New(신규) B) Fixed(수정 완료, 검증 대기) C) Closed(종료) D) Rejected(반려)

정답 보기

정답: B

일반적인 결함 생명주기는 New → Assigned → Fixed → Retest → Closed(또는 Reopened) 흐름을 따르며, Fixed는 수정은 됐지만 아직 재검증되지 않은 상태입니다.

Q8. 테스트 케이스를 사전에 문서로 다 정하지 않고, 탐색하며 학습한 내용을 바탕으로 즉석에서 다음 테스트를 설계하는 기법은? A) 결정 테이블 테스트 B) 경계값 분석 C) 탐색적 테스트(Exploratory Testing) D) 페어와이즈 테스트

정답 보기

정답: C

탐색적 테스트는 사전 스크립트 없이 테스터의 학습과 판단을 바탕으로 테스트 설계·실행을 동시에 진행하는 접근법입니다.

Q9. (단답형) 여러 조건의 조합과 그에 따른 결과를 표 형태로 정리해 테스트 케이스를 도출하는 블랙박스 기법의 이름은?

정답 보기

정답: 결정 테이블 테스트(Decision Table Testing)

결정 테이블은 여러 조건의 참/거짓 조합과 그에 따른 동작(결과)을 표로 정리해 조합 누락 없이 테스트 케이스를 도출하는 기법입니다.

Q10. (단답형) 코드의 모든 실행 가능한 문장을 최소 한 번씩 실행하도록 테스트 케이스를 설계하는 화이트박스 커버리지 기준은?

정답 보기

정답: 구문 커버리지(Statement Coverage)

구문 커버리지는 화이트박스 테스트의 가장 기본적인 커버리지 기준으로, 모든 코드 라인이 최소 한 번은 실행되는지를 측정합니다.

Q11. 요구사항 정의부터 시스템 테스트까지 각 개발 단계와 대응하는 테스트 레벨을 V자 모양으로 표현하는 V-모델에서, '시스템 설계' 단계와 대응되는 테스트 레벨은? A) 단위 테스트 B) 통합 테스트 C) 시스템 테스트 D) 인수 테스트

정답 보기

정답: C

V-모델에서는 요구사항 분석↔인수 테스트, 아키텍처 설계↔시스템 테스트, 상세(시스템) 설계↔통합 테스트, 모듈 설계↔단위 테스트가 서로 대응됩니다. (교재에 따라 아키텍처/상세설계 명칭 차이가 있을 수 있습니다.)

Q12. 테스트 케이스를 실행한 결과와 기대 결과가 다를 때, 이를 기록하고 추적·관리하는 문서화된 문제를 무엇이라 하는가? A) 이슈(Issue) B) 결함(Defect) C) 리스크(Risk) D) 요구사항(Requirement)

정답 보기

정답: B

결함(Defect/Bug)은 예상 결과와 실제 결과의 불일치를 가리키는 표준 용어로, 발견부터 수정, 재검증까지의 생명주기를 거쳐 관리됩니다.

Q13. 테스트 대상 프로그램의 실행 흐름을 제어하는 조건문에서, 모든 조건의 참/거짓 조합을 각각 한 번 이상 실행하도록 설계하는 화이트박스 커버리지 기법은? A) 문장 커버리지(Statement Coverage) B) 분기 커버리지(Branch Coverage) C) 조건/결정 커버리지(Condition/Decision Coverage) D) 조건 조합 커버리지(Multiple Condition Coverage)

정답 보기

정답: D

조건 조합 커버리지는 조건문 내 여러 조건들의 모든 참/거짓 조합을 테스트해 가장 높은 수준의 커버리지를 요구합니다. 분기 커버리지는 전체 분기의 참/거짓 결과만 각각 한 번씩 실행되면 충족됩니다.

Q14. 리스크 기반 테스트(Risk-Based Testing)에서 테스트 우선순위를 정할 때 주로 고려하는 두 가지 요소는? A) 테스트 케이스 수와 소요 시간 B) 결함 발생 가능성과 발생 시 영향도(비즈니스 임팩트) C) 테스터의 숙련도와 인원 수 D) 개발 언어와 플랫폼

정답 보기

정답: B

리스크 기반 테스트는 한정된 자원으로 효율적으로 테스트하기 위해, 결함이 발생할 가능성(확률)과 발생했을 때의 비즈니스 영향도를 곱해 우선순위 높은 영역에 테스트를 집중합니다.

Q15. 이미 통과했던 기능이 새로운 코드 변경으로 인해 다시 깨졌는지 확인하기 위해 반복 수행하는 테스트는? A) 회귀 테스트(Regression Test) B) 스모크 테스트(Smoke Test) C) 탐색적 테스트(Exploratory Test) D) 인수 테스트(Acceptance Test)

정답 보기

정답: A

회귀 테스트는 코드 변경(버그 수정, 기능 추가)이 기존에 정상 동작하던 기능에 영향을 주지 않았는지 재확인하는 테스트입니다.

Q16. (OX) 스모크 테스트(Smoke Test)는 배포된 빌드가 기본적인 핵심 기능이라도 동작하는지 짧게 확인해, 본격적인 테스트를 진행할 가치가 있는지 판단하는 목적으로 수행한다.

정답 보기

정답: O

스모크 테스트는 "이 빌드가 테스트할 가치가 있는 상태인가"를 빠르게 확인하는 최소한의 검증으로, 핵심 기능이 아예 동작하지 않으면 본 테스트를 진행하지 않고 빌드를 반려합니다.

Q17. (단답형) 테스트 프로세스에서 '테스트 계획 → 테스트 분석/설계 → 테스트 구현 → 테스트 실행 → 종료 기준 평가 및 리포팅 → 테스트 종료 활동'의 흐름을 정의한 국제 표준(테스트 프로세스 프레임워크)의 이름은 무엇인가?

정답 보기

정답: ISTQB(국제소프트웨어테스팅자격위원회) 표준 테스트 프로세스 / ISO/IEC/IEEE 29119

ISTQB 실러버스와 ISO/IEC/IEEE 29119 표준이 이 표준 테스트 프로세스의 근간이 되며, CSTS를 포함한 다수의 테스트 자격증이 이 흐름을 기준으로 출제됩니다.

7. 합격 꿀팁#

  • 오류·결함·실패, 검증(Verification)·확인(Validation)처럼 비슷해 보이는 용어의 정의 차이를 정확히 구분하는 것이 이 시험의 핵심입니다. 실무 감각만으로는 헷갈리기 쉬운 부분이라 별도로 정리해두세요.
  • 이론만 외우지 말고, 직접 짜본 테스트 코드에 각 기법(동등 분할, 경계값 분석)을 매칭해보세요. "내가 이미 이렇게 하고 있었구나"를 확인하면 암기가 훨씬 쉬워집니다.
  • 결함 생명주기는 GitHub Issues 같은 실제 이슈 트래커의 상태 흐름(열림→진행중→해결→종료)과 연결지어 외우면 오래 남습니다.

8. 자주 하는 실수#

  • 테스트 통과를 "버그가 없다"는 증명으로 착각
  • 동등 분할만 하고 경계값을 따로 챙기지 않아 경계 오류를 놓침
  • 결함 보고서에 재현 절차 없이 "안 됨"만 적어 담당자가 재현을 못함
  • 구문 커버리지만 보고 분기 커버리지를 확인하지 않음
  • 조건 조합이 여러 개인데 결정 테이블 없이 감으로 케이스를 뽑아 조합을 빠뜨림

9. 실전 체크리스트#

  • 오류·결함·실패 세 단어의 차이를 설명할 수 있는가
  • 검증(Verification)과 확인(Validation)의 차이를 설명할 수 있는가
  • V-모델에서 각 개발 단계와 짝지어지는 테스트 레벨을 아는가
  • 동등 분할과 경계값 분석을 함께 적용해본 적이 있는가
  • 조건 조합이 복잡한 기능에 결정 테이블을 그려본 적이 있는가
  • 상태가 바뀌는 기능에서 허용되지 않는 전환까지 테스트하는가
  • 명세 기반 기법과 경험 기반 기법(탐색적 테스트)의 차이를 아는가
  • 결함 생명주기(발견→보고→확인→수정→재테스트→종료)를 설명할 수 있는가
  • 정확한 시행 기관과 최신 시험 범위를 공식 공고에서 확인했는가

10. 진짜 기출문제·정확한 시험 정보는 여기서#

이 문서는 소프트웨어 테스트 분야의 표준 이론을 정리한 것으로, 특정 회차의 공식 시험 공고를 대체하지 않습니다. CSTS(SW 테스트 전문가)의 시행 기관은 한국정보통신기술협회(TTA)이며, 다음 공식 페이지에서 최신 정보를 확인할 수 있습니다.

  • TTA 자격시험 소개 — 자격시험 소개·공지사항 페이지
  • TTA 아카데미 교육/자격시험 안내 — 교육 과정 및 자격시험 안내
  • 민간자격정보서비스(PQI) 등록 정보 — 국가 등록 민간자격 공식 정보

다만 위 페이지들이 기출문제를 직접 다운로드할 수 있는 전용 게시판을 제공한다고 단정할 수는 없으므로, 정확한 시험 범위·일정·기출 자료 공개 여부는 위 사이트의 공지사항을 통해 직접 확인하세요.

12. 자주 헷갈리는 개념 정리#

헷갈리는 짝구분
검증(Verification) vs 확인(Validation)검증은 "명세대로 만들었는가"(Are we building the product right?), 확인은 "필요한 것을 만들었는가"(Are we building the right product?)
결함(Defect) vs 오류(Error) vs 실패(Failure)오류는 사람의 실수, 결함은 코드에 남은 잘못(버그), 실패는 결함이 실행되어 실제로 드러난 증상
블랙박스 vs 화이트박스 테스트블랙박스는 내부 구조를 모르고 입출력만으로 테스트(동등분할 등), 화이트박스는 내부 코드 구조를 보고 테스트(구문/분기 커버리지)
단위 vs 통합 vs 시스템 vs 인수 테스트V-모델의 4단계 순서 — 단위(모듈 하나) → 통합(모듈 간 연동) → 시스템(전체 요구사항) → 인수(실사용자 관점 최종 확인)
회귀 테스트 vs 재테스트(Confirmation Test)재테스트는 수정한 결함이 실제로 고쳐졌는지 확인, 회귀 테스트는 그 수정이 다른 기능을 망가뜨리지 않았는지 확인
정적 테스트 vs 동적 테스트정적 테스트는 코드를 실행하지 않고 검토(리뷰, 정적 분석), 동적 테스트는 실제로 실행해서 확인

13. 시험 직전 최종 점검 리스트#

  • 테스트의 7가지 기본 원칙을 순서 없이도 모두 나열할 수 있는가
  • 동등분할·경계값분석의 차이와 실제 테스트 케이스 도출 예시를 만들 수 있는가
  • 구문 커버리지와 분기(결정) 커버리지의 차이와 각각의 한계를 아는가
  • 테스트 프로세스(계획→분석/설계→구현→실행→종료) 각 단계의 산출물을 아는가
  • 결함 리포트에 반드시 포함되어야 할 항목(재현 절차, 기대/실제 결과, 심각도)을 아는가
  • 탐색적 테스트가 명세 기반 기법을 보완하는 이유를 설명할 수 있는가
