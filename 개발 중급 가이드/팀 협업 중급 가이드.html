1. 코드 리뷰 문화#

좋은 리뷰 코멘트#

text
나쁜 예: "이거 이상한데요"
좋은 예: "이 부분에서 course가 None이면 course.title에서 오류가 날 것 같습니다.
         널 체크를 먼저 하는 게 어떨까요?"
  • 무엇이 문제인지 + 왜 문제인지 + (가능하면) 대안을 함께 씁니다.
  • 사람이 아니라 코드에 대한 코멘트로 씁니다. ("이 로직이" ⭕ / "당신이 짠 게" ❌)
  • 취향 차이(const vs let처럼 결과가 같은 경우)는 "선택 사항입니다"라고 명시해 필수 수정처럼 보이지 않게 합니다.
  • 잘한 부분에도 코멘트를 남깁니다. 리뷰가 지적만 하는 자리가 아니라는 걸 팀 전체가 느끼게 합니다.

리뷰 SLA (얼마나 빨리 봐줄 것인가)#

리뷰가 늦어지면 PR이 쌓이고 브랜치가 오래되어 충돌이 커집니다. 팀 규칙으로 "PR 올라오면 하루 안에 최소 1차 코멘트"처럼 기준을 정해두면 병목을 줄일 수 있습니다.

리뷰 크기#

리뷰는 변경 줄 수가 커질수록 꼼꼼히 보기 어려워집니다. 큰 기능은 작은 PR 여러 개로 쪼개는 것이 리뷰 품질과 속도 모두에 유리합니다 (기초 문서의 "작업을 작은 단위로 나눈다" 원칙과 같은 맥락입니다).

2. ADR — 설계 결정을 기록하기#

Architecture Decision Record. "왜 이렇게 결정했는지"를 나중에 참고할 수 있게 짧은 문서로 남기는 방법입니다.

md
# ADR-003: 인증 방식으로 세션 대신 JWT 채택

## 상태
채택됨 (2026-03-10)

## 배경
프론트엔드와 백엔드를 다른 도메인에 배포할 예정이라, 쿠키 기반 세션은
CORS·SameSite 설정이 복잡해질 것으로 예상됨.

## 결정
JWT(access token만 사용, refresh 없음)로 인증한다.

## 이유
- 프론트/백엔드 도메인이 달라도 Authorization 헤더로 간단히 처리 가능
- 서버가 세션을 별도로 저장할 필요 없음 (무상태)

## 트레이드오프
- 토큰을 서버에서 강제로 무효화하기 어려움 (로그아웃은 클라이언트에서 토큰 삭제로 처리)
- 만료 시간을 짧게 유지해 위험을 줄임 (12시간)

## 대안으로 검토했으나 채택하지 않은 것
- 세션 + 쿠키: 크로스 도메인 설정이 복잡해 보류

기본 상식: ADR은 "왜 안 그렇게 했는지"까지 남기는 게 핵심입니다. 몇 달 뒤 "왜 이렇게 만들었지?"라는 질문에 코드만 봐서는 답할 수 없는 경우가 많습니다. 새로 합류한 팀원의 온보딩에도 큰 도움이 됩니다.

3. 기술 부채 관리#

기술 부채란#

"지금 당장 동작은 하지만, 나중에 갚아야 할 대가가 있는 선택." 예: 급하게 만드느라 테스트를 안 쓴 코드, 임시로 하드코딩한 값, 리팩토링을 미룬 중복 코드.

식별하고 관리하는 방법#

text
1. 발견 즉시 이슈로 등록 (라벨: tech-debt)
   → 나중에 "그때 그거 뭐였지" 상태로 흩어지지 않게
2. 부채의 영향도로 우선순위화
   → 자주 손대는 파일의 부채 > 거의 안 건드리는 파일의 부채
3. 새 기능 스프린트마다 일정 비율(예: 10~20%)을 부채 정리에 할당

기본 상식: 부채를 "언젠가 다 갚겠다"는 계획은 대체로 실행되지 않습니다. 매 스프린트에 조금씩 정리 시간을 고정으로 넣는 팀이 실제로 부채를 줄입니다.

4. 온보딩 문서화#

새 팀원이 합류했을 때 며칠 안에 첫 PR을 낼 수 있게 하는 문서 체계입니다.

text
README.md
→ 프로젝트가 무엇인지, 로컬 실행 방법 (5분 안에 서버가 떠야 함)

CONTRIBUTING.md
→ 브랜치·커밋·PR 규칙 (이 바인더의 github-collab-template 참고)

docs/architecture.md
→ 전체 구조를 그림 한 장으로 (프론트/백엔드/DB가 어떻게 연결되는지)

docs/adr/
→ 왜 이런 선택을 했는지 (위 2장 참고)

docs/troubleshooting.md
→ 자주 겪는 로컬 환경 문제와 해결법

실무 팁: 새 팀원이 온보딩 중 겪는 문제를 그때그때 troubleshooting.md에 추가하면, 문서가 실제로 부딪힌 문제를 기반으로 계속 자라납니다. 처음부터 완벽하게 쓰려 하지 않습니다.

5. 애자일 실전 — 스프린트 회고 잘하기#

회고가 "다들 괜찮았어요"로 끝나면 다음 스프린트도 똑같이 반복됩니다.

text
Keep (계속 유지할 것)
Problem (문제였던 것)
Try (다음에 시도할 것)
  • Problem은 사람이 아니라 상황을 지적합니다. ("A가 늦게 리뷰해서" ❌ → "리뷰 대기 시간이 평균 2일로 길었다" ⭕)
  • Try는 다음 스프린트에 실제로 실행 가능한 크기로 씁니다. ("소통을 더 잘하자" ❌ → "PR 올리면 팀 채널에 바로 공유하기" ⭕)
  • 이전 회고의 Try가 실제로 지켜졌는지 다음 회고 시작할 때 먼저 확인합니다.

6. 자주 하는 실수#

  • 리뷰 코멘트에 이유 없이 지적만 남겨 방어적인 분위기가 됨
  • 큰 설계 결정을 채팅으로만 논의하고 기록을 남기지 않아 나중에 이유를 아무도 기억 못함
  • 기술 부채를 "나중에 하자"고만 하고 실제 일정에 반영하지 않음
  • 온보딩 문서가 없어 새 팀원마다 같은 질문을 반복해서 받음
  • 회고에서 나온 Try 항목을 다음 스프린트에 아무도 확인하지 않음

7. 실전 체크리스트#

  • 리뷰 코멘트에 이유와 대안을 함께 쓰는가
  • 되돌리기 어려운 설계 결정을 ADR로 남기고 있는가
  • 발견한 기술 부채를 이슈로 등록하고 일정에 일부 반영하는가
  • 새 팀원이 참고할 온보딩 문서(README, 아키텍처, troubleshooting)가 있는가
  • 회고의 Try 항목을 다음 스프린트 시작 시 확인하는가
