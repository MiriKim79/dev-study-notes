> **대상:** 이슈 기반으로 브랜치·PR을 주고받는 흐름에는 익숙하고, 팀이 몇 명 이상으로 늘어난 사람
> **목적:** 코드 자체가 아니라 "여러 명이 함께 오래 일하는 방식"에서 부딪히는 문제를 정리합니다

---

# 0. 시작 전에 — 자주 나오는 용어

기초 가이드에서 다룬 이슈·브랜치·PR·커밋 규칙은 이미 안다고 가정합니다. 여기서는 이 문서에서 새로 나오는 용어만 정리합니다.

| 용어 | 쉬운 설명 |
| --- | --- |
| SLA (Service Level Agreement) | "이 정도 시간 안에는 처리한다"고 팀이 정해둔 기준. 여기서는 "PR 리뷰를 하루 안에 봐준다" 같은 약속 |
| ADR (Architecture Decision Record) | 중요한 설계 결정을 "왜 그렇게 정했는지"까지 남기는 짧은 기록 문서 |
| 기술 부채(Technical Debt) | 지금 당장은 동작하지만, 나중에 시간을 들여 손봐야 할 임시방편 코드나 설계 |
| 온보딩(Onboarding) | 새 팀원이 프로젝트에 적응해서 첫 작업을 할 수 있게 되기까지의 과정 |
| 애자일(Agile) | 큰 계획을 한 번에 세우기보다, 짧은 주기로 작업하고 계속 점검·조정해가는 개발 방식 |
| 스프린트(Sprint) | 애자일에서 보통 1~2주 단위로 정하는 작업 기간 |
| 회고(Retrospective) | 스프린트가 끝난 뒤 무엇이 잘됐고 무엇이 문제였는지 팀이 함께 돌아보는 시간 |
| Keep / Problem / Try | 회고를 진행하는 흔한 형식 — 계속 유지할 것 / 문제였던 것 / 다음에 시도할 것 |

---

# 1. 코드 리뷰 문화

## 좋은 리뷰 코멘트

```text
나쁜 예: "이거 이상한데요"
좋은 예: "이 부분에서 course가 None이면 course.title에서 오류가 날 것 같습니다.
         널 체크를 먼저 하는 게 어떨까요?"
```

- **무엇이 문제인지 + 왜 문제인지 + (가능하면) 대안**을 함께 씁니다.
- 사람이 아니라 코드에 대한 코멘트로 씁니다. ("이 로직이" ⭕ / "당신이 짠 게" ❌)
- 취향 차이(`const` vs `let`처럼 결과가 같은 경우)는 "선택 사항입니다"라고 명시해 필수 수정처럼 보이지 않게 합니다.
- 잘한 부분에도 코멘트를 남깁니다. 리뷰가 지적만 하는 자리가 아니라는 걸 팀 전체가 느끼게 합니다.

## 리뷰 SLA (얼마나 빨리 봐줄 것인가)

리뷰가 늦어지면 PR이 쌓이고 브랜치가 오래되어 충돌이 커집니다. 팀 규칙으로 "PR 올라오면 하루 안에 최소 1차 코멘트"처럼 기준을 정해두면 병목을 줄일 수 있습니다.

## 리뷰 크기

리뷰는 변경 줄 수가 커질수록 꼼꼼히 보기 어려워집니다. 큰 기능은 작은 PR 여러 개로 쪼개는 것이 리뷰 품질과 속도 모두에 유리합니다 (기초 문서의 "작업을 작은 단위로 나눈다" 원칙과 같은 맥락입니다).

---

# 2. ADR — 설계 결정을 기록하기

Architecture Decision Record. "왜 이렇게 결정했는지"를 나중에 참고할 수 있게 짧은 문서로 남기는 방법입니다.

```md
# ADR-003: 인증 방식으로 세션 대신 JWT 채택

## 상태
채택됨 (2026-03-10)

## 배경
프론트엔드와 백엔드를 다른 도메인에 배포할 예정이라, 쿠키 기반 세션은
CORS·SameSite 설정이 복잡해질 것으로 예상됨.

## 결정
JWT(access token만 사용, refresh 없음)로 인증한다.

## 이유
- 프론트/백엔드 도메인이 달라도 Authorization 헤더로 간단히 처리 가능
- 서버가 세션을 별도로 저장할 필요 없음 (무상태)

## 트레이드오프
- 토큰을 서버에서 강제로 무효화하기 어려움 (로그아웃은 클라이언트에서 토큰 삭제로 처리)
- 만료 시간을 짧게 유지해 위험을 줄임 (12시간)

## 대안으로 검토했으나 채택하지 않은 것
- 세션 + 쿠키: 크로스 도메인 설정이 복잡해 보류
```

**기본 상식**: ADR은 "왜 안 그렇게 했는지"까지 남기는 게 핵심입니다. 몇 달 뒤 "왜 이렇게 만들었지?"라는 질문에 코드만 봐서는 답할 수 없는 경우가 많습니다. 새로 합류한 팀원의 온보딩에도 큰 도움이 됩니다.

---

# 3. 기술 부채 관리

## 기술 부채란

"지금 당장 동작은 하지만, 나중에 갚아야 할 대가가 있는 선택." 예: 급하게 만드느라 테스트를 안 쓴 코드, 임시로 하드코딩한 값, 리팩토링을 미룬 중복 코드.

## 식별하고 관리하는 방법

```text
1. 발견 즉시 이슈로 등록 (라벨: tech-debt)
   → 나중에 "그때 그거 뭐였지" 상태로 흩어지지 않게
2. 부채의 영향도로 우선순위화
   → 자주 손대는 파일의 부채 > 거의 안 건드리는 파일의 부채
3. 새 기능 스프린트마다 일정 비율(예: 10~20%)을 부채 정리에 할당
```

**기본 상식**: 부채를 "언젠가 다 갚겠다"는 계획은 대체로 실행되지 않습니다. 매 스프린트에 조금씩 정리 시간을 고정으로 넣는 팀이 실제로 부채를 줄입니다.

---

# 4. 온보딩 문서화

새 팀원이 합류했을 때 며칠 안에 첫 PR을 낼 수 있게 하는 문서 체계입니다.

```text
README.md
→ 프로젝트가 무엇인지, 로컬 실행 방법 (5분 안에 서버가 떠야 함)

CONTRIBUTING.md
→ 브랜치·커밋·PR 규칙 (이 바인더의 github-collab-template 참고)

docs/architecture.md
→ 전체 구조를 그림 한 장으로 (프론트/백엔드/DB가 어떻게 연결되는지)

docs/adr/
→ 왜 이런 선택을 했는지 (위 2장 참고)

docs/troubleshooting.md
→ 자주 겪는 로컬 환경 문제와 해결법
```

**실무 팁**: 새 팀원이 온보딩 중 겪는 문제를 그때그때 `troubleshooting.md`에 추가하면, 문서가 실제로 부딪힌 문제를 기반으로 계속 자라납니다. 처음부터 완벽하게 쓰려 하지 않습니다.

---

# 5. 애자일 실전 — 스프린트 회고 잘하기

회고가 "다들 괜찮았어요"로 끝나면 다음 스프린트도 똑같이 반복됩니다.

```text
Keep (계속 유지할 것)
Problem (문제였던 것)
Try (다음에 시도할 것)
```

- Problem은 사람이 아니라 상황을 지적합니다. ("A가 늦게 리뷰해서" ❌ → "리뷰 대기 시간이 평균 2일로 길었다" ⭕)
- Try는 다음 스프린트에 실제로 실행 가능한 크기로 씁니다. ("소통을 더 잘하자" ❌ → "PR 올리면 팀 채널에 바로 공유하기" ⭕)
- 이전 회고의 Try가 실제로 지켜졌는지 다음 회고 시작할 때 먼저 확인합니다.

---

# 6. 자주 하는 실수

- 리뷰 코멘트에 이유 없이 지적만 남겨 방어적인 분위기가 됨
- 큰 설계 결정을 채팅으로만 논의하고 기록을 남기지 않아 나중에 이유를 아무도 기억 못함
- 기술 부채를 "나중에 하자"고만 하고 실제 일정에 반영하지 않음
- 온보딩 문서가 없어 새 팀원마다 같은 질문을 반복해서 받음
- 회고에서 나온 Try 항목을 다음 스프린트에 아무도 확인하지 않음

---

# 7. 실전 체크리스트

- [ ] 리뷰 코멘트에 이유와 대안을 함께 쓰는가
- [ ] 되돌리기 어려운 설계 결정을 ADR로 남기고 있는가
- [ ] 발견한 기술 부채를 이슈로 등록하고 일정에 일부 반영하는가
- [ ] 새 팀원이 참고할 온보딩 문서(README, 아키텍처, troubleshooting)가 있는가
- [ ] 회고의 Try 항목을 다음 스프린트 시작 시 확인하는가

# 8. 브랜치 전략 심화

## Git Flow vs GitHub Flow vs Trunk-Based

| 전략 | 구조 | 적합한 상황 |
| --- | --- | --- |
| Git Flow | `main`/`develop`/`feature`/`release`/`hotfix` 등 브랜치가 많고 역할이 세분화됨 | 배포 주기가 길고, 여러 버전을 동시에 유지해야 하는 프로젝트 |
| GitHub Flow | `main` + `feature` 브랜치만 사용, 머지되면 바로 배포 | 배포를 자주 하는 웹 서비스(이 저장소도 이 방식에 가까움) |
| Trunk-Based Development | 브랜치 수명을 아주 짧게(하루 이내) 유지하고 자주 `main`에 합침 | 강력한 CI/CD와 기능 플래그를 갖춘 성숙한 팀 |

## 기능 플래그(Feature Flag)

```python
if feature_flags.is_enabled("new_recommendation_engine", user):
    return new_recommend(user)
return legacy_recommend(user)
```

완성되지 않은 기능도 `main`에 미리 합치되, 플래그로 꺼둔 채로 배포합니다. 브랜치 수명을 짧게 유지하면서도 언제든 기능을 켜고 끌 수 있어, Trunk-Based Development의 핵심 도구로 쓰입니다.

# 9. 이슈 트래킹과 우선순위

## 우선순위·심각도 라벨링

```text
Priority: P0(즉시) / P1(이번 스프린트) / P2(다음 스프린트) / P3(백로그)
Severity: Critical(서비스 중단) / Major(주요 기능 장애) / Minor(불편함) / Trivial(사소함)
```

우선순위(언제 할지)와 심각도(얼마나 심각한지)는 다른 축입니다. "심각하지만 드물게 발생하는 버그"와 "사소하지만 모든 사용자가 겪는 버그"의 우선순위는 다르게 매길 수 있습니다.

## 이슈와 PR 연결

```text
이슈: "수강 신청 시 중복 결제 가능 (#42)"
PR 본문: "Closes #42"
→ PR이 머지되면 이슈가 자동으로 닫힘, 이력 추적이 쉬워짐
```

# 10. 원격/비동기 협업

시간대가 다르거나 재택 위주인 팀에서는 실시간 회의보다 비동기 커뮤니케이션이 중심이 됩니다.

```text
비동기 협업이 잘 되는 팀의 특징
- 결정 사항을 채팅 대화가 아니라 문서(ADR, 이슈)에 남김
- "지금 답을 안 주면 회의에서 결정된 대로 진행합니다"처럼 기본값을 명시
- 회의는 "정보 전달"이 아니라 "합의가 필요한 논의"에만 사용하고,
  정보 전달은 문서나 녹화로 대체
```

**기본 상식**: 비동기 협업은 회의를 줄이는 것이 목적이 아니라, "누군가 자리에 없어도 일이 멈추지 않는 것"이 목적입니다. 이를 위해서는 결정 과정과 결과가 항상 텍스트로 남아 있어야 합니다.

# 11. 코드 오너십과 리뷰어 지정

프로젝트가 커지면 "이 부분은 누가 봐야 하는지"를 사람이 매번 기억하기 어려워집니다.

```text
# CODEOWNERS 파일 예시
/frontend/  @frontend-team
/backend/   @backend-team
/docs/      @miri0
```

특정 경로가 수정된 PR이 열리면, 해당 경로의 소유자(owner)가 리뷰어로 자동 지정됩니다. 이 저장소의 "분업 경계"(frontend는 FE, backend는 BE 소유) 같은 규칙을 도구로 강제할 수 있습니다.

**기본 상식**: 오너십을 지정하는 목적은 "이 사람만 고칠 수 있다"가 아니라 "이 사람이 반드시 검토는 한다"입니다. 코드 소유자가 자리를 비웠을 때 리뷰가 막히지 않도록, 팀 단위(개인이 아니라 그룹)로 지정하는 것이 안전합니다.

# 12. 페어/몹 프로그래밍

여러 명이 동시에 하나의 코드를 함께 작성하는 협업 방식입니다.

| 방식 | 인원 | 특징 |
| --- | --- | --- |
| 페어 프로그래밍 | 2명 (운전자 1 + 관찰자 1) | 실시간으로 코드 리뷰가 이루어지는 효과, 역할을 주기적으로 교대 |
| 몹 프로그래밍 | 3명 이상 | 한 명이 타이핑, 나머지는 논의에 참여. 지식이 팀 전체에 가장 빠르게 퍼짐 |

**언제 유용한가**: 복잡한 버그를 추적할 때, 신규 팀원이 코드베이스에 익숙해질 때, 중요한 설계 결정을 내릴 때 특히 효과적입니다. 반대로 단순 반복 작업에는 비효율적이므로 상황에 맞게 선택합니다.

**실무 팁**: 원격 협업에서는 화면 공유 + 짧은 교대 주기(10~15분)로 운영하면 한 사람에게 피로가 몰리는 것을 방지할 수 있습니다.

# 13. 회의 없이 결정하기 — 비동기 의사결정

모든 결정을 회의에서 내리려 하면 일정이 회의 시간에 종속됩니다.

```text
비동기 결정 프로세스 예시
1. 결정이 필요한 사안을 이슈나 문서로 작성 (배경, 옵션, 제안)
2. 관련자에게 공유하고 마감 시한을 명시 ("금요일까지 의견 없으면 안대로 진행")
3. 마감 시한까지 반대 의견이 없으면 제안대로 확정
4. 결정 사항과 이유를 ADR 등 기록에 남김
```

**기본 상식**: 이 방식은 "회의를 아예 없애자"가 아니라, 정보 공유를 위한 회의를 줄이고 회의는 실제로 대면 토론이 필요한 사안에만 쓰자는 것입니다. 모든 결정에 적용하면 오히려 책임 소재가 흐려질 수 있어, 되돌리기 어려운 중요한 결정에는 여전히 실시간 논의를 병행합니다.

# 14. 협업 안티패턴

- **리뷰 병목**: 특정 한 명만 모든 PR을 리뷰해, 그 사람이 자리를 비우면 배포가 멈춤
- **문서 없는 구두 결정**: 회의에서 결정했지만 기록이 없어 나중에 "그런 얘기 없었다"는 논쟁이 반복됨
- **깨진 창문 방치**: 사소한 실패(플레이키 테스트, 경고 로그)를 방치하면 팀 전체가 "실패해도 괜찮다"는 문화에 익숙해짐
- **과도한 동기화**: 모든 작업에 대해 실시간 확인을 요구해, 팀원들이 깊게 집중할 시간을 확보하지 못함
- **일방적 기술 결정**: 팀에 영향을 미치는 결정(새 라이브러리 도입 등)을 합의 없이 혼자 진행

**기본 상식**: 안티패턴 대부분은 "속도를 위해 프로세스를 생략"하는 데서 시작되지만, 장기적으로는 오히려 속도를 떨어뜨립니다. 이 저장소의 "새 라이브러리 도입은 팀 합의 사항" 규칙도 같은 이유로 존재합니다.

# 15. 데일리 스탠드업 잘 운영하기

매일 짧게 모여 진행 상황을 맞추는 회의입니다. 형식은 단순하지만 잘못 운영되면 가장 먼저 시간 낭비 취급을 받는 회의이기도 합니다.

```text
기본 3가지 질문
1. 어제 한 일
2. 오늘 할 일
3. 막힌 것(blocker)이 있는지
```

- **시간 제한을 지킵니다.** 팀 규모에 상관없이 10~15분을 넘기지 않습니다. 길어지면 "스탠드업 중 논의"가 아니라 "스탠드업 후 관련자만 남아서 논의"로 분리합니다.
- **어제/오늘 나열이 목적이 아니라 blocker 발견이 목적**입니다. 모두가 순서대로 보고만 하고 끝나면, blocker가 있어도 묻히기 쉽습니다.
- 원격/비동기 팀이라면 매일 같은 시간에 채팅 채널에 3줄로 남기는 것으로 대체할 수 있습니다 (10장 비동기 협업 참고).

**실무 팁**: "어제 한 일"이 매번 "계속 그거 하고 있어요"로 반복된다면, 작업 단위가 너무 크다는 신호입니다. 하루~이틀 안에 끝낼 수 있는 크기로 이슈를 쪼갭니다.

# 16. 스프린트 플래닝 심화

스프린트를 시작하기 전에 "이번 스프린트에 무엇을 할지"를 정하는 회의입니다.

```text
플래닝 순서
1. 백로그에서 우선순위 높은 이슈를 검토
2. 팀의 가용 시간(캐파, capacity)을 먼저 계산
   → 휴가·다른 업무를 뺀 실제 작업 가능 시간
3. 이슈별로 크기를 추정 (아래 참고)
4. 캐파에 맞는 만큼만 스프린트에 담기
5. 스프린트 목표(goal)를 한 문장으로 정리
```

## 작업 크기 추정 방법

| 방법 | 설명 |
| --- | --- |
| 시간 추정 | "이 작업은 4시간" 처럼 절대 시간으로 추정. 초급 팀에 직관적이지만 사람마다 속도가 달라 오차가 큼 |
| 스토리 포인트 | 절대 시간이 아니라 "다른 작업 대비 상대적 크기"(1, 2, 3, 5, 8 등 피보나치)로 추정. 팀 전체가 합의해서 매김 |
| 플래닝 포커 | 각자 카드로 포인트를 동시에 제시하고, 크게 엇갈리면 왜 다르게 봤는지 토론 후 재추정 |

**기본 상식**: 초급 팀이 스토리 포인트부터 도입하면 오히려 혼란스러울 수 있습니다. 처음에는 "작업을 반나절 단위로 쪼갤 수 있는가"만 확인하는 것으로 시작해도 충분합니다.

**실무 팁**: 스프린트 목표를 정해두면, 스프린트 중간에 "이 작업을 지금 넣을지"를 판단하는 기준이 생깁니다. 목표와 상관없는 요청은 다음 스프린트로 미룰 근거가 됩니다.

# 17. 갈등 해결

의견 차이는 팀이 일하는 한 자연스럽게 생깁니다. 문제는 갈등 자체가 아니라 방치하는 것입니다.

## 기술적 의견 차이

```text
1. 각자의 제안과 근거를 글로 먼저 정리 (감정이 아니라 트레이드오프 비교)
2. 공통의 기준을 먼저 합의 (성능? 유지보수성? 일정?)
   → 기준이 다르면 같은 근거를 봐도 결론이 갈림
3. 기준에 따라 판단하고, 결정은 ADR로 남김
4. 정해진 뒤에는 반대했던 사람도 팀 결정으로 따름 (disagree and commit)
```

## 사람 사이의 갈등

- 문제가 되는 **행동**과 그로 인한 **영향**을 구체적으로 말합니다. ("항상 그런 식이다" ❌ → "지난주 PR 3개가 마감일을 넘겨서 제 작업이 막혔다" ⭕)
- 공개 채널에서 지적하기보다, 먼저 1:1로 대화합니다. 공개적으로 해결이 필요한 경우가 아니면 감정이 상하기 쉽습니다.
- 둘이서 해결되지 않으면 팀 리드나 스크럼 마스터 같은 중재자를 개입시킵니다. 방치하는 것이 가장 나쁜 선택입니다.

**기본 상식**: 갈등을 "누가 옳은가"로 끝내면 진 쪽이 팀에 대한 신뢰를 잃기 쉽습니다. "우리 팀에 가장 나은 결정이 무엇인가"로 프레임을 옮기면 감정 소모가 줄어듭니다.

# 18. 심리적 안전감

"실수하거나 모르는 걸 물어봐도 불이익을 받지 않는다"는 팀 전체의 믿음입니다. 구글의 대규모 사내 연구(Project Aristotle)에서 팀 성과를 가장 크게 좌우하는 요인으로 꼽혔습니다.

## 심리적 안전감이 낮은 팀의 신호

```text
- 회의에서 질문이 거의 나오지 않음 (몰라서가 아니라 물어보기 두려워서)
- 실수를 보고하지 않고 조용히 숨기려 함
- 신입이 몇 달이 지나도 의견을 내지 않음
- "이거 제 담당 아니에요"로 책임을 피하는 말이 자주 나옴
```

## 리더/시니어가 할 수 있는 것

- 자신의 실수를 먼저 공유합니다. "저도 지난주에 이 부분 착각해서 배포 후 롤백했어요"처럼요.
- 질문에 "그것도 몰라요?"가 아니라 "좋은 질문이네요, 이건 저도 헷갈렸던 부분이에요"로 반응합니다.
- 회고에서 나온 문제 제기를 보복 없이 받아들이는 모습을 반복해서 보여줍니다.

**기본 상식**: 심리적 안전감은 "친하게 지내자"와 다릅니다. 오히려 안전감이 높은 팀일수록 기술적으로는 더 날카롭게 반박하고 검증합니다. 사람에 대한 공격 없이 아이디어를 마음껏 비판할 수 있는 상태가 핵심입니다.

# 19. 1on1과 성과 피드백

정기적으로 리드와 팀원이 1:1로 대화하는 자리입니다. 진행 상황 보고가 아니라, 스탠드업에서 다루기 어려운 이야기를 하는 자리입니다.

```text
1on1에서 다루기 좋은 주제
- 성장 방향, 커리어 고민
- 팀 프로세스에 대한 솔직한 의견 (공개 회고에서는 말하기 어려운 것)
- 최근 피드백에 대한 감정적인 반응
- 개인적인 어려움이 업무에 미치는 영향
```

## 피드백을 주는 방법 — SBI 모델

| 요소 | 설명 | 예시 |
| --- | --- | --- |
| Situation (상황) | 언제, 어떤 상황이었는지 | "지난주 화요일 배포 직전 코드리뷰에서" |
| Behavior (행동) | 관찰된 구체적 행동 | "테스트 코드 없이 PR을 올리셨어요" |
| Impact (영향) | 그 행동이 미친 실제 영향 | "리뷰가 늦어지고, 배포 후 버그가 하나 발견됐어요" |

**기본 상식**: SBI 모델의 핵심은 "성격/의도 추측"을 빼는 것입니다. "책임감이 없으신 것 같아요"가 아니라 관찰 가능한 행동과 영향만 말하면, 듣는 사람이 방어적이 되지 않고 개선에 집중할 수 있습니다.

**실무 팁**: 부정적 피드백만 쌓이면 1on1이 불편한 자리가 됩니다. 잘한 부분에 대한 구체적 인정도 같은 SBI 형식으로 정기적으로 전달합니다.

# 20. 크로스팀 협업

프론트엔드/백엔드처럼 소유 영역이 다른 팀 간에 함께 일할 때 부딪히는 문제와 해법입니다.

## API 계약을 먼저 확정한다

이 저장소의 `docs/PLANNING.md`처럼, 실제 구현 전에 요청/응답 형식을 문서로 합의해두면 두 팀이 병렬로 작업할 수 있습니다.

```text
계약이 없을 때
FE: "이 필드 이름이 뭐예요?" → BE에게 매번 물어봐야 진행 가능 (직렬 작업)

계약(API 명세)이 있을 때
FE: mock 데이터로 명세대로 먼저 화면 개발
BE: 명세대로 실제 엔드포인트 개발
→ 병렬 진행, 명세대로만 맞추면 마지막에 합쳐도 크게 안 어긋남
```

## 의존성이 있는 작업 조율

- 상대 팀 작업이 끝나야 시작할 수 있는 작업은 스프린트 플래닝 때 미리 표시해둡니다.
- 인터페이스(API 명세, 컴포넌트 props 등)가 바뀌면 상대 팀에 먼저 알리고 합의한 뒤 바꿉니다. 이 저장소의 "API 응답 필드는 스네이크케이스" 규칙처럼, 계약을 임의로 바꾸지 않는 것이 핵심입니다.

**기본 상식**: 크로스팀 협업에서 가장 흔한 마찰은 "내 쪽에서는 사소한 변경"이 "상대 쪽에서는 화면이 깨지는 변경"이 되는 경우입니다. 계약으로 다루는 부분은 반드시 사전 공지 후 변경합니다.

# 21. 인시던트 대응 커뮤니케이션

서비스 장애가 발생했을 때는 "고치는 것"만큼 "누가 무엇을 하고 있는지 공유하는 것"이 중요합니다.

```text
인시던트 대응 흐름
1. 감지 — 알림/모니터링/사용자 신고로 장애 인지
2. 선언 — 담당자 한 명이 "인시던트 진행 중"임을 팀에 공지 (전용 채널 개설)
3. 대응 — 원인 파악과 임시 조치 (롤백 등) 우선, 근본 원인 분석은 나중
4. 해소 — 서비스 정상화 확인 후 종료 공지
5. 회고 — 포스트모템 작성 (아래 참고)
```

## 인시던트 중 커뮤니케이션 원칙

- **인시던트 커맨더(진행 총괄)를 한 명 정합니다.** 여러 명이 각자 판단해서 조치하면 서로 다른 수정이 충돌할 수 있습니다.
- 진행 상황을 정기적으로(예: 15분마다) 짧게라도 공유합니다. 침묵이 길어지면 관련자들이 각자 불안해하며 개별 문의를 시작해 오히려 대응이 늦어집니다.
- 원인을 추측만으로 단정해 공유하지 않습니다. "~로 추정되며 확인 중"처럼 확실성의 정도를 구분해서 씁니다.

## 포스트모템(사후 회고)

```md
# 포스트모템: 결제 API 5xx 급증 (2026-03-15)

## 영향
14:20~14:47(27분) 결제 요청의 약 40%가 실패

## 타임라인
14:20 - 알림 발생, 담당자 확인 시작
14:28 - DB 커넥션 풀 고갈이 원인으로 특정
```

# 22. 협업 도구 스택 활용

작은 팀이라도 도구별 역할을 정해두지 않으면 같은 정보가 여러 곳에 흩어져 무엇이 최신인지 알 수 없게 됩니다.

| 도구 | 용도 | 흔한 실수 |
| --- | --- | --- |
| Slack/Discord 등 채팅 | 실시간 소통, 빠른 질문 | 중요한 결정을 채팅으로만 하고 문서화하지 않음 |
| Notion/Confluence 등 위키 | ADR, 온보딩 문서, 회의록처럼 "찾아볼 수 있어야 하는" 정보 | 채팅에서 결론 난 내용을 위키에 옮기지 않아 위키가 낡음 |
| Jira/GitHub Issues 등 이슈 트래커 | 작업 단위, 우선순위, 진행 상태 | 이슈와 실제 진행 상황이 어긋남(PR은 됐는데 이슈는 열려있음) |
| GitHub/GitLab | 코드, PR, 리뷰 | 코드와 무관한 논의(일정, 인사)까지 PR 코멘트에 남겨 이력이 지저분해짐 |

## 채널 구조 예시(채팅 도구)

```text
#general       — 팀 전체 공지
#dev-frontend  — 프론트엔드 관련 논의
#dev-backend   — 백엔드 관련 논의
#incidents     — 장애 대응 전용 (21장 참고)
#random        — 업무 외 잡담
```

**실무 팁**: 도구가 많아질수록 "이 정보는 어디서 찾지?"라는 질문이 늘어납니다. 팀 온보딩 문서(4장)에 "이 종류의 정보는 이 도구에 있다"는 표를 한 번 정리해두면 반복 질문을 줄일 수 있습니다.

# 23. 지식 공유 문화

한 사람만 아는 지식(버스 팩터, bus factor)이 많을수록 그 사람이 자리를 비웠을 때 팀이 멈춥니다.

## 지식이 흩어지는 것을 막는 습관

```text
- 같은 질문을 두 번째 받으면 답 대신 문서 링크를 만들어 공유
- 복잡한 버그를 해결한 뒤 원인과 해결 과정을 짧게라도 기록 (문서 or 이슈 코멘트)
- 온보딩 중인 팀원에게 문서를 직접 고쳐보게 함
  → 기존 팀원이 당연하게 여겨 빠뜨린 부분을 신입이 가장 잘 찾음
```

## 정기 지식 공유 세션

- 주 1회, 30분 정도 팀원이 돌아가며 최근 배운 것/막혔다 해결한 것을 공유합니다.
- 발표 자료를 거창하게 준비하지 않아도 됩니다. 화면 공유 + 구두 설명으로 충분합니다.
- 공유 내용 중 재사용 가능한 것은 위키(22장)로 옮겨 나중에도 찾을 수 있게 합니다.

**기본 상식**: 지식 공유의 목표는 "모두가 모든 것을 알게 하는 것"이 아니라, "한 사람이 없어도 나머지가 최소한 어디를 봐야 할지는 아는 것"입니다. 완벽한 이해보다 접근 경로 확보가 우선입니다.

# 24. 협업 성숙도 자가 진단

아래 항목에 얼마나 해당하는지로 팀의 협업 수준을 가늠해볼 수 있습니다. 정답이 있는 시험이 아니라, 다음에 무엇을 개선할지 찾는 용도입니다.

| 항목 | 아직 안 됨 | 하고는 있음 | 습관으로 자리잡음 |
| --- | --- | --- | --- |
| 되돌리기 어려운 결정을 ADR로 남긴다 | | | |
| 리뷰 SLA가 정해져 있고 대체로 지켜진다 | | | |
| 온보딩 문서만으로 새 팀원이 첫 PR을 낼 수 있다 | | | |
| 회고의 Try 항목이 다음 스프린트에 실제로 실행된다 | | | |
| 장애 발생 시 인시던트 커맨더가 자동으로 정해진다 | | | |
| 팀원이 모르는 것을 회의에서 편하게 물어본다 | | | |

**실무 팁**: 모든 항목을 한 번에 "습관" 단계로 만들려 하지 않습니다. 이번 스프린트에는 가장 비어있는 항목 1~2개만 골라 회고의 Try로 등록하는 것이 현실적입니다.
