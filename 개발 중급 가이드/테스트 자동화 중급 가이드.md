> **대상:** 컴포넌트·API를 손으로 실행해가며 확인하는 데는 익숙하지만, 테스트 코드를 체계적으로 짜본 적은 적은 사람
> **목적:** 프론트/백엔드 어느 쪽에도 공통으로 적용되는 테스트 전략과 습관을 정리합니다

---

# 0. 시작 전에 — 자주 나오는 용어

기초 가이드에서 다룬 "테스트가 왜 필요한지" 수준의 개념은 이미 안다고 가정합니다. 여기서는 이 문서에서 새로 나오는 용어만 정리합니다.

| 용어 | 쉬운 설명 |
| --- | --- |
| 단위 테스트(Unit Test) | 함수·컴포넌트 하나처럼 가장 작은 단위를 따로 떼어 검증하는 테스트. 가장 빠르고 많이 씀 |
| 통합 테스트(Integration Test) | 여러 모듈(예: API + DB)이 함께 맞물려 잘 동작하는지 검증하는 테스트 |
| E2E 테스트(End-to-End) | 실제 사용자처럼 화면을 처음부터 끝까지 조작해보며 전체 흐름을 검증하는 테스트 |
| 테스트 피라미드 | 단위 테스트를 가장 많이, E2E 테스트를 가장 적게 두는 것이 좋다는 비율 원칙 |
| TDD (Test-Driven Development) | 코드를 짜기 전에 테스트부터 먼저 작성하는 개발 방식 |
| Mock | 실제 대신 넣는 가짜 객체 중, 호출 여부·횟수까지 검증할 수 있는 것 |
| Stub | 정해진 값만 그대로 돌려주는 단순한 가짜 객체 |
| 테스트 커버리지(Coverage) | 테스트가 전체 코드 중 몇 %를 실행했는지 보여주는 숫자 |
| assert(단언) | 테스트 코드 안에서 "실제 결과가 기대한 값과 같아야 한다"고 확인하는 구문 |
| 플레이키(Flaky) 테스트 | 코드는 문제없는데, 실행할 때마다 통과하거나 실패하는 결과가 들쭉날쭉한 불안정한 테스트 |
| Teardown | 테스트가 끝난 뒤 만들어뒀던 임시 데이터·상태를 정리하는 과정 |

---

# 1. 테스트 피라미드

모든 화면·기능을 E2E 테스트로만 덮으려 하면 느리고 깨지기 쉬운 테스트 스위트가 됩니다. 아래로 갈수록 빠르고 저렴하며, 위로 갈수록 실제 사용자 흐름에 가깝지만 느리고 비쌉니다.

```text
        /\
       /E2E\          적은 수 — 핵심 사용자 흐름만 (로그인, 결제 등)
      /------\
     /통합 테스트\      중간 수 — 여러 모듈이 함께 동작하는지
    /------------\
   /  단위 테스트   \   가장 많은 수 — 함수/컴포넌트 하나씩, 빠르게
  /------------------\
```

**기본 상식**: 이상적인 비율은 프로젝트마다 다르지만, "E2E로 모든 걸 검증하자"는 접근은 대부분 실패합니다. 테스트 실행 시간이 길어지고, 사소한 UI 변경에도 여러 E2E 테스트가 한꺼번에 깨져서 유지보수 비용이 커집니다.

---

# 2. TDD — Red, Green, Refactor

테스트를 먼저 쓰고, 그 테스트를 통과시키는 최소한의 코드를 짠 뒤, 정리합니다.

```text
1. Red   — 아직 없는 기능에 대한 테스트를 먼저 작성 (당연히 실패함)
2. Green — 테스트를 통과시키는 가장 간단한 코드 작성 (완벽하지 않아도 됨)
3. Refactor — 테스트가 통과하는 상태를 유지하면서 코드를 정리
```

```python
# 1. Red — 아직 함수가 없는 상태에서 테스트부터 작성
def test_할인가_계산():
    assert calculate_discounted_price(10000, 0.1) == 9000

# 2. Green — 테스트를 통과시키는 최소 구현
def calculate_discounted_price(price, discount_rate):
    return price - (price * discount_rate)

# 3. Refactor — 통과 상태를 유지하며 다듬기 (반올림, 입력 검증 등 추가)
def calculate_discounted_price(price, discount_rate):
    if not 0 <= discount_rate <= 1:
        raise ValueError("할인율은 0~1 사이여야 합니다")
    return round(price * (1 - discount_rate))
```

**실무 팁**: TDD를 모든 코드에 무조건 적용할 필요는 없습니다. 로직이 복잡하고 요구사항이 명확한 부분(가격 계산, 검증 로직)에 특히 효과적이고, 아직 요구사항이 자주 바뀌는 UI 프로토타입 단계에서는 오히려 속도를 늦출 수 있습니다.

---

# 3. Mock과 Stub

테스트가 외부 요인(실제 DB, 실제 API, 현재 시각)에 의존하면 느리고 불안정해집니다. 가짜 객체로 대체합니다.

```python
# 실제 외부 API를 호출하지 않고, 호출한 것처럼 가짜 응답을 돌려줌
def test_강의_요약_요청_실패시_처리(mocker):
    mocker.patch(
        "app.services.ai_client.generate",
        side_effect=TimeoutError("AI 응답 지연"),
    )
    result = summarize_course_description("설명 텍스트")
    assert result["error"] == "AI_UNAVAILABLE"
```

| 용어 | 의미 |
| --- | --- |
| Mock | 호출 여부·횟수·전달값까지 검증할 수 있는 가짜 객체 |
| Stub | 정해진 값만 돌려주는 단순한 가짜 (호출 검증은 하지 않음) |
| Fake | 실제 동작을 간단히 흉내 낸 구현 (예: 메모리 기반 가짜 DB) |

**기본 상식**: 무엇이든 Mock으로 바꾸지 않습니다. 테스트 대상 코드 자체의 로직은 실제로 실행되어야 하고, "느리거나 불안정하게 만드는 외부 의존성"만 골라서 대체합니다.

# 4. 테스트 커버리지의 함정

커버리지(coverage)는 테스트가 코드의 몇 %를 실행했는지 보여주는 숫자입니다.

```bash
pytest --cov=app --cov-report=term-missing
```

**기본 상식**: 커버리지 100%가 "버그가 없다"는 뜻이 아닙니다. 코드가 실행만 되고 결과를 검증(assert)하지 않는 테스트도 커버리지에는 잡힙니다.

```python
# 커버리지는 올라가지만 사실상 아무것도 검증하지 않는 나쁜 예
def test_강의_조회():
    get_course(1)   # 결과를 확인하지 않음 — 실행만 됨

# 좋은 예
def test_강의_조회():
    course = get_course(1)
    assert course.title == "React 입문"
```

커버리지는 "테스트가 안 되고 있는 위험 지대"를 찾는 용도로 쓰고, 숫자 자체를 목표로 삼지 않습니다.

---

# 5. 플레이키(Flaky) 테스트 다루기

가끔 통과하고 가끔 실패하는, 원인이 코드가 아니라 테스트 자체에 있는 테스트입니다.

```text
흔한 원인
- 테스트 간 순서에 의존 (다른 테스트가 남긴 데이터에 영향받음)
- 실제 시간에 의존 (현재 시각, 타임아웃)
- 비동기 작업이 끝나길 기다리지 않고 바로 검증
- 테스트끼리 같은 리소스(파일, 포트)를 공유
```

**해결 방향**: 각 테스트는 실행 순서와 무관하게 독립적으로 통과해야 합니다. 테스트 시작 시 필요한 데이터를 직접 만들고, 끝나면 정리(teardown)합니다. 시간 의존은 실제 `datetime.now()` 대신 고정된 값을 주입해서 제거합니다.

---

# 6. 자주 하는 실수

- E2E 테스트로 모든 케이스를 덮으려다 테스트 스위트가 너무 느려짐
- assert 없이 실행만 하는 테스트로 커버리지 숫자만 채움
- 외부 API·DB를 Mock 처리하지 않아 테스트가 네트워크 상태에 따라 실패
- 플레이키 테스트를 원인 파악 없이 재실행 버튼으로만 넘김
- 버그를 고친 뒤 재현 테스트를 남기지 않아 같은 버그가 재발

---

# 7. 실전 체크리스트

- [ ] 단위 테스트가 통합·E2E 테스트보다 훨씬 많은 비율을 차지하는가
- [ ] 외부 의존성(API, DB, 시간)을 Mock/Stub으로 격리했는가
- [ ] 커버리지 숫자가 아니라 핵심 로직이 실제로 검증되는지 확인했는가
- [ ] 각 테스트가 실행 순서와 무관하게 독립적으로 통과하는가
- [ ] 발견한 버그마다 재현 테스트를 남기는가

# 8. 테스트 데이터 관리 — Fixture와 Factory

## Fixture

테스트마다 반복해서 필요한 준비 작업(DB 연결, 로그인된 사용자 등)을 함수로 뽑아 재사용합니다.

```python
import pytest

@pytest.fixture
def logged_in_user(db_session):
    user = User(email="test@test.com")
    db_session.add(user)
    db_session.commit()
    return user

def test_수강신청(logged_in_user, db_session):
    result = enroll_course(logged_in_user.id, course_id=1)
    assert result["status"] == "enrolled"
```

## Factory 패턴으로 테스트 데이터 생성

```python
# factory_boy 예시
class CourseFactory(factory.Factory):
    class Meta:
        model = Course
    title = factory.Sequence(lambda n: f"강의 {n}")
    price = 10000

# 필요한 속성만 오버라이드해서 생성
course = CourseFactory(price=0)   # 무료 강의 케이스만 따로 테스트
```

**기본 상식**: 테스트마다 필요한 필드를 전부 손으로 채우면 코드가 길어지고, 정작 이 테스트가 검증하려는 핵심 속성이 무엇인지 알아보기 어려워집니다. Factory로 기본값을 만들어두고, 테스트에서 중요한 속성만 오버라이드하면 테스트 의도가 명확해집니다.

# 9. 프론트엔드 컴포넌트 테스트

## 사용자 관점으로 테스트하기 (Testing Library)

```jsx
import { render, screen, fireEvent } from "@testing-library/react";

test("수강 신청 버튼을 누르면 신청 완료 문구가 보인다", async () => {
  render(<CourseCard course={{ id: 1, title: "React 입문" }} />);

  fireEvent.click(screen.getByRole("button", { name: "수강 신청" }));

  expect(await screen.findByText("신청 완료")).toBeInTheDocument();
});
```

**기본 상식**: 내부 state 값이나 클래스명을 직접 검사하는 대신, "사용자가 화면에서 보고 클릭하는 것"을 기준으로 테스트를 짭니다(`getByRole`, `getByText`). 이렇게 하면 내부 구현(state 이름, 컴포넌트 구조)이 바뀌어도 테스트가 깨지지 않고, 실제 사용자 경험을 더 정확히 검증합니다.

## 비동기 UI 테스트

```jsx
test("로딩 중에는 스피너가, 완료되면 목록이 보인다", async () => {
  render(<CourseList />);

  expect(screen.getByText("불러오는 중...")).toBeInTheDocument();

  await waitFor(() => {
    expect(screen.getByText("React 입문")).toBeInTheDocument();
  });
});
```

# 10. API 계약 테스트 (Contract Test)

프론트와 백엔드가 각자 나눠 개발할 때, API 응답 형식이 서로의 기대와 어긋나지 않는지 자동으로 검증합니다.

```text
문제 상황: 백엔드가 응답 필드명을 title → name으로 몰래 바꿈
→ 프론트 개발자가 눈치채지 못하면 배포 후에야 화면이 깨짐

계약 테스트로 예방:
1. 프론트가 기대하는 응답 형식을 스키마로 정의(Pact, 또는 자체 JSON 스키마)
2. 백엔드 CI에서 실제 응답이 이 스키마를 만족하는지 검증
3. 스키마가 깨지면 배포 전에 CI에서 바로 실패
```

**실무 팁**: 별도 도구 도입이 부담스럽다면, API 응답에 대한 JSON 스키마를 정의해두고 백엔드 통합 테스트에서 `jsonschema.validate()`로 검증하는 것만으로도 계약 테스트의 핵심 효과를 상당 부분 얻을 수 있습니다.

# 11. 회귀 테스트와 스냅샷 테스트

## 회귀 테스트(Regression Test)

한 번 고친 버그가 나중에 다시 발생하지 않는지 확인하는 테스트입니다. 버그를 고칠 때마다 "이 버그를 재현하는 테스트"를 함께 추가하는 습관이 곧 회귀 테스트 스위트를 만드는 과정입니다.

## 스냅샷 테스트

```jsx
test("CourseCard가 기존 UI와 동일하게 렌더링된다", () => {
  const { container } = render(<CourseCard course={mockCourse} />);
  expect(container).toMatchSnapshot();
});
```

렌더링 결과를 파일로 저장해두고, 다음 실행부터는 이전 결과와 비교해 차이가 있으면 실패시킵니다.

**기본 상식**: 스냅샷 테스트는 "의도한 변경인지 실수인지"를 구분하지 못합니다. 실패했을 때 습관적으로 스냅샷을 갱신(`--updateSnapshot`)하기보다, 변경 내용이 실제로 의도한 것인지 diff를 직접 확인한 뒤 갱신합니다.

# 12. 병렬 테스트 실행과 속도 최적화

테스트가 많아질수록 전체 실행 시간이 늘어나, CI 파이프라인이 느려지는 원인이 됩니다.

```yaml
# pytest 병렬 실행 (pytest-xdist)
pytest -n auto   # CPU 코어 수에 맞춰 자동으로 여러 프로세스에 분산 실행
```

```text
병렬화의 전제 조건
- 각 테스트가 서로 독립적이어야 함 (같은 DB row를 여러 테스트가 동시에 수정하면 안 됨)
- 테스트마다 별도의 테스트 DB/스키마를 쓰거나, 트랜잭션으로 격리해 롤백
```

**기본 상식**: 테스트를 병렬로 돌렸을 때 가끔 실패한다면, 그 자체가 테스트 간 격리가 안 되어 있다는 신호입니다. "병렬 실행 시 실패"는 병렬화 설정 문제가 아니라 테스트 설계 문제인 경우가 대부분입니다.

---

# 13. 시각적 회귀 테스트 (Visual Regression Test)

로직은 정상인데 스타일이 깨지는 경우는 일반 단위 테스트로 잡히지 않습니다. 화면을 스크린샷으로 찍어 이전 버전과 픽셀 단위로 비교하는 테스트입니다.

```js
// Playwright 예시
test("강의 카드 UI가 이전과 동일하다", async ({ page }) => {
  await page.goto("/courses");
  await expect(page.locator(".course-card").first()).toHaveScreenshot("course-card.png");
});
```

처음 실행 시 스크린샷을 "정답(baseline)"으로 저장해두고, 이후 실행에서 픽셀 차이가 일정 기준을 넘으면 실패로 처리합니다.

**기본 상식**: 폰트 렌더링이나 애니메이션 타이밍처럼 실행 환경마다 미세하게 달라지는 요소 때문에 오탐(false positive)이 잦은 편입니다. CI 환경과 로컬 환경의 폰트·해상도를 맞추고, 허용 오차(threshold)를 적절히 설정해야 실용적으로 쓸 수 있습니다.

# 14. 부하 테스트(Load Test) 기초

기능이 올바른지가 아니라, "동시에 몰리는 트래픽을 견디는지"를 검증하는 테스트입니다.

```python
# locust 예시
from locust import HttpUser, task

class CourseUser(HttpUser):
    @task
    def view_courses(self):
        self.client.get("/api/courses")
```

```text
locust -f locustfile.py --users 100 --spawn-rate 10
→ 가상 사용자 100명을 초당 10명씩 늘려가며 /api/courses에 요청을 보냄
→ 응답 시간·오류율이 어느 시점부터 나빠지는지 관찰
```

**기본 상식**: 부하 테스트는 반드시 운영 서버가 아닌 별도 환경에서 실행합니다. 운영 DB에 직접 부하를 주면 실제 사용자에게 영향을 줄 수 있으므로, 스테이징 환경이나 별도의 성능 테스트 전용 환경을 준비합니다.

# 15. 자주 하는 실수 (심화)

- 병렬 테스트 실행 시 테스트 간 데이터 공유로 인한 간헐적 실패를 "플레이키 테스트"로 오인하고 재시도만 반복
- 시각적 회귀 테스트의 허용 오차를 너무 낮게 잡아, 사소한 안티에일리어싱 차이에도 매번 실패 처리됨
- 부하 테스트를 운영 환경과 다른 사양의 테스트 환경에서 돌려놓고 결과를 그대로 운영 환경 성능으로 착각
- 테스트 스위트 실행 시간이 계속 늘어나는데도 병렬화·불필요한 테스트 정리를 미룸
