> **대상:** 컴포넌트·API를 손으로 실행해가며 확인하는 데는 익숙하지만, 테스트 코드를 체계적으로 짜본 적은 적은 사람
> **목적:** 프론트/백엔드 어느 쪽에도 공통으로 적용되는 테스트 전략과 습관을 정리합니다

---

# 0. 시작 전에 — 자주 나오는 용어

기초 가이드에서 다룬 "테스트가 왜 필요한지" 수준의 개념은 이미 안다고 가정합니다. 여기서는 이 문서에서 새로 나오는 용어만 정리합니다.

| 용어 | 쉬운 설명 |
| --- | --- |
| 단위 테스트(Unit Test) | 함수·컴포넌트 하나처럼 가장 작은 단위를 따로 떼어 검증하는 테스트. 가장 빠르고 많이 씀 |
| 통합 테스트(Integration Test) | 여러 모듈(예: API + DB)이 함께 맞물려 잘 동작하는지 검증하는 테스트 |
| E2E 테스트(End-to-End) | 실제 사용자처럼 화면을 처음부터 끝까지 조작해보며 전체 흐름을 검증하는 테스트 |
| 테스트 피라미드 | 단위 테스트를 가장 많이, E2E 테스트를 가장 적게 두는 것이 좋다는 비율 원칙 |
| TDD (Test-Driven Development) | 코드를 짜기 전에 테스트부터 먼저 작성하는 개발 방식 |
| Mock | 실제 대신 넣는 가짜 객체 중, 호출 여부·횟수까지 검증할 수 있는 것 |
| Stub | 정해진 값만 그대로 돌려주는 단순한 가짜 객체 |
| 테스트 커버리지(Coverage) | 테스트가 전체 코드 중 몇 %를 실행했는지 보여주는 숫자 |
| assert(단언) | 테스트 코드 안에서 "실제 결과가 기대한 값과 같아야 한다"고 확인하는 구문 |
| 플레이키(Flaky) 테스트 | 코드는 문제없는데, 실행할 때마다 통과하거나 실패하는 결과가 들쭉날쭉한 불안정한 테스트 |
| Teardown | 테스트가 끝난 뒤 만들어뒀던 임시 데이터·상태를 정리하는 과정 |

---

# 1. 테스트 피라미드

모든 화면·기능을 E2E 테스트로만 덮으려 하면 느리고 깨지기 쉬운 테스트 스위트가 됩니다. 아래로 갈수록 빠르고 저렴하며, 위로 갈수록 실제 사용자 흐름에 가깝지만 느리고 비쌉니다.

```text
        /\
       /E2E\          적은 수 — 핵심 사용자 흐름만 (로그인, 결제 등)
      /------\
     /통합 테스트\      중간 수 — 여러 모듈이 함께 동작하는지
    /------------\
   /  단위 테스트   \   가장 많은 수 — 함수/컴포넌트 하나씩, 빠르게
  /------------------\
```

**기본 상식**: 이상적인 비율은 프로젝트마다 다르지만, "E2E로 모든 걸 검증하자"는 접근은 대부분 실패합니다. 테스트 실행 시간이 길어지고, 사소한 UI 변경에도 여러 E2E 테스트가 한꺼번에 깨져서 유지보수 비용이 커집니다.

---

# 2. TDD — Red, Green, Refactor

테스트를 먼저 쓰고, 그 테스트를 통과시키는 최소한의 코드를 짠 뒤, 정리합니다.

```text
1. Red   — 아직 없는 기능에 대한 테스트를 먼저 작성 (당연히 실패함)
2. Green — 테스트를 통과시키는 가장 간단한 코드 작성 (완벽하지 않아도 됨)
3. Refactor — 테스트가 통과하는 상태를 유지하면서 코드를 정리
```

```python
# 1. Red — 아직 함수가 없는 상태에서 테스트부터 작성
def test_할인가_계산():
    assert calculate_discounted_price(10000, 0.1) == 9000

# 2. Green — 테스트를 통과시키는 최소 구현
def calculate_discounted_price(price, discount_rate):
    return price - (price * discount_rate)

# 3. Refactor — 통과 상태를 유지하며 다듬기 (반올림, 입력 검증 등 추가)
def calculate_discounted_price(price, discount_rate):
    if not 0 <= discount_rate <= 1:
        raise ValueError("할인율은 0~1 사이여야 합니다")
    return round(price * (1 - discount_rate))
```

**실무 팁**: TDD를 모든 코드에 무조건 적용할 필요는 없습니다. 로직이 복잡하고 요구사항이 명확한 부분(가격 계산, 검증 로직)에 특히 효과적이고, 아직 요구사항이 자주 바뀌는 UI 프로토타입 단계에서는 오히려 속도를 늦출 수 있습니다.

---

# 3. Mock과 Stub

테스트가 외부 요인(실제 DB, 실제 API, 현재 시각)에 의존하면 느리고 불안정해집니다. 가짜 객체로 대체합니다.

```python
# 실제 외부 API를 호출하지 않고, 호출한 것처럼 가짜 응답을 돌려줌
def test_강의_요약_요청_실패시_처리(mocker):
    mocker.patch(
        "app.services.ai_client.generate",
        side_effect=TimeoutError("AI 응답 지연"),
    )
    result = summarize_course_description("설명 텍스트")
    assert result["error"] == "AI_UNAVAILABLE"
```

| 용어 | 의미 |
| --- | --- |
| Mock | 호출 여부·횟수·전달값까지 검증할 수 있는 가짜 객체 |
| Stub | 정해진 값만 돌려주는 단순한 가짜 (호출 검증은 하지 않음) |
| Fake | 실제 동작을 간단히 흉내 낸 구현 (예: 메모리 기반 가짜 DB) |

**기본 상식**: 무엇이든 Mock으로 바꾸지 않습니다. 테스트 대상 코드 자체의 로직은 실제로 실행되어야 하고, "느리거나 불안정하게 만드는 외부 의존성"만 골라서 대체합니다.

# 4. 테스트 커버리지의 함정

커버리지(coverage)는 테스트가 코드의 몇 %를 실행했는지 보여주는 숫자입니다.

```bash
pytest --cov=app --cov-report=term-missing
```

**기본 상식**: 커버리지 100%가 "버그가 없다"는 뜻이 아닙니다. 코드가 실행만 되고 결과를 검증(assert)하지 않는 테스트도 커버리지에는 잡힙니다.

```python
# 커버리지는 올라가지만 사실상 아무것도 검증하지 않는 나쁜 예
def test_강의_조회():
    get_course(1)   # 결과를 확인하지 않음 — 실행만 됨

# 좋은 예
def test_강의_조회():
    course = get_course(1)
    assert course.title == "React 입문"
```

커버리지는 "테스트가 안 되고 있는 위험 지대"를 찾는 용도로 쓰고, 숫자 자체를 목표로 삼지 않습니다.

# 5. 플레이키(Flaky) 테스트 다루기

가끔 통과하고 가끔 실패하는, 원인이 코드가 아니라 테스트 자체에 있는 테스트입니다.

```text
흔한 원인
- 테스트 간 순서에 의존 (다른 테스트가 남긴 데이터에 영향받음)
- 실제 시간에 의존 (현재 시각, 타임아웃)
- 비동기 작업이 끝나길 기다리지 않고 바로 검증
- 테스트끼리 같은 리소스(파일, 포트)를 공유
```

**해결 방향**: 각 테스트는 실행 순서와 무관하게 독립적으로 통과해야 합니다. 테스트 시작 시 필요한 데이터를 직접 만들고, 끝나면 정리(teardown)합니다. 시간 의존은 실제 `datetime.now()` 대신 고정된 값을 주입해서 제거합니다.

---

# 6. 자주 하는 실수

- E2E 테스트로 모든 케이스를 덮으려다 테스트 스위트가 너무 느려짐
- assert 없이 실행만 하는 테스트로 커버리지 숫자만 채움
- 외부 API·DB를 Mock 처리하지 않아 테스트가 네트워크 상태에 따라 실패
- 플레이키 테스트를 원인 파악 없이 재실행 버튼으로만 넘김
- 버그를 고친 뒤 재현 테스트를 남기지 않아 같은 버그가 재발

---

# 7. 실전 체크리스트

- [ ] 단위 테스트가 통합·E2E 테스트보다 훨씬 많은 비율을 차지하는가
- [ ] 외부 의존성(API, DB, 시간)을 Mock/Stub으로 격리했는가
- [ ] 커버리지 숫자가 아니라 핵심 로직이 실제로 검증되는지 확인했는가
- [ ] 각 테스트가 실행 순서와 무관하게 독립적으로 통과하는가
- [ ] 발견한 버그마다 재현 테스트를 남기는가
