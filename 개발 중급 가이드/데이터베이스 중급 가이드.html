0. 시작 전에 — 자주 나오는 용어#

기초 가이드에서 다룬 테이블·SQL·ORM 용어는 이미 안다고 가정합니다. 여기서는 이 문서에서 새로 나오는 용어만 정리합니다.

용어쉬운 설명
인덱스(Index)책의 찾아보기처럼, 특정 컬럼으로 빠르게 조회할 수 있게 미리 만들어두는 데이터 구조
EXPLAIN쿼리가 실제로 인덱스를 타는지, 테이블 전체를 훑는지 DB에게 물어보는 명령
Full Scan(전체 스캔)인덱스를 안 타고 테이블의 모든 행을 처음부터 끝까지 확인하는 것. 데이터가 많을수록 느림
정규화(Normalization)같은 데이터를 여러 곳에 중복 저장하지 않도록 테이블을 나누는 설계 원칙
역정규화(Denormalization)조회 속도를 위해 일부러 데이터를 중복 저장하는 것. 정합성 관리 비용과 맞바꾸는 선택
복제(Replication)같은 데이터를 여러 대의 DB 서버에 복사해두는 것
Primary / Read Replica쓰기를 전담하는 서버(Primary)와, 그 데이터를 복사해 읽기만 전담하는 서버(Replica)
복제 지연(Replication Lag)Primary에 쓴 내용이 Replica에 반영되기까지 걸리는 약간의 시간 차이
샤딩(Sharding)한 대로 감당이 안 될 만큼 커진 데이터를 여러 서버에 나눠 저장하는 것
RPO (Recovery Point Objective)장애가 나도 "최대 이만큼 전 시점까지의" 데이터 손실은 감수할 수 있다는 기준
RTO (Recovery Time Objective)장애가 났을 때 "이 시간 안에는" 서비스를 복구해야 한다는 기준

1. 인덱스 튜닝#

인덱스가 필요한 순간#

WHERE, JOIN, ORDER BY에 자주 쓰이는데 조회가 느린 컬럼이 후보입니다.

sql
-- 자주 실행되는데 느린 쿼리
SELECT * FROM courses WHERE instructor_id = 42 ORDER BY created_at DESC;

-- 인덱스 추가
CREATE INDEX idx_courses_instructor_created ON courses (instructor_id, created_at);

여러 컬럼을 함께 검색·정렬한다면, 인덱스도 그 순서를 그대로 반영한 복합 인덱스로 만드는 것이 효과적입니다.

EXPLAIN으로 실제 확인하기#

sql
EXPLAIN SELECT * FROM courses WHERE instructor_id = 42;

(MySQL 기준) type 값이 ALL이면 테이블 전체를 훑는 것(Full Scan)이고, ref나 range면 인덱스를 타고 있다는 뜻입니다. PostgreSQL은 출력 형식이 달라 Seq Scan이면 전체 스캔, Index Scan/Index Only Scan이면 인덱스를 타고 있다는 뜻입니다. DB마다 EXPLAIN 출력 형식이 다르므로 사용 중인 DB 문서를 함께 확인합니다. "인덱스를 만들었으니 빨라졌겠지"라고 짐작하지 않고, EXPLAIN으로 실제 실행 계획을 확인합니다.

기본 상식: 인덱스는 조회를 빠르게 해주지만 INSERT/UPDATE/DELETE는 느려지게 만듭니다(인덱스도 함께 갱신해야 하므로). 모든 컬럼에 인덱스를 걸지 않고, 실제로 자주 조회되는 컬럼에만 선택적으로 적용합니다.

2. 정규화와 역정규화#

정규화#

같은 데이터를 여러 곳에 중복 저장하지 않도록 테이블을 나누는 설계 원칙입니다. 기초 가이드에서 다룬 "하나의 값은 한 곳에만 저장"이 이 원칙입니다.

text
정규화 안 된 예: orders 테이블에 상품명을 직접 저장
→ 상품명이 바뀌면 과거 주문 데이터를 다 찾아서 고쳐야 함

정규화된 예: orders는 product_id만 저장, 상품명은 products 테이블에서 JOIN으로 조회
→ 상품명이 바뀌어도 한 곳만 수정하면 됨

역정규화#

정규화가 항상 정답은 아닙니다. 조회가 너무 잦고 매번 여러 테이블을 JOIN해야 한다면, 일부러 중복을 허용해 조회 속도를 높이기도 합니다.

text
예: 강의 목록 화면에 "수강생 수"를 매번 enrollments 테이블을 세어서 보여주면 느림
→ courses 테이블에 enrollment_count 컬럼을 두고, 수강 신청/취소 시점에 갱신
→ 대신 이 값이 실제 수강 수와 어긋나지 않도록 갱신 로직을 신경 써야 함

기본 상식: 역정규화는 "조회 성능을 위해 정합성 관리 비용을 감수하는 것"입니다. 처음부터 역정규화하지 말고, 정규화된 구조로 시작해서 실제로 느린 조회가 확인됐을 때 부분적으로 적용합니다.

3. 복제 (Replication)#

같은 데이터를 여러 대의 DB 서버에 복사해두는 것입니다. 흔히 쓰는 구조는 하나의 쓰기 전용 서버(Primary)와 여러 개의 읽기 전용 복제본(Read Replica)입니다.

text
쓰기(INSERT/UPDATE/DELETE) → Primary DB
읽기(SELECT)                → Read Replica (여러 대로 분산 가능)

장점: 읽기 요청을 여러 서버로 분산해 처리량을 늘릴 수 있고, Primary가 죽어도 읽기는 계속 가능합니다.

주의점 — 복제 지연(Replication Lag): Primary에 쓴 직후 바로 Replica에서 읽으면, 아직 복제가 안 끝나 이전 데이터가 보일 수 있습니다. "글을 쓰자마자 바로 보여야 하는" 화면은 Primary에서 읽거나, 쓰기 직후 응답에 결과를 포함해 다시 조회하지 않게 설계합니다.

4. 샤딩 기초 개념#

한 대의 DB 서버로 감당이 안 될 만큼 데이터가 커지면, 데이터를 여러 서버에 나눠 저장합니다.

text
사용자 ID 1~1000000  → DB 서버 A
사용자 ID 1000001~   → DB 서버 B

기본 상식: 샤딩은 강력하지만 대가가 큽니다. 서로 다른 샤드에 있는 데이터를 JOIN하기 어렵고, 샤드 키(위 예시의 사용자 ID) 선택을 잘못하면 특정 샤드에 부하가 몰립니다. 복제로 해결되지 않을 만큼 데이터·트래픽이 커졌을 때 최후에 검토하는 방법이며, 그 전에 인덱싱·캐싱·역정규화·복제로 해결되지 않는지 먼저 확인합니다.

5. 백업과 복구#

백업 전략#

text
전체 백업(Full Backup): 특정 시점의 데이터 전체를 복사
증분 백업(Incremental): 마지막 백업 이후 변경분만 저장

복구 목표를 미리 정해두기#

지표의미
RPO (Recovery Point Objective)장애 시 "최대 얼마 전 시점까지" 데이터 손실을 감수할 수 있는가
RTO (Recovery Time Objective)장애 시 "얼마 안에" 서비스를 복구해야 하는가

예를 들어 RPO 1시간이라면 최소 1시간 간격으로 백업이 필요하고, RTO 30분이라면 백업에서 실제로 30분 안에 복구할 수 있는지 미리 연습(복구 리허설)해봐야 합니다.

기본 상식: 백업은 "설정해뒀다"가 아니라 "실제로 복구가 되는지 검증해봤다"까지가 완성입니다. 백업 파일이 손상되어 있거나 복구 절차가 문서화되지 않아, 정작 장애 상황에 복구가 안 되는 경우가 실무에서 드물지 않습니다.

6. 자주 하는 실수#

  • 느린 쿼리를 확인 없이 무작정 인덱스부터 추가
  • 처음부터 성능을 걱정해 과도하게 역정규화해 정합성 버그가 잦아짐
  • Read Replica의 복제 지연을 고려하지 않고 쓰기 직후 바로 조회
  • 백업은 설정해뒀지만 실제 복구를 한 번도 테스트해보지 않음
  • 샤딩을 성급하게 도입해 JOIN이 필요한 기능을 구현하기 어려워짐

7. 실전 체크리스트#

  • 느린 쿼리를 EXPLAIN으로 실제 확인한 뒤 인덱스를 추가했는가
  • 자주 조회되지만 자주 안 바뀌는 데이터에 역정규화·캐싱을 검토했는가
  • Read Replica를 쓴다면 복제 지연이 문제 되는 화면을 파악했는가
  • RPO/RTO를 정하고 실제 복구 절차를 검증해봤는가
  • 인덱스가 쓰기 성능에 주는 영향을 고려했는가

8. 트랜잭션 격리 수준#

여러 요청이 동시에 같은 데이터를 읽고 쓸 때, 서로 어디까지 영향을 줄지 정하는 것이 격리 수준(Isolation Level)입니다.

격리 수준새로 추가로 허용되는 현상(SQL 표준 기준)설명
READ UNCOMMITTEDDirty Read다른 트랜잭션이 아직 커밋하지 않은 값까지 읽음(거의 사용 안 함)
READ COMMITTED+ Non-Repeatable Read커밋된 값만 읽지만, 같은 트랜잭션 안에서 두 번 읽으면 값이 달라질 수 있음
REPEATABLE READ+ Phantom Read이미 읽은 행은 같은 트랜잭션 안에서 항상 같은 값을 읽지만, SQL 표준상으로는 범위 조회 시 새로 추가된 행(Phantom)이 보일 수 있음
SERIALIZABLE없음가장 엄격. 사실상 순차 실행처럼 동작해 안전하지만 동시성이 크게 떨어짐

각 단계는 윗줄의 현상을 포함해 누적됩니다. 예를 들어 READ COMMITTED는 Dirty Read는 막지만 Non-Repeatable Read와 Phantom Read는 여전히 허용합니다.

DB마다 실제 동작은 다릅니다: 위 표는 SQL 표준의 정의이고, 실제 구현은 DB/엔진마다 차이가 있습니다. - MySQL InnoDB는 REPEATABLE READ가 기본값이지만, MVCC와 갭 락(gap lock) 덕분에 일반적인 조회(consistent read)에서는 SQL 표준과 달리 Phantom Read가 거의 발생하지 않습니다. 다만 SELECT ... FOR UPDATE 같은 락 조회나 특정 상황에서는 여전히 phantom이 나타날 수 있어, "MySQL의 REPEATABLE READ는 SERIALIZABLE급으로 완전히 안전하다"고 단정하면 안 됩니다. - PostgreSQL은 REPEATABLE READ가 기본값이 아니라 READ COMMITTED가 기본값이며, PostgreSQL의 REPEATABLE READ는 스냅샷 격리(Snapshot Isolation) 기반이라 Phantom Read는 막지만 write skew 같은 다른 이상 현상은 여전히 가능합니다. - 즉 같은 이름의 격리 수준이라도 DB마다 실제로 막아주는 범위가 다르므로, 사용 중인 DB의 문서로 반드시 재확인해야 합니다.

sql
-- 아래는 MySQL 문법 예시입니다. PostgreSQL 등에서는 트랜잭션 시작(BEGIN) 이후에
-- SET TRANSACTION ISOLATION LEVEL을 실행하는 등 문법과 적용 시점이 다를 수 있습니다.
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION;
SELECT stock FROM products WHERE id = 1;
-- 이 트랜잭션이 끝날 때까지 같은 조회는 같은 값을 반환
UPDATE products SET stock = stock - 1 WHERE id = 1;
COMMIT;

실무 팁: 격리 수준을 높일수록 데이터는 안전해지지만 동시 처리량이 떨어집니다. 재고 차감처럼 동시성 충돌이 치명적인 경우에만 엄격한 수준이나 명시적 락을 쓰고, 대부분의 조회는 기본 격리 수준으로 충분합니다. 다만 "기본값이면 안전하다"고 넘겨짚지 말고, 실제로 동시 접근이 몰리는 로직(재고 차감, 잔액 이체 등)은 격리 수준만 믿기보다 명시적 락이나 재시도 로직을 함께 검토합니다.

9. 락(Lock)과 데드락#

비관적 락 vs 낙관적 락#

sql
-- 비관적 락: 조회 시점에 행을 잠가서 다른 트랜잭션이 못 건드리게 함
SELECT * FROM products WHERE id = 1 FOR UPDATE;

-- 낙관적 락: 버전 컬럼을 두고, 수정 시 버전이 그대로일 때만 반영
UPDATE products SET stock = stock - 1, version = version + 1
WHERE id = 1 AND version = 5;
-- 영향받은 행이 0개면 그사이 다른 트랜잭션이 먼저 수정했다는 뜻 → 재시도
비관적 락낙관적 락
동작 방식미리 잠그고 시작일단 진행하고 충돌 시 재시도
충돌이 잦을 때유리(대기가 명확)재시도 비용이 커짐
충돌이 드물 때불필요한 대기 발생유리(락 오버헤드 없음)

데드락(Deadlock)#

두 트랜잭션이 서로 상대가 잠근 자원을 기다리며 영원히 멈추는 상황입니다.

text
트랜잭션 A: 상품 1 잠금 → 상품 2 잠금 시도(대기)

DB는 보통 데드락을 자동 감지해 한쪽 트랜잭션을 강제 롤백시킵니다. 애플리케이션에서는 "여러 자원을 잠글 때 항상 같은 순서로 잠근다"는 규칙을 지키면 데드락을 예방할 수 있습니다.

10. N+1 문제와 해결#

N+1 문제란#

python
courses = Course.query.all()          # 쿼리 1번
for course in courses:
    print(course.instructor.name)     # 강의 개수(N)만큼 추가 쿼리 발생

목록을 조회한 뒤 각 항목의 연관 데이터를 반복문 안에서 따로 조회하면, 목록이 100개면 101번의 쿼리가 나갑니다.

해결 — Eager Loading#

python
# SQLAlchemy 예시
from sqlalchemy.orm import joinedload

courses = Course.query.options(joinedload(Course.instructor)).all()
# JOIN 한 번으로 강사 정보까지 함께 가져옴
sql
-- 직접 SQL로는 애초에 JOIN으로 한 번에 가져오는 것과 같은 원리
SELECT courses.*, instructors.name
FROM courses
JOIN instructors ON courses.instructor_id = instructors.id;

기본 상식: ORM은 편하지만 관계된 데이터에 접근할 때 자동으로 추가 쿼리를 날리는 지연 로딩(Lazy Loading)이 기본값인 경우가 많습니다. 목록 화면처럼 반복문 안에서 연관 데이터를 쓰는 코드는 Eager Loading이 필요한지 확인합니다. 실제 쿼리 로그를 켜서 쿼리 수를 세어보는 습관이 유용합니다.

다만 Eager Loading이 항상 정답은 아닙니다. 목록 크기가 작거나 연관 데이터를 쓰지 않는 경로까지 무조건 JOIN으로 미리 가져오면, 불필요한 데이터까지 매번 읽어 오히려 느려질 수 있습니다. 특히 1:N 관계를 JOIN으로 즉시 로딩하면 상위 행이 연관 개수만큼 중복되어 반환되는 "카티션 곱" 문제가 생길 수 있어, 이런 경우는 배치로 나눠 조회(batch loading)하는 방식이 더 나을 수 있습니다. N+1이 실제로 쿼리 수·응답 시간에 영향을 주는지 확인한 뒤 적용하는 것이 안전합니다.

11. 커넥션 풀#

매 요청마다 DB 연결을 새로 맺으면 연결 자체에 시간이 걸립니다. 미리 여러 개의 연결을 만들어두고 재사용하는 것이 커넥션 풀입니다.

python
# SQLAlchemy 예시
engine = create_engine(
    "mysql+pymysql://user:pw@host/db",
    pool_size=10,        # 기본으로 유지할 연결 수
    max_overflow=5,       # 순간적으로 더 필요할 때 추가로 허용할 연결 수
    pool_timeout=30,      # 풀에 여유 연결이 없을 때 대기할 최대 시간(초)
    pool_recycle=1800,    # 오래된 연결을 재활용(끊긴 연결 방지)
)

기본 상식: 풀 크기를 무작정 크게 잡으면 DB 서버 쪽 최대 연결 수를 초과해 오히려 장애가 날 수 있습니다. 애플리케이션 서버 인스턴스 수 × 풀 크기가 DB의 max_connections를 넘지 않는지 확인합니다.

12. 페이지네이션 성능#

OFFSET의 함정#

sql
-- 뒤 페이지로 갈수록 느려짐
SELECT * FROM courses ORDER BY id LIMIT 20 OFFSET 100000;
-- DB는 100000개를 건너뛰기 위해 앞의 행들을 모두 훑어야 함

커서 기반 페이지네이션#

sql
-- 마지막으로 본 id를 기준으로 다음 페이지 조회
SELECT * FROM courses WHERE id > 12345 ORDER BY id LIMIT 20;
-- 인덱스를 타면 건너뛰는 비용 없이 바로 다음 구간부터 조회

실무 팁: 페이지 번호를 직접 입력해 이동하는 UI(1, 2, 3 ... 페이지)는 OFFSET 방식이 편하지만, 무한 스크롤처럼 "다음 페이지"만 필요한 화면은 커서 기반이 데이터가 많아질수록 훨씬 유리합니다.

13. 쿼리 캐싱 전략#

자주 조회되지만 자주 바뀌지 않는 데이터는 DB를 매번 거치지 않고 캐시에서 응답합니다.

python
import redis
r = redis.Redis()

def get_popular_courses():
    cached = r.get("popular_courses")
    if cached:
        return json.loads(cached)

    courses = db.query(...)  # 실제 DB 조회
    r.setex("popular_courses", 300, json.dumps(courses))  # 5분간 캐시
    return courses
캐시 무효화 전략설명
TTL(만료 시간) 기반일정 시간이 지나면 자동 삭제. 구현이 단순하지만 그 시간 동안은 오래된 데이터가 보일 수 있음
쓰기 시점 무효화데이터가 바뀌는 순간 관련 캐시를 직접 삭제. 정확하지만 무효화 대상을 빠뜨리기 쉬움

기본 상식: "캐시 무효화"는 컴퓨터 과학에서 어려운 문제로 꼽힙니다. 처음에는 TTL 기반으로 단순하게 시작하고, 실시간성이 중요한 데이터에만 점진적으로 쓰기 시점 무효화를 추가하는 편이 안전합니다.
