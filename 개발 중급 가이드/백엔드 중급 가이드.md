> **대상:** Route → Service → Model 구조로 API 서버 하나(인증, CRUD, 배포)를 끝까지 만들어본 사람
> **목적:** 요청이 몰리거나 데이터가 커졌을 때 실제로 부딪히는 문제와 대응 방법을 정리합니다

# 0. 시작 전에 — 자주 나오는 용어

기초 가이드에서 다룬 Route/Service/Model, HTTP, REST, 인증·인가 용어는 이미 안다고 가정합니다. 여기서는 이 문서에서 새로 나오는 용어만 정리합니다.

| 용어 | 쉬운 설명 |
| --- | --- |
| 캐싱(Caching) | 자주 조회되지만 잘 안 바뀌는 데이터를 미리 빠른 저장소(Redis 등)에 저장해뒀다 재사용하는 것 |
| 캐시 무효화(Cache Invalidation) | 원본 데이터가 바뀌었을 때, 저장해둔 캐시를 지우거나 갱신해서 옛날 값을 안 보여주게 하는 것 |
| TTL(Time To Live) | 캐시가 자동으로 사라지기까지의 유효 시간 |
| 메시지 큐(Message Queue) | "지금 당장 처리 안 해도 되는 작업"을 줄 세워뒀다가 별도 프로세스가 순서대로 처리하게 하는 장치 |
| 워커(Worker) | 메시지 큐에 쌓인 작업을 실제로 꺼내서 처리하는 별도 프로세스 |
| N+1 쿼리 문제 | 목록 하나를 조회할 때, 항목마다 연관 데이터를 별도 쿼리로 매번 가져와 쿼리 수가 크게 늘어나는 문제 |
| Eager Loading | N+1을 막기 위해, 연관 데이터를 처음부터 한 번의 쿼리로 함께 가져오는 방식 |
| API 버저닝(API Versioning) | API 응답 형식이 바뀌어도 기존 클라이언트가 계속 동작하도록 버전을 나눠 관리하는 것 |
| Rate Limiting | 한 사용자·IP가 짧은 시간에 너무 많이 요청하지 못하도록 횟수를 제한하는 것 |
| 구조화 로깅(Structured Logging) | 검색·필터링이 가능하도록 로그를 JSON 같은 정해진 형식으로 남기는 방식 |
| APM (Application Performance Monitoring) | 요청마다 걸린 시간과 느린 지점을 자동으로 추적·기록해주는 모니터링 도구 |
| 트랜잭션 격리 수준(Isolation Level) | 동시에 실행되는 여러 트랜잭션이 서로의 변경을 어디까지 볼 수 있는지 정하는 DB 설정 |
| 수평 확장(Scale Out) | 서버 사양을 올리는 대신 서버 대수를 늘려서 트래픽을 감당하는 방식 |
| 무상태(Stateless) | 서버가 사용자 상태(로그인 정보 등)를 자기 메모리에 담아두지 않는 설계. 어느 서버가 요청을 받아도 동일하게 처리 가능해짐 |
| 로드밸런서(Load Balancer) | 들어오는 요청을 여러 서버에 골고루 나눠주는 장치 |

# 1. 캐싱 전략

## 언제 캐싱이 필요한가

같은 조회 요청이 반복되고, 결과가 자주 바뀌지 않을 때 씁니다. 예: 인기 강의 목록, 카테고리 목록.

```python
import redis
import json

r = redis.Redis()

def get_popular_courses():
    cached = r.get("popular_courses")
    if cached:
        return json.loads(cached)

    courses = Course.query.order_by(Course.enrollment_count.desc()).limit(10).all()
    result = [c.to_dict() for c in courses]
    r.setex("popular_courses", 300, json.dumps(result))  # 300초(5분) 뒤 자동 만료
    return result
```

## 캐시 무효화 패턴

| 전략 | 설명 |
| --- | --- |
| TTL(Time To Live) | 일정 시간 뒤 자동 만료 — 구현이 가장 간단함 |
| 쓰기 시 무효화 | 데이터가 바뀌는 순간 관련 캐시를 직접 삭제 |
| 캐시 키에 버전 포함 | 데이터가 바뀌면 버전을 올려서 이전 캐시를 자연스럽게 못 쓰게 만듦 |

**기본 상식**: "캐시 무효화와 이름 짓기가 컴퓨터과학에서 가장 어려운 두 가지 문제"라는 말이 있을 만큼, 언제 캐시를 지울지가 캐싱 자체보다 어렵습니다. 처음엔 TTL만으로 시작하고, 데이터 정합성이 중요해지면 쓰기 시 무효화를 추가하는 순서를 권장합니다.

# 2. 메시지 큐 — 비동기 처리

이메일 발송, 썸네일 생성처럼 시간이 걸리지만 즉시 응답할 필요는 없는 작업을 요청-응답 흐름에서 분리합니다.

```text
사용자 요청 → 서버가 "작업 등록"만 하고 즉시 응답
                ↓
            메시지 큐(Redis, RabbitMQ 등)
                ↓
            별도의 워커(worker) 프로세스가 실제 작업을 처리
```

```python
# Celery 예시
from celery import Celery

celery_app = Celery("tasks", broker="redis://localhost:6379/0")

@celery_app.task
def send_welcome_email(user_id):
    user = User.query.get(user_id)
    mail.send(user.email, "가입을 환영합니다")

# 라우트에서는 이렇게 호출만 하고 바로 응답
send_welcome_email.delay(user.id)
return jsonify({"data": {"id": user.id}}), 201
```

**실무 팁**: 요청-응답 안에서 시간이 오래 걸리는 작업(외부 API 호출, 대용량 파일 처리, 이메일 발송)을 발견하면 "이걸 나중에 처리해도 되는가?"를 먼저 물어봅니다. 그렇다면 큐로 분리해 응답 속도를 개선할 수 있습니다.

# 3. N+1 쿼리 문제

목록을 조회할 때, 목록 하나당 연관 데이터를 별도 쿼리로 매번 가져오면 쿼리 수가 N+1개로 늘어납니다.

```python
# 나쁜 예 — courses가 10개면 쿼리가 11번 실행됨 (1 + 10)
courses = Course.query.all()
for c in courses:
    print(c.instructor.name)   # 강사 정보를 매번 별도 쿼리로 조회

# 좋은 예 — eager loading으로 한 번에 가져옴
from sqlalchemy.orm import joinedload
courses = Course.query.options(joinedload(Course.instructor)).all()
```

**확인 방법**: ORM이 실제로 어떤 SQL을 만드는지 로그로 켜두고, 목록 화면에서 쿼리 수가 데이터 개수에 비례해 늘어나는지 확인합니다. (Flask-SQLAlchemy는 `SQLALCHEMY_ECHO=True`로 쿼리 로그를 볼 수 있습니다.)

# 4. API 버저닝

이미 배포된 API의 응답 형식을 바꿔야 할 때, 기존 클라이언트(오래된 앱 버전 등)를 깨뜨리지 않는 방법입니다.

| 방식 | 예시 | 특징 |
| --- | --- | --- |
| URL 경로 | `/api/v1/courses`, `/api/v2/courses` | 가장 명확하고 흔히 씀 |
| 헤더 | `Accept: application/vnd.myapp.v2+json` | URL은 깔끔하지만 덜 직관적 |
| 쿼리 파라미터 | `/api/courses?version=2` | 캐싱과 함께 쓰기 까다로움 |

**기본 상식**: 처음부터 `v1`을 붙여두면, 나중에 `v2`가 필요할 때 기존 URL 구조를 유지한 채 확장할 수 있습니다. 버전을 아예 안 붙였다가 나중에 붙이려면 모든 클라이언트와 조율이 필요해 훨씬 어렵습니다.

# 5. Rate Limiting

한 사용자(또는 IP)가 짧은 시간에 너무 많은 요청을 보내는 것을 막습니다. 로그인 시도 무차별 공격, 크롤링 방지에도 쓰입니다.

```python
from flask_limiter import Limiter
from flask_limiter.util import get_remote_address

limiter = Limiter(get_remote_address, app=app, default_limits=["200 per day"])

@app.route("/api/auth/login", methods=["POST"])
@limiter.limit("5 per minute")   # 로그인은 더 엄격하게
def login():
    ...
```

한도를 넘으면 보통 `429 Too Many Requests` 상태 코드로 응답합니다.

# 6. 구조화 로깅과 APM 기초

## 구조화 로깅

`print()`나 단순 문자열 로그 대신, 검색·필터링이 가능한 JSON 형태로 남깁니다.

```python
import logging, json

logger = logging.getLogger("app")

def log_event(event, **fields):
    logger.info(json.dumps({"event": event, **fields}))

log_event("course_enrolled", user_id=user.id, course_id=course.id)
# {"event": "course_enrolled", "user_id": 42, "course_id": 7}
```

이렇게 남기면 로그 수집 도구(예: CloudWatch, ELK)에서 "특정 사용자의 이벤트만" 또는 "특정 이벤트가 몇 번 발생했는지" 바로 검색할 수 있습니다.

## APM(Application Performance Monitoring)

요청별로 얼마나 걸렸는지, 어느 함수가 느린지를 자동으로 추적하는 도구입니다(예: Sentry, Datadog). 운영 중 "왜 갑자기 느려졌는지"를 로그만으로 찾기 어려울 때 큰 도움이 됩니다.

# 7. 트랜잭션 격리 수준

여러 요청이 동시에 같은 데이터를 건드릴 때 어디까지 서로의 변경을 볼 수 있는지를 정합니다.

| 수준 | 설명 |
| --- | --- |
| Read Uncommitted | 다른 트랜잭션의 커밋 전 변경도 보임 (거의 안 씀) |
| Read Committed | 커밋된 변경만 보임 (대부분 DB의 기본값) |
| Repeatable Read | 같은 트랜잭션 안에서는 항상 같은 결과를 봄 (MySQL 기본값) |
| Serializable | 트랜잭션을 사실상 순차 실행한 것처럼 완전히 격리 (가장 안전하지만 느림) |

**기본 상식**: 격리 수준을 올릴수록 안전하지만 동시 처리 성능이 떨어집니다. 대부분의 서비스는 기본값(Read Committed 또는 Repeatable Read)으로 충분하고, 재고 차감·정산처럼 "동시에 건드리면 안 되는" 로직에만 `SELECT ... FOR UPDATE` 같은 명시적 잠금을 추가로 검토합니다.

# 8. 수평 확장과 무상태 설계

서버 한 대로 감당이 안 되면 서버를 여러 대로 늘립니다(수평 확장). 이걸 가능하게 하려면 서버가 **무상태(stateless)** 여야 합니다.

```text
상태를 서버 메모리에 두면 (나쁜 예)
→ 로그인 세션을 서버1의 메모리에 저장
→ 다음 요청이 서버2로 가면 로그인 정보를 못 찾음

무상태로 설계하면 (좋은 예)
→ 로그인 상태를 JWT 토큰(클라이언트가 들고 있음) 또는
  공용 저장소(Redis)에 저장
→ 어느 서버가 요청을 받아도 동일하게 처리 가능
```

로드밸런서가 여러 서버에 요청을 나눠줄 때, 서버마다 결과가 달라지지 않아야 안정적으로 확장할 수 있습니다.

# 9. 자주 하는 실수

- 캐시를 넣고 무효화 전략 없이 방치해 오래된 데이터가 계속 보임
- 오래 걸리는 작업(이메일, 파일 처리)을 요청-응답 안에서 동기로 처리해 응답이 느려짐
- 목록 API에서 N+1 쿼리를 방치해 데이터가 늘어날수록 급격히 느려짐
- API 버전 없이 배포하다가 클라이언트 호환성 문제로 롤백
- 세션을 서버 메모리에 저장해 서버를 늘릴 수 없는 구조가 됨

# 10. 실전 체크리스트

- [ ] 반복 조회되는 데이터에 캐싱을 검토했는가, 무효화 전략도 함께 정했는가
- [ ] 응답을 오래 지연시키는 작업을 큐로 분리할 수 있는지 확인했는가
- [ ] 목록 API의 쿼리 로그를 확인해 N+1이 없는지 점검했는가
- [ ] 인증처럼 민감한 엔드포인트에 Rate Limiting을 적용했는가
- [ ] 운영 로그가 검색 가능한 구조화 형태로 남는가
- [ ] 세션/상태를 서버 메모리가 아닌 공용 저장소에 두었는가 (확장 가능성 확보)
