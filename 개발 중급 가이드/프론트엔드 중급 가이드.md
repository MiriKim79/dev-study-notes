> **대상:** React로 화면 하나(목록 → 상세 → API 연동)를 끝까지 만들어본 사람
> **목적:** "일단 동작하는" 수준을 넘어 성능·테스트·렌더링 전략까지 고려하는 방법을 정리합니다

# 0. 시작 전에 — 자주 나오는 용어

기초 가이드에서 다룬 컴포넌트·상태·API 통신 용어는 이미 안다고 가정합니다. 여기서는 이 문서에서 새로 나오는 용어만 정리합니다.

| 용어 | 쉬운 설명 |
| --- | --- |
| 코드 스플리팅(Code Splitting) | 전체 코드를 한 번에 내려받지 않고, 필요한 화면에 진입할 때만 나눠서 불러오는 기법 |
| 메모이제이션(Memoization) | 같은 계산·렌더링을 반복하지 않도록 이전 결과를 기억해뒀다 재사용하는 것. React의 `memo`/`useMemo`/`useCallback`이 이 방식을 씀 |
| 서버 상태 / 클라이언트 상태 | 서버 상태는 API로 받아온 데이터(캐싱·재요청 필요), 클라이언트 상태는 모달 열림 여부처럼 화면 안에서만 쓰는 값 |
| 보일러플레이트(Boilerplate) | 기능마다 반복해서 작성해야 하는 정형화된 코드. 많을수록 손이 많이 감 |
| CSR (Client-Side Rendering) | 브라우저가 화면을 매번 직접 그리는 방식. 기초 가이드에서 다룬 React의 기본 동작(순수 React/Vite 프로젝트의 기본값) |
| SSR (Server-Side Rendering) | 요청이 올 때마다 서버가 HTML을 만들어 보내는 방식. Next.js·Remix 등 프레임워크가 이 방식을 지원하며, 순수 React만으로는 직접 서버 렌더링 코드를 짜야 함 |
| SSG (Static Site Generation) | 빌드할 때 미리 HTML을 만들어두는 방식. 거의 안 바뀌는 페이지에 적합. Next.js, Gatsby, Astro 등 특정 프레임워크가 제공하는 빌드 기능이며 React 자체 표준은 아님 |
| ISR (Incremental Static Regeneration) | SSG처럼 미리 만들어두되, 일정 시간마다 백그라운드에서 다시 생성하는 방식. **Next.js 고유 용어/기능**이며 다른 프레임워크에는 이 이름 그대로 존재하지 않음(유사 기능은 프레임워크마다 다르게 구현됨) |
| 컴포넌트 테스트 | 컴포넌트 하나를 화면에 렌더링해서 "사용자가 보는 결과"가 맞는지 확인하는 테스트 |
| E2E 테스트(End-to-End) | 실제 브라우저를 띄워 로그인 → 결제처럼 여러 화면에 걸친 흐름 전체를 확인하는 테스트 |
| Core Web Vitals | 구글이 정한 "사용자가 체감하는 성능"을 재는 3가지 지표(LCP·INP·CLS) |
| Lighthouse | 브라우저 개발자 도구에 내장된 성능·접근성 자동 측정 도구 |
| 포커스 트랩(Focus Trap) | 모달이 열려 있는 동안 키보드 Tab 이동이 모달 바깥으로 나가지 않게 가두는 것 |
| ARIA 속성 | 스크린 리더 같은 보조 기술에 "지금 이 요소가 열려 있다/닫혀 있다" 같은 상태를 알려주는 HTML 속성 |
| 번들(Bundle) | 여러 코드 파일을 빌드 도구가 하나(또는 몇 개)로 묶어낸 최종 결과물 |

# 1. 성능 최적화

## 언제 최적화해야 하는가

느낌으로 최적화하지 않습니다. React DevTools Profiler로 "무엇이 얼마나 자주 다시 렌더링되는지" 먼저 측정합니다.

## 코드 스플리팅

처음부터 모든 페이지의 코드를 한 번에 내려받지 않고, 필요한 페이지에 진입할 때만 불러옵니다.

```jsx
import { lazy, Suspense } from "react";

const CourseDetailPage = lazy(() => import("./pages/CourseDetailPage"));

function App() {
  return (
    <Suspense fallback={<p>불러오는 중...</p>}>
      <CourseDetailPage />
    </Suspense>
  );
}
```

라우트 단위로 나누는 것이 효과가 가장 큽니다. 자주 쓰지 않는 큰 라이브러리(차트, 에디터 등)도 같은 방식으로 지연 로드합니다.

## memo / useMemo / useCallback

```jsx
const CourseCard = React.memo(function CourseCard({ course }) {
  return <div>{course.title}</div>;
});
```

- `React.memo`: props가 바뀌지 않으면 컴포넌트를 다시 렌더링하지 않음(단, React 공식 문서 기준으로도 이는 "성능 최적화"일 뿐 "리렌더링 안 됨"을 보장하는 계약은 아닙니다)
- `useMemo`: 계산 비용이 큰 값을 props/state가 바뀔 때만 다시 계산
- `useCallback`: 함수를 매 렌더링마다 새로 만들지 않고 재사용 (자식이 `memo`로 감싸져 있을 때 효과가 있음)

**기본 상식**: 이 세 가지는 "무조건 붙이면 빨라지는" 도구가 아닙니다. 메모이제이션 자체에도 비용이 있어서, 리스트가 몇 개뿐이거나 계산이 가벼우면 오히려 코드만 복잡해집니다. Profiler로 실제 병목을 확인한 부분에만 적용합니다.

# 2. 상태관리 라이브러리 비교

기초 가이드에서 상태를 "지역/공유/서버 상태"로 나눴습니다. 프로젝트가 커지면 공유 상태와 서버 상태를 어떤 도구로 관리할지 선택이 필요합니다.

| 도구 | 용도 | 특징 |
| --- | --- | --- |
| Context API | 소규모 공유 상태 (로그인 사용자, 테마) | 별도 설치 불필요, 값이 자주 바뀌면 불필요한 리렌더링 발생 가능 |
| Redux / Redux Toolkit | 대규모, 복잡한 상태 로직 | 구조가 명확하고 디버깅 도구가 강력하지만 보일러플레이트가 있음 |
| Zustand / Jotai | 중소규모 공유 상태 | Redux보다 훨씬 적은 코드, 러닝 커브가 낮음 |
| TanStack Query (React Query) | **서버 상태** 전용 | 캐싱, 재요청, 로딩/에러 상태를 자동 관리 — API 데이터는 이 도구가 담당 |

**실무 팁**: "서버에서 받아온 데이터"와 "화면에서만 쓰는 상태"를 같은 도구로 관리하지 않는 것이 최근 흐름입니다. 서버 데이터는 TanStack Query 같은 전용 도구에 맡기고, Redux/Zustand/Context는 진짜 클라이언트 상태(모달 열림 여부, 폼 입력값 등)만 담당하게 하면 캐싱·로딩·재시도를 직접 구현하지 않아도 됩니다.

```jsx
// TanStack Query 최소 예시
function useCourses() {
  return useQuery({
    queryKey: ["courses"],
    queryFn: () => fetch("/api/courses").then((r) => r.json()),
  });
}

function CourseList() {
  const { data, isLoading, error } = useCourses();
  if (isLoading) return <p>불러오는 중...</p>;
  if (error) return <p>불러오지 못했습니다.</p>;
  return <ul>{data.map((c) => <li key={c.id}>{c.title}</li>)}</ul>;
}
```

# 3. 렌더링 전략 심화 — CSR / SSR / SSG / ISR

> **주의**: 아래 네 가지는 웹 표준이 아니라 렌더링 시점을 구분하는 개념적 분류입니다. CSR은 React 자체(순수 Vite/CRA 프로젝트)에서도 기본으로 동작하지만, SSR/SSG는 Next.js·Remix·Gatsby·Astro 같은 프레임워크가 있어야 실제로 구현할 수 있고, **ISR은 그중에서도 Next.js가 만든 고유 용어/기능**입니다. "React = CSR/SSR/SSG/ISR을 자유롭게 고를 수 있다"가 아니라, "어떤 프레임워크를 쓰느냐에 따라 선택지가 달라진다"가 정확한 설명입니다.

| 전략 | 언제 HTML을 만드는가 | 적합한 경우 |
| --- | --- | --- |
| CSR | 브라우저에서 매번 | 로그인 후에만 보이는 대시보드 등 SEO가 중요하지 않은 화면 |
| SSR | 요청이 올 때마다 서버에서 | 검색 결과처럼 자주 바뀌고 SEO가 중요한 페이지 |
| SSG | 빌드 시 미리 | 소개 페이지, 블로그 글처럼 거의 안 바뀌는 페이지 |
| ISR | 빌드 시 미리 만들고, 일정 시간마다 백그라운드에서 재생성 | 상품 목록처럼 자주는 아니어도 주기적으로 바뀌는 페이지 |

Next.js(App Router) 기준 최소 예시입니다.

```jsx
// app/courses/page.jsx — 기본은 서버에서 렌더링(SSR에 가까움)
export default async function CoursesPage() {
  const res = await fetch("https://api.example.com/courses");
  const courses = await res.json();
  return <CourseList courses={courses} />;
}

// 정적으로 미리 만들고 싶다면
export const revalidate = 3600; // 1시간마다 재생성 (ISR)
```

**기본 상식**: "React를 쓰면 무조건 CSR"이 아닙니다. 페이지 성격(자주 바뀌는가, SEO가 필요한가, 로그인 전용인가)에 따라 같은 프로젝트 안에서도 페이지마다 다른 전략을 씁니다.

**참고 — Server Components와의 차이**: React 19부터 정식 지원되는 서버 컴포넌트(Server Components, RSC)는 위의 SSR과 다른 개념입니다. SSR은 "HTML을 언제 만드는가"의 문제이고, 서버 컴포넌트는 "어떤 컴포넌트를 애초에 서버에서만 실행하고 클라이언트 번들에는 포함시키지 않을 것인가"의 문제입니다. 서버 컴포넌트도 React 단독으로는 쓸 수 없고 Next.js(App Router) 같은 프레임워크의 번들러 통합이 필요합니다.

# 4. 테스트

## 컴포넌트 테스트 (Jest + React Testing Library)

```jsx
import { render, screen, fireEvent } from "@testing-library/react";
import CourseCard from "./CourseCard";

test("무료 강의는 '무료'라고 표시된다", () => {
  render(<CourseCard title="React 입문" price={0} />);
  expect(screen.getByText("무료")).toBeInTheDocument();
});

test("버튼을 누르면 onEnroll이 호출된다", () => {
  const onEnroll = jest.fn();
  render(<CourseCard title="React 입문" price={0} onEnroll={onEnroll} />);
  fireEvent.click(screen.getByRole("button", { name: "수강 신청" }));
  expect(onEnroll).toHaveBeenCalledTimes(1);
});
```

**기본 상식**: "구현 세부사항"이 아니라 "사용자가 보는 결과"를 테스트합니다. `state` 변수 이름이나 내부 함수 호출 여부보다, 화면에 뭐가 보이는지·버튼을 눌렀을 때 뭐가 일어나는지를 검증합니다.

## E2E 테스트 (Playwright)

```js
test("로그인 후 마이페이지로 이동한다", async ({ page }) => {
  await page.goto("/login");
  await page.fill('input[name="email"]', "test@example.com");
  await page.fill('input[name="password"]', "password123");
  await page.click('button[type="submit"]');
  await expect(page).toHaveURL("/mypage");
});
```

컴포넌트 테스트보다 느리고 비용이 크므로, 핵심 사용자 흐름(로그인, 결제, 회원가입) 몇 개만 E2E로 커버하고 나머지는 컴포넌트 테스트로 촘촘히 덮는 것이 일반적입니다.

# 5. Core Web Vitals

Google이 정한 "사용자가 체감하는 성능" 지표입니다.

| 지표 | 의미 | 좋은 기준 |
| --- | --- | --- |
| LCP (Largest Contentful Paint) | 가장 큰 콘텐츠가 화면에 그려지는 시간 | 2.5초 이하 |
| INP (Interaction to Next Paint) | 클릭 등 상호작용 후 화면이 반응하는 시간 | 200ms 이하 |
| CLS (Cumulative Layout Shift) | 로딩 중 레이아웃이 얼마나 갑자기 움직이는가 | 0.1 이하 |

**개선 방향**

- LCP: 큰 이미지 압축·우선 로드(`loading="eager"`, `fetchpriority="high"`), 폰트 로딩 최적화
- INP: 무거운 동기 작업을 쪼개거나 지연 실행, 불필요한 리렌더링 감소
- CLS: 이미지·광고 영역에 미리 `width`/`height`(또는 `aspect-ratio`)를 지정해 공간을 확보

브라우저 개발자 도구의 Lighthouse 탭이나 PageSpeed Insights로 실제 점수를 측정할 수 있습니다.

# 6. 웹 접근성 심화

기초 가이드의 "키보드로 조작 가능", "대체 텍스트" 수준을 넘어서는 실전 패턴입니다.

- **포커스 트랩**: 모달이 열려 있는 동안 Tab 키가 모달 바깥으로 나가지 않게 가둡니다.
- **ARIA 속성**: 시맨틱 태그만으로 표현이 안 되는 상태(`aria-expanded`, `aria-live`, `aria-hidden`)를 스크린 리더에 전달합니다.

```jsx
<button aria-expanded={isOpen} aria-controls="menu">메뉴</button>
<div id="menu" role="region" aria-live="polite">
  {isOpen && <ul>...</ul>}
</div>
```

- **`aria-live="polite"`**: 알림·에러 메시지처럼 화면이 동적으로 바뀌는 부분을 스크린 리더가 자동으로 읽어주게 합니다.

# 10. 폼(Form) 처리 심화

```jsx
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { z } from "zod";

const schema = z.object({
  title: z.string().min(1, "제목을 입력하세요"),
  price: z.number().min(0, "가격은 0 이상이어야 합니다"),
});

function CourseForm() {
  const { register, handleSubmit, formState: { errors } } = useForm({
    resolver: zodResolver(schema),
  });

  const onSubmit = (data) => createCourse(data);

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input {...register("title")} />
      {errors.title && <p>{errors.title.message}</p>}
      <button type="submit">등록</button>
    </form>
  );
}
```

**기본 상식**: 폼 상태를 `useState`로 필드마다 직접 관리하면 검증·에러 메시지·제출 상태를 모두 손으로 구현해야 합니다. React Hook Form 같은 라이브러리와 zod 같은 스키마 검증 도구를 함께 쓰면 프론트엔드 검증 로직을 백엔드와 비슷한 스키마로 재사용할 수 있고, 리렌더링 횟수도 줄어듭니다.

# 11. 에러 바운더리(Error Boundary)

컴포넌트 트리 일부에서 예외가 발생해도 전체 화면이 하얗게 깨지지 않도록 막습니다.

```jsx
class ErrorBoundary extends React.Component {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error, info) {
    reportError(error, info);   // 모니터링 도구로 전송
  }

  render() {
    if (this.state.hasError) {
      return <p>문제가 발생했습니다. 새로고침해 주세요.</p>;
    }
    return this.props.children;
  }
}

<ErrorBoundary>
  <CourseDetailPage />
</ErrorBoundary>
```

**기본 상식**: 에러 바운더리는 렌더링 중 발생한 예외만 잡습니다. 이벤트 핸들러 안의 예외나 비동기 코드의 예외는 잡지 못하므로, 그런 곳은 `try/catch`로 별도 처리해야 합니다. 페이지 전체를 하나로 감싸기보다, 기능 단위(강의 카드 하나, 위젯 하나)로 나눠 감싸면 한 부분이 깨져도 나머지 화면은 정상 동작합니다.

# 12. 코드 스플리팅과 지연 로딩

앱 전체 코드를 하나의 번들로 묶으면 처음 페이지를 열 때부터 당장 필요 없는 코드까지 모두 내려받아야 합니다.

```jsx
import { lazy, Suspense } from "react";

const CourseDetailPage = lazy(() => import("./pages/CourseDetailPage"));

function App() {
  return (
    <Suspense fallback={<p>불러오는 중...</p>}>
      <CourseDetailPage />
    </Suspense>
  );
}
```

`lazy()`로 감싼 컴포넌트는 실제로 화면에 그려질 때가 되어서야 별도의 번들 파일로 다운로드됩니다. 라우트 단위(페이지 단위)로 코드 스플리팅을 적용하면, 사용자가 로그인 페이지만 봤다면 강의 상세 페이지의 코드는 아예 내려받지 않습니다.

**기본 상식**: 모든 컴포넌트를 잘게 쪼개 `lazy()`로 감싸면 오히려 네트워크 요청 수가 늘어 역효과가 날 수 있습니다. 라우트(페이지) 단위, 또는 모달처럼 "항상 쓰이지는 않는 큰 컴포넌트" 단위로 적용하는 것이 일반적인 기준입니다.

# 13. 커스텀 훅으로 로직 재사용

같은 로직(데이터 페칭, 폼 검증, 윈도우 크기 감지 등)이 여러 컴포넌트에서 반복되면, 커스텀 훅으로 분리해 재사용합니다.

```jsx
function useDebounce(value, delay) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(timer);   // 값이 바뀌면 이전 타이머 취소
  }, [value, delay]);

  return debounced;
}

function SearchBox() {
  const [keyword, setKeyword] = useState("");
  const debouncedKeyword = useDebounce(keyword, 300);

  useEffect(() => {
    if (debouncedKeyword) searchCourses(debouncedKeyword);
  }, [debouncedKeyword]);

  return <input value={keyword} onChange={(e) => setKeyword(e.target.value)} />;
}
```

위 예시는 검색어를 입력할 때마다 API를 호출하지 않고, 타이핑이 멈춘 뒤 일정 시간(300ms)이 지나야 검색을 실행하는 디바운스(debounce) 로직입니다.

**기본 상식**: 커스텀 훅의 이름은 반드시 `use`로 시작해야 React가 훅의 규칙(조건문 안에서 호출 금지 등)을 올바르게 검사할 수 있습니다. 컴포넌트 간에 "UI"가 아니라 "로직"이 중복될 때 커스텀 훅으로 뽑아내는 것이 기준입니다.

# 14. 리스트 렌더링 최적화

목록 화면(강의 목록, 리뷰 목록)에서 항목 수가 많아지면 렌더링 성능이 눈에 띄게 느려질 수 있습니다.

```jsx
// 좋지 않은 예: 배열 인덱스를 key로 사용
{courses.map((course, index) => <CourseCard key={index} {...course} />)}

// 권장: 고유하고 안정적인 값을 key로 사용
{courses.map((course) => <CourseCard key={course.id} {...course} />)}
```

배열 인덱스를 key로 쓰면, 목록 중간 항목이 삭제·정렬될 때 React가 "어떤 항목이 바뀌었는지"를 잘못 판단해 불필요한 리렌더링이나 상태 꼬임이 발생할 수 있습니다.

**대량의 리스트(수백~수천 개)**: 화면에 보이는 부분만 실제로 렌더링하는 가상 스크롤(virtualization, `react-window` 등)을 검토합니다. DOM에 한 번에 존재하는 노드 수를 줄여 스크롤 성능을 유지할 수 있습니다.

**기본 상식**: 리스트 최적화는 실제로 렌더링이 느려지는 게 체감될 때(리스트 항목이 수백 개 이상) 검토합니다. 항목이 몇십 개뿐인 목록에 가상 스크롤을 도입하면 오히려 구현 복잡도만 늘어납니다.

# 15. 다국어(i18n) 처리 기초

여러 언어를 지원해야 할 때, 텍스트를 코드에 직접 하드코딩하지 않고 별도 리소스 파일로 분리합니다.

```json
// locales/ko.json
{ "welcome": "환영합니다", "enroll_button": "수강 신청" }

// locales/en.json
{ "welcome": "Welcome", "enroll_button": "Enroll" }
```

```jsx
import { useTranslation } from "react-i18next";

function Header() {
  const { t } = useTranslation();
  return <button>{t("enroll_button")}</button>;
}
```

**기본 상식**: 단순 문자열 치환만으로는 부족한 경우가 많습니다. 복수형 처리("1개 강의" vs "2개 강의들"), 날짜·통화 형식은 언어권마다 규칙이 다르므로, 이런 것까지 처리해야 한다면 처음부터 i18n 전용 라이브러리를 쓰는 것이 직접 구현보다 안전합니다.
